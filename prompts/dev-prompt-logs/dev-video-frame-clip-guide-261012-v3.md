# Drop2Tunnel：视频画面提取与多媒体收藏子系统开发指南

> 适用代码基线：`dev/2610-s1`（实施时以实际工作区最新代码为准）  
> 文档定位：确认产品需求、业务原则、存储边界与验收目标；不指定函数、接口、数据表、文件目录或具体实现顺序。  
> 范围：后台独立页面与初始设置、资源导入、等间隔/随机取帧、手动精确 Clip 截取、提取会话、相似度比较、收藏资源库、存储缓存管理与音画同步质量。

## 一、总体定位与业务边界

本子系统是一套通过 **Web** 使用的媒体处理与收藏管理工具，重点解决反复从视频中寻找、截取、比较和保存画面过于繁琐的问题，并支持将喜欢的截图、短 Clip 及其它媒体资料统一收藏管理。

**核心流程：基础设施设置 → 导入（已有资源或关联现有 SNS/YT 下载流程）→ 导入就绪 → 提取会话 / 画面截取 / Clip 裁切 → 候选筛选与相似度比较 → 正式收藏。**

- **不独立实现网络抓取器**：SNS/YT 抓取仍由 Drop2Tunnel 原有下载页面和服务处理。本子系统既能导入已完成成果，也能接收 SNS/YT 链接并引导用户到现有下载页面创建任务；之后关联任务状态，等待下载完成后自动导入。
- 可复用现有网盘、S3 兼容访问、媒体读取、FFmpeg/ffprobe、转码、任务与进度管理能力；技术接入方式由实施者根据最新源码决定。
- 本文早期讨论中“由取帧工具直接抓取 YouTube URL”的方案，已被**统一导入、调用已有下载流程**替代；在本系统提交 SNS/YT 链接不等于本系统自行抓取。
- 本子系统放在网站**后台单独新增的专用页面**中统一组织，不零散附着在现有下载页或网盘页；具体页面布局与功能原型图待用户另行决定。

### 首次使用与基础设施设置

- 首次使用前，应提供集中设置流程，至少完成：**工作区网盘位置、正式收藏网盘位置、Node.js 两类本地临时缓存的存储与清理规则**，以及必要的数据库初始化。
- 两处网盘位置分别按**账号 → 分区 → 目录**选择；应检查访问权限和读写能力，确保后台任务可在用户关闭浏览器后继续使用已授权的服务端访问能力。
- 基础设施未配置完整或失效时，应明确提示并限制依赖它的操作；设置之后仍可查看、修改与检查状态。
- **本阶段不生成 UI 原型图**；具体界面结构留待用户确认。

## 二、资源导入

### 2.1 可导入来源

1. **SNS 已完成下载任务**：选择现有 `sns-dl` 已完成且成品仍可读取的任务。
2. **YouTube Premium 已完成下载任务**：选择现有 `yt-premium-dl` 已完成且成品仍可读取的任务。
3. **已有网盘文件**：从用户有权访问的网盘中选择视频或图片等资源。
4. **用户本地上传**：从设备上传视频、图片等资源。
5. **SNS/YT 链接**：在本系统提交链接，按来源携带必要的**透传参数**跳转至已有 `sns-dl` 或 `youtube-premium-dl` 页面创建抓取任务；创建后将任务 ID 与本系统工作区导入记录关联。

导入统一记录来源信息、原始下载任务 ID 或网盘文件关联、文件类型与大小，以及视频时长等可取得的必要信息。通过链接新建的任务应能在返回本系统后继续追踪，无须用户手动重新绑定；不得重复创建相同的导入任务。来源不完整、成品不存在、无权读取或导入失败时，应给出明确结果，不能标记为成功。

### 2.2 不同来源的存储处理

- **SNS/YT 已完成任务、用户上传文件**：导入时保存到为本子系统指定的**网盘工作区存储位置**；确认转存或上传成功后才算导入完成。
- **经链接创建的 SNS/YT 任务**：持续关联其任务 ID；抓取成功且成品可用后，由**服务端自动发起并完成网盘转存**，目标为已配置的工作区账号、分区和目录。此过程不依赖浏览器页面持续打开，关闭页面后仍能继续；刷新或重新进入页面能够恢复并查看任务状态。
- **后台导入可靠性**：应区分等待抓取、抓取失败、等待转存、转存中、转存失败、导入就绪等状态；安全处理重试、重复通知、服务器重启和目标网盘不可用，避免重复保存或错误标记成功。
- **已有网盘文件**：优先直接建立受权限约束的关联，不强制复制到工作区，也不因本系统清理而删除原文件。
- **本地上传与关页边界**：本地文件需要先完整到达服务器；不能承诺浏览器在上传字节尚未传完时关闭仍可继续传输。文件完整接收后，后续由服务端执行的转存和处理可独立完成。
- 同一个源资源可供多个提取会话使用；应避免不必要的重复导入及重复保存。
- 网盘文件受原账号和分区权限约束，不允许通过本系统的关联关系绕过授权。

## 三、基础设施与存储位置

全系统划分为 **两类网盘持久化存储、两类 Node.js 服务器本地短暂缓存、一个 SQLite 业务数据库**。

### 3.1 网盘存储（分别配置）

| 类别 | 存储内容 | 规则 |
|---|---|---|
| **① 导入资源存储区（工作区）** | 从已完成 SNS/YT 任务导入或本地上传的源视频、图片等 | 用作可复用的源资源缓存，完整源视频默认缓存 **1 年**，允许续期；由本子系统管理期限 |
| **② 正式收藏资源存储区** | 用户明确决定收藏的截图、Clip，以及其它正式收录成果 | 长期独立保存；不因工作区源视频到期或会话删除而被清理 |

两类网盘存储位置均按 **指定账号 → 指定分区 → 指定目录** 配置，可分别设置，也可位于同一分区的不同目录。不得把二者混同为同一类可自动清理的文件。**后台自动转存**必须使用已配置且仍然有效的工作区存储位置及访问授权；若账号或权限失效，应暂停并报错，不可悄悄写入其它账号或目录。

### 3.2 Node.js 本地临时缓存（分别管理）

| 类别 | 存储内容 | 规则 |
|---|---|---|
| **③ 视频片段缓存** | 从已导入源视频按起止时刻读取、截出的指定范围视频片段 | 供同一片段反复取帧或再裁成更短 Clip，降低反复访问网盘的开销；按期限、最近使用与容量清理 |
| **④ 候选提取结果缓存** | 随机批量产生的截图、Clip、缩略图，以及相似度比对的临时图片 | 与提取会话和批次关联，供浏览、比较、选择；正式保存后将成果写入收藏网盘区，而非只保留本地临时副本 |

两类缓存应具备可配置的容量限制和清理策略；正在使用或被多个会话引用的内容不能被提前删除。缓存清理后，日志记录仍应可查；若对应预览文件已经失效，应明确显示“缓存已清理”等状态，不得假装原图仍可用。

### 3.3 SQLite 业务数据库

**⑤ SQLite** 持久化记录导入资源及来源、**透传创建的 SNS/YT 任务 ID 与工作区关联、抓取及后台转存状态**、网盘关联、提取会话、提取批次、取帧日志、实际播放时刻、相似度结果、候选缓存状态、正式收藏记录、人物/组织/标签关系、任务进度及缓存生命周期等信息。

数据库是正式业务数据，不得与 Node.js 临时文件一起清理。业务记录应能区分：仅引用已有网盘文件、本系统持有的工作区缓存、已正式收藏的持久化成果。

## 四、随机取帧与提取会话

### 4.1 两种取帧方式与参数

在**已导入的视频**上支持两种相互独立的取帧方式：

1. **等间隔取帧**：用户指定时间粒度，例如每隔 500 毫秒提取一张；可以限定在整段视频或指定时间范围内。
2. **指定范围随机取帧**：用户指定一段或多段时间范围，并设置本次随机提取的**张数**；在有效范围内随机取帧，**不要求按固定时间间隔依次提取**。取帧粒度、最小间隔等可以作为可选约束，不应取代“范围内随机指定数量”的基本能力。

时间范围默认可覆盖整个视频，也支持 `12:34-56:01,01:02:10-01:05:30` 这样的多段输入；时间支持分:秒、时:分:秒及可选毫秒。重叠范围应合并，检查空范围、倒置和越界；按可用候选位置抽样，数量不足时返回实际提取数量，不为凑数无限重试。

尽量准确定位视频帧。**请求时刻**与**实际解码取得画面的播放时刻**必须区分并记录，不得将请求的毫秒值冒充实际帧时刻。

### 4.2 提取会话与批次

- 引入独立的**提取会话**：同一视频允许建立多个会话，也能在不同时间返回原会话继续操作。
- 每次执行取帧形成一个**提取批次**，保留该次的范围、粒度、数量等参数。
- 各会话独立管理其提取日志、候选结果与保存状态；同源视频可以共享源资源与可复用缓存。
- 应可发现同一视频跨会话、跨批次的重复截取，避免用户多次保存相同画面而不自知。

### 4.3 取帧日志与保存

每条取帧记录至少包括**图片或缩略图、请求时刻、实际帧时刻（毫秒精度）、提取时间、所属会话/批次、是否已保存**。日志支持按视频播放时刻或实际提取时间排序，并能查看、筛选和选择保存画面。

“日志是否保留”“候选本地图片是否清理”“用户正式收藏是否删除”是三种不同操作，必须分别处理。正式收藏成功应确认网盘写入并建立关联，不能只修改日志里的已保存标记。

## 五、相似度比较与重复检测

可选择把新提取画面与以下对象比对：

1. 当前会话历史画面；
2. 同一源视频全部会话的帧日志；
3. 已正式收藏的画面；
4. 用户临时上传的参考图片集。

同时考虑相同播放时刻、完全相同图片和不同时刻却高度相似的画面。支持高效初筛及更精细比较；将相似结果直观展示给用户，**近似画面是否保留由用户决定**。相似度比较旨在发现重复或接近画面，不在本阶段默认承担人物身份识别任务。

## 六、视频片段缓存、手动 Clip 与音画同步

### 6.1 片段缓存与交互式裁切

- 支持用户指定较长的视频工作范围，将其暂存为 Node.js **视频片段缓存**，供多次截图和继续裁切更短的 Clip，减少重复访问网盘。
- **Clip 不采用随机截取模式**。用户通过播放器观看、暂停，在当前播放位置设定**起点或终点**；暂停时支持键盘 `←`、`→` 微调当前时刻，优先支持逐帧定位，并显示调整后的精确时间。可反复修改两端位置，预览所选范围再执行截取。
- 不能把“每次加减固定毫秒数”直接冒充逐帧定位；帧率可变或存在非整数帧率时，应以实际视频帧为准。
- 支持是否保留音频、是否要求精确起止时刻、是否尽量保留原画质等选项；向用户清楚区分**精确裁切**与**快速免重编码裁切**的能力和限制。
- 候选 Clip 在正式保存前进入 Node.js 临时结果缓存。用户确认收藏后才保存到**网盘正式收藏区**，并记录源视频和起止时刻。

### 6.2 AV1 / AVC / HEVC 音画同步质量要求

**本要求不仅适用于该子系统的 Clip 截取，也要求检查并解决现有 SNS/YT 后台下载任务按起止时间抓取视频后发生的音画不同步、音频轨与视频轨长度明显不一致等问题。**修复应落在可复用的媒体处理能力上，不把不正常的源视频留给后续取帧系统自行猜测修复。

- 至少覆盖 **AV1、AVC/H.264、HEVC/H.265** 视频，以及常见的 AAC、Opus 等音轨组合；不因原始编码不同而使用未经校验的裁切策略。
- **精确裁切优先保证正确性**：选择的起止时刻应同时作用于音频与视频；正确处理关键帧依赖、音视频原始时间戳与起始偏移、可变帧率、音频编码延迟及容器封装。必要时对音视频重新编码，保证片段从正确位置开始，正常播放且同步。
- **快速免重编码裁切仅作为可选模式**：允许切点向可独立解码的位置调整，但必须明确告知用户精度限制；不允许以出现黑屏、冻结帧、音画漂移或明显长度异常为代价。
- 对分别下载的视频轨和音频轨，应以一致的媒体时间线合并及裁切，不能简单地假定两条轨道的首包时间、起点和持续时长天然一致。
- 处理完成后必须校验：音视频轨道存在性、实际起点与终点、时间戳连续性、解码是否正常、播放是否明显失步，以及是否存在不合理的长尾或轨道长度差异。**不能只凭进程退出码或文件存在就判定成功。**
- 音视频轨道并不一定能达到数值上完全相同的时长；允许编码帧长、音频采样和封装造成的小幅合理偏差，但不接受可感知的失步或明显错误的持续时长。
- 若输入片段已损坏或源媒体的时间戳本身异常，应明确报告并尝试合理恢复；无法保证可靠结果时标记失败，而不是产出貌似成功的错误文件。

具体命令、编码器、容器及处理流程由开发者结合最新代码、输入媒体和资源开销确定；不要将某一个 FFmpeg 参数组合视为适用于所有媒体的万能解法。

## 七、多媒体收藏资源库

资源库统一管理保存的截图、Clip，也允许将 SNS/YT 已有成品、网盘已有资源或手动上传资源正式收录。正式收录以确认文件已存在于可管理的网盘存储位置并建立关联为准；对于直接引用的网盘文件，应明确保留其外部引用属性，不擅自复制或删除原件。

每个资源可保存来源链接、来源任务或网盘文件、原视频标识、截取时刻/范围、类型、保存位置与标签等信息。

分类以**人物、组织、标签**及关联关系为主，而非完全依赖目录层级：

- 一个资源可关联多个人物、组织、标签；一个人物也可关联多个组织。
- 人物、组织支持别名，避免因中日文等不同名称重复建立实体。
- 人物与组织关系可随时间变化，保留必要的历史信息。
- 初期以人工建立与维护关联为主，不强制开发自动人物识别。
- 网盘中的资源失效、被删除或权限撤销时，保留来源和收藏记录并明确标记状态，不将失效误判为正常可用。

## 八、生命周期、可靠性与安全原则

- **一年期限仅属于本子系统的工作区缓存管理规则**：从源视频成功缓存时起算，可续期；**不修改网盘自身存储规则**，不对直接引用的现有网盘文件实施到期删除。
- 工作区缓存到期、临时片段清理、候选缓存清理、会话删除、正式收藏删除，必须按各自所有权和引用关系处理；不得级联误删已正式保存的图片或 Clip。
- 源资源应考虑来源、媒体版本、清晰度、音轨及访问身份等差异，避免错误复用。账号切换、权限失效、原文件删除时应有清晰反馈。
- 媒体处理优先复用现有网盘读取能力和可用缓存，减少重复传输；对于网盘实际的文件大小、范围读取及格式约束，以实施时的真实能力为准，超限需明确提示，不可静默失败。
- 导入、取帧、比对、裁切、转存等耗时操作应有任务进度、取消/失败反馈和必要的恢复手段；**后台抓取任务关联和自动转存不依赖浏览器长连接**，页面关闭后仍能继续并在重新打开后恢复展示。控制并发、内存、磁盘和 CPU 占用，不能显著拖累现有网盘与隧道任务。
- 缓存中的私人媒体及关联信息不得跨用户、跨账号或越权读取；浏览器与服务端显示的任务状态必须与实际完成情况一致。

## 九、功能验收要点

1. 后台独立页面可进入；首次设置可配置并验证两处网盘位置、两类本地缓存及业务数据库，基础设施不可用时提示准确。
2. 可从既有 SNS/YT 完成任务、已有网盘文件、本地上传及 SNS/YT 链接导入；链接通过透传参数进入原下载页面创建任务，**不在本子系统内重复实现抓取**，任务 ID 能正确关联工作区。
3. 新关联的 SNS/YT 下载任务完成后，服务端自动转存至指定账号/分区/目录；浏览器关闭或刷新不影响已经由服务端接管的任务；失败可发现并安全重试，未确认网盘保存成功不显示“导入就绪”。
4. 可配置两处网盘存储位置及两类本地缓存策略；源资源一年缓存、正式收藏独立长期保存，清理不误删。
5. **等间隔取帧**和**指定范围、指定张数的随机取帧**均可正常使用；多时间范围、毫秒定位、会话/批次日志、排序及保存状态正确。
