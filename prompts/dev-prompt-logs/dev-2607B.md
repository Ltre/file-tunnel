    ### 5. P2P 失败如何降级

    P2P 发送在 [sendViaDataChannel()](/D:/Workspace/github/Ltre/file-tunnel/client/file-assets.js:1719)，Socket.IO 兜底在 [sendViaSocketRelay()](/D:/Workspace/github/Ltre/file-tunnel/client/file-assets.js:1790)。

    普通建链失败、通道超时、连接关闭等，会降级 Socket.IO relay。服务端 relay 入口是 [server/file-assets.js](/D:/Workspace/github/Ltre/file-tunnel/server/file-assets.js:584)。

    Relay 每个 64KB 分块都要走：

    ```text
    供源浏览器 → Node.js → 接收浏览器 → ACK → 下一个分块
    ```

    因此它明显慢于 P2P。服务端不长期保存这些分块，只校验、转发并统计长度。

    一个特殊点：如果错误被认定为 DataChannel backpressure/发送队列满，目前会结束该次 P2P 尝试并重试，不立即切 relay，避免同一内容同时污染两条链路。

问：

    解释下 client/file-assets.js中的这两个常量
        const MULTI_SOURCE_WATCHDOG_INTERVAL = 5000;
        const MULTI_SOURCE_STALL_MS = 12000;

    不要改代码
    

答：

    这两个常量只用于“多源分片下载”的看门狗，不参与普通单源 P2P 或 Socket.IO relay 的链路选择。

    ```js
    const MULTI_SOURCE_WATCHDOG_INTERVAL = 5000;
    const MULTI_SOURCE_STALL_MS = 12000;
    ```

    含义分别是：

    - `MULTI_SOURCE_WATCHDOG_INTERVAL = 5000`

      每 5 秒检查一次当前文件的多源分片任务状态。

      代码会通过 `setInterval()` 定期调用：

      ```js
      this.checkMultiSourceStall(assetId)
      ```

    - `MULTI_SOURCE_STALL_MS = 12000`

      如果某个正在下载的分片，连续 12 秒没有任何活动，就判定该分片可能卡住。

      活动时间取自：

      ```js
      range.lastActivityAt
      transfer.lastProgressAt
      transfer.startedAt
      ```

      判断逻辑大致是：

      ```js
      当前时间 - 最近活动时间 >= 12000
      ```

    触发后，watchdog 会记录 `range-watchdog-stalled` 日志，并调用：

    ```js
    retryMultiSourceRange(...)
    ```

    重新调度这个分片。

    需要注意一个细节：5 秒是“检查间隔”，12 秒是“判定停滞阈值”，所以实际触发时间不是精确的 12 秒，而通常是约 12～15 秒。例如：

    - 分片最近一次活动：`12:00:00`
    - watchdog 检查：`12:00:05`，未满 12 秒
    - watchdog 检查：`12:00:10`，未满 12 秒
    - watchdog 检查：`12:00:15`，超过 12 秒，触发重试

    因此，这两个值的关系是：

    ```text
    每 5 秒检查一次
    连续约 12 秒无活动
    => 判定分片卡住并安排重试
    ```

    它们的作用是处理“某个多源分片没有真正失败、也没有继续产生数据”的情况，避免任务永远停在 0% 或某个百分比。代价是如果网络只是暂时变慢超过 12 秒，可能会过早重试，造成重复请求或进度表现跳动。

    调用链：

    1. 客户端请求 `/api/server-assets/0X0I3D_mdylbBHSesb5_qA`
    2. 服务端发现临时文件已不在磁盘
    3. [`ensureTelegramServerAssetFile()`](D:/Workspace/github/Ltre/file-tunnel/server.js:1642) 使用保存的 Telegram `file_id` 补拉
    4. [`downloadTelegramFile()`](D:/Workspace/github/Ltre/file-tunnel/server.js:2584) 调用 Telegram `getFile`
    5. Telegram 返回：`Bad Request: file is too big`
    6. [`/api/server-assets/:assetId`](D:/Workspace/github/Ltre/file-tunnel/server.js:402) 捕获后打印了这条日志

    原因是 Telegram 官方云端 Bot API 的 `getFile` **最多只能下载 20MB**。项目配置的 `maxFileSize=500MB` 只是本项目的限制，无法突破 Telegram 的限制。[Telegram Bot API 官方说明](https://core.telegram.org/bots/api#getfile)

    另外，当前代码会在客户端完整读取后删除服务器临时文件。于是大于20MB的文件一旦临时副本被删，后续再依靠 `file_id` 恢复就会失败。

    `0X0I3D_mdylbBHSesb5_qA` 是项目内部的 Telegram asset ID，不是报错来源本身。

    可行处理方向：

    - 大于20MB的 Telegram 文件不要过早删除服务器临时副本。
    - 至少确认已有浏览器设备完整缓存后再删。
    - 或部署 Telegram Local Bot API Server，官方说明本地版下载无大小限制。
