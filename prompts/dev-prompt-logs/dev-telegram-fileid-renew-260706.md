    # 在会话资源管理器中增加“Telegram 文件防失联检测及修复”功能

    **背景：**Telegram 的 `file_id` 可能与具体 bot 绑定。服务端以后可能会更换接入的 Telegram bot，导致旧 bot 时代写入传输记录的 Telegram 来源文件，在当前新 bot 下无法继续通过原 `file_id` 拉回文件。为避免这类 Telegram 来源文件在本机和其它设备都没有缓存副本时彻底失联，需要提供一个主动检测与修复机制。

    **入口位置：**会话资源管理器中新增一个按钮，暂定文案为：

    “Telegram 文件防失联检测及修复”

    **点击后执行以下流程：**

    1. 扫描当前隧道内所有带有 Telegram 来源信息的文件记录，包括单文件记录和合辑内文件。

    2. 对每个 Telegram 来源文件，检查其当前绑定的 Telegram `file_id` 是否仍可被当前服务端配置的 bot 使用。这里的“有效”指：Node.js 服务端使用当前 bot token 调用 Telegram API 时，能够通过该 `file_id` 获取文件信息或拉取文件内容。

    3. 如果某个文件的 Telegram `file_id` 对当前 bot 仍然有效，则不需要修复，只记录检测结果和最近检测时间。

    4. 如果某个文件的 Telegram `file_id` 对当前 bot 已经失效，不要误以为新 bot 可以直接读取旧 bot 的 `file_id`。此时应进入修复流程：

       * 优先从当前设备的浏览器缓存副本读取文件内容；
       * 如果当前设备没有缓存副本，则优先向同隧道内在线且拥有该文件缓存副本的设备请求同步；
       * 如果仍无法获得文件内容，则标记为“当前无法修复”，保留原 Telegram 来源信息，并提示需要等待拥有缓存副本的设备上线后再重试；
       * 只有在已经成功拿到文件内容的情况下，才允许继续执行重新上传修复。

    5. 重新上传修复时，由 Node.js 服务端使用当前配置的 bot 身份，把该文件发送给一个预先配置好的频道。发送成功后，从 Telegram 返回结果中取得当前 bot 可用的新 `file_id`。

    6. 将新的 Telegram `file_id` 绑定回原文件记录。绑定时不要改变文件本身的 `fileId`，也不要生成新的传输记录；只是更新该文件的 Telegram 备份来源信息。建议同时保存以下字段：

       * `telegramFileId`：当前最新可用的 file_id；
       * `telegramFileUniqueId`：如果 Telegram 返回了 file_unique_id，也一并保存；
       *
       * `telegramFileIdUpdatedAt`：本次更新 file_id 的时间戳；
       *
       * `telegramFileIdHistory`：可选，保留旧 file_id、旧 bot 标识、更新时间、失效原因，便于排查。

    7. 新的 `telegramFileIdUpdatedAt` 应作为版本依据同步给同隧道其它设备。其它设备如果发现同一个文件记录上出现更新时间更晚的 Telegram `file_id`，应以最新版本为准，更新本地记录。不要让旧设备用旧 file_id 覆盖新 file_id。

    8. 修复完成后，该文件的缓存恢复策略仍然保持原优先级：

       * 第一优先：从同隧道在线设备拉取浏览器缓存副本；
       * 第二优先：如果没有在线设备可供源，再由 Node.js 服务端使用最新 Telegram `file_id` 从 Telegram 拉取；
       * Telegram `file_id` 只是离线兜底来源，不应取代设备间缓存同步。

    9. UI 上应显示检测与修复进度，例如：

       * 已扫描多少个 Telegram 来源文件；
       * 多少个 file_id 仍有效；
       * 多少个已成功换绑新 file_id；
       * 多少个因没有任何缓存副本或在线供源而暂时无法修复；
       * 多少个因 Telegram API 错误、权限错误、目标频道不可用等原因修复失败。

    10. 注意边界：

    * 不要把“检测 file_id 是否有效”和“重新上传获取新 file_id”混成同一个动作；
    * 不要在没有文件内容来源的情况下声称可以修复；
    * 不要删除旧 Telegram 信息，除非已经成功绑定新的 file_id；
    * 不要改变传输记录的原始时间、发送者、合辑结构和文件自身 fileId；
    * 不要让这个功能把文件重新发送成一条新的传输记录，它只是修复文件记录上的 Telegram 兜底恢复来源。

    这个版本把“完全没有缓存副本”的风险讲清楚了：**真正完全没有任何缓存、也没有旧 bot 可用来源时，新 bot 不能凭空变出文件**；所以修复按钮的价值是“趁还有缓存副本/在线设备副本时，把旧 bot 的 fileId 轮换成当前 bot 可用的新 fileId”。
