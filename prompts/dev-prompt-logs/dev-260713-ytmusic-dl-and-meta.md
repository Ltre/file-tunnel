# 统一支持 YouTube 视频/歌曲解析、获取内容及歌曲合辑回传

请基于现有 `file-tunnel` 代码实现以下功能。实现前先检查当前 Telegram Bot 的 YouTube 链接提取、“获取文件”入口、yt-dlp 调用、媒体下载、任务状态、文件资产创建和传输记录发送流程，尽量复用现有能力，不要为 Telegram Bot 和客户端分别维护两套下载逻辑。

## 一、统一支持 Telegram Bot 和客户端消息

目前 Telegram Bot 转发含有 YouTube 链接的消息到隧道后，可以在传输记录详情页执行“获取文件”。

现在需要让用户直接从网页客户端或 PWA 客户端发送含有 YouTube 链接的消息时，对应传输记录的汉堡菜单详情页也显示相同的“获取文件”入口。

无论消息来源是：

- Telegram Bot；
- 网页客户端；
- PWA 客户端；

提取出 YouTube 链接后，都必须进入同一套服务端流程，包括：

- URL 校验与规范化；
- yt-dlp 解析；
- 歌曲或视频分类；
- 内容下载；
- 媒体处理；
- 任务进度；
- 文件资产创建；
- 结果发送；
- 与来源传输记录关联；
- 失败和重试处理。

消息来源只用于记录来源、执行权限校验和关联原始消息，不能决定该 YouTube 内容是歌曲还是视频。

支持识别以下域名：

- `youtube.com`
- `www.youtube.com`
- `m.youtube.com`
- `youtu.be`
- `music.youtube.com`
- `www.music.youtube.com`

必须解析 URL 并校验协议和主机名，不能只判断文本中是否包含 `youtube`。仅允许 `http` 和 `https`。

一条消息包含多个不同 YouTube 链接时，应在详情页分别提供获取入口；完全相同的链接需要去重。

本期不批量下载整个播放列表：

- 同时包含 `v` 和 `list` 时，只处理当前 `v` 对应的内容；
- 只有播放列表而没有具体视频时，提示暂不支持获取整个播放列表。

## 二、统一识别歌曲和视频

所有来源的 YouTube 链接都必须先解析，再分类为：

- `song`：歌曲；
- `video`：普通视频；
- `unsupported`：不支持的链接。

### 歌曲判断

原始 URL 属于 `music.youtube.com` 时，默认作为歌曲候选处理。必须在 yt-dlp 重定向或规范化前保留用户发送的原始 URL 和原始主机名。

普通 `youtube.com` 或 `youtu.be` 链接也可能是歌曲，需要根据 yt-dlp 返回的结构化音乐字段判断，例如：

- `track`
- `artist`
- `artists`
- `album`
- `release_year`
- `release_date`

存在可靠的歌曲结构化元数据时按歌曲处理，否则按普通视频处理。

不能只因为以下情况就判定为歌曲：

- 标题包含“歌曲”“MV”“Official Audio”等文字；
- 标题格式类似“艺术家 - 曲名”；
- 视频存在音频轨道；
- YouTube 分类为 Music；
- 视频中带有背景音乐。

教程、新闻、访谈、演唱会录像、歌曲评论、reaction、歌词讲解等内容，在缺少可靠歌曲元数据时仍按视频处理。

分类结果需要持久化到服务端任务及最终文件资产中，不能只保存在当前页面内存。

## 三、歌曲下载、元数据和封面处理

识别为歌曲后：

1. 使用 yt-dlp 获取合适的音频；
2. 最终输出真实有效的 `.m4a` 文件；
3. 不能只修改扩展名；
4. 如果源音频可以直接重新封装为 M4A，应优先避免不必要的有损转码；
5. 无法直接封装时，再通过 ffmpeg 转换；
6. 不要求写死输出码率或 AAC profile，应根据当前下载到的音频及项目策略选择合适的处理方式；
7. 完成后使用 ffprobe 或现有媒体探测能力读取最终文件的真实容器、编码、profile、码率和时长。

### 元数据提取

优先使用 yt-dlp 的结构化字段。

歌曲名优先级：

1. `track`
2. `title`
3. 视频 ID 或安全兜底名称

艺术家优先级：

1. `artist`
2. `artists`
3. `uploader`
4. `未知艺术家`

如果 `artists` 是数组，转换为适合标签展示的字符串，例如：

`Artist A, Artist B`

专辑：

1. 使用 `album`
2. 缺失时留空

年份：

1. 使用 `release_year`
2. 从 `release_date` 提取四位年份
3. 缺失时留空

不能使用 `upload_date` 冒充歌曲发行年份。

Comment：

- 使用用户原始消息中的完整 YouTube 链接；
- 不能只写 yt-dlp 规范化后的链接。

将以下标签真正写入最终 M4A 文件：

- title；
- artist；
- album；
- date/year；
- comment；
- cover artwork。

最终文件名为：

`艺术家 - 曲名.m4a`

文件名需要处理跨平台非法字符、控制字符、末尾空格和句点、超长文件名及重名问题（优先将上述特殊字符转换为全角字符），不得静默覆盖已有文件。

### 封面处理

优先下载 yt-dlp 返回的高质量适用封面。

YouTube Music 封面可能是“中间正方形封面＋左右黑边”的横向图片，需要处理为正方形：

- 原图已经是正方形时不裁剪；
- 横向图片优先识别左右对称的黑色或近黑色区域；
- JPEG 压缩后的黑边可能不是纯黑，需要允许亮度误差和少量噪点；
- 检测到黑边后，裁掉左右黑边；
- 无法可靠识别黑边时，以图片中心为基准裁成正方形；
- 禁止将长方形图片直接拉伸为正方形；
- 需要避免越界裁剪或错误裁掉真实封面内容。

独立封面图片和写入 M4A 的内嵌封面必须使用同一份最终处理结果。

歌曲文件生成后，应重新探测和读取最终文件，确认：

- 文件可以正常播放；
- 容器确实为 M4A；
- 元数据已写入；
- 封面已嵌入；
- 时长、码率和编码信息可以读取。

## 四、歌曲获取成功后以合辑发送

对于 YouTube 歌曲执行“获取内容”，并成功完成下载、封面处理、元数据写入和最终文件校验后，应自动在原链接所在的隧道中新增一条合辑传输记录。

合辑固定包含：

1. 处理后的正方形歌曲封面；
2. 已填好元数据并嵌入相同封面的 M4A 歌曲文件。

顺序必须是封面在前、歌曲文件在后。

不能发送：

- 未裁剪的原始封面；
- 下载过程中的临时文件；
- 尚未写入元数据的音频；
- 未完成转换的中间文件。

如果歌曲文件或封面没有处理完整，不应发送一条伪装成功的残缺合辑，应明确标记任务失败并允许重试。

### 合辑备注

该合辑必须附带传输记录级别的“备注”。备注不是封面说明，也不是 M4A 内部的 Comment 标签。

格式如下：

```text
艺术家 - 曲名.m4a
    - Track name：曲名
    - Performer：艺术家
    - Recorded date：YYYY
    - Bit Rate：实际码率，例如256kbps
    - Fomat：实际编码格式，例如AAC LC
    - Duration：实际时长，例如01:23
    - Comment：原始YouTube链接
```

其中 `256kbps`、`AAC LC`、`01:23` 、YYYY仅用于说明显示格式，所有字段都必须动态读取和生成，不能写死。

字段取值要求：

- 第一行：最终歌曲文件的实际文件名；
- `Track name`：最终写入歌曲文件的 title；
- `Performer`：最终写入歌曲文件的 artist；
- `Recorded date`：最终写入歌曲文件的发行年份；
- `Bit Rate`：通过 ffprobe 或现有媒体探测能力读取最终歌曲文件的实际音频码率，并格式化为 `128kbps`、`192kbps`、`256kbps` 等形式；
- `Fomat`：读取最终歌曲文件的实际音频编码及 profile，例如 `AAC LC`、`HE-AAC` 等；
- `Duration`：读取最终文件的实际时长，不足一小时显示为 `MM:SS`，达到一小时显示为 `HH:MM:SS`；
- `Comment`：用户原始消息中的完整 YouTube 链接，并与写入 M4A Comment 标签的链接一致。

备注必须在最终文件处理完成后，根据最终文件的真实标签和媒体探测结果生成，不能根据下载参数、转换计划或默认值提前拼接。

例如最终文件实际是 129kbps、AAC LC、4 分 17 秒，应显示：

```text
艺术家 - 曲名.m4a
    - Track name：这是一首歌的曲名
    - Performer：老张
    - Recorded date：2020
    - Bit Rate：129kbps
    - Fomat：AAC LC
    - Duration：04:17
    - Comment：https://music.youtube.com/watch?v=xxxxxxxxxxx
```

如果最终文件是其他码率或编码，必须显示实际结果。

某个字段确实无法取得时，显示 `未知` 或留空，不得伪造默认值。

### 与原始传输记录关联

新生成的歌曲合辑必须与触发获取操作的原歌曲链接传输记录建立持久化关联。

至少需要保存：

- 原始传输记录 ID；
- 原始消息 ID；
- 原始 YouTube URL；
- YouTube 视频 ID；
- 获取任务 ID；
- 结果合辑传输记录 ID；
- 封面文件资产 ID；
- 歌曲文件资产 ID。

具体字段名可根据项目现有数据结构调整，但不能只通过备注文本或 URL 模糊匹配。

原歌曲链接传输记录的详情页应显示：

- 已获取歌曲；
- 最终歌曲文件名；
- 获取结果合辑的打开或定位入口。

结果合辑详情页应显示：

- 来源为 YouTube 获取；
- 原始 YouTube 链接；
- 返回或定位原始链接传输记录的入口。

原始链接传输记录必须保留，不得被结果合辑覆盖或删除。

关联需要在以下情况下继续有效：

- 页面刷新；
- Socket 重连；
- 设备切换；
- 历史记录重新加载；
- 服务端重启；
- 备份和恢复。

歌曲合辑应完全进入现有合辑、缓存和文件资产体系，支持现有的：

- 合辑预览；
- 音乐播放；
- 下载；
- 详情；
- 删除；
- 释放缓存；
- 恢复文件；
- 转发到其他隧道；
- 跨设备同步；
- 文件供源。

独立封面图片不能被错误加入音乐播放队列。

## 五、视频处理、任务控制和兼容要求

识别为普通视频时，继续复用现有 Telegram Bot 的 YouTube 视频获取逻辑，包括：

- 视频和音频流选择；
- 合并及封装；
- 输出格式；
- 文件大小限制；
- 时长限制；
- 下载超时；
- 下载进度；
- 文件资产创建；
- 临时文件清理；
- 失败处理。

普通视频：

- 不强制转换为 M4A；
- 不使用“艺术家 - 曲名”文件名；
- 不生成歌曲元数据备注；
- 不使用“封面＋歌曲文件”的歌曲合辑结构。

任务状态至少需要区分：

- 正在解析；
- 正在获取歌曲；
- 正在获取视频；
- 正在处理封面；
- 正在写入元数据；
- 正在创建合辑或文件记录；
- 获取完成；
- 获取失败，可重试。

任务状态必须持久化在服务端，页面刷新、Socket 重连或设备切换后可以恢复。

需要实现幂等控制。同一个隧道、同一条来源记录、同一个 YouTube 视频 ID，在以下情况下不能重复下载、重复转码或重复创建结果：

- 用户连续点击；
- 多个设备同时点击；
- 页面刷新后再次点击；
- Socket 重连导致请求重放；
- 服务端已创建结果但客户端未收到成功响应。

如果歌曲文件已经处理成功，仅合辑创建或关联写入失败，重试时只补做失败步骤，不能重新下载和转码整首歌曲。

调用 yt-dlp、ffmpeg、ffprobe 或图片处理程序时，必须使用安全参数数组或项目现有的安全进程调用方式，不能把 URL、标题、艺术家或文件名直接拼接到 shell 命令中。

需要继续遵守项目现有的：

- 允许域名限制；
- 重定向校验；
- 下载大小限制；
- 时长限制；
- 并发限制；
- 超时限制；
- 临时目录清理；
- SSRF 防护；
- 命令注入防护；
- 路径穿越防护。

本次改动不能破坏：

- Telegram Bot 原有消息接入；
- 客户端普通文本和富文本消息；
- 原有 YouTube 视频获取；
- 传输记录；
- 文件缓存和供源；
- 合辑功能；
- 跨设备同步；
- 音乐和视频播放器；
- 下载、删除、转发、释放缓存和恢复功能。

## 六、验收重点

至少验证以下场景：

1. Telegram Bot 转发 YouTube 链接后可以执行获取。
2. 客户端直接发送 YouTube 链接后也可以执行获取。
3. 两种来源共用同一套服务端任务流程。
4. YT Music 单曲能够识别为歌曲。
5. 普通 YouTube 链接存在可靠音乐元数据时能够识别为歌曲。
6. 教程、访谈、reaction、演唱会录像等不会被误判为歌曲。
7. 普通视频继续按原有视频逻辑处理。
8. 歌曲最终生成有效 M4A，并正确写入 title、artist、album、year、comment 和封面。
9. 文件名符合“艺术家 - 曲名.m4a”。
10. 横向封面的左右黑边被裁掉。
11. 独立封面与 M4A 内嵌封面一致。
12. 歌曲获取成功后自动发送“封面＋M4A”的合辑。
13. 合辑备注格式正确。
14. `Bit Rate` 来自最终文件的实际码率，不能写死。
15. `Fomat` 来自最终文件的实际编码和 profile，不能写死。
16. `Duration` 来自最终文件的实际时长。
17. `Comment` 为用户发送的原始 YouTube 链接。
18. 原始链接记录可以定位到结果合辑。
19. 结果合辑可以定位回原始链接记录。
20. 页面刷新、设备切换和服务端重启后，任务状态及关联仍然存在。
21. 重复点击和多设备同时点击不会创建重复任务或重复合辑。
22. 仅合辑创建失败时，重试不会重新下载歌曲。
23. 一条消息中的多个链接可以分别获取。
24. 相同链接在同一条消息中不会重复显示。
25. 只有播放列表的链接不会触发批量下载。
