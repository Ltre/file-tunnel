    ## Telegram 消息中的 SNS 媒体识别与下载

    当 Telegram 转入隧道的消息备注或 Caption 中包含 YouTube 等受支持的 SNS 链接时，系统应提供媒体识别和按需下载能力。

    Telegram 消息写入传输记录后，服务端异步扫描该记录的备注内容，提取其中受支持的 SNS URL。

    服务端仅使用 `yt-dlp` 获取媒体元数据，此阶段不得下载完整媒体文件。

    一个 URL 可能解析出一条或多条待下载媒体，例如播放列表中的多个视频。每条媒体信息至少保存：

    * SNS 媒体 ID；

    * 封面；
    * 时长；
    * 来源平台；
    * 当前状态；
    * 错误信息；
    * 下载进度；
    * 下载完成后对应的 server asset ID。

    * 标题；

    * 原始 URL；
    * 当前状态；
    * 操作按钮。

    * 正在识别；

    每条处于“等待下载”状态的 SNS 媒体显示“下载到隧道”按钮。

    服务端应使用任务队列执行下载，并持续向当前隧道广播：

    * 下载阶段；
    * 已下载字节数；
    * 总字节数；
    * 下载百分比；
    * 下载速度；
    * 预计剩余时间；
    * 失败原因。

    ### 4. 注册为普通文件

    `yt-dlp` 下载成功后：

    1. 将文件登记为 server asset；
    2. 为其生成普通文件传输记录；
    3. 新文件记录关联原 Telegram 传输记录和对应的 SNS 媒体条目；
    4. SNS 媒体条目保存新文件记录 ID 和 server asset ID；
    5. 后续预览、下载、缓存、释放空间和还原流程均复用现有普通文件逻辑。

    不得把下载后的媒体二进制直接写入原 Telegram 文本记录。

    ### 5. 客户端获取文件

    对于由服务器持有的 SNS 媒体文件，客户端优先通过带鉴权的 HTTPS 接口下载，不通过 Socket.IO 传输完整文件。

    HTTPS 下载接口应支持：

    * `Range` 分段请求；
    * 断点续传；
    * Content-Length；
    * 正确的 Content-Type；
    * 下载进度；
    * 临时访问令牌；
    * 防止跨隧道越权访问。

    客户端下载完成并校验文件大小后，将文件写入本机普通文件缓存，并向服务端发送“完整缓存成功”确认。

    ### 6. 服务端临时文件清理

    服务端收到至少一个客户端的“完整缓存成功”确认后，才允许清理对应的 yt-dlp 临时文件。

    清理策略应同时满足：

    * 至少一个客户端已明确确认完整缓存；
    * 当前没有客户端正在读取该文件；
    * 文件已超过最短保留时间；
    * 清理后仍保留 SNS 元数据、普通文件记录和客户端供源信息。

    同时设置最长保留时间和服务器空间上限，避免客户端始终不确认时临时文件永久占用磁盘。

    临时文件删除后，该文件继续按照普通文件恢复链路处理：优先从已有客户端缓存供源；如果所有客户端副本均不可用，则显示当前没有可用文件来源，不得再次自动调用 `yt-dlp` 下载。

    关于 HTTPS：**这里应该使用 HTTPS 下载，而不是 Socket.IO Relay。** 大文件通过 HTTP 更容易实现流式读取、Range、断点续传、反向代理优化和客户端直接写入磁盘；Socket.IO 更适合状态广播、进度通知和缓存成功 ACK。

    ## Telegram 备注中的多 URL、列表媒体解析及“SNS 媒体文件”区域

    Telegram 转入隧道的传输记录，其备注或 Caption 中可能同时包含：

    * 一个或多个独立媒体 URL；
    * 一个或多个列表 URL；
    * 普通非 SNS URL；
    * 重复 URL。

    服务端应扫描备注中的全部 URL，只处理 `yt-dlp` 支持的 SNS URL，并对规范化后的重复 URL 去重。

    ---

    ### 1. 数据层级

    SNS 解析结果必须分为两层：

    #### 1.1 SNS 来源 `snsSource`

    每一个被识别的 SNS URL 对应一个来源对象：

    ```js
    {
      id,
      messageId,
      sourceUrl,
      sourceType: "single" | "collection",
      title,
      coverUrl,
      sourceOrder,
      parseStatus,
      parseError,
      mediaItemIds: []
    }
    ```

    其中：

    * `single`：独立视频、独立音频或其他单媒体 URL；
    * `collection`：播放列表、频道列表或一次可解析出多个媒体条目的 URL。

    #### 1.2 SNS 媒体条目 `snsMediaItem`

    每一个最终可抓取的媒体文件对应一个媒体条目：

    ```js
    {
      id,
      sourceId,
      messageId,
      sourceUrl,
      mediaUrl,
      title,
      coverUrl,
      duration,
      platform,
      mediaIndex,

      serverState,
      serverProgress,
      serverAssetId,
      generatedMessageId,

      clientStates
    }
    ```

    列表 URL 本身只作为来源分组，不得被当成一个可下载文件。

    ---

    ### 2. 顶层展示顺序

    在“传输记录详情”全屏浮层底部增加：

    ```text
    SNS 媒体文件
    ```

    区域中的顶层内容分为两类：

    1. 独立媒体条目；
    2. 列表来源组。

    按照本需求图示：

    * 所有独立媒体条目优先显示；
    * 所有列表来源组随后显示；
    * 独立媒体之间按照其 URL 在备注中的出现顺序排列；
    * 列表来源组之间按照列表 URL 在备注中的出现顺序排列；
    * 列表内部的媒体条目按照原列表顺序排列。

    ---

    ### 3. 独立媒体展示

    独立媒体 URL 直接显示为完整媒体条目，不增加收缩层。

    示例：

    ```text
    纯视频 1 的标题
    原始 URL
    封面

    文件状态：未抓取

    [文件预览区块]
    [抓取到服务器] [下载] [磁力链接] [释放空间/还原文件]

    [客户端下载进度条]
    ```

    具体按钮和区块根据状态机决定是否显示，不是全部同时显示。

    ---

    ### 4. 列表来源展示

    列表 URL 显示为可展开、可收缩的来源组。

    收缩状态：

    ```text
    > 列表标题（3 项）
    ```

    展开状态：

    ```text
    v 列表标题（3 项）

      - 第一个纯视频标题
        URL
        封面
        文件状态
        文件预览区块
        操作按钮
        客户端下载进度条

        ...

      - 第三个纯视频标题
        ...
    ```

    * `>` 表示收缩；
    * `v` 表示展开；
    * 点击整个列表标题栏切换展开状态；
    * 列表标题栏本身不显示“下载”“预览”“释放空间”等单文件操作；
    * 列表中的每个子媒体使用与独立媒体完全相同的媒体条目组件；

    ### 5. 状态必须拆为服务端状态和客户端状态

    不能只保存一个 `status`。

    #### 5.1 服务端状态 `serverState`

    ```text
    not_fetched
    fetching
    ready
    deleted
    failed
    ```

    含义：

    * `not_fetched`：尚未调用 yt-dlp；
    * `fetching`：服务端正在通过 yt-dlp 抓取；
    * `ready`：文件已经完整抓取到服务器临时目录，并已注册为 server asset；
    * `deleted`：服务端临时文件已经按清理策略删除；
    * `failed`：识别或抓取失败。

    #### 5.2 当前客户端状态 `clientState`

    每个客户端分别保存：

    ```text
    none
    downloading
    cached
    released
    interrupted
    ```

    含义：

    * `none`：当前客户端尚未取得文件内容；
    * `downloading`：正在从服务器或其他供源设备拉取；
    * `cached`：完整文件已经写入当前客户端缓存；
    * `released`：当前客户端曾完整缓存，但后来执行了“释放空间”；
    * `interrupted`：客户端下载中断，尚未形成完整缓存。

    ### 7. 文件预览区块

    每个媒体条目都预留文件预览区块，但根据状态控制内容。

    #### 尚无本地完整缓存

    ```text
    文件内容尚未获取
    [获取文件内容]
    ```

    * 从服务器 HTTPS 下载；

    #### 已有本地完整缓存

    * 视频使用 video；
    * 音频使用 audio 或现有音乐预览；
    * 图片使用 image；
    * 默认不自动播放；
    * 复用现有普通文件预览能力。

    ### 8. 操作按钮显示规则

    #### 抓取到服务器

    仅在以下状态显示：

    ```text
    serverState = not_fetched | failed
    ```

    不得因识别出 URL 而自动抓取完整媒体。

    #### 下载

    “下载”表示保存到用户系统下载目录。

    如果当前客户端尚无完整缓存：

    1. 先拉取文件；
    2. 拉取完成后再执行普通文件下载；
    3. 或允许通过鉴权 HTTPS 直接流式下载。

    #### 磁力链接

    即：

    ```text
    serverAssetId 已存在
    ```

    如果当前系统无法为 server asset 生成有效磁力链接，则隐藏该按钮，不得显示无效入口。

    #### 释放空间

    仅在：

    ```text
    clientState = cached
    ```

    时显示。

    #### 还原文件

    仅在：

    ```text
    clientState = released
    ```

    且至少存在一个可用来源时显示。

    ---

    ### 9. 服务端抓取完成后的处理

    yt-dlp 抓取成功后：

    1. 将媒体文件写入 `.tunnel-data` 下专用临时目录；
    2. 注册为 server asset；
    3. 生成一条普通文件传输记录；
    4. 新文件记录关联：

       * 原 Telegram 传输记录；
       * SNS 来源；
       * SNS 媒体条目；
    5. 把新文件记录 ID 写入 `generatedMessageId`；
    6. 把 server asset ID 写入 `serverAssetId`；
    7. 将 `serverState` 更新为 `ready`；
    8. 向隧道内设备广播状态更新。

    同一个媒体条目重复点击时，不得重复创建下载任务、server asset 或文件传输记录。

    ---

    ### 10. 客户端获取文件

    服务器持有临时媒体文件时，客户端优先通过带鉴权的 HTTPS 接口拉取。

    HTTPS 下载应支持：

    * Range；
    * 断点续传；
    * Content-Length；
    * Content-Type；
    * 下载进度；
    * 临时访问令牌；
    * 隧道权限校验；
    * 文件大小校验；
    * 可选哈希校验。

    Socket.IO 只负责：

    * 状态广播；
    * 下载进度事件；
    * 客户端缓存成功确认；
    * server asset 生命周期通知。

    不得通过 Socket.IO 传输完整的大型 SNS 媒体文件，除非 HTTPS 路径不可用并明确进入降级流程。

    ---

    ### 11. 客户端缓存成功确认

    客户端只有在以下条件全部满足后，才向服务端发送完整缓存成功 ACK：

    * 文件完整写入浏览器缓存；
    * 实际大小与 server asset 元数据一致；
    * IndexedDB 事务已经完成；
    * 文件状态已经更新为普通完整缓存。

    服务端不能仅根据 HTTP 响应结束判断客户端已经缓存成功。

    ---

    ### 12. 服务端临时文件清理

    服务端收到至少一个客户端完整缓存成功 ACK 后，才允许进入清理流程。

    同时需要满足：

    * 没有客户端正在读取该文件；
    * 已超过最短保留时间；
    * 当前下载任务已经结束；
    * 文件没有被其他服务端任务占用。

    清理后：

    ```text
    serverState = deleted
    ```

    但仍保留：

    * SNS 元数据；
    * SNS 来源分组；
    * server asset 元数据；
    * 普通文件传输记录；
    * 已缓存客户端的供源信息；
    * 原始 SNS URL。

    服务端临时文件删除后，不得自动再次调用 yt-dlp。

    ---

    ### 13. 示例

    假设备注中包含：

    ```text
    列表 URL（含 3 个视频）
    纯视频 URL 1
    纯视频 URL 2
    ```

    “SNS 媒体文件”区域按照本需求展示为：

    ```text
    纯视频 1 标题
      URL
      封面
      文件状态
      文件预览区块
      操作按钮
      客户端下载进度

    纯视频 2 标题
      URL
      封面
      文件状态
      文件预览区块
      操作按钮
      客户端下载进度

    v 列表标题（3 项）

      - 列表视频 1
        URL
        封面
        文件状态
        文件预览区块
        操作按钮
        客户端下载进度

      - 列表视频 2
        ...

      - 列表视频 3
        ...
    ```

    收缩后显示：

    ```text
    > 列表标题（3 项）
    ```

    这版最重要的改进是：**视觉层级按 URL 来源分组，文件状态按“服务端状态 × 当前客户端状态”组合计算。**这样即使备注里有多个普通视频、多个播放列表，或者服务端文件已删除但某些客户端仍有缓存，状态也不会混乱。
