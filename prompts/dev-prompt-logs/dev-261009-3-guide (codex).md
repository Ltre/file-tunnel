## 1. 完整需求整理（保留原编号）

### 1、修复回收站名称及补全信息

回收站应展示被删除项目的原始文件名或目录名，不得展示内部保留名 `:recycle:<id>`。至少显示原位置、项目类型、文件大小或目录内文件总大小、删除时间；目录可附文件数量。进入被删除目录后，子项应沿用原名称与层级。

同时修复已经保存错误名称的历史回收站摘要，但不能改变正文、Content Object 引用、回收站归属及原有还原/彻底删除规则。

### 2、固定协同列表的关闭区域

“查看协同列表”浮层的右上角关闭按钮和底部右侧“关闭”操作区应始终可见。内容较多时，仅中间列表滚动；兼顾窄屏、屏幕安全区及虚拟键盘，不把关闭按钮固定到错误的页面容器。

### 3、网盘导入显示忙碌状态

网页工坊“从网盘导入”选择器点击“导入”后，在按钮上显示旋转 Loading，直到本次资源读取和导入过程结束。期间禁止重复提交，但保留取消能力。成功、失败、取消都应正确清理忙碌状态，错误不能留下永久灰显按钮。

### 4、协同挂载在网盘内原地浏览与操作

点击自己原生目录中的协同挂载项后，在同一个网盘浮层的列表、工具栏和面包屑中进入协同内容，不再因此打开协同页 iframe。底层仍保持独立协同命名空间，不把他人的目录记录或逻辑文件伪装成自己的原生数据。

挂载内部按实际权限支持多选、预览、下载、重命名、复制/移动、复制路径、属性、缓存到浏览器、复制到协同项目、转发到隧道、分享、复制静态链接及删除。其中：

- 重命名、协同内部移动及删除，实际作用于原所有者的数据，须有 editor 权限并遵守既有保护规则。
- 复制到自己的分区后，副本属于自己；移动到自己的分区采用复制完成后删除来源的两阶段操作，部分完成必须明确说明。
- 分享记录只存于发起分享者自己的网盘，不在原所有者网盘生成分享记录，不因为此次分享冻结原文件；每次访问须验证来源及协同授权仍有效。
- 静态资源开放只能设置在本地 Mount 指针上，只产生本地开放记录；内部文件/目录可复制由 Mount 前缀和相对路径组成的链接，不能单独设置开放记录。
- 不提供挂载内部的防失联修复、二次邀请协同或二次设置协同；禁止目录嵌套污染、父目录进入自身后代、名称冲突及越界操作。
- Mount 本体的重命名、移动和移除只操作自己的指针。移除 Mount 不等于删除远端内容。
- 顶部“查看协同列表”的入口保持既有行为：受邀项目用全屏 iframe，自己创建的项目定位到自己的原生项目；不因原地挂载改造而一并替换。
- S3 与传统网盘 API 可列出和读取挂载内容，但对 Mount 本体及内部全部禁止写、删、改名、移动和移除挂载。

### 5、整目录全量下载（暂缓）

本轮不实现整目录打包下载，也不实现“是否包括挂载协同内容”的下载选项。现有单文件下载保持不变。

### 6、系统目录拖放递归上传及全局限制

支持从系统文件管理器拖放目录，完整读取各级目录与文件，保留目录结构和空目录。上传前先完成枚举和校验，再提示来源总大小、目标分区/目录，确认后开始上传。

个人网盘齿轮设置新增“上传文件夹最大尺寸”和“网盘允许最大目录层级”，默认分别为 500MB 和 30 层。前后端统一校验实际总大小、目标已有层级与新增目录层级；不得仅相信浏览器声明，也不能因为降低限制删除已有深层数据。

此限制针对网盘目录上传，不改变网页工坊 ZIP 项目的 20 层、100MB 限制，也不替代现有单文件上传限制或用户容量限制。

### 7、新建及编辑网盘文件

新增纯文本、Markdown、十六进制文件的创建及编辑入口。Markdown 与十六进制提供编辑/预览双栏；窄屏可上下排列，不能挤压到无法操作。

编辑正文发生变化时，通过写时复制创建或复用经过验证的新 Content Object，再只更新当前 Logical File 的内容引用；不得直接改写原共享 Content Object、原物理分片或其它逻辑文件。正文未变化时可以直接保存为无变化，不产生无意义的新版本。

## 3. 先修复三个独立问题

### 3.1 回收站内部名泄露：原因、修复与历史兼容

当前 `archive()` 先取得 `root = drive.get(...)`，再调用 `moveToTrash()`。后者保存快照后原地修改文件对象的 `name`，随后 `archive()` 将同一个对象此时的 `name` 写入回收站摘要。因此不仅 UI 显示错，已有 `trash_items` 摘要也可能已存入错误名称。此结论来自当前代码调用关系，不是文件名解析猜测。

实施要求：

1. 归档前复制原始名称、原父目录、完整原路径、类型及大小，或从已保存的精确根节点快照生成摘要。
2. 内部 `:recycle:<id>` 用于保留逻辑记录和释放原名称槽位，继续保持。回收站不是直接删除 Content 引用。
3. 历史修复优先使用 `snapshot.files` 中对应原逻辑 ID 的原名，其次使用可信的 `trashOriginalName`；不能从 UUID 猜名字，不能向 Telegram 批量重新下载。
4. 修复仅写摘要元信息；在同步事务中执行，可重复运行。证据不足时展示“原名称信息缺失”及可辨认标识，不编造名称。
5. 文件摘要建议输出 `originalName/originalPath/type/size/deletedAt`，并保持旧字段兼容。目录大小和数量由快照统计；子项删除时间继承本次归档时间。
6. 原有顶级整项还原、分区隔离、原父目录存在性及重名检查不变；保留还原后的原逻辑 ID 定位。

### 3.2 协同列表布局

为包含 `.disk-collaboration-list` 的对话框使用有最大可视高度的 flex 列布局：header/actions 不缩小，body `min-height:0`、`flex:1`、`overflow:auto`，卡片本体不滚动。采用和设置浮层一致的结构，而非将按钮绝对定位到整个浏览器角落。若此 class 同时用于协同管理列表，应一并验收其表现。

### 3.3 导入按钮的生命周期

集中管理 `setBusy()`：同步设置 spinner、`aria-busy`、按钮文字和禁重复点击，保留取消；在 plan、预校验、流读取、校验与提交完成/失败/取消的所有出口清理。

选择器负责的 Loading 至少覆盖完整资源读取；网页工坊后续保存草稿的阶段也应有明确反馈，不能选择器刚关闭就宣称“已导入”而实际保存失败。继续保持整次导入成功前不提前留下无正文节点；取消信号传给实际 fetch/reader，退出后不得晚到回调继续落数据。

## 4. 挂载命名空间和权限：改造的共同基础

### 4.1 建议新增统一 resolver，不取消现有作用域

建议在现有 `mounts.resolve()` 和协同作用域中间件之上形成公共 namespace resolver，可单独放入新模块；名称在实施时确定。输出应区分：

```text
actorId、channel                       操作者与可信访问渠道
localPartitionId、localScope、mountId  自己的分区及本地挂载
collaborationId、grantVersion、role    当前协同授权
sourceOwnerId、sourceScope             远端真实所有者及分区
rootKind、rootFileId / rootPath        授权根
relativePath、resolvedFileId / path    本次范围内的真实对象
```

- `channel` 由已认证的路由/中间件赋值，不能接受客户端自报 `web` 绕过 API 只读。
- 只接收 mountId、相对路径或文件 ID 等必要定位输入；远端 owner、store、角色和授权版本必须服务端解析。
- 路径解码、标准化、目录分隔符、`.`/`..`、大小写策略及 Unicode 沿用现有网盘规则；先验证范围，再查实体。拒绝路径穿越，不能把 UI 虚拟路径直接当远端磁盘路径。
- 每次列出、读缓存、下载、分享、静态读取和变更均复核 Mount、分区、grant、实体/审核状态；长操作提交前再复核授权版本及源版本。
- 授权撤销后已有 UI 清空或退出该 namespace，取消在途可取消请求；不把上次列表快照视为当前有效授权。

### 4.2 数据及拓扑边界

Mount 继续使用 `disk_collaboration_mounts` 的本地叶子记录，不创建远端子目录副本，不向自己的 `disk_files/disk_directories` 混入远端节点。只有用户明确执行复制/转存，才创建自己的 Logical File 引用。

保留 `assertTopology()`、`assertCanEnableDirectory()`、`assertCanRelocateDirectory()`、名称保护及数据库约束：原生协同目录不能混入 Mount，Mount 不能再挂到协同内部。两个协同项目可能对应同一真实 owner/scope 的父子路径，比较真实位置后再判断“把父目录复制/移动进子目录”，不能只比较 collaborationId。

单文件协同根及目录协同根仍遵守现有 root 保护；“像原生文件操作”不等于取消原有不能移动/删除协同根的规则。普通内部子项可在授权下操作。

### 4.3 权限矩阵

| 对象 / 渠道 | 读、预览、下载 | 改名 / 编辑 / 范围内移动 / 删除 | 分享 | 静态设置 |
| --- | --- | --- | --- | --- |
| Web：自己的 Mount 指针 | 可进入 | 本地改名、移动、移除指针；不删远端 | 本地代理入口 | 可设置 Mount |
| Web：内部 viewer | 可 | 禁止 | 默认允许有权访问的内容 | 禁止单项设置，可复制继承链接 |
| Web：内部 editor | 可 | 按实时授权及既有保护执行 | 默认允许 | 同上 |
| S3 / 外部 API：Mount 及内部 | 可，只读范围受凭证约束 | 全部禁止，不能移除指针 | 不在本轮新增这些写接口 | 禁止 |

底层要同时检查渠道和角色。隐藏按钮只能改善交互，不能代替服务端拒绝。

### 4.4 同一个网盘 UI 的导航与实体定位

建议在 `client/disk-ui.js` 引入独立 NavigationContext，区分 native 与 mounted 两种状态；保存自己的分区、Mount 所在目录、协同相对路径、选中项及滚动位置。

- 进入 Mount 更新列表和虚拟面包屑；点击自己目录的面包屑退出远端 namespace，恢复原生列表。不能把全局 `DiskClient.getSpace()` 改成远端 owner 的分区。
- 对列表项使用统一实体 locator 和包含 namespace/mount/源实体的复合 key。名称不作为选中、删除、缓存或进度匹配主键。
- `openTelegramDriveItem()`、搜索结果打开、多选、右键/长按菜单、目录目标树、拖放、预览、缩略图、下载、属性、缓存、转发、静态链接及任务进度均根据 locator 分派，不能仅替换 Mount 的 click 回调。
- `openDiskCollaborationFrame()` 保留给顶部协同列表；独立邀请页不受影响。
- 属性中明确显示来源所有者、协同项目、真实来源与本地挂载位置，避免用户把远端删除误认为只删指针。
- 复制路径用于虚拟导航时与静态 URL/真实来源字段区分；提供可引用链接时编码每个路径段，不混入 displayName。

## 5. 文件操作、跨协同移动与异常恢复

### 5.1 优先复用现有操作层

现有 `/api/telegram/drive/mounts/:id/resolve` 和 `/collaboration-scope/:collaborationId` 可作为基础。建议增加 Mount 绑定的浏览器 namespace 路由包装层，解析本地 Mount 后再调用既有操作，不复制一套 Telegram 上传/分片实现。

`copyAcrossNamespaces()` 已有源/目标 scope 检查、源快照、Content lease、事务内授权复核和复制证明；`copyGrantedItem()` 已实现授权资源转存。扩展时同时核对 `disk-content-repository.js` 的 SQL 层证明，不能仅在 HTTP 路由里说“已授权”便直接写引用。

同 namespace 的目录复制/移动继续检查目标存在、所有重名、静态保护、目录深度与父子关系。viewer 可复制可读数据到自己的网盘，但不能执行含来源删除的移动。

### 5.2 跨协同 → 自己网盘：两阶段移动

建议用持久化操作记录协调以下状态（名称为方案建议）：

```text
PREPARED → COPYING → COPY_COMMITTED → DELETING_SOURCE → COMPLETED
                         └────────────→ COPIED_SOURCE_RETAINED
复制前失败/取消 → FAILED / CANCELLED
```

1. **准备**：明确告知将删除他人的来源内容；记录操作者、源/目标 namespace、源 ID/路径/内容版本、授权版本、目标分区/目录、幂等键及目录清单。
2. **复制**：验证完整源树，申请必要 lease。目标新 Logical File 使用自己的 owner/scope，共享有效 Content Object；历史资源走当前受控迁移/复制路径，不伪造已验证内容键。
3. **提交目标**：同步短事务复核权限、名称、路径、Content 状态和快照版本，创建全部目标逻辑引用及目录，原子记录目标映射与 `COPY_COMMITTED`。
4. **删除来源**：重新验证 source editor、grantVersion、源实体未变以及原有删除保护。按 Web 当前删除语义进入**真实原所有者的回收站**；不能误归档到操作者回收站，也不能调用删除 Mount 的函数代替来源删除。
5. **成功**：目标可读、源已归档，记录完成并定位目标。
6. **部分完成**：目标已提交，但来源改动、授权撤销、保护限制或删除故障时，保留目标副本，显示“复制已完成，来源未删除”，提供查看目标和安全重试删除入口。

事务内不得等待 Telegram、浏览器或任何网络操作。复制后源与目标共享正文，来源删除只解除/归档对应逻辑关系，不能删除目标仍引用的物理 anchor。

### 5.3 幂等及 recovery

- 重复请求、刷新或服务重启读取持久化阶段，不重新复制已完成目标，不把同名其它文件当成目标。
- 来源变化后禁止自动删除新版本；重试必须使用原清单 ID/版本进行 CAS，而不是按当前路径全删。
- 复制成功后取消只能停止后续来源删除，并报告保留了两份；不能在用户已改动目标后自动回滚该目标。
- 权限撤销后的新读/写被拒绝；此前已合法复制完成、已属于自己的副本不被自动追删。
- 崩溃恢复只推进有充分证据的阶段；未确定提交结果先查事务记录，不靠内存计数推断成功。
- 多选需定义逐项结果或整组选项事务，失败提示准确列出已复制、已删除、未处理项；不能只展示 `CONTENT_COPY_SCOPE_INVALID`。
- 原因通过 `server/disk-errors.js` 的错误码和细分 reason 表达，业务路径可读，敏感 SQL/凭证/堆栈不返回。

本轮明确要求协同到自己原生分区的移动。不同协同项目之间的**复制**继续保留；不要擅自将跨协同项目移动扩展成新的产品要求。

## 6. 本地代理分享与 Mount 静态资源

### 6.1 分享记录与源身份

`disk_shares` 增加兼容旧记录的来源类型。建议 mounted 来源记录包含 mountId、collaborationId、远端文件 ID 或受限目录定位、必要的源身份信息；share.ownerId 仍为发起分享者。

每次请求通过“分享者拥有此 Mount → 仍有该协同授权 → 对应实体仍位于范围内”解析真实 store。公开 token 只授予读取分享所选内容，不是绕过协同权限的永久副本凭证。

- 不在远端 owner 的分享表产生记录，不建立额外 Logical File，不增加公开再分享审批。
- 原所有者修改正文后可读取更新内容；移动出授权范围、删除、审核封禁、grant 失效或 Mount 被移除，相关代理访问必须失败。
- 用文件 ID 锚定文件，不能按旧文件名误认同名新文件。当前目录以路径为键，缺少稳定目录 ID；实施时需补稳定目录身份或安全失效规则，避免“旧目录被删，同路径新目录”自动获得旧分享。
- 若目录来源身份无法确认，宁可令旧代理分享失效，不扩大授权。目录改名/移动的关联更新应在对应源变更事务中完成，或通过明确身份校验安全失效。
- 分享页转存这类来源时，也应验证代理分享 + Mount + 当前 grant；现有只针对原生 share.ownerId 的 Content 复制证明不能原样套用。

### 6.2 Mount 级静态开放

扩展 `disk_static_resources` 支持明确的 Mount 来源类型，记录在本地 owner/scope，签名绑定开放记录及有效期。只在 Mount 本体创建记录；内部链接由当前相对路径拼接，不能在远端逐项创建静态记录。

静态请求、目录枚举、HEAD、Range 与条件请求都经过相同动态 resolver。更新默认缓存期限、停止开放、复制链接继续使用现有设置体验；内部菜单只提供“复制静态链接”，不提供“静态资源设置”。

本地 Mount 开放不能给远端附加禁止修改/移动/删除的保护；原所有者自行设置的原生静态保护仍照常生效。Mount 自身的路径保护与停止开放流程应沿用原生静态链接的本地规则，避免无提示破坏本地发布路径。

**缓存边界**：无法撤回用户已下载或第三方 CDN 已缓存的数据。建议挂载代理响应采用 `no-store` 或必须重新验证的策略，保证下一次服务端访问及时反映撤权；不要直接套用原生永久静态资源的长期 public 缓存。此为安全实现建议，须在文档中说明与原生静态缓存的区别。

## 7. S3 与传统 API 的挂载只读适配

### 7.1 读取路径

在 `server/object-storage.js` 的 stat/list/open 及传统 API 的列表/读取层，识别当前凭证 owner/partition 下的 Mount，并映射到受限虚拟目录。

- S3 Mount 表现为可枚举的只读前缀，而非一个可以上传覆盖的普通对象；单文件协同要定义清楚唯一子文件的键。
- ListV1/V2、prefix、delimiter、分页、HEAD、GET、Range/流取消按现有协议返回。分页必须有界，不为列出一页下载正文，也不无限扫描全部远端树。
- continuation token 与本地 bucket/prefix/身份范围一致；即使 token 来自旧列表，后续页仍重新验证 grant。
- 远端正文读取保持现有分片流、取消、缓存、ETag 与版本机制，不能通过远端 owner 的身份绕过调用者凭证范围。
- 普通原生对象的 S3/API 行为保持原状，避免挂载规则把整个 bucket 变为只读。

### 7.2 写拒绝必须覆盖的入口

覆盖 S3 PUT、multipart 初始化/上传/完成、DELETE、批量 DeleteObjects、CopyObject 的**目标**、目录 marker；覆盖外部 API 新建、上传、repair/替换、PATCH 改名/移动、删除及递归目录删除。

- 目标路径只要落入 Mount 前缀，即使子项不存在，也先拒绝写入；不能先按普通 missing object 路径自动创建原生目录。
- 删除 Mount 指针直接拒绝；批量操作逐项返回明确只读错误，不能因一个挂载项而错误删除整个原生父树。
- 删除/移动原生父目录若会移除其内 Mount，应阻止这一 API 操作并说明原因；不得隐式绕过“禁止移除挂载”，也不得静默跳过然后宣称全部成功。
- editor、管理员形式的普通用户凭证或构造请求参数不能绕过此访问渠道限制。管理后台已有专门管理能力不与外部用户 API 混为一谈。
- 本轮不新增“API 跨挂载复制到自己”的写操作；Web 复制保留。若现有协议适配允许 CopyObject 读取挂载作为源，目标必须为自己的原生空间，并有明确的源授权证明；不能用 Copy 的源可读绕过目标只读。

可采用统一 `MOUNT_READ_ONLY` 错误码（建议名称），附可读说明及协议对应状态；不得仅返回内部 SCOPE 错误。

## 8. 目录上传、全局设置及统一深度

### 8.1 设置与有效限制

建议新增用户级设置表/仓储或既有用户设置的有版本结构，包含 `folderUploadMaxBytes`、`maxDirectoryDepth`；不要将全局限制只写到某个 partition.settings 或 localStorage。后端校验类型、上下限及默认值，设置页加载和更新后准确回显。

- 目录深度根目录为 0，根下第一层目录为 1；文件名不计目录层级。
- 系统硬上限 30，个人默认 30。降低个人值只约束后续创建/上传/移动，不让已有目录消失或在启动时报错删除。
- 挂载内写入按**真实目标 owner** 的有效限制执行；不把自己的 Mount 虚拟路径叠加到远端真实层级。
- 500MB 的字节单位需统一。建议按 `500_000_000` 字节定义并在 UI/文档明确；若使用 MiB 必须标注并统一换算，不能前后端差一档。
- 现有单文件 2,000MiB 限制、用户容量及分片限制分别保留；文件夹合计限制只覆盖本次目录来源文件集，不统计目标旧文件占用。

`server.js` 中 `driveMaxFolderDepth` 的归一化、配置默认值，`pages/tgbot.html` 的表单范围，以及 `telegram-drive.js` 的 `assertDepth()`、初始化重建、各方法默认 20、manifest 恢复默认值必须一起审查。旧站点配置 20 不能无意成为所有用户默认 30 的第二套永久限制；建议明确迁移为新策略的站点默认来源，随后各入口统一调用有效限制 resolver。

覆盖新建、多级目录、目录复制/移动/改名、跨分区转移、跨 namespace 复制、S3 marker/PUT、传统 API、上传 finish/recovery、回收站还原。降低设置后仍能浏览既有深层数据；还原超限时给出原因，不删除回收站记录。

### 8.2 来源目录枚举与完整预校验

浏览器优先使用支持的文件系统 entry/handle API；旧 `webkitGetAsEntry()` 目录需循环 `readEntries()` 直至返回空批次，不能只读取第一批。能力不足时提示改用目录选择输入或逐文件上传，不将目录默认为空而假成功。

生成清单：相对目录（含空目录）、文件路径、大小、类型与对应 File。不要在枚举成功前上传或创建目标目录。

预校验包括：

- 来源所有层级字节合计；多个目录属于同次目录导入时合计校验，不能分开调用逃避限制。
- 目标真实目录深度 + 来源目录层级，不超过有效限制。
- 同名、文件占用目录路径、非法段、重复条目、目标 static/review/grant 保护及 mount 只读渠道。
- 避免跟随目录链接无限循环，拒绝不可读取的来源并明确哪些文件失败，不静默漏导入。
- 同时拖入目录和散文件时，在确认中分别列明来源；目录清单内文件不因混合选择而跳过限制。

服务端再次验证清单及实际收到字节，逐批核验文件与目标路径；不能相信浏览器总大小或忽略后续改动。限制和授权在提交前复核。

### 8.3 复用渐进式上传，处理 100 文件批次边界

当前 `DiskClient.uploadFiles()` 和 store.begin 都有 100 文件上限，现有上传预校验也有请求数量边界。目录可能超过 100 个文件，建议增加父级目录上传任务及子批次协调，而非直接删除该安全限制。父级完整清单使用有界、可分页的专门预校验，不能把完整目录清单直接塞进仍限制 100 项的旧接口。

- 客户端计划增加每文件 `folderPath`，服务端已有此能力；仍采用现有分片规划、progressive staging、重试、PoP/内容复用及 finalization。
- 全目录预校验完成后分批上传。每个原有子批次维持“整批成功后显示文件”的事务语义；本轮不改成每分片或每文件完成即写最终文件列表。
- 父任务持久化已完成批次、目标 ID、版本及新建目录清单；空目录单独可靠创建并记录归属，不漏掉空文件夹。
- 父任务显示整体实际上传、Telegram 发送/确认、已完成文件和批次数，不能把当前子批次 100% 当整个目录完成。
- 某个后续批次失败时，说明已有批次完成、哪些失败/未开始，允许安全重试；除非额外实现可靠的全目录原子提交，不能承诺整目录自动全量回滚。
- 清理只处理本任务创建且仍未被其它操作改变的实体；不能按目标路径递归删除所有数据。Content lease、零引用物理清理与现有失败补救机制照常使用。
- 浏览器关闭/重启后 File 对象不能从服务器凭空恢复。需重新选择来源并核验清单再续传，不能仅凭文件名续传另一个正文。
- 取消信号贯通枚举、排队、fetch/上传、服务端任务及 Telegram 拉取/推送；使用已有诊断与幂等恢复，不修改代理控制策略。

## 9. 文件编辑：新内容、新引用，保留旧共享正文

### 9.1 UI 与内容语义

新增“新建文件”类型选择与“编辑”入口；创建时检查文件名、当前目标路径、分区、目录深度、同名文件/目录/Mount，不能静默改名后保存到意外位置。

- 纯文本编辑注意 UTF-8、BOM、换行；不支持可靠解码的正文转入十六进制或提示，不用替换字符覆盖二进制。
- Markdown 提供编辑/渲染预览。必须安全处理 HTML/脚本和资源引用；不能假设项目已安装某个 Markdown parser/sanitizer，实施时检查依赖再选择。
- 十六进制按字节偏移编辑，可显示十六进制与 ASCII/文本预览；验证每个字节、奇数半字节及无效字符，保存原始 bytes，而非十六进制字符串本身。
- 为大文件设置有说明的编辑能力边界，不能把任意大文件一次性加载到主线程。具体上限是实现配置建议，不将其伪装成用户已经确认的产品额度。
- mounted viewer 不显示写入口；mounted editor 支持有权限的编辑；API 挂载只读不受 Web 编辑入口影响。

### 9.2 建议接口与保存过程

当前没有完整原生编辑器接口。建议浏览器新增创建正文和按逻辑 ID 替换正文的受控接口，路径在实施时确定；提交至少包含 expectedContentId、expectedLogicalContentVersion/记录 revision 和新内容长度/类型。

1. 验证 owner/scope 或 Mount 当前 editor、static/review、源逻辑版本和名称范围。
2. 读取/上传新正文，计算已验证内容哈希；正文无变化则 no-op，不申请无意义的新 anchor。
3. 正文变化则使用新 Content Key 创建 Content Object，或按现有同内容验证、PoP/授权及 claim 规则复用已经有效的新内容；绝不能用旧 Content ID 代表新 bytes。
4. Telegram 正文、缩略图和 mediaIndex 准备在数据库事务外执行；不能继承旧正文的哈希、媒体索引及封面当成新内容。
5. 短事务再次检查 grant、源版本及所有保护，只更新当前 Logical File 的引用、内容版本和相应元信息；保持其逻辑 ID、所有权及位置，除非用户另行执行改名/移动。
6. 其它引用旧 Content Object 的文件不变；旧 anchor 只在真正零引用且没有有效 lease 时进入清理。
7. 提交失败时保留旧文件及编辑缓冲；按现有 orphan/remote cleanup 机制处理新上传但未关联的物理资源，不能留下 READY 可复用的未完成半成品。

`syncFile()` 已有 expectedContentId、expectedContentVersion、expectedPhysicalRevision 检查，应复用并补明确的冲突响应。两个标签页同时编辑，后保存者应收到“原文件已更新”而非覆盖前者。

### 9.3 不能混淆正文编辑与 repair

当前 `/files/:id/repair` 原生流程校验原大小及原正文哈希，是修复同一内容的物理托管；协同 replacement 已支持不同正文并有授权/CAS 复核。可以提取共同的上传与补救机制，但不能放宽原生 repair 的同正文校验来冒充编辑功能。

编辑保存后失效当前逻辑版本的预览、缩略图、浏览器缓存及媒体进度索引，刷新相关列表和属性。挂载缓存命中也须先检查当前授权；不能因缓存已有 bytes 而把已撤权来源继续呈现为在线可访问。

## 10. 持久化、迁移与事务约束

当前通用 schema 为 4，`disk-repository.js` 提供 WAL 及同步 `atomic()`。当前 Content 表包括 `disk_contents`、`disk_content_refs`、`disk_content_leases`、`disk_content_cleanup`、`disk_content_claims`、PoP、批次及 caption/历史表；应复用，不能另造一套 Content 引用数据库。

建议迁移内容：

- 用户全局设置的有版本结构，默认 500MB/30 层；增加 owner 约束和有界校验。
- 分享、静态记录增加 mounted 来源类型及必要绑定字段；旧 native 类型默认保持原义。
- 跨 namespace 移动和目录父任务的持久化阶段、幂等键、源/目标映射、版本及错误摘要；可复用 operations 展示，但恢复所需数据不能只存显示文案。
- 回收站错误摘要修复标记及幂等校准，不改变引用生命周期。
- 若采用稳定目录身份，应先设计其生成、目录移动/删除/还原及历史目录兼容规则，不能仅加一个未被操作层维护的 UUID 字段。

下一 schema 编号在实施时按实际 HEAD 决定，不将“5”视为已经落地。沿用当前迁移备份原则，在变更前生成可恢复的 SQLite 备份；处理 payload 兼容、索引、已有重复与半完成任务，失败回滚，不用 JSON 整库覆盖 SQLite。

关键事务边界：

| 操作 | 数据库事务内 | 事务外 |
| --- | --- | --- |
| 回收站归档/还原 | 快照、逻辑记录、Mount 指针、摘要一致提交 | UI 刷新与定位 |
| 跨 scope 复制 | 当前授权、源版本、目标冲突复核，目录/逻辑引用及阶段提交 | 长枚举、必要网络准备、任务展示 |
| 跨 scope 移动 | 目标提交与来源删除分别可靠记录；来源删除前 CAS | 两阶段之间的协调、重试及用户反馈 |
| 正文编辑 | 当前单逻辑引用切换、版本增加、旧引用释放 | 哈希/PoP、Telegram 上传、封面和媒体索引 |
| 目录上传 | 每个子批次的最终提交、父任务阶段和目标映射 | 来源枚举、浏览器上传、Telegram 推送 |

任何网络 await 都不能放进同步 SQLite 事务。授权撤销、同名竞争和 Content 清理竞态必须在提交点再次校验；回滚后同步刷新内存 store，避免数据库回滚而内存仍显示成功。

## 11. 实施顺序与阶段验收

### 阶段 A：小问题和共同规则

完成需求 1～3；建立最终需求矩阵、30 层有效限制和设置数据模型，确定 namespace locator、渠道策略及旧数据迁移方式。

验收：回收站原名与历史修复、关闭按钮固定、导入 Loading/取消；现有 20 层 ZIP 限制不变；只读渠道有服务端单测，不依赖菜单隐藏。

### 阶段 B：Mount 原地只读浏览

先接通统一 resolver、NavigationContext、列表/面包屑、搜索、预览、下载、属性和缓存，不立即放开变更按钮。顶部协同列表仍用既有 iframe。

验收：native 与 mounted 来回切换正确，真实 scope 隔离，过期/撤权/同名不同 ID 不串数据，缓存和 Range 读取遵守授权。

### 阶段 C：Web 写操作及跨边界移动

接入 rename、内部复制/移动、多选删除、目标树和跨 scope Copy；再开发持久化“复制后删除来源”状态机及恢复，补充可读错误细分。

验收：viewer 禁写，editor 只能操作范围内子项；父子目录与同名拦截准确；复制后源删除失败明确部分完成；重试/重启不重复复制、不误删新版本。

### 阶段 D：代理分享、Mount 静态与协议只读

按顺序接入 mounted share、静态前缀、S3/传统 API 虚拟读取，完善源证明、撤权、缓存和全部写入口拒绝。

验收：只在本地生成分享/开放记录，远端不被本地分享冻结；静态子项不产生个体开放记录；API editor 仍只读，缺失路径写入和父目录递归删除不能绕过。

### 阶段 E：目录递归上传

完善系统目录枚举、清单预校验、500MB/30 层、空目录与超过 100 文件的父任务/子批次协调；接入设置页，保持原 progressive 上传链路。

验收：深度/大小边界、空目录、Unicode、重名、来源读取失败、分批失败、取消/恢复及目标改动均有准确结果，无目录污染。

### 阶段 F：新建与正文编辑

新增三类编辑器与 COW 接口，补版本竞争、失败清理和新正文相关缓存刷新；最后执行整体回归。

验收：修改同 Content 的一个文件后其它引用保持原内容；保存冲突不覆盖；hex bytes 往返正确；原生 repair、分享、S3 原生写和网页工坊未回归。

阶段完成不代表整个任务完成。最终必须逐项对照需求 1～7（第 5 条明确暂缓）及最终 a～e 检查，不能只验收新增 UI。
