# interrupt-agent-logs

本目录用于保存**因额度不足、上下文中断、程序异常或其它原因未能一次执行完成的 Agent 任务记录**。

这些记录主要用于后续重新启动 Agent 时，恢复上一轮任务的：

- 原始需求；
- 已执行过程；
- 已完成修改；
- 中断位置；
- 尚未完成的工作；
- 测试与验收状态。

恢复任务时，不应仅根据日志末尾机械续接，而应结合日志、当前代码状态和 Agent 可用的上下文，重新判断任务的真实完成度。

---

## 一、文件命名

中断记录文件统一以：

```text
ir-
```

开头，后接原任务编号。

例如原任务编号为：

```text
261003-1
```

则记录文件命名为：

```text
ir-261003-1.log
```

---

## 二、记录内容格式

基本格式：

```text
[编号261003-1]问：

    XXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX
    XXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX
    XXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXXX


[因额度不足被中断]答：

    YYYYYYYYYYYYYYYYYYYYYYYYYYYYYYYYYYYYYYYY
    YYYYYYYYYYYYYYYYYYYYYYYYYYYYYYYYYYYYYYYY
    YYYYYYYYYYYYYYYYYYYYYYYYYYYYYYYYYYYYYYYY
```

其中：

- `问`：保存该轮任务的完整原始需求；
- `答`：保存 Agent 在中断前产生的完整执行记录；
- 中断原因可根据实际情况填写，例如：
  - `因额度不足被中断`
  - `因上下文中断`
  - `因程序异常被中断`

应尽量保存完整执行记录，包括 Agent 已进行的分析、文件修改、命令执行、测试结果以及中断前最后状态。

---

# 三、如何发起任务恢复

重新启动 Agent 后，应创建一个新的任务编号，并明确指出上一轮任务编号及对应的中断日志。

例如：

```text
上一轮：261003-1
恢复任务：261003-2
```

恢复任务的核心要求是：

1. 读取上一轮原始需求；
2. 读取上一轮 Agent 执行记录；
3. 检查当前工作区实际代码状态；
4. 判断哪些工作已经完成；
5. 判断哪些工作在执行过程中被中断；
6. 判断哪些工作尚未开始；
7. 检查中断位置是否留下半成品或错误状态；
8. 从正确的位置继续执行；
9. 最后重新按照上一轮**完整原始需求**进行整体验收。

不要简单依据日志最后一行直接继续。

Agent 的执行记录只是判断依据之一，**当前工作区的实际代码状态才是确认上一轮修改是否真正落地的重要依据。**

---

# 四、任务恢复需求示例

## 示例 1：简单版

```text
[编号261003-2]问：

    上一轮任务（`编号261003-1`）因额度不足被中断。

    请结合 `prompts/dev-prompt-logs/interrupt-agent-logs/ir-261003-1.log`
    中记录的上一轮原始需求和 Agent 执行记录，以及本 Codex 程序中的记忆上下文，
    定位上一轮任务被中断的位置，并按照 `ir-261003-1.log` 中的原始需求继续执行任务。

    特别注意：

    如果上一轮任务的中断点恰好位于某项修改、测试或验收过程中，
    应重新检查该部分的实际完成状态，避免中断位置留下未完成、
    错误完成或状态不一致的问题。

    最后应按照上一轮原始需求重新进行整体验收。
```

---

## 示例 2：严谨版

```text
[编号261003-2]问：

    上一轮任务（`编号261003-1`）因额度不足被中断。

    请结合：

    1. `prompts/dev-prompt-logs/interrupt-agent-logs/ir-261003-1.log`
       中记录的上一轮原始需求及 Agent 完整执行过程；
    2. 本 Codex 程序中的记忆上下文；
    3. 当前工作区的实际代码状态；
    4. 当前相对于 HEAD 的未提交、未暂存差异；

    准确恢复上一轮任务的执行上下文，并继续完成任务。

    当前工作分支为：

    `dev/2609-s5-disk-chunks-progressive-push`

    除明确说明不属于上一轮任务的文件（如 `prompts/dev-prompt-log/dev-2609.md` ）外，本分支当前所有未提交、
    未暂存的代码差异，均应视为判断上一轮实际执行进度的重要依据。

    不要误删、覆盖、回退或重复实现已经正确完成的修改。

    恢复时不要简单从日志最后一行机械续接。

    应根据上一轮原始需求，结合执行记录、记忆上下文和当前代码差异，
    逐项判断：

    - 哪些内容已经正确完成；
    - 哪些内容正在执行时被中断；
    - 哪些内容尚未开始；
    - 哪些修改虽然已经产生代码差异，但尚未完成测试或验收；
    - 中断位置是否留下半成品、错误状态或前后不一致。

    如果中断点位于某项代码修改、测试、恢复流程或验收过程中，
    不能默认中断前的操作已经成功完成，应重新检查实际状态。

    确认中断位置不存在半成品、错误完成或状态不一致之后，
    再从正确的位置继续执行。

    完成续接后，应重新按照 `ir-261003-1.log` 中
    `编号261003-1` 的完整原始需求对整个任务进行整体验收。

    不能只验收本轮恢复后新增的修改，
    必须确认上一轮任务最终已经整体、完整、正确地完成。
```

# 五、建议附加的通用任务约束

任务恢复需求末尾最好继续附上当前任务的分支、提交规则、开发日志位置等通用约束。

例如：

````text
---

目前处于分支：

```text
dev/2609-s5-disk-chunks-progressive-push
```

请直接在该分支当前代码基础上修改。

**不要提交，不要暂存（不要执行 `git commit`、`git add`）。**

推理结论、问题根因、实际修改内容、测试情况及开发记录保存到：

```text
docs/devlog/dev-2610-features.md
```

最后请另外给出建议使用的 Git 提交日志，但不要实际提交。

Git 提交日志要求：

- `title` 以中文为主，简洁概括本次改动；
- `description` 以中文为主；
- `description` 按功能分成若干简短小节；
- 每个小节使用几行列表概括主要修改；
- 内容有条理，但不要写得过于冗长；
- 将 Git 日志的 `title` 和 `description` 分开显示；
- `title` 和 `description` 分别使用代码块，便于直接复制。
````

# 六、恢复任务时的判断原则

任务恢复的目标不是“接着上次最后一句继续”，而是：

```text
原始需求
    ↓
上一轮执行记录
    ↓
当前工作区实际状态
    ↓
判断真实完成度
    ↓
修复中断现场
    ↓
继续剩余任务
    ↓
按照原始需求整体验收
```

尤其需要避免以下情况：

- 重复实现上一轮已经完成的功能；
- 覆盖上一轮已经正确完成的代码；
- 因日志声称“已完成”就默认代码一定已经正确落地；
- 忽略中断前尚未运行完成的测试；
- 忽略处于中间状态的文件修改；
- 只完成中断后的剩余步骤，却没有重新验收整个原始需求；
- 将其它历史任务留下的工作区差异误认为本轮任务产生的修改。

如果当前工作区存在多轮任务留下的未提交修改，应在任务恢复需求中明确指出哪些差异属于上一轮任务，避免 Agent 错误归因。
