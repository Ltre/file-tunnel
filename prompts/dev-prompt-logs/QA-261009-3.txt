    而不是把协同文件真的合并到自己网盘的目录表里。

    ### 2. 你要求的操作应该怎样分配作用域

    这里最容易发生误操作的地方，是对 Mount 本体操作与对 Mount 内部文件操作的区别。

    | 操作     | Mount 本体    | Mount 内文件/目录         |
    | ------ | ----------- | -------------------- |
    | 打开     | 进入协同命名空间    | 浏览或预览                |
    | 重命名    | 只改自己挂载名称    | 真正修改原所有者的名称          |
    | 移动     | 移动本地挂载指针    | 协同内部允许；跨作用域需特殊处理     |
    | 复制     | 复制挂载指针      | 复制 Content Object 引用 |
    | 删除     | 移除挂载，不删除远端  | 真正删除原所有者的文件          |
    | 分享     | 可考虑分享整个挂载内容 | 在自己账号下建立分享记录         |
    | 静态资源开放 | 可以设置        | 不允许单独设置              |
    | 防失联检测  | 不适用         | 不提供该操作               |
    | 邀请协同编辑 | 不适用         | 禁止二次发起协同             |

    其它如下载、浏览器缓存、属性、复制路径、转发到隧道，都应按实际来源文件处理，而不是伪造一份自己的 Logical File。

    这需要增加统一的 Mounted Namespace Resolver，使网盘原有操作在执行前清楚知道：

    ```
    当前登录用户
    当前本地分区
    mountId
    collaborationId
    远端真实 owner / scope
    协同根目录
    当前相对路径
    当前 viewer/editor 权限
    ```

    尤其不能仅凭 UI 展示的 `/我的网盘/项目/张三项目/src` 字符串直接推导远端数据位置。

    ### 3. “复制/移动”存在一个尚未解决的语义冲突

    之前我们已经约定：

    > 跨 Native / Collaboration 边界只能 Copy，不能 Move。

    但你这次希望支持“复制/移动到指定网盘分区的原生目录”。

    这里需要分开：

    同一个协同项目内部移动：可以保留真正的 Move。只要目标仍在协同授权范围内，并且用户具备 `editor` 权限。

    协同 → 自己的原生分区：Copy 很容易实现，直接新建 Logical reference，共用已有 Content Object。

    但真正 Move 意味着：

    ```
    复制到我的分区
        ↓
    删除对方原始文件
    ```

    虽然能开发，但操作风险明显更大。

    我的建议是保留之前的约定：跨协同作用域只允许 Copy。 如果一定要支持 Move，也必须将它作为一个明确的“复制后删除来源”操作单独设计，而不是复用普通 Move 接口。

    值得区分的是：S7 已经实现的本人两个原生分区之间的 Move 可以继续保留，这不是跨他人协同边界的 Move。

    ### 4. 分享和静态链接：这是第 4 条真正新增的复杂业务

    你提出的想法可以概括为：

    > 被挂载的协同项目仍属于别人，但是我可以从自己的网盘对它建立分享或静态资源入口，而不会在原所有者的网盘中生成分享记录，也不会要求原所有者冻结文件。

    这可以实现，但我建议将其定义为 基于动态授权的代理分享。

    例如：

    ```
    我的网盘
      └── 🔗 张三项目     ← 本地 Mount M1
            └── docs
                 └── a.pdf
    ```

    你可以对 `a.pdf` 建立自己的普通分享记录。

    分享记录只需要引用：

    ```
    分享所有者 = 我
    mountId = M1
    collaborationId = C1
    远端文件 ID = F1
    ```

    它不必在张三的 `disk_shares` 中新增记录，也不必复制文件正文。

    但是打开分享链接时，必须重新验证：

    - M1 是否仍存在；
    - C1 是否仍有效；
    - 我是否仍有访问权限；
    - 目标文件是否仍存在且仍处于协同授权范围。

    因为你已经要求原所有者不必因为我的分享而冻结文件，所以应该接受这样的结果：

    张三删除文件，我的分享自动失效；张三替换文件，分享读取更新后的内容；张三撤销我的协同权限，相关分享和静态访问不应继续泄漏原内容。

    这正是“不冻结原所有者文件”需要付出的代价。

    还有一个必须正视的权限问题：别人允许你查看或编辑，并不天然代表允许你把文件公开分享给任何人。

    我建议 `viewer/editor` 之外，再预留一个类似 `allowPublicReshare` 的协同授权能力。它可以在协同授权时一次性确定，不要求每次分享都在原所有者网盘生成记录。

    #### 静态资源链接需要与普通分享区别对待

    你已经明确：

    只能给 Mount 本体设置静态资源开放，不能给里面每个文件独立设置。

    这个模型可以相当简洁：

    ```
    本地 Mount M1
        ↓
    一条静态资源开放记录
        ↓
    静态 URL 前缀
        ├── docs/a.pdf
        ├── docs/b.pdf
        └── images/c.png
    ```

    内部文件的访问链接由 Mount 级的开放令牌加相对路径构成，不为每个文件生成独立开放记录。

    但是仍有几个细节：

    文件改名或移动以后，原来按路径生成的 URL 可能失效。这与“不冻结原所有者操作”的要求一致；如果要保持旧 URL 有效，就得增加文件 ID 定位或历史重定向机制，复杂度会增加。

    Mount 被移除或协同授权被撤销以后，静态链接必须失效。

    长期缓存可能使已经下载到第三方浏览器或 CDN 的内容继续存在。服务端可以撤销后续访问，但不能保证收回已经缓存出去的数据。

    我建议第一版明确这些行为，不要暗中承诺永久链接稳定性。

    ### 5. S3API：这里有一个协议层面的冲突

    S7 当前 `server/object-storage.js` 主要仍面向原生 `files/directories`。挂载项尚未完整投影成 S3 的目录前缀。

    你现在想让：

    ```
    S3 Bucket
    └── 张三项目/
        ├── docs/
        └── a.pdf
    ```

    可以正常 LIST、GET、PUT、COPY，且根据权限支持其它操作。

    这个方向可行。

    但禁止删除 Mount 本体与允许删除 Mount 内部的普通文件之间存在一个 S3 协议问题。

    S3 里的目录通常只是对象 Key 的前缀，并非真正的文件系统目录。

    例如 FolderSync 等客户端删除整个：

    `张三项目/`

    可能实际上是先列出：

    `张三项目/a.pdf`、`张三项目/docs/b.pdf`

    再逐个发起 `DeleteObject`。

    这时服务器收到的是普通文件删除请求，无法可靠判断用户究竟是在主动删除某个文件，还是执行了递归删除整个挂载目录。

    因此，仅禁止 `DeleteObject("张三项目/")` 并不能保证不发生递归误删。

    要严格保证你要求的安全性，我建议：

    S3 初期允许对挂载内容进行 LIST、HEAD、GET，以及经过授权的新增和覆盖等操作；对挂载内部的 DELETE 先采用保守策略，等定义了明确的外部删除权限或额外保护机制后再开放。

    否则“允许任何客户端删除挂载内部文件，同时绝对禁止客户端递归删除挂载项目”这两种要求无法仅靠标准 S3 请求语义可靠兼得。

    Web 网盘则没有这个问题，因为它能够明确区分“删除文件”和“移除挂载”。

    ### 6. 防嵌套污染的规则仍然有效

    第 4 条虽然升级了浏览方式，但不应该重新放开之前已经确定的限制。

    Mount 在本地仍是一种特殊叶节点。打开后只是进入一个 Foreign Namespace，并不是将远端目录合并到本地目录树。

    所以继续坚持：

    - 不允许 Mount 内再创建 Mount；
    - 不允许对来自他人的协同内容重新发起协同；
    - 不允许创建会导致 Mount 与协同根目录祖先/后代重叠的结构；
    - 禁止同一个父目录下 Mount、普通文件、目录出现名称冲突；
    - 递归删除本地父目录绝不能进入 Mount 内部删除远端文件；
    - 所有权限和目录边界必须由服务端校验，不能依赖前端菜单隐藏。

    在这个前提下，原地浏览本身不会增加循环嵌套风险。危险主要来自把原生目录操作不加区分地套用到挂载节点上。

    ## 二、第 5 条：指定目录全量下载，包括可选的协同挂载内容

    这个功能很适合直接做成 ZIP 打包下载。

    用户对某个目录执行：

    下载目录

    包含已挂载协同项目内的文件

    预计 ZIP 结构示例

    我的目录/ ├── a.txt ├── 图片/ │   └── 1.jpg

    默认不包含协同内容；勾选后按用户当前授权将其加入压缩包。此处为结构示例。

    这里有三个问题需要定义。

    第一，下载 ZIP 时不能把整个目录全部读进服务器内存。

    应使用流式 ZIP，支持大文件和 ZIP64，同时利用目前已有的 Telegram Content Object 读取机制。

    第二，协同项目的授权必须实时校验。

    用户勾选“包含协同内容”，不代表能绕过 `viewer/editor` 权限和协同范围。

    如果某个 Mount 已失效，应在开始打包前明确提示跳过或拒绝，不应静默生成看起来完整、实际却缺失文件的 ZIP。

    第三，下载目录时应保留空目录、相对路径及原文件名。

    同时防止恶意路径中的 `../`、绝对路径或特殊文件名污染 ZIP 结构。

    由于同一个协同项目可以被挂载到不同位置，ZIP 应按它们各自的本地挂载路径呈现。用户主动选择包含挂载时，重复文件可以允许出现，这是符合用户所见目录结构的。

    另一个值得考虑的是：下载过程中如果原所有者修改、删除或替换文件，压缩结果应如何处理。我的建议是为任务建立尽可能一致的文件清单，使用已有 Content Object 读取租约保护已选定内容；无法继续读取时明确报告失败，不静默宣称完整成功。

    ## 三、第 6 条：文件夹递归拖放上传及全局设置

    ### 1. 最新代码现状

    目前 S7 有文件拖放上传：

    `client/disk-ui.js → confirmLocalDiskUpload() → DiskClient.upload()`

    但是当前路径主要把 `DataTransfer.files` 当普通文件列表处理，并没有完成从系统文件管理器递归读取目录、保留完整相对路径、创建多级目录的上传流程。

    还有两个硬约束：

    - `server/telegram-drive.js` 的 `assertDepth()` 仍将目录层级硬限制在 20 层；
    - `client/disk-client.js` 的一批文件上传仍有 100 个文件的数量限制。

    因此，将上限改成 30 层，不是只改网盘齿轮设置和前端拖放判断就能完成。

    服务端、目录创建、上传预检、跨分区复制、协同操作、S3 等相关入口都需要统一理解新的层级上限。

    ### 2. 300MB 与 500MB 的需求互相冲突

    你写的是：

    > 拖放文件夹上传前，总大小不能超过 300MB。

    又写：

    > 齿轮设置中，上传文件夹最大尺寸默认 500MB。

    如果 300MB 是固定硬上限，那么默认 500MB 的设置实际上不会生效。

    我建议直接统一成一个可配置的限制：

    `上传文件夹最大尺寸`，由个人网盘全局设置决定。

    例如默认值设置为 500MB，那么拖放包含 450MB 文件的文件夹就应允许上传；修改设置为 300MB 后，450MB 就不允许上传。

    如果你的本意是始终禁止单次拖放超过 300MB，那就应该将设置默认值也定为 300MB，而不是 500MB。

    另外，这里的大小必须如你强调的那样定义：

    \\[ \text{上传文件夹大小}=\sum \text{来源文件夹下所有层级的普通文件大小} \\]

    不包括目标网盘目录中原本已有的文件，也不是限制该网盘目录未来能够存放多少内容。

    ### 3. 目录层级的计算

    建议使用：

    \\[ \text{最终层级}=\text{目标目录层级}+\text{来源目录相对层级} \\]

    例如：

    ```
    网盘目标位置：
    A/B/C/                 // 已有 3 层

    本地拖放目录：
    Photo/
    └── Japan/
        └── 2026/
            └── images/    // 新增 4 层
    ```

    最终为 7 层，而不是只检查本地的 4 层。

    前端要在上传前检查，服务端也必须独立验证。

    ### 4. 递归上传的完整性

    ### 确认后的需求约定

    1\. 目录层级与文件夹上传限制

    2\. 跨协同作用域移动

    - Web 网盘允许将协同项目内的文件或目录移动到自己的指定分区、指定目录。
    - 底层可以采用“先复制，后删除来源”的实现方式。
    - 必须确认目标内容已完整、可靠地创建后，才能删除来源；如果复制成功但删除失败，要明确报告部分完成状态，避免重复复制或误删。

    3\. 协同内容对外分享

    - 本系统默认允许受邀用户分享其有权访问的协同文件和目录。
    - 不要求原所有者额外授权，也不在原所有者网盘生成分享记录。
    - 将来支持细粒度协同权限后，才根据相应配置限制特定文件或目录的分享能力。
    - 分享不冻结原所有者对文件的修改、移动和删除；授权失效后，不能继续通过分享读取原内容。

    4\. S3API / 网盘 API 的挂载访问权限

    - 对已挂载协同项目及其内部文件、目录，统一为只读。
    - 允许列表、读取、下载等只读操作。
    - 暂不允许新增、上传、覆盖、重命名、移动、删除等写操作。
    - 禁止通过 API 移除 Mount，更不能以递归删除方式影响协同内容。
    - 这一限制只针对 S3API 和网盘 API。 Web 网盘界面仍按照第 4 条原始需求支持有权限的编辑、移动、删除、分享及移除挂载等操作。

    | 网盘 API | 只读          | 只读                |
