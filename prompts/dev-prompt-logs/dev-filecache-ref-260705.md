
# 因导入/导出[传输记录数据备份文件]引发的file cache 引用策略选择问题



问：

    导入导出新BUG：在原隧道A，以元数据（不带文件二进制数据）导出传输记录备份文件后，本机设备新建一个隧道并导入之，可以看到几乎是瞬间完成（因为原隧道有很多大文件），猜测可能没有复制文件副本。这时，点击退出这个新建的隧道，再回到原来的隧道A，看到其传输记录内的所有文件的缓存都没了。期望：如果是本机创建一个新隧道导入从本机所在另一个隧道的传输记录数据，不论是以元数据还是完整带文件二进制数据导入，要么在新隧道创建缓存副本，要么就是在触发文件缓存删除操作前要检查文件有没有被本机设备内的其它隧道在引用。 我有这个需求，请你看看你理解的怎样，我准备提交给codex，怕它理解错
    
    
答：


    你的理解方向是对的，而且这个**应该算真 BUG**，不是“矛盾需求”。

    本质问题不是“导入导出慢不慢”，而是：

    ```text id="4j0m2s"
    同一个本机 IndexedDB 里，多个隧道引用了同一批 fileId / file cache record。
    退出/清理新隧道 B 时，按 fileId 清掉了全局文件缓存，结果把原隧道 A 正在引用的缓存也清掉了。
    ```

    也就是说，**新隧道导入的传输记录和原隧道 A 之间发生了缓存引用串线**。

    ## 我对这个需求的理解

    你真正想要的是：

    ```text id="xwrb5e"
    导入备份到新隧道后，新隧道的文件记录不能和原隧道共享同一个本机缓存实体，除非系统有明确的引用计数/多隧道引用保护。
    ```

    所以它有两种正确解法：

    ### 解法 A：导入时创建新副本，推荐优先

    导入到新隧道 B 时，所有导入的文件记录都应该生成新的 fileId / assetId。

    如果是**元数据备份**：

    ```text id="xc6wrs"
    只复制文件元信息；
    新隧道 B 的文件记录是无缓存状态；
    但它的 fileId 应该是新的；
    不能复用原隧道 A 的 fileId。
    ```

    如果是**完整备份**：

    ```text id="003r9y"
    复制文件元信息 + 二进制数据；
    新隧道 B 应该创建独立的缓存副本；
    也应该使用新的 fileId。
    ```

    这样 B 退出/删除/清缓存时，只会影响 B 自己的文件，不会误伤 A。

    ### 解法 B：允许共享缓存，但必须做引用保护

    如果导入时故意复用同一个 fileId 或同一个缓存对象，那退出/清理时必须先查：

    ```text id="g2y6qn"
    这个 fileId 是否还被本机其它隧道的消息、合辑、资源记录、任务记录引用？
    ```

    如果还有其它隧道引用，就不能删除二进制缓存，只能删除当前隧道 B 的消息记录/引用关系。

    但这个方案更复杂，容易漏查，所以我更建议第一版做 **导入新隧道时重映射 fileId**。

    ## 重点不要让 Codex 理解错

    不要只说：

    ```text id="nc41fy"
    退出新隧道时不要清理原隧道缓存
    ```

    这样 Codex 可能只在退出逻辑里打补丁，但导入时已经污染了数据结构。

    应该明确说：

    ```text id="66lxvw"
    问题源头是导入时复用了原 fileId / 缓存记录，导致两个隧道共享同一份 IndexedDB files 记录。
    ```

    然后要求它同时修：

    ```text id="moc9cr"
    导入阶段：跨隧道导入时重映射文件 ID，并同步更新消息/合辑/文件引用。
    删除阶段：清缓存/退出隧道时增加跨隧道引用保护，不能删除其它隧道仍在引用的缓存。
    ```

    我查的是 `dev/2607A-NEWCODE` 的普通发送链路。

    关键证据：

    1. `files` store 的主键是 `id`，不是 `sessionId + id`，但同时建了 `sessionId` 索引。也就是说，缓存实体本身按 `fileId` 全局索引。

    2. 普通从本机文件创建 `fileInfo` 时，`fileId` 默认走 `generateId()`，不是根据文件内容、文件名、大小、hash 去重。

    3. `generateId()` 是 UUID-like 随机 ID，所以同一个实体文件第二次发送，正常也会生成新 ID。

    4. 发送文件缓存写入时，会把当前 `state.sessionId` 写入 asset，然后 `saveToStore('files', asset)`。所以 A 里发送一次会生成 A 的 fileId/cache 记录，B 里再发送一次会生成 B 的另一个 fileId/cache 记录。

    5. 多文件合辑也是同样逻辑：每个文件都会调用 `createFileInfoFromFile()`，从而各自生成新的 `fileInfo.id`。

    所以你的判断依据可以这样写：

    ```text
    普通传输路径目前没有内容级去重，也没有跨隧道共享缓存。
    同一个本机文件 H 在隧道 A 和隧道 B 分别发送，会生成两个不同 fileId，并写入两个不同 files 记录。
    ```

    真正的历史坑主要来自**导入备份**。现在导入逻辑会用备份里的 `asset.id` 去查 `getFromStore('files', asset.id)`，然后如果备份没有二进制数据，就直接复用 `existing?.data`；接着又用同一个 `asset.id` 保存到当前新隧道。 这才会造成“新隧道 B 导入了原隧道 A 的记录后，B 和 A 共享同一个 fileId/cache record”的污染。

    ```text
    不主动引入：内容 hash 级跨隧道共享缓存
    ```

    这样最符合现有代码结构，改动风险最低。你现在不需要把系统升级成“全局文件池 + 引用计数 + 假性清缓存”的复杂模型。那套适合以后做资源管理器 2.0，现在为了修这个 bug 上那套，反而容易扩大风险。

    给 Codex 的一句话重点可以改成：

    ```text
    普通传输当前已天然生成独立 fileId/cache，问题只出在备份导入复用了原 asset.id；请修复跨隧道导入时的 fileId 重映射，并在删除/清缓存前加跨隧道引用保护作为兜底，不要引入新的内容级全局去重模型。
    ```
