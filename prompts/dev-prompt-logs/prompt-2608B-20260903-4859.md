1、考虑到有些用户不会翻墙，无法使用 Telegram User 身份登录网盘，因此网盘登录方式不能只支持 Telegram 登录，还需要增加“账号名 + 密码”的普通账号登录方式。

网盘内部的用户身份模型也要从原先依赖 `Telegram User` 的身份体系，泛化为独立的通用 `user` 身份体系。Telegram User 只作为一种登录/身份绑定方式，不再作为网盘用户的唯一身份来源。

也就是说，网盘内部应该存在独立稳定的 `user_id`。一个 `user_id` 后续可以对应：

* 普通账号名 + 密码；
* Telegram User 身份；
* 以后新增的其它登录方式。

Telegram 的 `tg_user_id` 不应继续直接承担网盘内部主用户 ID 的职责，而应该作为 Telegram 身份与通用 `user_id` 之间的绑定信息。

如果同一个用户已经通过 Telegram 登录创建过网盘账号，后续应该支持为该 user 补充账号名+密码登录方式，而不是重新创建另一套完全独立的网盘数据。

密码必须使用安全哈希方式保存，不能明文保存。

2、网盘中的上传、修改、移动、删除、打开、预览文件等操作，如果过程中涉及 Telegram、文件下载、上传、转存、远程接口调用、外部存储系统或其它明显耗时操作，则不能只让前台长时间等待，而应该提供具体的执行状态和进度。

建议网盘内部统一设计一套“操作任务 / Operation Job”机制，而不是每个功能分别实现一套 loading 状态。

每个耗时任务至少应具有：

* operation_id；
* 操作类型；
* 当前状态，如 queued / running / completed / failed / cancelled；
* 当前执行阶段；
* 当前进度百分比；
* 已处理字节数；
* 总字节数；
* 当前状态说明；
* 失败错误码和错误信息；
* 创建时间、开始时间、完成时间。

如果底层外部系统能够提供准确进度，则显示真实百分比。

如果某个外部接口无法得到准确百分比，则不要伪造百分比，应显示具体阶段，例如：

* 正在请求 Telegram；
* 正在下载源文件；
* 正在上传文件；
* 正在更新虚拟目录；
* 正在写入索引；
* 正在等待外部系统响应。

用户切换页面、重新打开网盘界面后，仍然应该能够查看尚未结束的任务状态。

3、网盘文件和目录需要支持拖放移动到其它目录。

同时，文件和目录需要支持上下文菜单：

* PC：鼠标右键打开；
* 触屏设备：单指长按打开。

* 预览；
* 重命名；
* 移动；
* 删除；
* 转发到隧道；
* 新建子目录等。

目前目录/文件使用双击执行主要操作，需要改成单击。

单击目录：

* 直接进入该目录。

单击可预览类型文件：

* 直接进入全屏预览。

单击不可直接预览的文件：

* 根据文件类型执行适合的默认行为，例如打开、下载或显示文件信息。

底部显示：

`当前序号/总数`

例如：

`3/17`

这里的总数应以“当前目录、当前排序条件下可进入该预览浏览序列的文件”为准，不应把不能参与预览切换的目录或无关节点混入序号。

拖放移动目录时，需要禁止把目录移动到自己或自己的子目录中。

移动目标存在同名文件/目录时，不要静默覆盖，需要明确提示冲突并由用户决定如何处理。

这里的“手动输入全路径新建目录”的目的是：
在移动流程中无需先退出移动浮层，就可以直接创建移动目标目录，并立即选择新创建的目录作为移动目标。

需要支持两种方式：

第一种：
在某个目录上鼠标右键或触屏长按，选择“新建子目录”。

第二种：
在目录输入框中直接输入多级目录，例如：

`音乐/日本/2026/专辑名`

系统自动逐层检查并创建不存在的目录。

多级目录创建需要正确处理：

* `/`；
* `\`；
* 连续分隔符；
* 空目录名；
* `.`；
* `..`；
* 中间某一级已经存在同名文件；
* 非法目录名称。

不能允许通过类似 `../` 的路径语义绕过当前虚拟网盘目录范围。

移动浮层中的“新建目录”与网盘正常界面的“新建目录”，底层应调用同一套目录创建逻辑。

6、网盘重命名文件或目录时，需要支持按 Enter 回车键直接保存新名称。

建议统一交互为：

* Enter：保存；
* Esc：取消；
* 点击其它区域时不要因为失焦而自动误保存。

7、网盘中的文件和目录需要支持“转发到隧道”。

根据用户选择的文件数量和类型决定发送形式：

单文件：

* 按隧道现有单文件发送逻辑发送。

多文件：

* 可以选择作为合辑发送；
* 如果作为合辑发送，需要完整进入现有隧道合辑发送流程，包括备注等现有合辑能力。

如果用户选择目录进行“转发到隧道”，建议递归展开该目录中的文件，并允许作为一个合辑发送，同时保留文件相对于所选目录的相对路径信息。

特别注意：

网盘核心代码不能直接依赖隧道内部业务逻辑。

以后这个网盘可能会独立成为一个子系统或公共网盘系统，也可能提供给 MusicoletWeb 或其它第三方系统使用。

因此应该明确分层：

网盘核心层只负责：

* 用户；
* 虚拟目录；
* 文件；
* 文件读取；
* 文件流；
* 文件元信息；
* 外部存储对象；
* 网盘 Operation Job；
* 网盘 API。

网盘核心层不应该直接理解：

* tunnel session；
* 隧道 message；
* 隧道 collection；
* 隧道备注输入界面；
* 隧道发送状态。

应该单独设计一个类似 `Tunnel Adapter` 的适配层。

网盘只把一个或多个文件以通用文件对象/文件流形式交给 Tunnel Adapter。

Tunnel Adapter 再负责：

* 选择目标隧道；
* 判断单文件还是合辑；
* 生成隧道传输记录；
* 填写合辑备注；
* 调用现有隧道文件发送逻辑。

这样以后网盘独立出来时，不需要拆除大量和隧道耦合的代码。

8、考虑以后第三方系统，例如正在开发中的 MusicoletWeb，需要调用本系统提供的 Telegram 虚拟网盘 API 保存歌曲文件。

例如 MusicoletWeb 保存手机歌曲时，希望按照歌曲在原手机中的文件路径，在 Telegram 虚拟网盘中自动建立对应的虚拟目录结构。

因此，需要设计一整套操作 Telegram 虚拟网盘的 API，包括：

* 第三方系统鉴权；
* 网盘用户登录/注册；
* 用户身份查询；
* 虚拟目录管理；
* 文件上传；
* 文件查询；
* 文件读取/下载；
* 文件移动；
* 文件重命名；
* 文件删除；
* 多级目录创建；
* Operation Job 查询等。

本系统负责管理虚拟网盘的目录和文件信息，并将虚拟网盘信息保存到 SQLite 或可靠的索引数据文件中。

Telegram 主要承担底层文件对象托管。

虚拟网盘中的文件节点，需要与 Telegram 中实际用于保存文件的 message 建立可靠关联。

也就是说：

虚拟目录树属于本系统的数据模型；

Telegram message/file_id 等属于底层存储对象信息；

不要直接把 Telegram message 本身当成虚拟目录树。

网盘数据层级定义为：

`user_id -> 虚拟挂载分区 disk_space -> 虚拟目录/文件`

其中：

`user_id`
代表通用网盘用户身份。

`disk_space`
代表该用户下面的虚拟挂载分区。

`disk_space` 默认值为空字符串：

`""`

虚拟挂载分区对普通用户不可见，也不在普通网盘 UI 中提供分区切换功能。

disk_space 主要给第三方系统调用 API 时使用。

其目的不是给不同第三方系统做权限隔离，而是让同一个 user 可以拥有多个彼此独立的逻辑网盘分区。

例如：

`user_id=10001`
`disk_space=""`

表示该用户默认网盘。

而：

`user_id=10001`
`disk_space="musicolet"`

可以作为 MusicoletWeb 使用的独立虚拟网盘空间。

其它第三方系统也可以使用其它 disk_space。

如果两个经过合法鉴权的第三方系统故意使用：

相同 `user_id`
+
相同 `disk_space`

那么它们访问的就是同一个逻辑网盘分区。

这是允许的设计，不需要根据 app_id 再强行给资源划分额外分区。

因此真正的网盘资源定位键应该是：

`user_id + disk_space + path/node_id`

而不是：

`app_id + user_id + disk_space`。

第三方 API 的 `access_token` 只承担“第三方系统身份鉴权”的职责，不承担网盘资源分区标识职责。

也就是说：

`app_id + app_secret`
用于证明第三方系统身份，并换取：

`access_token`

之后：

`access_token`
只用于证明当前 API 请求来自一个已经授权的第三方系统。

真正访问哪个网盘资源，由：

`user_id + disk_space`

决定。

第三方系统调用鉴权接口时，需要传递：

* app_id；
* app_secret；
* tg_bot_token；
* tg_channel。

其中：

`app_id`
标记第三方应用。

`app_secret`
作为第三方应用密钥。

`tg_bot_token`
指定该第三方系统希望使用哪个 Telegram Bot 管理网盘底层文件。

`tg_channel`
指定该 Bot 使用哪个 Telegram Channel 托管文件。

鉴权成功后，服务端返回：

`access_token`

之后第三方系统使用：

`access_token + user_id + disk_space`

调用具体网盘业务 API。

access_token 需要定期失效/轮换。

当接口提供方发现 access_token：

* 已过期；
* 已失效；
* 已被撤销；

需要返回稳定、可供程序识别的错误。

建议：

HTTP 状态码：

`401`

并在 JSON 中提供明确错误码，例如：

`ACCESS_TOKEN_EXPIRED`

或者：

`ACCESS_TOKEN_INVALID`

第三方调用方识别到这些错误码后，自动重新使用：

`app_id + app_secret + tg_bot_token + tg_channel`

调用鉴权接口，重新换取新的 access_token，然后重试原网盘业务操作。

access_token 不建议直接保存敏感 Telegram 凭据。

服务端应该维护第三方应用、access token 与 Telegram 存储后端之间的内部关联。

tg_bot_token 属于敏感信息：

* 不得写入普通日志；
* 不得直接返回给前端；
* 不得包含在 access_token 可解码内容中；
* 如果服务端需要长期保存，应采用安全方式保存。

tg_channel 最好在首次绑定时验证 Bot 是否具有对应频道的操作权限，并在内部记录稳定的 Telegram chat_id，不能长期只依赖可能发生变化的频道 username。

在后台 `/tgbot` 页面中，需要单独增加一个“第三方系统接入 Telegram 网盘”的配置区域。

该区域支持无限追加第三方应用配置。

每个应用至少配置：

* app_id：必填；
* app_secret：必填；
* 备注。

建议同时保存：

* 是否启用；
* 创建时间；
* 最近使用时间；
* 最近签发 access_token 时间。

后台还应该支持：

* 新增应用；
* 禁用应用；
* 删除应用；
* 重置 app_secret。

app_secret 不应该长期以明文重新展示。

建议只在创建或重置时展示一次，服务端之后只保存安全哈希。

整体数据模型建议至少在逻辑上区分：

* users：通用网盘用户；
* auth_identities：账号密码、Telegram 等登录身份；
* drive_apps：第三方应用；
* app_access_tokens：第三方 access token；
* storage_backends：Telegram Bot + Channel 等底层存储后端；
* drive_spaces：user_id 下的 disk_space；
* drive_nodes：虚拟目录和虚拟文件节点；
* telegram_file_objects：虚拟文件与 Telegram message/file 的存储映射；
* drive_operations：上传、移动、远程处理等长任务状态。

具体第一版是否全部拆成 SQLite 独立表，可以根据现有项目规模决定，但代码边界和数据语义应该从一开始就按照这些概念区分，避免把 Telegram、用户体系、虚拟目录、第三方 API 和隧道逻辑重新耦合在一起。
