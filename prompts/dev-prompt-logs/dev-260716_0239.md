# 1、支持粘贴截图到隧道发送

隧道页面需要支持用户直接粘贴剪贴板中的截图或图片，并作为文件发送到当前隧道。

## 1.1 触发方式

当用户在隧道页面执行以下操作时：

```text
Ctrl + V
Command + V
移动端或浏览器支持的粘贴操作
```

如果剪贴板内容中包含图片 Blob，应将图片作为普通图片文件发送到当前隧道。

## 1.2 发送行为

粘贴得到的图片应进入现有文件发送流程，包括：

* 文件缓存；
* 文件大小计算；
* MIME 类型识别；
* 图片预览；
* 传输记录；
* 传输进度；
* P2P 或服务器传输；
* provider 供源登记；
* 失败重试；
* 多设备同步。

不要只在页面中临时显示图片，也不要建立仅粘贴图片可用的特殊消息类型。

建议为没有原始文件名的剪贴板图片生成文件名，例如：

```text
截图_20260716_013025.jpg
```

文件扩展名应根据实际 MIME 类型生成，不要始终写死为 `.jpg`。

## 1.3 与富文本编辑器的冲突处理

必须区分两种行为：

```text
在普通隧道页面粘贴图片
→ 将图片作为文件发送到隧道。

在富文本编辑器内部粘贴图片
→ 继续按照富文本编辑器现有逻辑插入图片。
```

如果事件发生在富文本编辑器、可编辑元素或有自身粘贴处理逻辑的区域内，不得重复触发普通文件发送。

同一次粘贴不能同时：

* 插入富文本图片；
* 再额外发送一条图片文件记录。

## 1.4 其他边界

* 剪贴板没有图片时，不影响普通文本粘贴。
* 剪贴板同时有文本和图片时，优先尊重当前输入区域原有行为。
* 不要拦截密码框、输入框、文本域等正常文本粘贴。
* 粘贴多个图片 Blob 时，应支持全部发送，并复用多文件合辑发送流程。
* 不得因为某张图片处理失败而阻止其他有效图片发送。

# 2、禁止移动端缩放整个页面

移动端应禁止用户通过双指捏合、双击放大等方式缩放整个页面，避免缩放后出现：

* 页面布局偏移；
* 三栏切换错位；
* 顶栏或浮层位置异常；
* 抽屉尺寸异常；
* 页面无法恢复原始比例；
* 横向出现多余空白区域。

## 2.1 应禁止的行为

包括但不限于：

* 双指捏合缩放；
* 双击页面放大；
* Safari 的 gesture 缩放；
* 浏览器对整个页面的视觉缩放。

## 2.2 不得破坏的行为

禁止页面缩放时，不得破坏：

* 页面纵向滚动；
* 三栏横向滑动；
* 文件列表滚动；
* 播放器进度拖动；
* 富文本编辑器选择文字；
* 输入框光标操作；
* 图片或视频预览中的正常操作；
* 按钮点击；
* 长按；
* 拖放文件；
* 其他现有触摸手势。

不要简单地在全局设置：

```css
touch-action: none;
```

因为这可能会破坏页面滚动和现有手势。

请综合处理：

* viewport 配置；
* `gesturestart`、`gesturechange`、`gestureend`；
* 必要的 `touchmove` 多指判断；
* 双击缩放；
* iOS Safari 和 Android Chrome 的差异。

# 3、拖放文件支持多文件发送

当前隧道拖放文件只发送单个文件，需要改为支持一次拖入多个文件。

## 3.1 预期行为

用户一次拖入多个文件时：

* 读取所有有效文件；
* 忽略被选中的文件夹，并在弹出的"发送 n 个文件 <br> 以合辑发送会在传输记录里合并成一条，方便预览…… <br>合辑备注（可选） <br> <textarea></textarea> <br> <button>拆分成多条</button> <button>以合辑发送</button>"浮层补充说明文件夹被忽略）；
* 不得只读取 `files[0]`；
* 使用现有多文件选择或合辑发送流程；
* 多个文件应作为同一次用户发送动作处理；
* 保留每个文件独立的缓存、传输进度和失败状态；
* 保留合辑内文件预览和详情功能。

如果现有文件选择器一次选择多个文件时会生成合辑，拖放多文件也必须使用相同的合辑逻辑，不要建立另一套表现不同的拖放消息。

## 3.2 失败隔离

多个文件中某一个出现以下问题时：

* 文件读取失败；
* 文件为空；
* 类型异常；
* 文件过大；
* 缓存失败；

不得导致其他有效文件全部停止发送。

应跳过或标记失败文件，并继续处理其他文件。

## 3.3 拖放交互

* 拖入有效文件时显示现有拖放提示或高亮状态。
* 离开拖放区域后及时清除高亮状态。
* 防止浏览器默认打开被拖入的文件。
* 不得重复触发两次发送。
* 拖放处理结束后清理临时状态。

# 4、禁止拖放文件夹到隧道

隧道暂时不支持通过拖放发送文件夹。

用户拖入文件夹时，应明确拒绝，不要：

* 递归读取文件夹；
* 把文件夹当成普通文件发送；
* 生成大小为 0 的异常记录；
* 生成无文件名记录；
* 触发目录句柄绑定；
* 产生莫名其妙的文件缓存状态；
* 进入发送队列；
* 建立空合辑。

## 4.1 文件夹识别

请综合使用浏览器可用能力识别文件夹，例如：

```js
DataTransferItem.webkitGetAsEntry()
FileSystemHandle
getAsFileSystemHandle()
```

不要仅通过：

```js
file.type === ''
```

判断是否为文件夹，因为部分正常文件也可能没有 MIME 类型。

## 4.2 文件夹和文件混合拖入

如果用户同时拖入：

* 若干普通文件；
* 一个或多个文件夹；

应：

1. 拒绝所有文件夹；
2. 对用户显示一次明确提示；
3. 继续发送其中合法的普通文件。

不要因为其中存在文件夹，就把全部普通文件也一起拒绝。

提示文案可类似：

```text
暂不支持拖放文件夹，请拖入一个或多个文件。
```

该提示需要接入现有多语言系统。

# 5、传输进度条抽屉调整

传输进度抽屉需要支持三种明确状态：

```text
展开
收缩
完全隐藏
```

必须保留现有传输任务、进度显示和记录定位能力。

---

## 5.1 支持抽屉完全隐藏

用户可以将传输进度抽屉完全隐藏。

完全隐藏后：

* 抽屉本体不可见；
* 不占用页面空间；
* 不保留露出的边缘；
* 不自动因为普通进度刷新而再次弹出。

当当前处于“进行中”状态的任务数大于 0 时，在功能首页顶栏的齿轮设置按钮右侧，相邻插入一个数字按钮。

数字按钮要求：

* 显示当前进行中的任务数；
* 位置紧邻齿轮按钮右侧；
* 数字变化时及时更新；
* 使用轻微持续跳动、脉冲或呼吸动画提示用户；
* 不得造成顶栏明显抖动或改变其他按钮位置；
* 任务数为 0 时立即隐藏；
* 点击数字按钮后，重新显示传输进度抽屉；
* 建议点击后直接恢复为展开状态。

这里的“进行中任务”必须依据项目现有任务状态模型准确判断。

原则上只统计真正正在传输、下载、上传、同步或处理中的任务。

以下状态不应默认计入“进行中”，除非现有产品定义本来就把它们算作进行中：

* 已完成；
* 已失败；
* 已取消；
* 已暂停；
* 建链中；
* 已停滞
* 等待；

请先检查现有任务状态定义后统一处理，不要在多个地方分别写不同的统计规则。

---

## 5.2 抽屉收缩状态增加隐藏按钮

当传输进度抽屉处于收缩状态时：

* 保留原有收缩展示；
* 在收缩抽屉的右侧边缘放置“眼睛带斜线”图标；
* 点击该图标后，抽屉进入完全隐藏状态；
* 点击收缩抽屉的其他区域，仍按原有逻辑展开抽屉。

隐藏按钮必须：

* 有明确的 `title`、`aria-label`；
* 支持触摸点击；
* 阻止事件冒泡；
* 不得在隐藏时同时触发抽屉展开；
* 不得误触任务定位；
* 图标大小和点击区域适合移动端。

---

## 5.3 抽屉展开状态增加隐藏按钮

当传输进度抽屉处于展开状态时：

* 保留原有点击抽屉标题区域或指定区域后收缩的逻辑；
* 保留点击某条进度任务后，跳转到该任务对应传输记录锚点的逻辑；
* 在抽屉右上角增加“眼睛带斜线”图标；
* 点击该图标后，抽屉进入完全隐藏状态。

点击隐藏按钮时：

* 不得触发抽屉收缩；
* 不得触发记录定位；
* 不得触发任务点击；
* 必须阻止事件冒泡。

---

## 5.4 抽屉状态管理

抽屉状态应统一管理，不要用多个互相矛盾的布尔变量。

建议使用明确状态，例如：

```js
expanded
collapsed
hidden
```

状态转换至少包括：

```text
expanded → collapsed
expanded → hidden
collapsed → expanded
collapsed → hidden
hidden → expanded
```

用户手动隐藏后：

* 普通进度更新不得自动把抽屉重新显示；
* 页面刷新后是否保留隐藏状态，可遵循项目现有本地 UI 状态保存策略；
* 如果保存，使用独立、明确的 localStorage key；
* 进行中任务数大于 0 时，仅显示顶栏数字按钮提醒；
* 任务数归零后隐藏数字按钮，但不要强制修改用户选择的抽屉状态。

# 7、修复 SNS / Telegram Bot 记录的阻塞加载与供源同步问题

当前发现：对于通过 SNS 链接解析生成的传输记录，例如 YouTube 解析结果，或通过 Telegram Bot 转发生成的传输记录，即使隧道内已经有一台浏览器设备成功从 Node.js 服务器下载并缓存了对应文件，其他设备之后进入隧道时，仍然会从最早的一条 SNS / Telegram Bot 记录开始逐条加载。

当前表现似乎类似：

```text
加载记录 A 的元数据
↓
下载或恢复记录 A 的全部文件内容
↓
记录 A 文件内容完成
↓
再加载记录 B 的元数据
↓
下载或恢复记录 B 的全部文件内容
↓
继续下一条
```

如果其中某一条 SNS / Telegram Bot 记录的文件内容：

* 一直无法取得；
* Node.js 服务端缓存缺失；
* 请求长时间 pending；
* 下载任务没有超时；
* provider 暂时离线；
* 文件状态异常；
* Promise 永不 resolve；

后续 SNS / Telegram Bot 记录就会被整体阻塞。

阻塞后的记录甚至连元数据都不能进入传输记录区域显示。

普通浏览器直接发送的传输记录目前没有受到同样阻塞，说明 SNS / Telegram Bot 记录很可能使用了另一套串行历史加载、文件 hydration 或服务器队列逻辑。

必须检查真实原因并从架构上修复，不能只增加超时时间掩盖问题。

---

## 7.1 元数据同步和文件内容恢复完全解耦

新设备加入隧道时，应优先快速同步并展示全部传输记录元数据。

不得因为某一条记录的文件内容尚未取得，而阻塞：

* 后续记录元数据同步；
* 后续记录卡片渲染；
* 历史记录分页或游标推进；
* 传输记录区域显示；
* 后续文件恢复任务进入队列；
* 普通浏览器记录加载；
* SNS / Telegram Bot 后续记录加载。

即使文件内容暂时不可用，记录也必须先显示。

记录可以显示以下状态之一：

* 正在获取文件内容；
* 正在从服务器缓存恢复；
* 正在从其他设备同步；
* 等待供源设备上线；
* 文件暂时不可用；
* 获取失败，可重试；
* 缓存缺失；
* 已有其他设备可供源。

消息列表顺序必须按照原始消息时间或现有排序规则显示，不得按照文件下载完成时间排序。

---

## 7.2 文件内容恢复使用独立任务队列

SNS / Telegram Bot 文件内容应在元数据同步后，通过独立异步任务队列恢复。

不得使用类似以下整体串行逻辑：

```js
for (const record of records) {
  await loadMetadataAndDownloadAllFiles(record);
}
```

也不得在消息插入列表前等待文件下载完成。

可以设置合理并发数，例如同时恢复 2～4 个文件或记录，但必须保证：

* 单个任务失败不会阻塞其他任务；
* 单个任务长期等待不会占住整个队列；
* 一个任务等待来源设备时，其他任务仍能继续；
* 每个任务有独立状态；
* 每个任务有超时或可取消机制；
* 每个任务在 `finally` 中释放并发槽位；
* 队列可以继续调度后续任务。

如果一条记录是合辑，合辑内部某个文件失败，也不应阻塞：

* 同合辑其他文件；
* 后续记录；
* 后续合辑。

---

## 7.3 任意成功下载文件的设备立即成为供源端

当任意浏览器设备成功取得来自 SNS / Telegram Bot 的完整文件内容后，无论文件最初来自：

* Node.js 服务端缓存；
* SNS 下载任务；
* YouTube 解析任务；
* Telegram Bot 上传；
* 其他浏览器设备；
* 本地缓存恢复；
* WebRTC；
* Socket.IO；
* 其他既有传输链路；

该设备都必须立即成为该文件的有效 provider 供源端。

不应要求用户：

* 刷新页面；
* 重新进入隧道；
* 重新发送记录；
* 手动点击重新登记；
* 重启浏览器；

之后才成为供源端。

文件完整保存成功后，应立即执行：

1. 更新本地缓存完整状态；
2. 更新本地 asset 或文件状态；
3. 向服务端上报该设备已经持有完整文件；
4. 更新该资源的 provider 设备清单；
5. 通知隧道内相关设备 provider 状态变化；
6. 允许其他设备立即向该设备拉取文件；
7. 保证重复上报幂等；
8. 防止同一设备重复登记为多个相同 provider。

只有在完整文件已经校验成功后，才能登记为完整 provider。

部分下载、损坏缓存或未完成文件不得被登记为完整供源端。

---

## 7.4 provider 状态需要实时失效

当设备出现以下情况时，应及时更新 provider 状态：

* 清除了该文件缓存；
* 文件缓存损坏；
* 文件句柄失效；
* 文件已被删除；
* 设备离开隧道；
* 设备断线；
* 浏览器关闭；
* 设备不再具备完整文件；
* 本地缓存完整性检查失败。

不要让服务端长期保留已经失效的 provider。

可以保留历史 provider 记录，但必须明确区分：

```text
在线且可供源
离线但历史上持有
缓存已失效
未知状态
```

其他设备选择来源时，只能优先使用当前真实可用的 provider。

---

## 7.5 文件获取来源支持动态选择和自动回退

其他设备恢复文件时，不应始终强制从 Node.js 服务端排队获取。

应根据当前可用来源选择合适的供源端，例如：

1. 当前在线并已持有完整文件的浏览器设备；
2. Node.js 服务端已有完整缓存；
3. 原始发送设备；
4. 其他在线 provider；
5. 必要时重新触发 SNS 或 Telegram Bot 来源获取。

具体优先级可以根据现有项目传输策略调整，但必须满足：

* 不绑定单一来源；
* 一个来源失败后自动尝试其他来源；
* provider 设备成功供源后可直接完成；
* Node.js 缓存缺失时，不得阻止从浏览器 provider 获取；
* 浏览器 provider 离线时，可回退到 Node.js 或其他 provider；
* 不得因第一个来源请求长期 pending 而永远不尝试其他来源。

需要为来源尝试设置明确状态和超时。

---

## 7.6 消息来源类型和供源能力解耦

SNS / Telegram Bot 只表示传输记录最初从哪里产生。

它不应永久决定该文件只能由 Node.js 或 Bot 来源提供。

一旦任意设备完整持有该文件，该设备就应和普通浏览器直接发送文件一样，成为正常 provider。

后续文件同步应依据：

* 哪些设备在线；
* 哪些设备持有完整文件；
* 哪些缓存真实有效；
* 哪条链路可以使用；
* 哪个来源响应更快；
* 哪个来源已经失败；

而不是依据：

```text
SNS 文件必须从服务器获取
Telegram Bot 文件必须从 Bot 获取
```

必须尽量统一普通浏览器文件、SNS 文件和 Telegram Bot 文件的 asset/provider 处理逻辑。

---

## 7.7 幂等、去重和并发控制

同一文件恢复和 provider 登记必须保证幂等。

包括：

* 同一设备不能重复启动多个相同下载任务；
* 同一文件不能被重复写入缓存；
* 同一 provider 不能重复登记；
* 同一 provider 上报可以安全重试；
* 服务端重复收到 provider 上报时不产生重复项；
* 页面刷新后不重复生成消息记录；
* 页面刷新后不无条件重新下载完整文件；
* 多个来源同时成功时只确认一次最终文件；
* 下载任务完成后及时取消或忽略其他重复来源；
* 文件恢复完成顺序不得改变消息排序；
* 同一合辑中的文件要按 assetId 或稳定资源 ID 去重；
* 不能只用文件名去重。

---

## 7.8 重点排查位置

请重点检查客户端和服务端以下位置：

* SNS / Telegram Bot 历史记录是否使用单独串行循环；
* 是否逐条 `await` 文件下载后才插入消息列表；
* 服务端历史接口是否等待文件准备完成后才返回记录；
* Socket.IO 历史回放是否逐条等待文件读取；
* 历史记录游标是否在文件下载完成后才推进；
* 是否存在永不 resolve 的 Promise；
* 文件下载是否缺少超时、取消或失败状态；
* 队列槽位是否没有在 `finally` 中释放；
* provider 上报是否只在浏览器直接发送文件时执行；
* 从 Node.js 下载完成后是否遗漏 provider 注册；
* SNS / Telegram Bot 文件是否使用不同的 assetId、sourceType 或 messageType，导致普通 provider 逻辑没有命中；
* provider 是否只在页面初始化时扫描一次；
* 文件下载完成后是否没有实时触发 provider 更新；
* 浏览器设备已有完整缓存时，是否仍错误地被判断为没有文件；
* Node.js 是否对 SNS / Telegram Bot 请求使用全局单并发队列；
* 单个任务卡住时是否阻塞整个服务端队列；
* 文件内容恢复与历史消息同步是否错误共用同一个 Promise 链。

---

## 7.9 验收场景

至少完成以下测试：

### 场景 A：元数据不被文件内容阻塞

1. 准备 10 条 SNS / Telegram Bot 文件记录。
2. 故意让最早的第 1 条文件内容永久不可用。
3. 新设备加入隧道。
4. 10 条记录的元数据都应快速显示。
5. 第 1 条显示等待、不可用或失败状态。
6. 第 2～10 条仍可继续恢复文件内容。
7. 普通浏览器发送的记录正常显示。
8. 不得因为第 1 条失败而阻塞历史游标。

### 场景 B：下载成功后立即成为 provider

1. 设备 A 从 Node.js 成功下载某个 SNS / Telegram Bot 文件。
2. 不刷新设备 A 页面。
3. 设备 B 随后进入隧道。
4. 设备 B 应能发现设备 A 已成为该文件 provider。
5. 设备 B 可以从设备 A 拉取文件内容。
6. 设备 B 不应必须再次等待 Node.js 重新下载。

### 场景 C：Node.js 来源失败时自动回退

1. Node.js 上对应文件缓存不可用。
2. 设备 A 在线并持有完整文件。
3. 设备 B 请求该文件。
4. 设备 B 应自动从设备 A 获取。
5. Node.js 来源失败不得让任务永久 pending。

### 场景 D：provider 失效

1. 设备 A 已经登记为 provider。
2. 设备 A 清除该文件缓存。
3. 服务端和其他设备应及时更新 provider 状态。
4. 设备 B 不应继续选择设备 A 作为有效完整供源端。

### 场景 E：幂等和重复加载

1. 刷新页面多次。
2. 不得重复创建消息记录。
3. 不得重复写入相同文件缓存。
4. 不得重复登记相同 provider。
5. 不得重复启动相同完整下载任务。

---

# 统一实现要求

1. 尽量复用现有文件发送、多文件合辑、缓存、provider、任务队列和进度条逻辑。
2. 不要为截图、拖放、SNS 和 Telegram Bot 分别建立互不兼容的文件模型，对于之前SNS 和 Telegram Bot渠道发送的逻辑请继续保持不变。
3. 不得破坏浏览器直接发送文件的现有行为。
4. 不得破坏 PWA、Telegram Bot、SNS 解析、富文本、协同编辑、播放器等现有功能。
5. 新增提示文案必须接入现有多语言系统。
6. 不得依靠仅修改 UI 隐藏问题，服务端权限、任务状态和 provider 状态也必须真实正确。
7. 所有事件监听应避免重复绑定。
8. 所有异步队列应避免永不释放。
9. 所有新增按钮应支持移动端点击，并提供无障碍标签。
10. 修改完成后输出：

* 根因分析；
* 修改文件清单；
* 关键实现说明；
* 实际执行的测试；
* 未能执行的测试；
* 仍存在的风险。

最终目标：

* 用户可以直接粘贴截图发送；
* 移动端页面不会因捏合缩放而错位；
* 拖放可以发送多个普通文件；
* 文件夹拖放会被明确拒绝；
* 传输进度抽屉支持展开、收缩和完全隐藏；
* 隐藏后有进行中任务时，顶栏出现跳动的任务数按钮；
* Admin 页显示隧道短码；
* SNS / Telegram Bot 记录的元数据加载不再被单个文件阻塞；
* 任意设备成功取得完整 SNS / Telegram Bot 文件后，会立即成为该文件的供源端；
* 其他设备可以从可用浏览器 provider 同步文件，而不是始终依赖 Node.js 串行获取。
