1. **网盘指定目录整体下载**

   当前网盘已有目录树、文件读取和协同挂载权限检查，可以作为基础；现有前台下载主要还是读取单个文件再保存，尚未形成完整的目录下载任务。[当前网盘接口](D:/Workspace/github/Ltre/file-tunnel/server/disk-api.js:1822)

   建议流程是：**选择目录 → 勾选是否包含挂载内容 → 查看文件数、大小及不可读取项 → 选择本机保存目录 → 按目录结构下载**。后台生成下载清单，前台按有限并发逐个流式写入，不把整个目录装进内存。失败文件单独记录，可以重试；已经成功的文件保留。

   需要补充这些规则：

   - “整体下载”默认包含所选目录本身，保留其下所有层级和空目录。
   - 包含挂载时，目录型挂载沿用本地挂载名称；文件型挂载保存为一个文件。不要暴露来源用户的完整目录路径。
   - 下载清单生成后，文件可能被覆盖、移动或撤权。应记录文件版本，读取时重新检查；变化或失效项明确报错。
   - 同一内容出现在不同路径时，仍保留这些路径，不能因为底层内容相同就只下载一份。
   - Windows 文件名限制、大小写冲突和已有同名文件，需要提前给出处理方式；建议默认不覆盖。
   - 如果以后允许递归进入挂载中的挂载，还要处理循环。首版可以只读取挂载授权范围中的原生内容。

   **浏览器兼容性是主要限制。**直接创建本机目录树需要用户授权，目录选择接口要求安全环境和用户操作，而且并非所有主流浏览器都支持。[MDN 目录选择说明](https://developer.mozilla.org/en-US/docs/Web/API/Window/showDirectoryPicker)

   建议桌面支持的浏览器提供原结构保存；其他浏览器提供 ZIP 或逐文件下载选项。若这里也要求绝不使用 ZIP，就需要接受部分浏览器无法完整保存目录树，或增加本机客户端。

2. **隧道树形文件夹传输记录**

   当前“发送文件夹”会先生成 ZIP，再作为普通文件发送，所以这项需要新的记录模型，不能只换一个文件夹图标。[现有文件夹发送逻辑](D:/Workspace/github/Ltre/file-tunnel/app.js:18657)

   建议一条文件夹记录包含：**目录结构清单、各文件对应的传输资产、空目录信息、版本和完成状态**。文件正文继续使用现有缓存、P2P、服务端中继和供源机制。界面只显示一条文件夹记录，展开后按树查看成员；成员不额外刷成一堆独立传输记录。

   下载整个目录或部分文件时，复用第 1 项的本机目录写入能力。所选项目仍保留它们在记录中的相对路径，避免两个不同目录的同名文件落到一起。

   容易遗漏的是：

   - **目录结构存在，不代表每个文件都有在线来源。**应分别显示可下载、等待供源、失败和已缓存状态，允许完成部分下载。
   - 拖入时先完整枚举结构，但不要一次读取全部正文；需要限制文件数、层级和清单大小。
   - 如果源文件在枚举后被修改，发送时应检查并提示，避免清单与正文不一致。
   - 空目录、无法读取的文件、符号链接和浏览器无法完整枚举的目录，都要有明确结果。
   - 删除文件夹记录时，只释放它自己的资产引用，不能误删其他记录仍使用的缓存。
   - 浏览器历史、接收端、服务端记录和缓存节点都要认识这种记录，不能只完成发送端界面。

   你要求“不打 ZIP”，因此首版建议明确支持能够写入目录树的桌面浏览器。其他浏览器可以浏览和单文件下载，但不能承诺相同的整体落盘效果。

3. **视频随机取帧、提取会话和长期缓存**

   当前已有 yt-dlp、Cookie、JavaScript 运行时配置及 FFmpeg/ffprobe 调用，可以复用工具链；目前下载任务主要使用 JSON 记录和服务端成品目录，尚没有提取会话、帧日志和一年缓存生命周期。[现有视频工具配置](D:/Workspace/github/Ltre/file-tunnel/server.js:5119)

   建议分成五类数据：**源视频、提取会话、每次提取批次、帧日志、已保存帧**。源视频可以供同一用户的多个会话复用；每次改变范围、粒度或数量，生成一个批次，保留当时的参数。

   按你的存储要求：会话和日志存 SQLite，帧图及缩略图存服务器本地，完整视频长期存网盘。删除会话、清理未保存帧、删除已保存帧，应分别处理，避免清理日志时把收藏一并删掉。

   随机取帧建议采用下面的规则：

   - “粒度”定义为候选时刻间隔，例如每 500 毫秒一个候选位置；每次从有效候选位置中随机抽取指定数量。
   - 多段范围按时间长度参与抽样，重叠范围先合并，避免重复范围获得额外权重。
   - 支持 `分:秒`、`时:分:秒`及可选毫秒；检查倒置、越界和空范围。
   - 记录**请求时刻和实际解码帧的播放时刻**。视频帧并非落在每一个毫秒，日志不能用请求值冒充实际帧时间。
   - 同一源视频的重复检查应跨会话进行。完全重复可以跳过，近似画面先提示，让用户决定是否保留。
   - 候选数量不足时明确返回实际数量，避免为凑数无限重试。

   视频精确定位会涉及关键帧和解码，不能把“跳到某个时间”直接等同于“取得该时间的准确帧”。[FFmpeg 定位说明](https://www.ffmpeg.org/ffmpeg.html#Main-options)

   相似度建议分两层：先用感知哈希筛出候选，再进行较细的画面比较。比较对象可以选择当前会话、该视频全部日志、已保存帧或临时图片集。相似度适合提示重复画面；人物识别和“是不是同一个偶像”需要另外设计。[OpenCV 图像哈希](https://docs.opencv.org/4.7.0/d4/d93/group__img__hash.html)

   **完整视频缓存还存在几个实际问题：**

   - 当前网盘单个逻辑文件上限是 **2000 MiB**。长视频可能超限，首版需要明确提示并允许选择合适格式；后续再评估扩大文件能力或分段保存。[当前限制](D:/Workspace/github/Ltre/file-tunnel/server/disk-api.js:30)
   - 建议一年从缓存完成时计算；执行中的任务暂缓清理，已保存帧不随源视频到期删除。
   - 缓存身份除了视频标识，还要区分清晰度、音轨和访问身份，不能让私人视频被其他用户复用读取。
   - 网盘 Range 对应字节范围，播放时间还要通过媒体索引定位。建议把相邻取帧时刻合并处理，并缓存近期解码片段，减少反复读取。
   - 提取、比较和转码需要独立队列与资源限制，避免抢占隧道传输和网盘上传。

   “不用下载视频到本地”需要区分用户电脑和服务器。用户电脑无需保存完整视频；但首次抓取仍要经过服务器，并可能产生临时文件。当前下载器本身会生成本地成品。首版建议上传网盘确认成功后清理临时视频，后续再评估全程流式入库。

   Deno 可以纳入工具配置，但完整 YouTube 支持还涉及 yt-dlp 的 EJS 组件，不能只检查 Deno 是否安装。[yt-dlp 官方说明](https://github.com/yt-dlp/yt-dlp#dependencies)

   当前已有浏览器缓存、文件传输、网盘保存和 ZIP 处理基础，可以复用；需要补上 Markdown 文档及其资源关系。

   建议草稿保存 Markdown 源文和资源清单，媒体正文进入浏览器持久缓存，预览时再生成 Blob URL。PC 提供左右分栏，移动端提供编辑/预览切换。编辑器提供语法高亮、链接和资源补全、常用格式操作。

   保存网盘时，从主文档开始收集它需要的本地媒体和本地 Markdown，生成 mdpack：**主文档、引用文档、媒体文件和版本化清单**。包内改用相对路径，并可记录文件校验值。已有 mdpack 从网盘发到隧道时，保持一个完整文件资产，预览时再按需读取包内内容。

   需要补充这些边界：

   - 普通 Markdown 链接到另一个 Markdown，默认是跳转；如果要把另一篇内容嵌入正文，需要另外定义行为。
   - 文档之间可能循环引用，收集时必须去重并限制数量、深度和总大小。
   - 缺少本地引用资源时应提示，不能默默生成内容不完整的包。
   - 网络链接保留原样，因此不能承诺所有网络资源都能离线查看。
   - 清理缓存时，要保留仍被草稿或文档引用的媒体。
   - 预览不应直接沿用会执行脚本的网页工坊运行方式；Markdown 内的 HTML和链接需要安全处理。
   - 解包时限制展开大小、文件数量和路径，避免损坏包拖垮浏览器。
   - 修改网盘中的 mdpack 后重新保存，需要检查版本，避免覆盖另一处的更新。

   首版建议支持普通 Markdown、表格、任务列表和本地媒体，先把保存、恢复、引用收集和完整包传输做好。

   还要明确解析规则：

   - 标签中的 `]` 和反斜杠如何转义，空标签和未闭合括号如何处理。
   - URL 中的 `#片段`是否算标签，备注里的代码示例是否参与解析。
   - 大小写是否视为同一标签，前后空白是否拒绝或去除。
   - 同一备注重复写同一标签，统计只算一条记录。
   - 多标签筛选采用“同时具备”还是“具备任意一个”。
   - 文件夹记录和合辑默认索引父记录备注，避免自动扫描成员文件。

   索引可以保存“标签对应哪些记录”和“记录有哪些标签”。新增、修改或删除时，只更新受影响记录；启动时检查版本或备注摘要，必要时修复。不要在滚动、渲染或每次搜索时扫描所有记录，更不要读取文件正文。

   大量记录时把解析放到 Worker 或分批执行。重新连接收到远端修改、多标签页修改和索引格式升级，也要触发对应更新。

8. **服务器中继网**

   当前中继主要依赖本服务器上的隧道成员、在线连接和传输状态，还不是跨独立服务器的中继协议。[当前文件中继](D:/Workspace/github/Ltre/file-tunnel/server/file-assets.js:642) Socket.IO 的不同服务器也不会自动共享房间状态。[Socket.IO 多节点说明](https://socket.io/docs/v4/rooms/#with-multiple-socketio-servers)

   建议保留原服务器负责隧道身份、成员权限和记录同步，新增其他服务器提供文件数据中继。客户端继续留在原站点页面，只连接其他节点的传输通道，这样不会因切换站点丢失浏览器缓存。

   邀请关系需要稳定节点身份和签名密钥。A 邀请 B，B 同意后完成身份验证，双方保存关系、额度和有效期；地址变化时更新地址，身份不随地址变化。

   **A—B、B—C 成立后，可以让 A 和 C 自动建立直接关系，但需要双方预先允许可信节点引荐。**这样符合你希望减少人工邀请的目标，又能让节点自主决定接纳范围。A、C 完成独立握手后，才能真正使用彼此的中继服务。

   文件传输时，由原服务器签发短期授权，限定参与设备、文件和读取范围。发送方与接收方要协调连接同一个中继，不能各自随便挑一个节点就期待互通。

   需要补充的核心问题：

   - 节点发现、关系建立、实际网络可达和传输质量，应分别检查；认识某个节点不代表它更快。
   - 需要并发、流量和带宽额度，以及过载拒绝、故障切换和关系撤销。
   - 撤销或密钥更换后，旧授权需要到期或失效，不能永久有效。
   - 邀请地址验证要避免把节点变成任意地址代理；如需内网节点，应明确允许的范围。
   - 如果不希望外部中继管理员读取正文，需要客户端之间加密，中继只处理密文；HTTPS 本身不提供这个保证。
   - 公网浏览器连接通常需要 HTTPS/WSS，HTTP 节点不能保证能从 HTTPS 页面直接使用。
   - 普通文件 WebSocket 中继与实时音视频的 TURN 中继是不同能力，需要分别规划。
   - 节点版本、协议兼容和超时规则必须协商，不能因为运行同一套程序就假定永远一致。

   建议分三步推进：先做双方同意的直接中继，再做可信引荐和自动建立关系，最后才考虑数据实际经过多个服务器转发。你举的 A、C 经介绍后直接中继，可以在第二步完成，不需要先实现多跳数据转发。

开发顺序建议是：**先稳定现有协同挂载与目录权限 → 第 5、7 项 → 第 1 项 → 第 2、6 项 → 第 3 项 → 第 4 项**。第 8 项单独推进。这样目录写入、缓存续接、视频缓存和资源引用各自只建设一次，也能先验证基础能力再承接更大的功能。
