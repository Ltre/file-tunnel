    ### 先明确最终的数据形态

    这里不能理解成：

    ```text
    旧逻辑文件
      19 个 Telegram file_id
            ↓
    sendMediaGroup
            ↓
    1 个新的 Telegram file_id
    ```

    Telegram 不会这样合并。

    实际应该是：

    ```text
    旧逻辑文件
      part1 file_id
      part2 file_id
      ...
      part19 file_id
            ↓
    使用相同 Bot 的 file_id 重新发送
            ↓
    sendMediaGroup 10 个
    sendMediaGroup 9 个
            ↓
    得到 19 条新的 Telegram Message
            ↓
    得到 19 个目标消息对应的 file_id / message_id
            ↓
    本系统创建一个新的逻辑文件 UUID
            ↓
    parts[19]
    ```

    也就是说，**不再重新切片、不再上传文件正文**，但目标逻辑文件仍然由原来的物理分片组成。

    如果源逻辑文件只有一个 part，则不能调用 `sendMediaGroup`，应该直接：

    ```text
    sendDocument(file_id)
    ```

    2～10 个可以一个 `sendMediaGroup`。

    超过 10 个就拆多个最终 Album，而且必须避免留下单项尾组。例如：

    ```text
    11 → 9 + 2
    19 → 10 + 9
    21 → 10 + 9 + 2
    ```

    这和我们前面 S5 重构里讨论的 final media group 规则一致。

    ## 现在已有的能力其实非常适合复用

    当前 `disk-chunk-file-cache.js`：

    ```text
    key =
    backendFingerprint
    + sha256
    + size
    ```

    而且**key 里面没有 ownerId**。

    所以当前“分片 file_id 复用”实际上已经天然是跨用户的，只要这些用户使用的是**同一个 Telegram Bot/backend**。

    这个边界非常重要：

    ```text
    用户 A —— Bot X
    用户 B —— Bot X
    ```

    可以复用。

    但：

    ```text
    用户 A —— Bot X
    用户 B —— Bot Y
    ```

    不能直接复用 `file_id`。

    `file_unique_id` 也不能解决这个问题，因为它不能拿来发送文件。

    同一个 Bot、不同频道倒不是问题，只要该 Bot 有权限往目标频道发消息：

    ```text
    源频道 A
       ↓
    file_id

    同一个 Bot
       ↓
    目标频道 B
    ```

    是这个功能最适合的场景。

    ## 真正缺失的第一件东西：**逻辑文件内容 ID**

    目前文件记录里有：

    ```text
    parts[].sha256
    parts[].size
    parts[].offset
    parts[].fileId
    ...
    ```

    但是没有一个稳定的：

    ```text
    整个逻辑文件 content hash
    ```

    所以当前服务器只能做到：

    ```text
    Browser 上传第 N 片
    → Node 收完整片
    → 算 SHA256
    → 查 chunk_ids
    → 命中 file_id
    → 不上传这一片正文
    ```

    也就是说，**现在必须先把分片传到服务器，才能知道它是不是重复的。**

    而你现在的目标是：

    ```text
    Browser 准备上传 370MB 文件
            ↓
    还没有切片上传
            ↓
    服务器就知道：
    “这个完整逻辑文件以前已经存过”
            ↓
    Browser 不再上传这 370MB
            ↓
    直接复用旧 parts[].fileId
    ```

    因此一定需要一个**上传前即可提供的整文件身份**。

    我倾向于为逻辑文件增加：

    ```text
    contentSha256
    size
    ```

    组成：

    ```text
    logicalContentKey =
    botFingerprint
    + contentSha256
    + size
    ```

    文件名、目录、MIME 都**不应该进入内容 key**。

    同样的文件：

    ```text
    A用户：
    /Music/a.mp3

    B用户：
    /下载/乱七八糟名字.mp3
    ```

    应该照样命中。

    ## 但这里有一个很容易漏掉的严重问题：跨用户不能只相信 SHA256

    假设接口允许：

    ```json
    {
      "size": 388123456,
      "sha256": "abcdef..."
    }
    ```

    服务器一查：

    ```text
    这个 hash 已经存在
    ```

    然后直接把别人的 file_id 克隆给这个用户。

    那就会出现一个安全问题：

    **用户根本不需要拥有这个文件。只要知道某个私人文件的 SHA256，就可能让系统把文件复制进自己网盘。**

    所以跨用户逻辑复用不能简单做成：

    ```text
    hash 相同
    → 直接给文件
    ```

    至少应该有一个 **Proof of Possession（内容持有证明）**。

    比较适合这个项目的做法是：

    ```text
    客户端：
    我有 SHA256 = H，size = 370MB

    服务器：
    发现有候选文件
    但不告诉来源，也不直接复用

    服务器随机产生若干 challenge：
    offset 12345678, length 64KB
    offset 172938221, length 64KB
    offset 301237711, length 64KB

    客户端：
    返回这些位置的数据 / nonce hash

    服务器：
    从候选 Telegram 文件对应 ranges
    读取少量数据进行比对

    全部一致
    → 证明客户端确实持有该文件
    → 才允许逻辑文件复用
    ```

    这样可能只需要下载几百 KB，而不是重新上传 370MB。

    而且**绝对不要向客户端返回候选文件属于哪个用户、源 logical ID、源目录或者源 message_id**。

    否则就会形成跨用户信息泄露。

    ## 可以利用现有分片 SHA 再做一层优化

    还有一个比从零开始更容易落地的方案。

    你当前已经永久保存：

    ```text
    part1.sha256
    part2.sha256
    ...
    partN.sha256
    ```

    所以可以定义一个：

    ```text
    logicalManifestHash v1
    ```

    例如：

    ```text
    SHA256(
      "Drop2TunnelLogicalV1"
      + totalSize
      + part1.size + part1.sha256
      + part2.size + part2.sha256
      ...
    )
    ```

    这样现有历史文件**不用重新从 Telegram 下载整个文件**，就能立即生成逻辑内容索引。

    但它有一个缺点：

    同样的原始文件如果分片边界不同：

    ```text
    20MB + 20MB + 5MB
    ```

    和：

    ```text
    15MB + 15MB + 15MB
    ```

    得到的 manifest hash 会不同。

    所以我建议最终支持两层：

    ```text
    contentSha256
        真正的整个文件内容 ID
        与分片方式无关

    logicalManifestHash
        基于已有 parts[].sha256
        可以零成本给历史文件建立索引
    ```

    第一版甚至可以先用 `logicalManifestHash`，因为你现在默认分片策略非常固定，实际命中率应该已经很高。

    ## Telegram 复用路径本身也可以再优化

    现有 `object-storage.copy()` 已经这样做：

    ```text
    source.parts
    → reuseFileId
    → getFile 校验每片
    → uploadPhysical()
    ```

    但是 `uploadPhysical()` 当前组成 batch 时仍然使用：

    ```text
    MAX_TELEGRAM_BATCH_SIZE = 40MB
    ```

    因此一个普通 20MB part：

    ```text
    最多通常 2 个 / sendMediaGroup
    ```

    这对真实二进制上传有意义。

    但对于：

    ```text
    sendMediaGroup(file_id, file_id, file_id...)
    ```

    请求体只是 JSON，不再上传这 200MB 数据。

    所以纯复用路径应该特殊处理：

    ```text
    全部 reuseFileId
    → 不应用 40MB batch 限制
    → 只应用 Telegram 2～10 items 限制
    ```

    例如 370MB，假设 19 个 part：

    当前 Copy 可能近似：

    ```text
    2 + 2 + 2 + ...
    ```

    整逻辑复用优化后应该：

    ```text
    10 + 9
    ```

    只需要两个创建消息请求。

    这会非常明显地进一步降低 Telegram API 次数。

    ## 删除和缓存生命周期也必须先定义

    如果 A 上传一个私人文件：

    ```text
    A 删除
    ```

    但是：

    ```text
    logical_file_cache
    ```

    永久保存其全部 Telegram file_id。

    那实际上系统仍保留了一个可复用入口。

    我建议至少做引用语义：

    ```text
    logical cache entry
        ↓
    有多少 active logical file 引用该内容
    ```

    ```text
    refCount == 0
    ```

    可以删除逻辑复用索引。

    是否同时删 Telegram 实体则是另一层问题。

    尤其需要注意后台审核：

    ```text
    reviewStatus = blocked / deleted
    ```

    ```text

    → B 上传同 hash
    → cache hit
    → 文件重新出现
    ```

    所以至少要有：

    ```text
    content blocked
    → logical cache 禁止复用 / 删除
    ```

    ## “缩略图/封面”也不能忘

    逻辑文件正文可以完全复用 parts。

    ### PoP：你的理解正确，但建议加一次性 nonce

    你说的不是：

    ```text
    服务器取样内容
    → 下载给客户端
    → 客户端比较
    ```

    而是：

    ```text
    服务器生成随机 challenge：
    offset=...
    length=...

    服务器：
    从已有 Telegram 文件读取这个 range
    → SHA256

    客户端：
    从本地待上传 File.slice(offset, offset+length)
    → SHA256

    客户端只把 digest 发给服务器

    服务器：
    digest_server === digest_client
    ```

    **完全可以这样做，样本正文不需要从服务器传给客户端。**

    不过不能单纯比较：

    ```text
    SHA256(sample)
    ```

    最好每次 challenge 再生成一个一次性随机 nonce，例如：

    ```text
    SHA256(
        "Drop2Tunnel-PoP-v1"
        || nonce
        || offset
        || length
        || sampleBytes
    )
    ```

    服务器和客户端都这样算。

    这样可以避免以前某次 PoP 的：

    ```text
    offset + sampleHash
    ```

    被截获之后直接重放。

    challenge 应绑定：

    ```text
    challengeId
    userId/session
    contentKey
    fileSize
    nonce
    expiresAt
    ```

    而且只能成功使用一次，几十秒或一两分钟过期。

    offset 必须由服务器随机产生，不能让客户端自己选。

    对于 370MB 这类文件，可以随机抽例如 6～8 个互不重叠的 32～64KiB range，并尽量分散到文件各处。实际服务器读取量只有几百 KB。

    还有一个隐私细节值得补上：**不要在客户端提交整个 SHA256 后立即告诉它“服务器存在这个文件”。** 可以统一返回 PoP challenge；有候选就真正比较，没有候选最终正常走上传。这样一个只知道某私人文件 SHA256、但并没有文件内容的人，不能拿接口当“本站是否存有这个文件”的查询器。

    # 第 9 点：能不能连 sendMediaGroup/sendDocument 都省掉？

    **Telegram Bot API 层面看，是有可能的。**

    官方明确说 `file_id` 是“可用于下载或重新使用该文件”的标识；发送已经存在于 Telegram 服务器上的文件时，可以直接传 `file_id`，不需要重新上传，而且同一个文件对同一 Bot 甚至可能存在多个有效的 `file_id`。官方明确限制的是 `getFile` 得到的下载 URL 至少有效 1 小时，而不是说 `file_id` 只有 1 小时。[Telegram](https://core.telegram.org/bots/api%20?utm_source=chatgpt.com)

    但是官方**没有给出一个我认为足以支撑存储系统的承诺**：

    > 当产生这个 `file_id` 的所有 Telegram message 都被删除后，这个 `file_id` 永久有效。

    底层 MTProto 甚至存在会过期、需要从原始消息等 source 重新取得的 `file_reference` 概念。Bot API 对此做了封装，但这说明“Telegram 后端文件引用永久不依赖任何 source”不能当成正式契约。[Telegram](https://core.telegram.org/api/file-references?utm_source=chatgpt.com)

    所以我不建议采用下面这种裸方案：

    ```text
    A 的 message 包含 part file_id
           ↓
    B 复用

    B 的逻辑文件仅记录 A 的 file_id
    但不给 B 创建 Telegram message

           ↓

    A 删除文件
    → A 原 message 被删除

           ↓

    系统继续永久相信 B 保存的 orphan file_id 一定有效
    ```

    它大概率可能还能工作，但**不适合作为 Drop2Tunnel 的持久性保证**。

    ```text
    用户逻辑文件
        ↓
    Telegram messages / parts
    ```

    ```text
                     ┌─ 用户A logicalFileId
                     │
    Content Object ──┼─ 用户B logicalFileId
                     │
                     └─ 用户C logicalFileId

    Content Object
        contentKey
        size
        parts[]
            sha256
            offset
            size
            telegramFileId
            messageId
            channelId
        thumbnail...
    ```

    ```text
    A 第一次上传
    → 正常 Browser → Node → Telegram
    → 创建 Content Object C1
    → A.logicalFile → C1
    ```

    ```text
    contentKey 命中
    → PoP 成功
    → 根本不用 Browser 上传正文
    → 根本不用 sendMediaGroup
    → 创建 B 自己的新 logicalFileId
    → B.logicalFile → C1
    ```

    ```text
    C.logicalFile → C1
    ```

    ## 1. Caption：现有用户/逻辑文件 caption 确实应该废掉

    当前 `diskCaption()` 写的是类似：

    ```text
    网盘文件
    user_id: A
    disk_space: xxx
    name: aaa.flac
    channel_id: ...
    logical_file_id: UUID-A
    part: 1/19
    original_size: ...
    file_id: ...
    message_id: ...
    album_id: ...
    ```

    共享 Content Object 后，一个 Telegram message 可能同时被：

    ```text
    Logical A
    Logical B
    Logical C
    ```

    引用。

    那么这些字段全部出现语义冲突：

    ```text
    user_id
    disk_space
    name
    logical_file_id
    ```

    物理 message 不再“属于”其中任何一个 logical file。

    因此目前这些功能都应该一起退出：

    ```text
    renameFile()
    → captionSyncPending = true

    modifyFile(name)
    → captionSyncPending = true

    syncCaptions()

    retryCaptions()

    TELEGRAM_CAPTION_SYNC_PENDING

    上传完成后的 editMessageCaption 补用户定位信息
    ```

    也就是说，**重命名文件以后只改 SQLite logical record，不再碰 Telegram。**

    这反而会让系统干净很多。

    ### Caption 是否完全为空？

    可以。

    Telegram message 真正承载的是物理 Content Object，所有定位信息已有 SQLite，就存储功能而言完全可以：

    ```text
    caption = ''
    ```

    不过我觉得保留一个**纯物理、无用户信息的极简 caption**还有一点运维价值，例如：

    ```text
    Drop2Tunnel Content
    content_id: <uuid>
    part: 3/19
    ```

    或者干脆：

    ```text
    content:<uuid> · 3/19
    ```

    只允许 Content Object 级字段：

    ```text
    contentObjectId
    partIndex
    partCount
    ```

    不要再放：

    ```text
    用户名
    userId
    逻辑文件名
    目录
    diskSpace
    logicalFileId
    MIME
    来源 App
    ```

    甚至 `contentHash` 我也不觉得有必要写进 Telegram；数据库才应该是 source of truth。

    已有历史 message 不必为了迁移强制全部改 caption；但如果某个旧 physical object 第一次被提升为共享 Content Object，可以选择顺手把旧的用户型 caption 清成中性 caption。Bot API 对普通由 Bot 自己发送的消息没有像 `deleteMessage` 那样明确的通用 48 小时 caption 编辑限制；官方这里特别列出的 48 小时限制针对某些 business message。[Telegram](https://core.telegram.org/bots/api%20?utm_source=chatgpt.com)

    # 2. 当前删除链路受影响的地方比普通 DELETE 多

    这部分是最重要的牵连面。

    现在很多地方的基本假设都是：

    ```text
    Logical File == Telegram Physical Object
    ```

    所以只要 Logical File 不要了，就 `telegram.remove(file)`。

    共享后必须统一改成：

    ```text
    releaseLogicalReference(logicalFileId)
    ```

    由 content 层决定要不要物理删除。

    当前至少这些入口都会受影响。

    ### 普通单文件删除

    现在：

    ```text
    DELETE /files/:id
    → objectStorage.deleteFile()
    → telegram.remove(file)
    → store.remove()
    ```

    应该变成：

    ```text
    DELETE logical
    → transaction:
        remove logical
        release content ref

    → if content refCount == 0
        schedule physical cleanup
    ```

    不能先删 Telegram 再删 logical。

    ---

    ### 目录递归删除

    当前逐个：

    ```text
    for file:
        objectStorage.deleteFile(file)
    ```

    共享以后一样必须逐个 release ref。

    例如：

    ```text
    目录内 A、B、C

    A → C1
    B → C1
    C → C2
    ```

    删目录后：

    ```text
    C1 减 2 个 reference
    C2 减 1 个 reference
    ```

    只有真正归零的 object 才进入 Telegram cleanup。

    ---

    ### 管理员 review delete

    当前管理员：

    ```text
    review delete
    → telegram.remove(file)
    → tombstone(logical file)
    ```

    共享后不能这样。

    必须：

    ```text
    review delete Logical A
    → tombstone A
    → release A → Content C

    如果 C 还有 B/C 引用
    → Telegram 什么都不删
    ```

    这正符合你前面强调的：

    > 审核只针对 logical file，不形成 content block。

    目录 review delete 同理。

    ---

    # 3. `pendingRemoteCleanup` 的模型需要重构

    当前很多覆盖、替换场景会把旧 physical 信息塞进：

    ```text
    logicalFile.pendingRemoteCleanup
    ```

    然后后台：

    ```text
    retryRemoteCleanup()
    → telegram.remove(stale)
    ```

    共享以后这不应该再挂在 Logical File 上。

    因为：

    ```text
    Logical A
    Logical B
           ↓
    Content C
    ```

    A 覆盖成新文件后：

    ```text
    A → C2
    B → C1
    ```

    C1 明明还活着。

    如果 A 自己携带：

    ```text
    pendingRemoteCleanup = C1
    ```

    后台一清理，就把 B 的内容干掉了。

    所以 cleanup debt 应该变成 Content Object 级：

    ```text
    Content Object
        state
        physicalCleanupPending
        cleanupAttempts
        lastCleanupError
    ```

    只有 refcount 归零时才能进入 cleanup。

    # 4. Repair 是一个比删除更容易出严重 Bug 的地方

    当前 repair 大致：

    ```text
    Logical A
    → 上传替代物
    → update A 的 fileId/parts
    → telegram.remove(A 原来的 physical)
    ```

    如果：

    ```text
    A → Content C1
    B → Content C1
    ```

    那么 A 执行 repair 时，绝对不能直接修改 C1 或删除 C1。

    这里要区分两种情况。

    ### Repair 内容相同

    例如 Telegram physical 丢了，但用户拿本地同一文件修复：

    ```text
    contentSha256 == C1.contentSha256
    ```

    这是真正的 Content Object repair。

    可以：

    ```text
    重新上传 physical parts
    → 原子替换 C1.physicalRepresentation
    → A/B/C 全部恢复
    → 清理失效旧 messages
    ```

    因为内容没变。

    ### Replacement 内容变化

    尤其协同编辑现在就允许文件内容发生变化。

    那么：

    ```text
    A → C1

    用户上传了不同内容
    ```

    必须：

    ```text
    创建 C2
    A → C2
    release C1

    B 仍然 → C1
    ```

    不能把 C1 原地改掉。

    所以未来 API 最好明确区分：

    ```text
    repairContentObject()
    replaceLogicalContent()
    ```

    即使外部仍用同一路由，内部语义也必须分开。

    ---

    # 5. S3 PUT / overwrite / Copy 也全部受影响

    这个影响很大。

    ### S3 overwrite

    当前覆盖一个 object 时，逻辑 ID 可以保持不变，但旧 physical 会进入 cleanup。

    以后应该是：

    ```text
    Logical L
    原来 → C1

    PUT 新正文
    → C2

    transaction:
    L.contentId = C2
    release C1

    if C1 refCount == 0
    → cleanup C1
    ```

    Logical ID 可以继续不变。

    ---

    ### S3 Copy

    这个反而大幅简化。

    当前同 Bot Copy：

    ```text
    读取 source.parts[].fileId
    → getFile
    → sendDocument/sendMediaGroup
    → 新 Telegram messages
    → putCopiedObject
    ```

    共享模型以后，同一 Content Object 的 Copy 可以完全变成：

    ```text
    Source Logical → C1

    创建 Target Logical
    Target Logical → C1
    ```

    连 Telegram API 都不需要调用。

    如果 Copy 的源和目标本来就是本系统管理的 Content Object，这应该是 O(1) SQLite 操作。

    所以现有 `putCopiedObject()` 最终很可能都不再是主路径了。

    ---

    # 6. `fileIdHistory` 要重新归属

    当前 Logical File 有：

    ```text
    fileIdHistory
    ```

    共享以后，物理历史属于：

    ```text
    Content Object
    ```

    而不是逻辑文件。

    比如：

    ```text
    Content C1
    physical version 1
    physical version 2
    ```

    应该保留：

    ```text
    C1.physicalHistory
    ```

    如果是 Logical A 内容发生变化：

    ```text
    A: C1 → C2
    ```

    那这不是：

    ```text
    fileIdHistory
    ```

    而是逻辑内容版本关系。

    可以另有：

    ```text
    Logical A.contentHistory
    ```

    如果产品以后需要版本历史。

    不要把两者混在一起。

    ---

    # 7. 下载 / Stream / Range 本身改动不大，但取数据的入口要变

    现在大量代码直接：

    ```text
    file.parts
    file.fileId
    file.channelId
    file.backendId
    ```

    以后 Logical File 最好不要再持有整套 physical parts。

    应该：

    ```text
    LogicalFile {
        id
        ownerId
        name
        folderPath
        type
        metadata
        contentId
        ...
    }
    ```

    然后：

    ```text
    ContentObject {
        id
        size
        contentSha256

        backendId
        channelId

        parts[]
    }
    ```

    下载时：

    ```text
    Logical
    → resolve contentId
    → Content.parts
    → Telegram
    ```

    `Range`、part cache、逐片验证这些机制基本可以原样使用。

    当前 part cache 的 key 本来就主要依赖：

    ```text
    backend
    fileId
    size
    sha256
    range
    ```

    所以共享 physical part 反而天然提高缓存命中。

    # 8. Part cache 的“owner”概念需要注意，但不一定要大改

    当前 `disk-part-cache.js` 允许同一个缓存项注册多个：

    ```text
    userId + diskSpace
    ```

    这已经有共享缓存的味道。

    Content Object 后：

    ```text
    A 下载 C1
    B 下载 C1
    ```

    两边实际会命中同一个物理 cache key。

    目前 owner registry 会记录两个 scope。

    这基本可继续用。

    只是要确认“用户清缓存”的语义：

    ```text
    A 清理自己的缓存
    ```

    如果 B 还注册引用同 cache item，就不能把共享 cache 文件删掉。

    当前代码已经有 remaining owners 逻辑，方向是对的。

    # 9. Thumbnail 也应该拆成 Content 与 Logical 两层

    这个前面我们说过，现在从代码牵连关系看更应该这么做。

    当前：

    ```text
    Logical File
        thumbnail {
            fileId
            messageId
        }
    ```

    如果 thumbnail 是从文件内容自动提取：

    ```text
    音频内嵌封面
    视频自动截图
    ```

    那它应该属于：

    ```text
    ContentObject.thumbnail
    ```

    于是：

    ```text
    A/B/C
    ```

    直接共用。

    删除 A 不动 thumbnail。

    C1 refCount == 0 时，才和正文 physical messages 一起清。

    如果以后有：

    ```text
    用户手动设置封面
    ```

    则另放：

    ```text
    LogicalFile.customThumbnail
    ```

    不能污染 Content Object。

    # 10. `mediaIndex` 也要判断归属

    当前 Logical File 里直接保存：

    ```text
    mediaIndex
    ```

    如果它描述的是：

    ```text
    时长
    音轨
    视频轨
    编码信息
    关键帧
    媒体内部结构
    ```

    这是**内容属性**，应该进入 Content Object。

    ```text
    用户自定义标签
    展示偏好
    ```

    # 11. Share 基本不用重构

    当前分享保存的是：

    ```text
    ownerId
    logical file IDs
    name/path snapshot
    ```

    这其实很好。

    分享应该继续引用 Logical File，而不是直接引用 Content Object。

    例如：

    ```text
    A 分享 Logical A
    A 删除 Logical A
    ```

    即使：

    ```text
    B → 同一个 Content C
    ```

    A 的分享也应该失效。

    所以：

    ```text
    Share → Logical File → Content Object
    ```

    不能改成：

    ```text
    Share → Content Object
    ```

    当前 `disk-shares.js` 这一层整体语义可以保留。

    # 12. Collaboration 也必须继续绑定 Logical File

    同样：

    ```text
    Collaboration
    → Logical File
    ```

    不是 Content Object。

    否则 B 复用了同一个内容，就莫名加入 A 的协同关系，这是绝对不对的。

    但协同内容替换会触发前面说的：

    ```text
    Logical A
    C1 → C2
    ```

    因此 collaboration replacement 是 Content Object 重构后的重点测试项。

    # 13. Content health / check 的状态也要重新分层

    现在：

    ```text
    lastCheckedAt
    repairedAt
    ```

    挂在 Logical File。

    共享后，真正的：

    ```text
    Telegram file_id 是否还能 getFile
    part hash 是否正确
    message anchor 是否还存在
    ```

    是 Content Object 的健康状态。

    所以应该有：

    ```text
    ContentObject {
        lastCheckedAt
        healthStatus
        lastPhysicalError
        repairedAt
    }
    ```

    Logical File 可以有：

    ```text
    lastUserCheckAt
    ```

    但不能把物理健康状态复制 N 份。

    如果 C1 物理坏了：

    ```text
    A/B/C
    ```

    实际上全部都受影响。

    # 14. 后台审核查询正好可以利用 Content Object 的反向索引

    你之前要求：

    > 可以查询引用相同内容的所有逻辑文件 ID。

    Content Object 模型天然就能做：

    ```text
    contentId = C1

    SELECT LogicalFile
    WHERE contentId = C1
    ```

    后台可以看到：

    ```text
    C1
    ├─ logical A
    ├─ logical B
    ├─ logical C
    └─ logical D
    ```

    然后管理员显式选择：

    ```text
    全部 content unavailable
    ```

    或者：

    ```text
    全部 content delete
    ```

    这仍然只是批量作用于 Logical File。

    **不会创建 content block。**

    未来新上传同样内容：

    ```text
    PoP
    → C1 如果仍存在并且健康
    → 正常引用

    如果 C1 已经因 refCount=0 被物理清理
    → 正常重新创建 Content Object
    ```

    完全符合你前面定的边界。

    ```text
    telegramFileId
    telegramFileUniqueId
    telegramChatId
    telegramMessageId
    telegramPartFileIds
    ```


    # 16. Backend / channel 的归属也要搬到 Content Object

    当前 Logical File 保存：

    ```text
    backendId
    channelId
    ```

    共享后它们属于 physical storage：

    ```text
    ContentObject.backendId
    ContentObject.channelId
    ```

    Logical File 本身不应该知道自己“在哪个 Telegram channel”。

    尤其以后即使仍只有一个 Bot，也可能有多个 storage channel。

    Content Object 负责：

    ```text
    在哪个 channel 有 anchor messages
    ```

    Logical File 只负责业务命名空间。

    另外当前类似：

    ```text
    hasChannel(channelId)
    ```

    这种“看 logical records 判断 channel 是否正在使用”的代码，如果本地版本仍有，就要改成检查 Content Object。

    # 17. 上传失败 / recovery manifest 仍然属于“未提交 Content Object”

    这块不能简单绑到 Logical File。

    合理状态是：

    ```text
    upload staging
        ↓
    pending Content Object candidate
        ↓
    Telegram messages confirmed
        ↓
    Content Object READY
        ↓
    Logical refs commit
    ```

    如果 Telegram 上传完成但 Logical commit 失败：

    ```text
    Content Object refCount == 0
    ```

    就进入 recovery cleanup。

    如果 commit 已经完成：

    ```text
    refCount > 0
    ```

    recovery 绝不能删 physical messages。

    因此当前：

    ```text
    pendingRollbackParts
    recoveredUploads
    cleanupExpiredUploads
    ```

    未来都需要知道：

    ```text
    这个 physical object 是否已经成为 READY Content Object
    以及是否已经有 committed references
    ```

    # 18. 并发去重是新增的核心竞态

    这是共享 Content Object 后必须额外处理、当前 chunk cache 级别没有完全解决的问题。

    例如 A/B 同时上传同一个新文件：

    ```text
    A contentSha256 = H
    B contentSha256 = H

    A 查 MISS
    B 查 MISS

    A 开始上传
    B 也开始上传
    ```

    最后可能产生两套 physical object。

    最好 Content Object 有状态：

    ```text
    CREATING
    READY
    DELETING
    BROKEN
    ```

    并且：

    ```text
    UNIQUE(contentSha256, size)
    ```

    流程：

    ```text
    A INSERT content(H) → CREATING
    B INSERT → conflict

    B 发现已有 CREATING
    → 可以等待
    → 或正常上传但最终竞争合并
    ```

    我比较倾向前者。

    不过不能让恶意用户通过“别人正在上传 H”直接获得内容，因此：

    ```text
    READY ≠ 可直接引用
    ```

    跨用户仍必须经过 PoP。

    ---

    # 19. RefCount 最好不要只维护一个裸整数

    可以有：

    ```text
    content_objects.refCount
    ```

    作为性能字段。

    但真正删除时最好在事务内验证：

    ```sql
    SELECT COUNT(*)
    FROM logical_files
    WHERE content_id = ?
    ```

    或者用 FK/reference table 做 source of truth。

    否则：

    ```text
    创建 logical 成功
    refCount +1 写失败

    或

    删 logical 成功
    refCount -1 写失败
    ```

    都可能误删共享物理内容。

    最稳的是数据库关系本身决定引用：

    ```text
    disk_files.content_id
            ↓ FK
    disk_contents.id
    ```

    删除 Logical File 的事务里先解除引用。

    然后：

    ```text
    COUNT references == 0
    ```

    才将 Content Object：

    ```text
    READY → DELETE_PENDING
    ```

    网络删除 Telegram message **不能放 SQLite 长事务里**。

    因此应该：

    ```text
    TX:
      delete logical
      content.state = DELETE_PENDING if refs=0
    COMMIT

    异步：
      Telegram cleanup

    成功：
      delete content row

    失败：
      留 DELETE_PENDING 重试
    ```

    这和你当前项目“不把 Telegram 网络请求放进数据库事务”的原则是一致的。

    ---

    # 20. 删除时还有一个“复活竞态”

    例如：

    ```text
    C1 refCount 从 1 → 0
    → DELETE_PENDING

    与此同时新用户 D 上传同内容
    → PoP 成功
    ```

    这时不能：

    ```text
    D → C1
    同时后台把 C1 messages 删除
    ```

    所以 lookup 时要区分：

    ```text
    READY
    DELETE_PENDING
    DELETING
    ```

    建议：

    ```text
    READY
    → 可复用

    DELETE_PENDING
    → 可以在事务里取消删除，重新变 READY
       前提 Telegram cleanup 尚未开始

    DELETING
    → 不允许复用，重新上传/创建新 Content Object
    ```

    需要一个明确的物理生命周期。

    # 21. 关于 Telegram messages：我建议把它们定义成“anchor”

    这样整个模型最清楚：

    ```text
    Content Object
      ├─ content identity
      ├─ physical parts
      └─ Telegram anchor messages
    ```

    这些 message 的意义已经不是：

    > “A 用户上传的 aaa.mp3”

    而是：

    > “Content Object C1 的第 3 个物理 part 的持久锚点”

    所以：

    ```text

    用户移动目录
    用户分享
    用户取消分享
    用户改 metadata
    ```

    一律不应该编辑 Telegram anchor。

    只有：

    ```text
    Content Object 物理修复
    Content Object 最终删除
    ```

    才碰这些 messages。

    我觉得这是共享模型里最重要的边界。

    ## 牵连程度我会这样分

    **必须重构，否则会误删别人数据：**

    - 目录递归删除
    - review delete / tombstone
    - S3 delete / overwrite
    - repair
    - collaboration replace
    - `pendingRemoteCleanup`
    - recovery cleanup
    - `fileIdHistory`
    - Telegram backend/channel 归属

    - `diskCaption`
    - `syncCaption`
    - rename caption retry

    - mediaIndex
    - health/check 状态

    - Share

    - Range 下载协议
    - Part cache 主体

    ```text
    ≠
    ```

    ### 有一个实现细节尤其重要：`message_id` 和最终 `file_id` 不能在首次发送前写进 caption

    首次真正上传正文时：

    ```text
    sendDocument / sendMediaGroup
    ```

    发送之前你已经知道：

    ```text
    contentObjectId
    originalName
    originalMimeType
    partIndex
    partCount
    originalSize
    ```

    ```text
    message_id
    file_id
    file_unique_id
    media_group_id
    ```

    所以仍然需要和当前代码类似的两阶段 caption：

    ```text
    第一次发送：
    caption 写已知字段

    Telegram 返回 Message[]
            ↓
    取得：
    file_id
    message_id
    media_group_id
            ↓
    editMessageCaption
    补齐最终物理定位信息
    ```

    ```text

    name: abc.mp4
    mime_type: video/mp4
    part: 22/45
    original_size: 892345678
    ```

    ```text
    Drop2Tunnel Content
    content_object_id: C123
    name: abc.mp4
    mime_type: video/mp4
    part: 22/45
    original_size: 892345678
    file_id: BQACAg...
    message_id: 123456
    ```

    所以我们前面说的“删除 caption sync 机制”需要更准确地说：

    > **删除 Logical File 级 caption sync；保留 Content Object physical caption finalize / repair sync。**

    也就是原来这种：

    ```text
    Logical File rename
    → captionSyncPending
    → editMessageCaption
    ```

    应该消失。

    但这种应该留下：

    ```text

    ```

    ```text

    repair 后：
    file_id = BBB
    ```

    因为：

    ```text

    ```

    数据库应该保存。

    caption 我认为属于可选。
