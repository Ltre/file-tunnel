## 修正参考概念中的语义

- 普通设备发现列表只展示可见设备关系内的公开台；Q12／Q32 已明确创作者主页及公开台直接观看链接是其它入口，不要求观看设备原本同隧道或已关注。不能再把普通发现范围当作公开台全部观看范围。
- 「仅限邀请」不在未授权设备的普通发现列表中泄露；图中展示的相关条目均已有有效邀请。
- 「下线」停止当前串流，保留订阅及监控位置，不表示继续向接收端供流。
- 摄像头与屏幕单独作为实时来源；文件池支持多渠道混合，不把实时源与文件混排。
- 文件列表限定音频、视频、图片、Markdown / TXT，不沿用概念图扩展出的 PDF / ZIP。
- 不沿用概念图 RTMP / RTSP / SRT / HLS 等未确定协议字样。
- 监控播放 / 暂停默认本机观看操作；共享播放控制进入单台后执行。
- 原版 v2 的非阻塞浮窗方案由本次要求的全屏浮层取代；使用首页通过收起 / 恢复快速完成。

## 结合当前代码的接入边界（设计约束，未实施）

当前首页原三栏见 `pages/index.html`，手机侧滑与栏位切换见 `app.js`。现有栏位只有连接设备、传输记录、协同编辑；原有手势判断也有自己的弹层识别范围，不能假定新增串流浮层天然被隔离。后续开发需要显式阻断后台三栏手势并在切换时清理未完成手势，根节点放在原侧滑容器外。

串流页面切换、来源弹层、排序拖动与原三栏侧滑不共用位移或栏位索引。返回首页按原索引恢复；快捷跳转到原三栏时调用对应的打开动作，避免误触首页原有的重复点击动作。验收时覆盖正在横滑时开关浮层、拖动排序、播放器拖进度、方阵滚动、虚拟键盘及横竖屏切换。

本文件记录的是原型设计及接入注意事项，没有修改应用实现，也没有宣称已解决真实手势或播放问题。

| --- | --- | --- |
| 创建仅邀请台后选择可见设备发送 | [设备邀请](42-invitation-flow.html#devices)；移动创建页保存仅邀请台后进入 09 | 设备多选、发送及待接受状态 |
| 接收端通过通知中心接受 | [本机通知中心](42-invitation-flow.html#notifications)；移动首页通知中心入口 | 仅本机通知的核对、接受、拒绝及订阅状态，无设备切换 |
| 邀请链接转发到所选隧道 | [选择隧道](42-invitation-flow.html#tunnel) → [邀请消息](42-invitation-flow.html#message) | 邀请说明、链接及可选媒体缩略图；不附带完整源文件，不显示下载或上传到网盘；看到消息的设备可接受邀请 |
| 发送结果提示 | 设备邀请、转发到隧道 | 横向带背景色的扁平提示面板 |
| 普通 Markdown 预览、引用及打包 | [独立消息示例](42-invitation-flow.html#markdown) | 十行高度预览、毛玻璃、展开、作者自行引用的隧道 Blob 和 ZIP 清单；仅普通无特殊用途的消息提供“下载”“上传到网盘” |

Q4 已确认：能看到隧道邀请消息的设备可直接接受，无需另行定向批准。创建端不能管理接收端通知；各设备页面只通过原型审核导航作对照，产品 UI 不提供切换其它设备通知的能力。支线要求整理后继续串流控制台主线。

Q30／Q31 最新结论优先：观看不需要先订阅，订阅必须先登录用户；接受邀请取得观看许可，不自动订阅。订阅列表跟随用户账号跨设备共用，各设备创建的台、加入的隧道及监控布局仍独立。订阅记录不等于观看授权，原型中的对应入口及文案需后续分开整合。

Q39 更正：通用邀请可在多个设备多次使用，不因首次接受时未登录而绑定首次设备；之后登录账号，也可通过账号携带订阅及相应观看资格到电脑。定向邀请始终只允许指定设备多次进入，不因登录同一账号而扩展。不能把旧原型的设备绑定规则套用于所有邀请。

Q40 已确认：同一 Plus 账号在多设备上共用资格，但各端自由观看的节目与进度独立，一端操作不改变另一端，且均可主动返回全局同步。不能将账号共享资格实现成所有设备强制共用一个个人播放位置。

Q41 已确认：同一来源可对应多个节目项，分别排序及设置播放参数。后续原型整合需区分来源文件与节目项，不能按来源去重而取消用户主动重复编排的项目；移除节目项不删除来源文件，也不制作媒体副本。

Q34 至 Q37 的跨设备归属用户也沿用观看者视图，显示“创建者是自己、来源设备 A”，允许全局播控、可见性设置、邀请管理及踢出／重新允许观看设备，不开放修改导入源、删除台或放弃归属等重大操作。不能复用 A 的完整创建者视图来代替 B 的观看者视图，后续原型整合需体现这一差别。

Q7／Q20 按上述模型更正：邀请到期或被撤销只阻止后续凭该邀请取得观看许可，已获观看许可不追溯撤销；终止已有设备访问另用踢出。订阅记录与许可分别处理，旧原型中“撤销邀请即停止接收”的文案需纠正。

Q38 已确认：公开转为仅邀请时，旧接收端退出并撤销旧观看权限，切换前生成的通用及定向邀请也一并失效，需要重新发出邀请；已有订阅记录不因此删除。这是可见性切换的规则，与单独撤销一份邀请分别处理。

Q5／Q6 已确认：网盘与隧道来源不依赖串流台创建者持续在线；串流只按需读取原始来源，不复制保底文件、不限制删除，也不延长源内容的保留期限。来源删除后可以失效，已经进入浏览器缓存或播放缓冲的部分可继续使用。原型中的来源离线示意应按具体来源判断，不能把创建者离线一律当作来源不可用。
