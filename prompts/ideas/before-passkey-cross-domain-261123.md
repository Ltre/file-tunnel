
# 多域名 Passkey 关联与账号中心开发指引

## 一、项目背景与目标

开发基线：`dev/2611-s`3。

当前系统允许多个独立主域名（例如 `a.com`、`b.com`、未来的 `c.com`）访问同一套服务，共用相同的账号及业务数据。

目前存在以下问题：

- 用户在 `b.com` 注册用户名 `aaa` 并创建 Passkey 后，访问 `a.com` 使用相同用户名登录，提示 `PASSKEY_ACCOUNT_NOT_FOUND`。
- 用户尝试在 `a.com` 再次注册 `aaa`，又提示 `USERNAME_EXISTS`。
- 已有用户账号全站唯一，但缺少跨域 Passkey 身份验证与关联流程。

**开发目标：使用户使用任何已绑定域名访问系统时，都能通过已有 Passkey 验证同一个用户身份，并允许为不同域名创建独立 Passkey，形成域名退役冗余。**

必须兼容已经注册的用户及其现有 Passkey，不强制迁移、不要求重新注册账号。

## 二、用户与 Passkey 数据模型

### 1. 一个用户可以关联多把 Passkey

这是不可改变的核心要求：

- 全站用户名唯一，同一个用户只保留一条用户记录。
- 用户通过不同域名登录，最终必须关联同一个稳定的 `userId`。
- 一条用户记录允许关联多把 Passkey。
- 多把 Passkey 可以属于不同 RP ID。
- **同一个 RP ID 下也允许关联多把不同 Passkey**，以支持用户使用不同设备、浏览器或密码管理器分别注册。
- 不得将 `(userId, rpId)` 设计为仅允许一条 Passkey。
- 凭据通过 RP ID、Credential ID 等稳定标识区分，不通过备注名区分。

示例：

```text
用户账号
  userId: 123
  username: aaa

  Passkeys:
    - Credential #1
      RP ID: a.com
      备注名: 我的笔记本

    - Credential #2
      RP ID: a.com
      备注名: 备用手机

    - Credential #3
      RP ID: b.com
      备注名: 主力手机
```

应复用、扩展现有的一用户多 Passkey 结构，避免重建用户体系或产生重复用户。

### 2. 不设置唯一的主 RP ID

不同域名创建 Passkey 时，默认使用各自的 RP ID：

| 注册域名    | 新凭据的 RP ID |
| ------- | ---------- |
| `a.com` | `a.com`    |
| `b.com` | `b.com`    |
| `c.com` | `c.com`    |

不得将所有新凭据统一绑定到 `a.com` 或其他某个固定主域名。

原因是某个域名将来可能停止使用。用户提前在其他域名创建独立 Passkey 后，应能不依赖已退役域名继续登录。

保留现有 Passkey 的原始 RP ID，不得通过修改数据库字段来伪装迁移凭据。

## 三、统一用户名与 Passkey 备注名

严格区分以下概念：

| 概念                    | 作用                         |
| --------------------- | -------------------------- |
| `username`            | 用户在前台注册、登录时输入的用户名，例如 `aaa` |
| `userId`              | 本系统内部稳定、唯一的用户身份标识          |
| RP ID + Credential ID | 定位和验证对应 Passkey 凭据         |
| Passkey 备注名           | 仅用于本系统「账号中心」展示、区分和管理不同凭据   |
| 密码管理器中的账号显示名          | 创建 Passkey 时使用用户名，例如 `aaa` |

### 强制要求

1. **Passkey 备注名不能用于数据库账号检索、身份认证或权限判断。**
2. Passkey 备注名不要求唯一，允许多把 Passkey 使用相同备注名。
3. 备注名由用户在 Passkey 创建成功后，于本系统「账号中心」修改。
4. 修改本系统备注名，不应修改 Passkey 的身份、Credential ID、RP ID 或认证能力。
5. 备注名不需要同步到密码管理器。
6. 创建 Passkey 时，WebAuthn 的 `userName`、`userDisplayName` 应使用真实用户名，例如 `aaa`，而不是本系统的 Passkey 备注名。
7. 应认识到密码管理器可能自行决定实际显示方式，系统不能保证所有密码管理器永久显示完全相同的名称，也不能依赖显示名称完成身份验证。

### 正确的登录检索流程

1. 用户在前台输入用户名 `aaa`。
2. 服务端根据 `username` 查找用户记录，取得 `userId`。
3. 查询该用户关联的 Passkey。
4. 根据 RP ID 选择当前认证流程可使用的凭据，包括通过 ROR 获得授权的其他域名凭据。
5. 服务端向浏览器提供对应的 Credential ID 列表。
6. **浏览器根据 RP ID + Credential ID，从可用的密码管理器或认证设备中寻找凭据。**
7. 用户完成验证后，服务端校验签名等认证信息，确认其身份。

不得让浏览器按照用户名或 Passkey 备注名匹配凭据。

## 四、跨域 Passkey 登录

### 1. 优先使用当前域名的 Passkey

例如用户 `aaa` 在 `a.com` 已有凭据，访问 `a.com` 登录时，优先使用该 RP ID 下的有效 Passkey。

如果当前设备无法使用这些凭据，应允许用户选择其他可用认证方式，不应直接判定账号不存在。

### 2. 使用 ROR 实现跨域直接认证

假设 `aaa` 只有 `b.com` 的 Passkey，首次访问 `a.com`。

如果浏览器支持 Related Origin Requests（ROR），应优先通过 ROR，直接在 `a.com` 使用已有的 `b.com` Passkey 验证身份。

要求：

- 按 WebAuthn ROR 规范维护各 RP ID 对其他已绑定可信 Origin 的授权。
- 不强制所有域名共用同一个 RP ID。
- 支持已有不同 RP ID 的凭据。
- 服务端正确选择、验证实际使用的 RP ID 与 Origin。
- ROR 认证成功后，直接登录原用户账号。
- 不因为跨域认证创建第二条用户记录。

ROR 只用于复用已有凭据进行认证，不代表为当前域名创建了新的独立 Passkey。

### 3. ROR 不可用时安全回退

当浏览器不支持 ROR，或无法完成跨域直接认证时：

1. 根据用户已有 Passkey 的 RP ID，选择可用的原注册域名。
2. 引导用户前往该域名完成 WebAuthn 身份验证。
3. 验证成功后，通过安全的一次性认证交接返回原访问域名。
4. 原访问域名为同一 `userId` 建立自己的登录会话。

跨域认证交接应使用短时、一次性、绑定发起会话及目标域名的凭证，并防止重放、伪造和跨账号绑定。

不得直接跨独立主域名共享登录 Cookie，也不得相信前端自行声明的 `userId`。

如果存在多个可用的原注册域名，应支持合理选择或失败回退。

## 五、跨域验证后的独立 Passkey 创建

用户通过其他域名的 Passkey 成功登录当前域名后：

**允许直接完成登录，不强制立即创建新 Passkey。**

同时引导用户为当前域名创建一把独立凭据，以降低原域名未来退役造成的影响。

建议提示文案：

> 你已使用 b.com 的 Passkey 登录账号 aaa。
>
> 建议为该账号再创建一把属于当前域名（a.com）的 Passkey。这样即使 b.com 日后停止使用，也不影响你通过 a.com 登录。

操作按钮：

- `为当前域名创建 Passkey`
- `暂不创建`

其中，**创建提示必须保留“原账号”“另一把 Passkey”“属于当前域名”这三个含义**，不得误写成复制、迁移或重新注册账号。

用户选择创建时：

- 保留原账号 `userId`。
- 新 Passkey 使用当前域名对应的 RP ID。
- 使用原用户名作为密码管理器收到的账号名称。
- 创建成功后，将新 Credential ID 和公钥等信息追加到原用户的 Passkey 集合。
- 不改变其他域名的原有凭据。
- 不要求再次填写用户名或重复注册资料。

WebAuthn 不支持静默复制其他域名的私钥。新凭据需要正常执行注册和用户确认流程。

用户选择「暂不创建」时：

- 本次登录继续有效。
- 不创建新 Passkey。
- 不影响原有凭据。
- 以后可以通过「账号中心」再次执行添加操作。

## 六、已有用户名的注册处理

对于前台「注册账号与 Passkey」：

### 用户名不存在

正常注册用户，并为当前域名创建 Passkey。

应在凭据注册成功并验证后，完成对应的用户及凭据保存，避免留下无有效凭据的半成品账号。

### 用户名已经存在

不得直接创建同名用户。

也不能仅显示 `USERNAME_EXISTS`，使用户既无法登录又无法继续绑定。

应引导用户使用已有 Passkey 验证账号所有权：

- 优先 ROR。
- 不支持时通过原注册域名验证。
- 验证成功后登录原账号。
- 允许用户选择是否为当前域名再创建独立 Passkey。

认证失败、取消或超时，不能取得绑定权限。

## 七、通用账号对话框调整

在现有通用 **「登录 / 移除账号」** 对话框中：

将当前登录的焦点账号右侧文案：

`当前账号`

改为可点击按钮：

**`管理当前账号`**

点击后进入新开发的：

**「账号中心」**

要求：

- 操作对象必须是当前焦点账号，不得误操作其他账号。
- 保留现有账号选择、登录、重新验证与移除本机登录状态的能力。
- 「移除账号登录状态」与「删除账号 Passkey」是不同操作，不能混淆。

## 八、新增「账号中心」

这是面向普通用户的前台页面，不是管理员后台。

### 1. 账号信息

至少展示：

- 用户名
- 用户 ID
- 已绑定 Passkey 数量

### 2. Passkey 列表

必须包含以下字段：

| 字段        | 要求                     |
| --------- | ---------------------- |
| **备注名**   | 本系统内部用户自定义备注，可在创建后修改   |
| **RP ID** | 实际绑定的域名                |
| **创建时间**  | `YYYYMMDD hh:mm:ss`    |
| **最近使用**  | 显示最后一次成功使用时间，尚未使用时明确标识 |

时间数据使用可靠时间戳保存，前端按用户本地时区格式化显示。

不得凭空推断某把凭据属于 Chrome、Samsung Pass 或其他密码管理器；这些内容如需出现，只能作为用户自行填写的备注。

### 3. Passkey 管理功能

至少支持：

- 查看当前用户全部 Passkey，包括其他域名下的凭据。
- 为当前域名新增 Passkey。
- 当前域名已存在 Passkey 时，仍允许新增另一把不同凭据。
- 创建成功后修改备注名。
- 通过稳定凭据标识定位需要修改的记录，不通过备注名定位。

Passkey 移除功能如纳入本次实现，应具有充分的身份验证与确认保护，避免误删最后一个可用登录凭据。

新增 Passkey 属于敏感账号操作。用户已登录但缺乏近期身份验证时，应要求重新验证身份。

同一 RP ID 下创建多把 Passkey 时，应兼容不同认证设备或密码管理器。若具体密码管理器对相同账号的凭据采取复用或覆盖策略，应正确处理，不能把旧凭据意外失效当作新增成功。

## 九、域名动态绑定及退役

系统今后可能新增或停用域名，因此：

1. 不应将域名列表或单一主域名写死为不可替换的认证基础。
2. ROR 授权关系必须对应当前实际启用的可信域名，并考虑浏览器的 ROR 支持范围限制。
3. 新增 `c.com` 时，既有 `a.com`、`b.com` Passkey 保持有效，无需批量迁移。
4. 停用域名前，应识别仅依赖该 RP ID 的用户，提示其提前创建其他可用域名的独立 Passkey。
5. 域名已经彻底下线时，不能假定仍然可以通过该域名的 ROR 授权或跳转完成认证。
6. 用户未建立其他有效凭据时，应有安全的账号恢复策略，不能通过绕过 Passkey 验证处理。

## 十、安全要求

- 跨域绑定必须先证明目标账号所有权。
- 验证 Challenge、签名、Credential ID、RP ID、实际 Origin 及用户验证结果。
- 不得因支持 ROR 而关闭 Origin 校验。
- 跨域验证交接必须短期有效、一次性、绑定账号与目标 Origin，并具备 CSRF、重放和过期保护。
- 不得仅凭用户名、请求中的 `userId` 或 Passkey 备注名授予绑定权限。
- 新增、修改及删除凭据必须具备适当的身份验证和权限检查。
- 保留现有登录会话隔离、账号切换及多账号能力。
- 不能将密码管理器的显示名称当作身份验证依据。
- 新增流程异常不得破坏用户已有 Passkey 或其他账号数据。

## 十一、验收要求

至少覆盖以下场景：

1. `a.com` 首次注册 `aaa`，成功创建用户和 Passkey。
2. `aaa` 已在 `b.com` 注册，首次从 `a.com` 登录，支持 ROR 时直接验证成功。
3. 浏览器不支持 ROR 时，通过 `b.com` 验证后安全返回 `a.com` 并完成登录。
4. `a.com` 登录成功后选择「暂不创建」，仍能正常使用系统。
5. 随后在 `a.com` 为原账号新增独立 Passkey，用户记录数量不变。
6. 用户同一 RP ID 下拥有两把不同 Credential ID 的 Passkey，两把均可正确验证。
7. 在「账号中心」修改 Passkey 备注名，不影响任意域名的登录。
8. 密码管理器收到的注册账号名称使用用户名 `aaa`，不使用本系统的备注名。
9. 账号中心正确显示备注名、RP ID、创建时间、最近使用时间。
10. `USERNAME_EXISTS` 与 `PASSKEY_ACCOUNT_NOT_FOUND` 不再造成已有账号无法跨域登录或绑定的死胡同。
11. 跨域授权被取消、过期、重复使用或篡改时均不能成功绑定。
12. 已有 `b.com` Passkey 不因功能上线而失效或被强制迁移。
13. 新增 `c.com` 后，可以使用已有账号跨域验证，并选择创建属于 `c.com` 的独立 Passkey。
14. 当前域名正常登录、账号切换、多账号保存及移除本机登录状态等原有功能不得退化。
15. 验证某域名的独立 Passkey 后，即使另一个域名不再可用，仍能通过当前有效域名正常登录。

## 十二、开发约束

- 基于 `dev/2611-s2` 的实际实现增量开发。
- 优先复用现有的一用户多 Passkey 结构，不重建账号体系。
- 不要为每个域名创建一套独立用户记录。
- 不要擅自统一所有 Passkey 的 RP ID。
- 不要强制用户迁移或重新注册既有 Passkey。
- 不要把 ROR 当成独立 Passkey 的替代品。
- 不要强制用户在每个新域名登录后立即创建 Passkey。
- 不要将「备注名」写成「用户名」或「Passkey 名称」造成混淆。
- 不要为了实现跨域认证削弱现有身份安全验证。
- 保留原有网盘、账号、登录和权限功能，避免顺带进行无关重构。
- 新增必要的自动化回归测试，并明确报告真实执行结果及尚未验证的环境。
