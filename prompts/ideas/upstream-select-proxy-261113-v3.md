# file-tunnel｜yt-dlp / SNS 多出口代理支持方案

## 一、需求背景

正式环境曾出现 YouTube Music 曲目无法解析、普通 YouTube 内容仍可抓取的问题。起初怀疑 yt-dlp / Deno / EJS 版本、Cookie、播放器客户端或后台执行参数。后来通过同版本、同曲目、不同网络出口的对照测试，发现日本出口可正常解析并下载，而测试过的新加坡出口及韩国服务器本机出口返回 `UNPLAYABLE / Video unavailable`；浏览器直接播放也呈现同样的差异。

因此，需求重点不是修改抓取算法，而是**在后台管理多个网络出口，让 YouTube、YouTube Music 及其他 SNS 的内容获取任务按需选择出口，并在任务首次获取失败时尝试其他节点，提高地区受限内容的抓取成功率**。

## 二、总体方案与改造边界

- 将网络出口管理作为现有 yt-dlp / SNS 抓取流程的**独立逻辑旁路**，不重写或改动原有解析、格式选择、下载、进度及业务处理逻辑。
- **yt-dlp 通过原有的 `--proxy` 参数接入**：仅在命令执行边界传入任务选定的代理配置；其他内容获取方式在各自的请求边界接入同一任务出口策略，避免与核心抓取逻辑耦合。
- 代理支持覆盖**现有 YouTube、YouTube Music 及其他 SNS 内容获取入口**，不只限于 yt-dlp 解析和下载。完善歌曲元数据所需的页面、专辑信息抓取，以及前台将 YT/SNS 链接生成 Markdown 所需的信息获取等，即使使用网页爬虫或其他技术，也应纳入适用范围，并遵循相同的任务出口规则。
- 项目内置 **sing-box** 可执行组件，由 Node 服务统一启动、维护和管理，连接已有的 Trojan-GFW 节点；不要求另装图形客户端，不通过服务器系统代理或启动命令中的 `HTTP_PROXY` 等环境变量切换出口。
- 组件放在 **`tool/sing-box/win-x64/`** 和 **`tool/sing-box/linux-x64/`**。新增、修改、切换节点无需重启 Node 服务，也不得中断正在使用其他节点的抓取任务。
- 页面及专辑信息获取、元数据解析、格式获取、下载、链接生成 Markdown 所需的信息抓取及同任务相关请求，均须遵循**同一任务选定的出口**；不同并发任务可使用不同出口，互不干扰。

## 三、节点管理

- 每个代理节点用**唯一 ID** 标识，名称与备注由用户自行填写；不根据 IP、端口或地区推断节点身份。
- 节点支持 IP / 域名、端口、Trojan 密码、TLS SNI / Server Name、**是否验证 TLS 证书**等配置。
- 支持直连的 Trojan 节点，以及经过 **HAProxy TCP 透传中转**的 Trojan 节点。TLS 保持开启；按节点需要允许关闭证书验证，中转连接地址与 TLS 服务端 SNI 可不同。
- **允许节点的 IP、端口甚至完整配置重复**，不以这些字段去重，只以节点 ID 区分。
- **不检测出口 IP 是否变化，不自动识别地区，不按延迟或地区排序，不根据历史成功记录推荐或优先复用节点。**
- 敏感配置单独存放在受保护的私有数据中，不硬编码到代理管理逻辑，不提交至代码仓库，不在普通日志或管理界面明文暴露密码。
- **“本机直连”也是一种可选出口**。当其参与候选轮询时，与 Trojan 节点地位完全平等；不把它当作最后尝试的“兜底”节点。

## 四、全局设置与节点轮询规则

全局设置应提供以下选项：

- **全局默认出口**：某任务没有单独指定节点时采用；可以是一个 Trojan 节点或“本机直连”。
- **候选节点切换顺序**：二选一——**随机顺序**、**指定顺序**。指定顺序由用户在全局设置中排列；禁止自动插入延迟排名、地区优先级等策略。
- **“本机直连参与节点轮询”复选框**：勾选时，直连作为普通候选，按所选随机或指定顺序参与尝试，可位于任意位置；不勾选时，不进入失败后的自动候选轮询。**该选项不限制用户把“本机直连”单独指定为任务初始出口或全局默认出口。**

**每个任务的执行规则：**

1. **初始出口优先级**：任务单独指定的出口优先；否则使用全局默认出口。每个新任务均重新执行这条规则，绝不继承上一个任务成功使用的出口。
2. **初次尝试失败才切换**：先尝试上述初始出口；未能获取当前任务所需的有效内容或可用媒体格式时，按全局配置的随机顺序或指定顺序，依次尝试其他候选出口；已尝试的出口不重复尝试，直至成功或候选全部失败。
3. **成功判定**：以取得**当前任务所需的有效内容或可用媒体格式**为准；仅网络连通、网页请求成功或取得部分网页信息，不算首次成功。
4. **首次成功后保持出口不变**：该任务后续获取其他格式、下载音视频、封面、补充元数据或重新请求，都继续使用首次成功的出口；**即便后续失败，也绝不自动换节点**。
5. **只约束当前任务**：上述保持行为不是全局锁定；管理员调整全局默认出口或其他任务选择出口，不会改变已开始任务的出口。候选全部失败则报告本任务失败，并记录尝试过的节点 ID 及错误原因。

**示例：** 任务 1 指定节点 A，首次获取失败 → 按设定顺序尝试 B 失败 → 尝试“本机直连”成功（前提是已勾选参与轮询）→ 任务 1 后续所有请求都保持直连，即便后续失败也不再换。任务 2 仍从自己指定的出口（否则全局默认出口）开始。若采用“随机顺序”，只改变首次成功前其他候选的尝试顺序，不改变以上规则。

## 五、Web 管理与验收要求

后台应支持节点增删改查及备注维护、全局默认出口设置、**随机 / 指定轮询顺序**选择、**本机直连是否参与轮询**的复选框；各抓取任务可独立指定初始出口，并显示本任务已尝试及实际采用的节点 ID（或“本机直连”）。

验收重点：原有抓取行为保持兼容；所有相关内容获取入口（包括 yt-dlp 与其他获取方式）遵循统一代理规则；只在首次成功前允许切换，成功后无论后续失败与否都不再切换；同任务的页面信息解析、元数据获取与媒体下载保持相同出口；**本机直连与代理平等参与排序，不能被强制放在最后**；新任务不继承旧任务节点；并发任务互不干扰；节点管理无需登录服务器手动调整代理工具或重启 Node 服务。

> 本文仅记录已确认的需求与架构边界，不预设具体业务代码文件或实现细节。
