
二维码循环闪烁，可以随时扫

盲猜是在每个二维码帧超级帧序号和总帧数

我看懂了。这个点子本质不是“扫码打开链接”，而是：

> **把大屏幕当成单向光学广播信道，把文件切成很多分片，每个分片编码成一个二维码帧，循环播放。观众手机只要持续扫到足够多帧，就能在本地拼回文件。人数从 1 人变成 10 万人，发送端成本基本不变。**

你盲猜的“每个二维码帧带超级帧序号和总帧数”方向是对的。类似的二维码文件传输 demo 已经有人做过：把文件切成约 1KB 小块，转 Base64，每块二维码携带序号、总数、校验码和数据；接收端循环扫描并补齐分片。([Numfeel][1])

这类东西可以叫：

* **QR Multicast**
* **Optical File Broadcast**
* **视觉广播传输**
* **循环二维码分片广播**
* **屏幕到手机的单向离线分发**
* **光学 AirDrop**
* **雷霆二维码**这个名字还真有传播感

它跟你之前提到 file-tunnel 的“可恢复传输任务容器”定位也能接上：二维码广播负责无网络首包下发，后续可以进入隧道恢复、补包、下载和资源管理。

# 一、这个方案最核心的价值

它不是为了大文件，也不是为了替代网络。

它最强的地方是：

```text
一块屏幕
→ 无限接收者
→ 无需登录
→ 无需网络
→ 无需蓝牙配对
→ 无需热点
→ 无需知道对方是谁
→ 只要看得见屏幕就能接收
```

所以它适合的是：

* **小文件**
* **短消息**
* **活动资料**
* **密钥**
* **配置**
* **离线入口**
* **全场同时分发**
* **大规模人群弱网场景**

不适合直接发几百 MB 视频。

# 二、最基础协议应该怎么设计

一个二维码帧不要只放“序号 + 总数 + 数据”，最好设计成完整包头。

例如：

```json
{
  "magic": "D2TQR",
  "version": 1,
  "sessionId": "8F3K2A",
  "fileId": "abc123",
  "frameType": "data",
  "codec": "fountain",
  "index": 42,
  "total": 300,
  "payloadEncoding": "base45",
  "payload": "...",
  "crc32": "..."
}
```

但 JSON 太浪费，正式版应使用二进制包头，再 Base45/Base64Url 编码。

更合理：

```text
D2Q1|会话ID|文件ID|总长度|文件名Hash|MIME|帧号|总帧数|CRC|payload
```

二维码循环播放：

```text
0,1,2,3,4,...,N-1, manifest, parity, 0,1,2,3...
```

接收端：

```text
扫到任意帧
→ 识别属于哪个广播任务
→ 按 frameId 填进 bitmap
→ 进度条增长
→ 收齐后校验
→ 解压/解码
→ 保存文件
```

# 三、最关键优化：不要只用“固定序号分片”，要用喷泉码

你现在设想的是：

```text
总共 300 帧
必须收齐 0～299
```

问题是现场扫码会漏帧：

* 有人手抖；
* 有人距离远；
* 有人只扫到部分循环；
* 屏幕曝光过曝；
* 摄像头自动对焦；
* 人头遮挡；
* 二维码切换瞬间识别失败；
* 手机扫码频率不同。

如果必须收齐每个固定序号，用户体验会卡在：

```text
已接收 299/300
一直缺第 137 帧
```

所以更好的方案是 **Fountain Code / RaptorQ / LT Code**：

```text
文件切成 K 个源块
每个二维码不是固定块
而是若干源块的随机异或组合
手机只要收集略多于 K 个有效编码块
就能解出完整文件
```

效果是：

```text
不怕漏掉具体某一帧
只要“数量够多”就能恢复
```

这非常适合循环闪烁二维码。

如果先做 MVP，也可以用简单 Reed-Solomon：

```text
原始 100 帧
额外生成 30 帧纠错帧
收到任意 100 帧左右即可恢复
```

但长期看，喷泉码更适合无限循环广播。

# 四、第二个优化：Manifest 帧独立高频播放

不要让手机等很久才知道“这是什么文件”。

应设置一种特殊帧：

```text
Manifest Frame
```

内容包括：

* 文件名；
* 文件大小；
* MIME；
* 缩略图 Hash；
* 总分片数；
* 编码方案；
* 校验 Hash；
* 可选下载 URL；
* 可选隧道短码；
* 活动名；
* 过期时间；
* 安全签名。

播放策略：

```text
每 10 帧插入 1 帧 Manifest
每轮开头连续播 2～3 帧 Manifest
```

这样用户刚开始扫，就能看到：

```text
正在接收：演唱会歌词包.zip
大小：380KB
已接收：12%
```

而不是一直“识别中”。

# 五、第三个优化：分层码，不要所有数据塞同一个二维码密度

二维码容量越高，码越密，远距离越难扫。

大屏幕活动场景下，应该区分：

## 远距离模式

* 低密度二维码；
* 大模块；
* 黑白高对比；
* 单帧数据较少；
* 播放更慢；
* 稳定性优先。

## 近距离模式

* 高密度二维码；
* 单帧数据更多；
* 播放更快；
* 适合手机靠近电脑屏幕。

## 舞台大屏模式

* 超大二维码；
* 留白足够；
* 中间可加入 Logo 但不要过度美化；
* 周围加进度环和提示语；
* 帧率不宜太高，否则很多手机扫码器跟不上。

二维码也可以考虑彩色码提升容量，但彩色二维码会受到色偏、屏幕、摄像头、照明和几何畸变影响，研究中确实有通过颜色分类和几何校正提高彩色 QR 可解码率的方案。([arXiv][2])
不过产品 MVP 不建议一上来做彩色码，先黑白稳。

# 六、第四个优化：二维码帧不要用普通微信“扫一扫”作为主接收器

如果只用微信原生扫码，很可能只能扫到某一帧内容，无法持续视频流解码、累计分片和显示进度。

真正好用的体验应该是：

```text
微信扫码第一个二维码
→ 打开小程序
→ 小程序调用摄像头连续识别后续二维码帧
→ 本地累计分片
→ 显示进度
→ 拼回文件
```

也就是说：

## 第一帧/入口码

用于打开小程序：

```text
weapp://...
或小程序码 scene=...
```

## 后续动态码

由小程序内扫码器连续识别：

```text
D2TQR 数据帧
```

体验：

```text
打开微信扫一扫
扫大屏
进入 Drop2Tunnel Mini
继续对着大屏
进度条开始增长
```

这样才能形成“循环闪烁二维码多播下发数据”。

# 七、第五个优化：用“双通道”设计

纯光学可以传完整小文件，但如果现场有网络，可以更聪明。

每个二维码帧可以同时携带：

```text
离线数据分片
+ 在线补包入口
```

手机接收时：

```text
有网络：
  光学接收部分数据
  网络补缺失块
  秒完成

无网络：
  继续扫屏幕
  纯光学收齐

弱网：
  光学兜底
  网络只补少量缺失
```

这样它不只是“没网时传文件”，也是一种**广播加速入口**。

例如：

```text
大屏播放 500KB 活动包
用户手机扫到 60%
现场网络很差
但还能发少量请求
服务器只补缺失 40%
```

对 file-tunnel 来说，可以变成：

```text
二维码广播：
  下发隧道信息、文件 manifest、部分分片

file-tunnel 网络：
  后续补包、缓存确认、跨设备恢复
```

# 十、技术细节建议

## 1. 分片大小

实际可根据场景调参：

```text
远距离大屏：200～600 字节/帧
普通投影：500～1000 字节/帧
电脑屏幕近扫：1000～2000 字节/帧
```

不要盲目追求单帧最大容量。

## 2. 帧率

二维码切换太快，手机扫码器未必跟得上。

建议：

```text
保守：2 fps
普通：4 fps
激进：6～10 fps
```

大屏/远距离建议 2～4 fps。

## 3. 传输速度粗估

假设每帧有效载荷：

```text
600 字节
4 fps
```

速度：

```text
2.4 KB/s
```

一个 300KB 文件：

```text
约 125 秒
```

如果每帧 1200 字节、6 fps：

```text
7.2 KB/s
300KB 约 42 秒
```

所以它适合：

```text
1KB～1MB 的小包
```

不是视频文件分发。

## 4. 压缩

发送前先压缩：

* 文本：gzip/brotli 很有效；
* JSON：很有效；
* 图片/视频：基本没必要；
* 多小文件：先打包 zip。

## 5. 编码

不要直接 Base64 过度浪费。可以考虑：

* Base45
* Base64Url
* 二进制到 QR byte mode
* CBOR/MessagePack
* 自定义紧凑包头

如果扫码库能稳定读取 QR byte mode，效率更好。

## 6. 校验

至少需要：

* 每帧 CRC；
* 全文件 SHA-256；
* Manifest 签名；
* 版本号；
* 会话 ID；
* 文件 ID；
* 过期时间。

## 7. 安全

必须防止大屏被替换成恶意广播。

需要：

```text
广播签名
发送者公钥
活动 ID
过期时间
文件 hash
小程序内显示来源
```

例如手机端显示：

```text
来源：Drop2Tunnel 官方活动屏
签名已验证
```

不要让用户盲目接收任意屏幕数据。

# 十一、和 file-tunnel 怎么结合

我觉得这个点子很适合成为 file-tunnel 的一个新入口：

```text
光学广播入口
```

## 1. 发送端

在 file-tunnel 里选一个文件：

```text
更多 → 生成循环二维码广播
```

选择：

```text
纯离线广播
光学首包 + 网络补包
只广播隧道邀请
只广播文件 manifest
```

## 2. 接收端

手机扫码：

```text
加入临时光学接收任务
```

收完后，自动进入资源管理器：

```text
已通过光学广播接收：xxx.zip
[打开] [保存] [转入隧道]
```

## 3. 与可恢复任务结合

如果没收完：

```text
已接收 63%
```

然后用户离开现场。

如果 QR 帧里包含 file-tunnel 隧道信息，之后可以：

```text
通过网络补齐缺失块
或者下次看到屏幕继续扫
```

这就变成：

> **光学可恢复传输任务。**

非常符合你产品的主线。

# 十三、一个更狠的玩法：二维码不是唯一光学载体

二维码只是最容易落地。

以后可以拓展成：

## 1. 彩色动态码

一帧携带更多数据，但抗干扰难度更高。

## 2. 边缘光带

屏幕中央播放正常视频，边缘一圈闪烁数据条。

## 3. 隐形水印

视频画面中嵌入低可见度数据，手机摄像头持续接收。

## 4. 声音 + 光混合

用超声/音频广播低速信道，二维码做高速帧。

## 5. 多二维码矩阵

一屏同时显示 4 个二维码：

```text
[QR0] [QR1]
[QR2] [QR3]
```

手机能识别几个算几个，提升吞吐。

但 MVP 先不要搞这些，先把普通动态二维码做稳。

# 最终判断

这个点子成立，而且和 file-tunnel 很搭。

它的定位不是：

> 用二维码传大文件。

而是：

> **用屏幕进行无限接收者的短距离小文件广播，并把未完成接收变成可恢复任务。**

最优方向是：

```text
动态二维码循环广播
+ 分片进度
+ Manifest 高频帧
+ 纠错/喷泉码
+ 小程序连续扫码
+ 网络补包
+ file-tunnel 隧道恢复
```

如果做成产品功能，我建议命名为：

> **雷霆二维码广播**

入口文案可以是：

```text
生成雷霆二维码
让附近设备对准屏幕接收文件
```

接收端文案：

```text
保持摄像头对准二维码
文件分片会自动填满
```

这个比普通“扫码下载”更有想象力，因为它解决的是**巨量人群同时接收**而不是单点传输。
