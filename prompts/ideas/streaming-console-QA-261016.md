    ## 三、推荐的整体架构

    我不建议默认把发起端正在播放的视频画面捕获成 WebRTC MediaStream，再实时推送给所有接收端。

    对于你提出的音频、视频、图片、Markdown、TXT，以及上一个/下一个、拖动进度、随机播放等能力，更合适的是：

    媒体数据按需传输 + 串流台状态集中同步。

    串流发起端 A

    创建频道 01、02、03，配置媒体来源与播放列表

    发布频道、控制指令、状态广播

    Node / Socket.IO 串流台状态中心

    频道发现 · 订阅管理 · 控制指令排序 · 播放状态同步 · 权限校验

    共享播控状态

    设备 B

    独立取流

    设备 C

    独立取流

    设备 D

    独立取流

    媒体字节另外通过现有 WebRTC 文件链路、缓存或有权限的 HTTP/Range 接口获取，不必经 Socket.IO 控制消息重复传送。

    这种架构有四个好处：

    1. 同一个串流台的观看状态统一，但不同串流台完全独立。
    2. 接收端可以使用自己的本地缓存，而不必重复从发起端下载同一文件。
    3. 重新订阅、重新连接、切换设备时，可以迅速恢复当前文件及播放位置。
    4. 图片、文档和音视频采用统一的频道机制，但具体预览使用各自的渲染器。

    不过需要强调：当前隧道文件传输虽然支持分块和 Range，但还不能直接等同于浏览器原生 `<video>` 的随机访问式流媒体播放。要实现远端大视频即开即播、任意拖动，仍需要补齐对应的媒体读取适配层。Telegram 网盘已有的 `/stream` 接口则更接近可复用的基础。

    ## 四、最需要设计正确的六个问题

    ### 1. 同频道多用户控制竞态

    这是整个需求最核心的一点。

    假设三个接收端同时观看频道 01：

    - B 点击暂停。
    - C 几乎同时点击播放。
    - D 拖动到 20 分钟。
    - 发起端 A 也点击了下一首。

    如果各浏览器自行更新状态再互相广播，极易出现各设备播放不同文件、进度不一致的问题。

    建议由服务端维护每个频道的唯一权威播放状态：

    ```
    {
      "channelId": "deviceA:channel01",
      "revision": 108,
      "currentItemId": "file-123",
      "playing": true,
      "positionSec": 152.5,
      "playbackRate": 1,
      "updatedAt": 1792112345000
    }
    ```

    控制过程为：

    ```
    接收端发送控制命令
            ↓
    Node 校验权限、顺序处理
            ↓
    更新该频道唯一权威状态
            ↓
    revision 递增
            ↓
    广播给所有订阅者和发起端
            ↓
    所有设备采用新状态
    ```

    接收端不得仅靠收到其他接收端的指令，自行确定最终状态。

    对于播放进度，也不需要每 100ms 广播一次。可以使用基准位置、服务端时间、播放速度来推算，定期校准漂移；发生暂停、拖动、文件切换时立即广播。

    这样能够实现共享播放进度，但不能保证不同网络和解码设备每一帧都绝对同步。这应该是合理的产品边界。

    ### 2. 静音与暂停应该区分「全局」和「本机」

    这里我建议对你的原始需求做一个重要补充。

    | 操作               | 建议作用范围       |
    | ---------------- | ------------ |
    | 播放、暂停、快进、快退、进度拖动 | 影响当前串流台所有订阅者 |
    | 上一个、下一个          | 影响当前串流台所有订阅者 |
    | 静音、取消静音、音量调整     | 默认仅影响本机      |
    | 离开串流台            | 仅影响本机        |
    | 关闭串流台            | 由发起端执行，影响所有人 |

    这样一来，某个用户静音，不会造成所有订阅者突然没有声音。

    而在“监控大爷模式”中，点击“批量暂停”有两种可能的语义：

    - 全局暂停多个频道： 所有订阅这些频道的设备都会暂停。
    - 本机暂停观看： 只停止当前设备播放/取流，不改变频道本身的状态；恢复观看时自动追上频道进度。

    我更建议两者明确区分，避免一个正在看九宫格的用户点击“全部暂停”，结果让其他人的九个频道也全部停下来。

    ### 3. 已关注设备不等于自动拥有查看权限

    当前 `followDevice()` 主要是在本机 IndexedDB 维护关注列表。

    所以你的“可见设备 = 关注的设备，或当前同隧道设备”，可以作为发现规则，但不能单独作为媒体访问授权。

    尤其是跨隧道的关注设备，不能因为接收端单方面关注了发起端，就直接浏览发起端所有媒体。

    我建议：

    - 同隧道：在具备对应读取权限的前提下允许发现，发起端可限制频道可见性。
    - 跨隧道已关注设备：接收端可以查询自己关注的设备公开给自己的频道，但发起端需要明确允许被订阅。
    - 每次订阅、读取媒体、发送控制命令，都由服务端验证权限。

    这是需要补充的一层服务端控制，而不仅是复用当前设备列表。

    ### 4. 不同串流源的持久化语义

    你列出的五种串流来源，我建议这样处理：

    | 来源     | 推荐实现                  |
    | ------ | --------------------- |
    | 单文件    | 固定一个文件引用              |
    | 多文件    | 固定有序播放列表              |
    | 单条隧道记录 | 解析该记录可预览的文件或文本内容      |
    | 多条隧道记录 | 按选定顺序形成播放列表           |
    | 随机隧道记录 | 建立频道共享的随机队列，由服务端决定下一项 |

    尤其要注意：随机不能由每个接收端独立执行。

    否则虽然都订阅频道 01，但 B 随机出歌曲 A，C 随机出歌曲 B，马上违反你的同步要求。

    另外，持久化不能只保存 `fileId`。至少要能定位：

    ```
    文件标识
    所属隧道 / 资源空间
    来源类型
    文件版本 / 内容引用
    播放列表顺序
    播放方式
    ```

    还需要确定一个语义：隧道记录后来被编辑、删除，频道究竟跟随最新记录，还是保持创建时的快照？我建议默认保存明确的资源引用及播放列表快照，来源失效时提示，而不是悄悄播放不相干的资源。

    ### 5. 浏览器的自动播放限制

    这是实际使用中一定会遇到的。

    例如设备 B 订阅了频道 01，发起端 A 开始播放音乐，但设备 B 可能因为浏览器自动播放策略而无法直接有声播放。

    `HTMLMediaElement.play()` 在这种情况下会以 `NotAllowedError` 拒绝。

    [image](https://www.google.com/s2/favicons?domain=https://developer.mozilla.org\&sz=32)

    MDN

    +1



    所以首次订阅可以要求用户主动点击“开始观看/启用声音”，并对播放失败明确提示，而不是误判为连接故障。

    频道的全局状态是“播放中”，不代表每个浏览器实际都已经成功解码、开始发声。

    因此发起端的监控面板最好能看到：

    ```
    频道 01：正在播放 02:32

    设备 B：播放中
    设备 C：缓冲中
    设备 D：等待用户启用播放
    ```

    这比只显示一个全局进度条更有用。

    ### 6. 视频带宽与多画面解码

    不到 20 个用户，控制命令几乎不构成压力，真正的瓶颈在媒体带宽和终端解码。

    假设一个视频平均码率为 4 Mbps：

    | 同时观看人数 | 若由单一设备分别供流 |
    | ------ | ---------- |
    | 1      | 4 Mbps     |
    | 3      | 12 Mbps    |
    | 5      | 20 Mbps    |
    | 10     | 40 Mbps    |

    这只是理想化的媒体净负载估算，不包括协议开销，也没有计算缓存复用。

    监控墙也类似。如果一台电脑同时打开 9 个 1080p 视频，那么视频解码和绘制负担可能比网络还突出。

    因此“监控大爷模式”最好具备：

    - 同时打开 1、4、9 个画面的布局选择。
    - 单独控制每个画面的音量，默认只开启一个画面的声音。
    - 可按需降低非焦点视频的画质或帧率；如果没有转码能力，则不能假定可以真正节省源视频带宽。
    - 允许暂时停止不重要画面的本地解码或取流。
    - 点击某个画面放大，其他画面继续作为小窗或缩略图。

    ## 五、「监控大爷模式」是最有特色的部分

    我认为它不应该只是“同时打开几个播放器”。

    可以把它设计成一个真正的多频道控制工作台。

    串流控制台 · 多画面监控

    4 宫格

    01 · 纪录片

    播放中 · 12:38

    02 · 音乐电台

    正在播放 · 03:25

    03 · 图片轮播

    第 8 / 24 张

    04 · 文档演示

    README.md

    4 个频道 · 3 台来源设备

    布局概念示意，非现有程序界面。

    它还可以有一个非常实用的能力：布局记忆。

    例如你保存：

    ```
    我的监控墙 1

    左上：A 设备 / 01 台
    右上：A 设备 / 02 台
    左下：B 设备 / 01 台
    右下：C 设备 / 03 台
    ```

    下次打开就恢复这些订阅关系及布局。发起设备暂时离线时，只显示离线占位，恢复在线后重新订阅。这样“监控大爷模式”就不只是视觉效果，而是一个日常可复用的工作台。

    第一阶段

    第二阶段

    第三阶段

    监控大爷模式

    ### 需要提前确定的持久化边界

    你希望串流台下次可以复用，我完全赞同。但需要区分：

    持久化串流台配置，不等于串流台永久在线。

    例如发起端是某台笔记本，文件只保存在它本地，那么笔记本关闭 PWA 后，其他设备不应该还能假装该频道正在正常供流。

    第一版可以规定：

    - 串流台配置持久化在发起端，重新上线后恢复发布。
    - Node 维护当前在线频道和订阅关系。
    - 接收端保存订阅与监控墙布局。
    - 只有当媒体来源仍然可访问时，重新上线才能恢复播放。

    ## 八、最终评价

    我支持这个功能立项，但会特别强调以下几点：

    第一，技术路线不要走偏。 核心应是多媒体资源访问、共享播放状态和多设备播控，而不是给所有文件强行套上实时视频推流。只有未来真正需要屏幕直播、摄像头实时画面时，再考虑专门的 WebRTC 音视频推流链路。

     四、三档可见性：我建议这样精确定义
     这是整个功能最重要的新规则。
     可见性 自动发现    新订阅 已有订阅
     公开  可见设备能够发现    满足访问权限即可订阅  正常保持
     仅限邀请    不在普通发现列表展示  必须获得有效邀请/授权 从公开切入此模式时，立即踢出所有当前订阅者
     下线  不再对新设备发布    暂停接受新订阅 保留订阅关系，不踢出，但停止频道供流
     这里的“公开”应限定在你原先定义的可见设备范围，并非互联网匿名用户可以随意访问。即：
     - 已关注设备；
     - 当前同隧道且有适当权限的设备。
     其中“关注”是现有客户端的单方面本地关系，服务端还需要独立的访问授权判断，不能直接把关注当成媒体访问许可。
     可见性切换行为
     公开 → 仅限邀请

     立即撤销当前所有订阅者的访问资格，关闭对应实时媒体连接，并从接收端退出该频道的观看状态。已经订阅过的设备也不能继续使用旧授权。之后必须重新获得邀请才能订阅。
     公开 / 仅限邀请 → 下线

     不删除任何现有订阅关系，接收端保留频道卡片、监控墙位置和订阅配置，但显示“频道已下线”，不再继续接收实时媒体，也不再执行频道控制命令。
     下线 → 公开 / 仅限邀请

     频道重新发布后，原订阅设备可以尝试恢复，但必须重新通过当前权限校验；若频道恢复为仅限邀请，没有有效授权的旧订阅者不能自动重新观看。

     我特别赞同“下线不踢订阅者”。
     因为它把频道变成了一种可长期订阅的资源，而不是每次发起端离线后订阅关系就彻底消失。
     例如家庭电脑长期保存“01 客厅摄影机”，其他设备只要订阅过一次，今后就可以一直保留在自己的监控墙里，电脑重新上线后尝试自动恢复。
     但需要区分：
     频道下线不踢出订阅者 ≠ 下线后仍然可以观看。
     下线只保留订阅关系，不代表实时媒体继续传输。
     五、建议将「订阅关系」与「实时连接」拆开
     这是为了正确实现你所说的三档状态。
     Channel：频道定义
     发起设备、台号、名称、媒体来源、可见性、当前播放状态


     Subscription：持久订阅关系
     哪台设备订阅了哪个频道、是否仍有授权、订阅配置


     ViewerSession：当前观看连接
     是否在线、是否正在播放、WebRTC 连接、缓冲状态


     三者生命周期各不相同：
     - 频道下线：保留 Channel 和 Subscription，关闭 ViewerSession。
     - 从公开改成仅限邀请：保留 Channel，但撤销原有 Subscription 的有效性，关闭 ViewerSession。
     - 设备临时断线：保留 Channel 和 Subscription，等待重新连接。
     - 用户主动取消订阅：删除该设备的 Subscription 与 ViewerSession。
     可见性切换必须由服务端权威处理，不能只在浏览器里隐藏频道。尤其公开转仅邀请时，应立即使旧订阅凭据失效，并关闭现有 WebRTC 媒体传输。

     # Drop2Tunnel 串流控制台功能需求

     ## 2. 串流控制台

     在功能首页的“连接设备”区域右上角汉堡菜单中增加 **“串流控制台”**，支持跨设备发现、订阅、播放和控制多媒体串流台。

     系统允许任意设备同时创建和订阅多个串流台，各串流台独立运行，并支持多台接收设备同步观看同一串流台。

     ### 2.1 串流台创建与管理

     发起端可以创建一个或多个串流台，每个串流台具有台号、名称、媒体来源、播放配置和可见性设置。

     支持以下串流来源：

     1. 单个本地/隧道文件
     2. 多个本地/隧道文件
     3. 单条隧道记录
     4. 多条隧道记录
     5. 随机隧道记录
     6. 单个 Telegram 网盘文件
     7. 多个 Telegram 网盘文件
     8. 随机 Telegram 网盘文件
     9. 摄像头实时直播
     10. 屏幕、窗口或浏览器标签页实时直播

     文件类型支持音频、视频、图片、Markdown、TXT 等可预览资源。

     串流台支持持久化保存，重新打开应用后可以复用原有台号、来源、播放列表和设置。摄像头及屏幕直播重新启动时，仍需遵守浏览器采集权限要求。

     ### 2.2 串流台自动发现

     接收端进入串流控制台时，自动发现来自可见设备的串流台。

     这里的“搜寻”不是输入关键词检索，而是类似 Wi-Fi、蓝牙设备发现列表：自动列出当前可以发现的串流台，并根据频道上线、下线及可见性变化实时更新。

     ### 2.3 可见设备范围

     可见设备包括：

     - 当前设备已经关注的设备；
     - 当前处于同一隧道内的设备。

     频道发现与实际媒体访问仍需经过相应权限校验。

     ### 2.4 串流台订阅

     接收端发现串流台后，可以订阅并打开观看。

     订阅关系应支持持久化，允许下次重新打开原频道。一个设备可以同时订阅多个串流台。

     ### 2.5 接收端控制能力

     **2.5.1 音频、视频文件**

     支持播放、暂停、进度条拖动、快进、快退、静音和取消静音。

     **2.5.2 图片、Markdown、TXT 文件**

     支持相应的内容预览。图片暂不需要额外的播放控制；文本文件可根据实际预览方式支持阅读。

     **2.5.3 多资源串流来源**

     对于多个文件、多条隧道记录、随机隧道记录、多个网盘文件、随机网盘文件等来源，额外支持“上一个”“下一个”。

     随机播放的下一项必须由串流台统一确定，不能让不同接收端各自随机选择。

     **2.5.4 摄像头、屏幕直播**

     支持实时观看、静音及取消静音。直播源默认不提供文件式的进度条拖动、快进或快退。

     ### 2.6 发起端与接收端身份

     任何设备都可以同时作为串流发起端和接收端。

     同一设备允许创建多个串流台，同时订阅来自其他设备的多个串流台，彼此互不排斥。

     ### 2.7 监控大爷模式

     接收端支持启用 **“监控大爷模式”**，将多个串流台以方阵形式平铺到一个屏幕中，同时查看不同设备提供的媒体文件或实时直播画面。

     支持：

     - 对单个串流台静音、取消静音、暂停、播放；
     - 对多个串流台批量执行上述操作；
     - 切换单画面、四宫格、九宫格等布局；
     - 保存并恢复订阅频道和方阵布局。

     应区分“本机暂停观看/静音”和“全局控制串流台”，避免批量操作意外影响其他接收设备。

     ### 2.8 多接收端统一播放状态

     发起端能够查看各接收端的订阅、观看和播放状态，包括当前文件、播放进度、播放/暂停状态及连接状态。

     为解决多个接收端同时操控同一串流台的竞态问题：

     - 同一串流台只维护一份权威播放状态；
     - 所有接收端共享相同的当前文件、播放/暂停状态与目标播放位置；
     - 多文件、多个隧道记录、多个网盘文件和随机来源必须保持相同的当前播放项；
     - 任意接收端执行全局控制操作后，由服务端统一处理并广播最新状态；
     - 断线重连的接收端应重新获取频道权威状态，不得继续使用过期状态。

     不同设备的网络延迟、解码缓冲可能存在差异，因此允许合理的短暂播放偏差，但应持续校准。

     默认静音/取消静音和本机音量属于接收设备自身状态，不强制同步到其他设备。

     ### 2.9 串流台可见性

     发起端可以为每个串流台设置以下三档可见性：

     **公开**

     向符合可见设备范围和权限要求的设备公布串流台，允许发现和订阅。

     **仅限邀请**

     不在普通自动发现列表中公开展示，仅允许获得有效邀请或授权的设备订阅。

     当串流台由“公开”切换为“仅限邀请”时，必须立即踢出当前已订阅的接收端，并撤销旧订阅访问权限。接收端需要重新取得授权才能加入。

     **下线**

     串流台停止对外发布，不接受新的普通订阅，并停止当前串流服务。

     **设为下线时，不得踢出或删除已有接收端的订阅关系。** 接收端应保留该频道及原有布局位置，显示下线状态；频道重新上线后，符合当前权限条件的设备可以恢复观看。

     ### 2.10 技术与兼容性要求

     - 优先复用现有 Socket.IO、WebRTC、文件资产传输、Telegram 网盘流式读取与本机缓存机制。
     - 区分文件点播与实时直播的传输方式，不强制所有媒体统一进行视频编码和推流。
     - 串流台管理、订阅状态和媒体传输尽量独立实现，不破坏已有远程预览、音乐播放器、文件传输、Telegram 网盘等功能。
     - 支持串流台状态恢复、资源不可访问提示、设备离线处理及订阅权限校验。
     - 多频道同时播放应考虑网络带宽、浏览器解码能力及资源释放，避免影响主应用正常交互。

     其中有一个架构决定值得明确：串流台是长期存在的逻辑频道，不等于持续运行的媒体连接。 即使摄像头关闭、文件来源暂时不可用或发起设备下线，频道配置和符合规则的订阅关系仍可以保留。

     这样一来，新增的网盘随机播放、摄像头直播和监控墙，都能够统一纳入同一套频道体系，而不必各自重复开发设备发现与订阅机制。

### 术语对齐

- **串流台**：由一个发起设备创建、供其它设备观看的长期逻辑台；不是某一次播放器打开或媒体连接，观看不以订阅为前提。
- **观看许可**：按公开台进入规则或有效邀请取得的有限观看资格，与订阅记录、当前观看连接分别处理。通用邀请可供多设备多次进入，不因最初未登录接受而锁定在该设备；之后登录账号，相应观看资格也可随账号及订阅入口带到其它设备。定向设备邀请仅限指定设备多次进入，不因登录账号而跨设备扩展，见 Q24／Q33／Q39。
- **订阅关系**：登录用户对某个串流台保存的账号级收藏书签，跟随账号在各设备展示；主体是账号，不存在设备对台的订阅关系。订阅及取消订阅不决定观看资格或是否继续观看，见 Q30／Q31／Q49。
- **全局用户**：由原先局限于网盘的用户身份提升而来，可用于全站身份及付费资格；同一账号登录多台设备，不等于合并各设备的隧道与串流台集合。
- **当前账号**：本机保留的多个已登录账号中，当前界面用于操作的身份；切换当前账号不等于退出其它账号，见 Q42。
- **设备范围**：每台设备各自加入的隧道、可见数据及串流台配置范围；登录同一用户不会自动扩大或同步这个范围。
- **台归属用户**：可选的账号归属，独立于创建设备。已登录后新建的台默认归属当前账号；登录动作不自动认领已有的无归属台。归属用户可以在创建设备随时放弃自己台的归属，不限于创建阶段；在其它设备上仍使用观看者视角，可按 Q34／Q36／Q37 进行全局播控、可见性设置、邀请及观看设备访问管理，不提供 Q35 限定的放弃归属操作。
- **串流台订阅**：登录用户主动为账号添加串流台收藏书签的行为；取消订阅只移除书签。不作为观看前置条件，也不等于购买 Plus 或创作者专属会员。接受邀请不自动订阅。
- **通用邀请**：创建者生成并通过链接／邀请码转交的加入凭据，可供多个设备多次进入，不要求先登录或原本满足同隧道、关注关系。它是独立加入渠道，不自动改变普通设备发现范围；有效期、撤销及可见性切换仍按 Q7／Q20／Q38 处理。
- **定向设备邀请**：创建者通过设备选择器发送给指定设备的邀请，只允许该设备接受及多次进入，转交或登录同一账号均不会让其它设备因此取得加入资格。
- **Plus 订阅**：平台级付费资格，绑定用户而非设备；提供个人自由观看，以及未来存在广告时的免广告能力。同一账号的多设备共用资格，但各端自由观看的节目和进度独立，见 Q40。本轮开通先 Mock。
- **创作者专属会员**：针对某个创作者的另一套会员资格，与平台 Plus 独立；会员身份不自动授予全局播控权限，也不是获得特殊授权的必要条件。
- **特殊授权**：由创建者用户明确授予观看者用户的特定操作权限，按具体串流台分别设置，与 Plus、创作者专属会员身份分别处理；系统不把专属会员资格作为授权或使用这些权限的硬性前提，也不把授权自动扩展到创建者的其它台。
- **当前观看**：某个接收设备此刻接收和展示某个串流台内容的状态。
- **共享播控**：某个串流台共同使用的当前资源、播放/暂停状态和目标播放位置。
- **本机观看控制**：只影响当前接收设备的观看、静音或音量，不修改该台的共享播控状态。
- **已导入资源／节目单**：创建者已确认加入当前串流台的资源及其排列顺序；不等于来源网盘目录、本机文件目录或隧道范围。Q19 已确认导入后按手动调整的顺序播放。
- **节目项**：同一来源在节目单中的一次编排，可独立排序并设置适用的停留时间或播放起始时刻。同一来源可以对应多个节目项，不等于复制媒体文件，见 Q41。
- **随机导入**：在导入阶段，从用户选定的来源范围中随机选取资源，确认后加入当前串流台的资源池。该功能保留，与导入后的播放顺序分开处理。
- **随机播放**：在已导入资源中随机决定播放项。Q19 已确认本期不提供该模式，不能因此取消随机导入。
- **来源资源权限**：原文件所属的网盘、隧道等来源系统中的访问权限。根据 Q1，接收端不必另行持有来源权限；有效串流许可仅提供对该台所选资源的有限观看及必要读取能力，不扩展为来源系统的其它访问权限。Q48 补充覆盖 Markdown 节目源明确引用、且创建者有权读取的隧道资源，不扩展为浏览整个隧道。

### 观看与订阅的最新边界（Q30／Q31／Q49，优先于旧表述）

- 不需要订阅就可以观看。未登录设备也可按公开／邀请规则观看有权访问的台，不能为了观看强制要求先订阅或登录。
- 要订阅，首先必须登录用户。订阅是独立的主动操作，接受邀请或打开播放器不能自动生成订阅记录。
- 订阅仅属于用户账号，类似收藏书签；设备只提供账号订阅列表的展示和操作入口，不形成设备级订阅。取消订阅只是从账号列表移除书签，不撤销观看许可，也不影响已经有权进行的观看。这是已确认原则，不再用跨设备场景重复询问。
- 接受有效邀请取得的是观看许可；此前问答和原型中“接受邀请并订阅”“有效订阅许可”等把二者捆绑的表述，按此更正，不视为额外的观看门槛。
- 订阅记录本身不是观看授权，不能绕过被踢出、改为仅邀请、下线等限制。邀请到期／撤销不追溯撤销已获观看许可，与是否订阅分别处理。
- Q30 确认的可见关系变化规则针对已经取得的观看资格，不应解释成“因为订阅了才有权观看”。Q31 已确认订阅列表跟随用户账号，各设备创建的台、加入的隧道及监控布局仍独立；同步订阅列表不自动扩大设备的发现范围或免除观看许可检查。
- Q33／Q39 确认通用邀请可以跨设备多次使用；先未登录接受、之后再登录，也可通过账号携带订阅及相应观看资格到其它设备，不能要求电脑仅因手机当时未登录就重新索取邀请。定向邀请始终仅限指定设备，不随账号扩展。订阅入口可以承接已有的通用邀请观看资格，但不能把任何订阅记录都当作绕过邀请及访问限制的凭据；接受邀请不自动订阅的规则继续保留。

### Q2：公开台是否允许单向关注者直接订阅观看

**具体场景**：设备 A 将串流台设为公开；设备 B 单方面关注了 A，A 没有关注 B，双方也不在同一隧道。

**待确认问题**：B 是否可以直接发现、订阅并观看 A 的公开台，无需 A 再逐个批准？

**建议答案（已确认）**：是。按接收端视角判断“已关注设备”，发起端将台设为公开，即允许符合该发现范围的设备订阅观看；需要逐个限制接收端时使用“仅限邀请”。观看范围仍受 Q1 限制，不包含来源系统的其它内容。

### 支线 QA：通过隧道 Markdown 消息转交串流邀请

**问（用户补充）**：为了支持把串流邀请转发到隧道，需要增加简单的 Markdown 消息发送能力。Markdown 默认最多预览 10 行，超过部分以毛玻璃效果遮挡，点击后展开完整内容。Markdown 可以引用隧道中的任意 Blob 资源，不引用网盘资源；下载或上传到网盘时，将 Markdown 本身和其中引用的多媒体资源一同打包成 ZIP。该支线处理后回到串流控制台主线。

**整理后的需求**：

- 邀请管理提供“转发到隧道”，用户选择目标隧道后发送一条 Markdown 消息。消息包含串流台邀请说明及可点击的邀请链接，不将发出消息等同于接收端接受邀请。
- **邀请消息与串流源严格分开**：自动生成的邀请包含必要说明、台信息及邀请链接，可以附带媒体缩略图帮助识别内容；缩略图属于邀请预览，不是导入完整媒体。邀请不导入、附带或打包串流播放列表及串流源文件。普通 Markdown 可以由作者自行引用隧道 Blob，这是独立的消息能力，不是发送串流邀请的步骤。
- **通知中心只属于本机**：接收端只查看和处理发给当前设备的通知，不提供切换到其它设备通知中心的功能。发起端只能查看本机发出的邀请及接受状态，不能打开或管理对方的通知中心。
- 隧道增加 Markdown 类型的消息；默认最多预览 10 行，超出部分使用毛玻璃效果遮挡，点击可展开完整 Markdown。

- 普通 Markdown 下载或上传到网盘时，正文及其中引用的多媒体资源一起打包为 ZIP；按钮文案仍为“下载”，不使用“下载 ZIP”。
- 发送邀请的结果使用带背景色、横向铺满内容区域的扁平提示面板，清晰显示发送结果，不使用按钮下方的一行小字代替。
- 本轮将以上要求记录在本文，并补充 v3 交互演示；尚未实现真实消息发送、媒体读取或 ZIP 打包。原型中的消息、通知及文件清单均为演示数据。

### Q4（支线）：隧道内看到邀请消息的设备是否均可接受

**具体场景**：A 将“仅限邀请”串流台的邀请链接转发到一个隧道。B 可以查看该隧道中的这条 Markdown 消息，但 A 没有在定向邀请中单独选择过 B。

**待确认问题**：B 是否可以直接打开消息中的邀请并确认加入，无需 A 再逐个批准？

**建议答案（已确认）**：是。定向设备邀请与转发到隧道是两种独立的邀请渠道；后者允许能查看该消息的隧道设备主动接受邀请，而不要求事先出现在定向邀请名单中。邀请到期及撤销的影响已分别由 Q7、Q20 确认；通用链接转交到其它渠道后的使用范围继续由 Q23 澄清。

**用户结论**：是。并明确纠正：串流邀请只是带链接的通知，不应导入串流源资源；接收端通知中心就是当前设备自己的通知中心，不允许切换到其它设备。

**原型纠正（以最新补充为准）**：邀请包含说明、链接及可选的媒体缩略图，不附带完整媒体，也没有下载或上传到网盘的操作。普通 Markdown 的资源引用、十行预览及打包另设独立演示页。删除“当前查看设备”选择器及发起端“查看接收端通知”操作；各设备视角只在标明“非产品菜单”的原型审核导航中展示，产品界面始终保持本机身份。Q4 的邀请接受入口已启用，不再显示待确认拦截。

**后续补充（用户最新确认，优先于上段原型纠正）**：串流邀请可以附带媒体缩略图，使接收者直观看到内容；发送结果改为有背景色的长扁提示面板。串流邀请消息不显示“下载”“上传到网盘”；这两个按钮只属于普通、无特殊用途的 Markdown 消息，其中“下载”的文案不加“ZIP”。一般 Markdown 的资源引用与打包能力继续保留，不能与邀请通知混为一体。

### Q5（主线，已确认并扩展）：创建者设备离线后，网盘及隧道来源继续服务

**已有说明与未决边界**：本文和 v3 已区分“收起控制台”“串流台下线”“提供设备离线”，并明确台配置持久化不等于媒体始终可用；历史建议倾向先依赖发起设备在线。但对于服务端可以独立读取的网盘文件，创建者完全关闭网页／PWA 后是否仍提供服务，尚未形成用户确认结论。

**具体场景**：A 创建的串流台只使用网盘文件，B 正在观看。随后 A 彻底关闭网页或 PWA；服务端与网盘资源仍然可用，串流台未被主动设为下线。

**待确认问题**：B 是否应继续观看该台，并继续使用共享播放控制，而不因 A 的浏览器退出就中断？

**建议答案（已确认，范围由用户扩展）**：是。网盘及隧道来源继续提供服务，串流台的播放状态和观看许可不依赖创建者的浏览器持续在线。本机文件、摄像头及屏幕仍受实际提供设备和采集状态限制；这一结论不等于将所有来源永久托管。

**用户结论**：是。对于来自网盘、隧道的串流源，不受创建者离线影响。

**生效原则**：不能因为串流台创建者关闭网页／PWA 或设备离线，就让仍然可读取的网盘、隧道来源停止播放、失去共享播控或被当作串流台主动下线。本结论覆盖隧道来源，而非只覆盖网盘。原始来源被删除后按 Q6 处理，不能为了创建者离线续播而制作保底副本；创建者离线与来源删除是不同事件。本节结论优先于历史“所有来源都先依赖发起设备在线”的建议。

**Q10 后用户补充的离线范围**：网盘来源在仍可读取时继续放送；隧道来源中，若订阅者就在文件所在隧道且内容仍可取得，也可继续观看。不能据此承诺所有跨隧道来源在创建者离线后都可独立服务，也不能为了达到这种效果复制文件或把台配置变成账号云端配置库。

### Q6（主线，已确认）：按需加载原始来源，不复制或保留源内容

**具体场景**：A 从自己的网盘文件或隧道记录导入一个视频到串流台，之后删除原网盘文件或原隧道记录，但仍将该视频保留在串流台播放列表中。

**待确认问题**：串流台是否应继续保留导入时的内容并允许播放，而不随原位置的删除一起失效？

**此前建议已被用户否决**：不采用“导入时独立保留内容”的方案，不以串流台为理由增加源内容的保留、锁定或防删除机制。

**用户结论**：否。按普通网页加载资源的方式处理：已经加载到浏览器、缓存或缓冲区仍可使用的内容，可以继续播放；原来源被删除后，下次无法读取或播放就按失效处理。不得偷偷复制副本，以保证来源删除后仍然可播。

**最终约束**：

- 串流台只保存来源定位信息、播放列表和播放设置；选择来源不等于保存一份源文件，也不产生用于阻止来源清理的关系。
- 不因资源被用于串流，就冻结原文件／隧道记录、阻止删除、延长原内容生命周期，或建立保底副本。不得把普通播放缓存变成永久归档来绕过来源删除。
- 网盘或隧道来源仍可读取时，创建者离线不影响服务；原来源删除或确实不可读取时，后续请求按实际结果处理，不能伪装成有可靠副本继续服务。
- 浏览器已有缓存或已解码缓冲能继续使用就允许使用，不承诺删除来源后立即中断已经交付的画面。
- 来源删除时，应处理后续响应的缓存有效性与校验，避免把失效来源继续当作有效资源。缓存响应头不能追溯修改已经发出的响应，也不保证强制撤回浏览器已经拿到的数据；不为了实现立即失效而另行引入缓存追踪或强制清除系统。

本结论优先于本文历史中可能被理解为“保存内容快照”的建议：可以保存列表和来源定位信息，不保存用来抵抗来源删除的媒体副本。

### Q7（主线）：邀请到期是否只限制新加入，不影响已加入设备

**具体场景**：B 已在有效期内接受 A 的串流邀请并获得观看许可。后来这份邀请到期，但 A 没有另行终止 B 的访问，串流台仍在服务；是否另行订阅不作为观看前提。

**待确认问题**：B 是否仍可继续观看，并在断线后通过已有订阅重新进入，而不用再次索取邀请？

**建议答案（已确认，术语按 Q30 更正）**：是。邀请有效期只限制能否使用该邀请新取得观看许可；到期本身不踢出已加入设备，也不追溯撤销其已获观看许可。创建者要终止某设备访问时，应使用明确的访问管理操作，不将其与邀请自然到期混为一谈。本问当时未确定默认邀请时长，具体默认值及设置方式后由 Q26 确认。

**用户结论**：是。

### Q8（主线）：手动踢出是否阻止该设备立即重新加入

**具体场景**：A 手动将 B 从当前串流台踢出，但该台仍然公开，或者 B 仍保存着此前使用的邀请链接。若只断开连接，B 可能立即自动重连或重新点击入口加入。

**待确认问题**：是否阻止 B 凭原订阅、旧邀请或公开发现入口立即重新加入，直到 A 明确重新允许？

**建议答案（已确认）**：是。手动踢出应终止该设备对当前台的访问，并阻止上述立即重入；创建者明确重新允许或重新邀请后才能加入。这一限制只作用于该串流台和被踢设备，不改变其它台或其它设备的访问，也不等同于普通网络断线。

**用户结论**：是。

### Q9（主线）：文件台无人观看时，播放进度是否继续推进

**当前结论（261020-1 修订，取代下列历史答案中的无人推进规则）**：不继续推进。最后一个有效观看实例离开或心跳租约到期后，全台暂停并保存位置；有效观看数从 0→1 时自动启动／恢复。新台第一次有人观看、手动全台停止或播完停止后，都允许由下一次 0→1 自动启动。非循环播完后从节目单开头开始；手动停止后从已选节目起点开始。

- 已有观众且全台暂停／停止时，后来的观众不能解除该状态；不得把任意“进入观看”都实现为全台播放命令。
- 创建者本人观看、收起控制台、暂停本机观看，均保留观看实例；只查看台列表／管理资料不计入观众。界面提供“结束本台观看”释放实例。
- 正常离开立即释放；全部断线以心跳租约失效确认无人（当前实现为 45 秒，15 秒续约），在最后租约期限处冻结，不能无限推进。实例仅驻内存，服务重启后保持最近持久化位置暂停，等待重新进入。
- 客户端自动尝试静音播放；浏览器拒绝时明确提示“开始观看”，不能把浏览器本机限制误报成全台停止。普通观众始终跟随权威全局状态。
- 此次只改变文件台的观众／时钟规则；下述 Plus 自由观看的需求和阶段划分保持原意，第一阶段不扩展会员体系。

**以下为历史问答，涉及“无人继续推进”的结论已被上文修订替代：**

**具体场景**：台处于播放状态，当前视频已经播放到 10 分钟；最后一名接收者关闭观看，没有人执行全台暂停。5 分钟后再有设备进入，该视频尚未到结尾。

**待确认问题**：重新进入时是否应看到约第 15 分钟，而不是停留在最后一名观众离开时的第 10 分钟？

**建议答案（已确认）**：是。台的播放进度独立于是否有人观看，直到明确执行全台暂停、停止或下线。无人观看期间只推进播放状态，不需要为了模拟播放而持续下载、解码或转码视频，也不制作媒体副本。此处讨论文件台；实时采集仍按实际来源状态处理。

**用户结论**：是。另增加业务规则：所有订阅者默认跟随全局播放进度、全局翻看节目单的位置；需要自由翻看或调整进度时，需要购买 Plus 订阅。成为 Plus 的流程先简单 Mock，后续再做支付购买；未来可能有包月、包季、包年及购买点数等形式。

### 新增业务规则：Plus 自由观看与 Mock 资格

- 观看串流台时，普通观看者默认与全局播放进度及全局翻看节目单位置同步，不论是否订阅。
- 自由翻看及自行调整播放进度属于 Plus 能力。
- 本轮只计划 Mock Plus 开通，不接入真实支付；包月／包季／包年和点数是后续可能形式，当前不据此设定价格、扣点规则或账单体系。
- “观看某台”“订阅某台”与“购买 Plus”是不同操作，界面和需求用语应区分；观看不需要先订阅，订阅需要登录用户。
- 此项是对原先“所有接收端始终同一播放项、任意接收端均可全局播控”的业务调整，不能机械保留旧规则。Q10 已确认 Plus 自由操作只影响本人，全局播控由创建者管理；未来创作者授权管理员的细节另定。当前旧原型的播控按钮不能直接视为已经满足新规则。

### Q10（主线）：Plus 自由观看是否只影响本人，全台播控由创建者管理

**具体场景**：普通订阅者正在跟随全局节目和进度，某个 Plus 订阅者希望自行换节目或拖动进度。

**待确认问题**：是否采用以下统一边界：普通订阅者跟随全局，不能自行换节目／拖动进度；Plus 可选择自由观看，所选节目和进度只影响本人；全局节目和进度仍由串流台创建者管理？

**建议答案（已确认）**：是。Plus 提供个人自由观看，而非影响所有人的全台控制权限；默认仍跟随全局，自由观看时可回到全局同步。创建者管理本台的全局播放。既有本机音量、静音、暂停观看不因此自动变成收费项；本机暂停观看后恢复时按所处模式处理。

**用户结论**：是。并补充以下全局用户与会员业务边界。

### Q10 后补充确认：全局用户、设备独立配置与会员体系

**全局用户**：原先只用于网盘的用户概念提升为全局用户。用户身份通用，不意味着其登录的全部设备自动具有相同的隧道、数据或串流台集合。

**设备范围不自动合并**：

- 用户在什么设备加入什么隧道，就由该设备接触相应可见隧道和可见数据。允许同一用户的不同设备各自加入不同的隧道集合。
- 用户示例：A 设备加入 `ABCDE / DEFGH / CCCCC`，B 设备加入 `55555 / 22222 / FFFFF / 000ERK`；登录同一账号不会相互补充加入。
- 串流台同样独立。A 可有“苹果录屏”“摄像头”“2个图片+1首歌曲+10个影片”，B 可有“android录屏”“5个图片+8首歌曲”，不要求保持一致。
- 串流台配置不随用户账号保存到服务器，不能形成登录账号后自动恢复到所有设备的配置集合。
- 用户主动把某个隧道或某个串流台配置同步到另一台设备的功能，只记录为以后开发，不在当前自动实现。
- 为服务已获准的观看者，网盘及隧道来源按 Q5 的最新补充尽可能继续播放。服务器需要的运行信息与完整台配置的保存边界，不可混同，见 Q11。

**Plus 与用户绑定**：

- Plus 资格作用于用户，不绑定某台设备；同一用户在不同设备使用时适用同一资格，但不会因此同步隧道或台配置。
- Plus 支持个人自由翻看节目及拖动串流进度，不影响别人；如果将来有广告，还可免广告。
- Q40 确认同一 Plus 用户在手机、电脑等多设备同时自由观看时，各端选择的节目和进度独立，不因一端操作而改变另一端；各端均可主动返回全局同步。
- 开通流程先 Mock，真实支付以后再做；包月／包季／包年及点数购买为后续可能形式，不在本轮确定计费细则。

**创作者专属会员独立于 Plus**：

- 观看者可以看到串流台创建者，进入其主页，并加入该创作者的专属会员。
- 其与 Plus 的关系类似创作者专属会员与 YouTube Premium 的区别，不能合并为一种资格。
- 创建者用户未来可以向观看者用户授予特权，例如控制全局进度、切换节目；会员身份可以是创建者决定是否授权的业务参考，但按 Q21 的补充，不是系统硬性条件，非会员也可以获得明确授权。
- 等级、具体特权和授权操作以后再细化；不能直接把所有专属会员都设为管理员，也不能因用户购买 Plus 就授予管理他人串流台的权限。实际权限以创建者的授权为准，不用会员身份替代权限判断。

### Q11（主线）：服务器重启后，创建者仍离线的台是否自动恢复

**具体场景**：创建者已关闭网页／PWA，订阅者仍在观看可读取的网盘来源；此时服务器重启。原台配置不作为账号云端配置库保存。

**待确认问题**：是否要求服务器重启后，仍能在创建者没有上线的情况下恢复该台服务？

**建议答案（已确认）**：是。服务端保存恢复当前服务所需的少量运行信息，例如台标识、来源定位、全局节目／进度和授权状态；按设备／台隔离，不形成账号下可跨设备同步恢复的完整配置库，也不保存媒体副本。不能借恢复服务之名擅自把完整台配置存到服务器。

**用户结论**：是。确保不会将串流台相关的必要信息自动同步到其它设备；观看者要能看到串流台由哪个用户创建，为日后的订阅功能铺路。

**补充约束**：

- 服务端保存必要运行信息，只用于原台继续服务及故障恢复；同账号登录另一设备，不自动导入这些信息，不增加那台设备的自有串流台或隧道集合。
- 获准发现或观看时展示必要台信息、创建者用户和播放状态，不等于把台配置同步成接收设备自己的配置。
- 有归属用户的台应向观看者显示该用户及其主页入口；无归属台只显示来源设备、没有创建者用户名是正常状态。归属不能根据当前登录账号临时推断，具体按 Q13 的最新规则处理。
- 用户归属与创建设备范围分别处理，为后续创作者会员提供一致的归属基础，但不因此开放所有设备的配置。
- v3 既有页面主要展示设备名称；这不能替代新的创建者用户展示要求，后续原型整合及实现需补齐。

### Q12（主线）：创作者主页是否仍遵守当前设备的串流台可见范围

**具体场景**：同一创作者在 A、B 两台设备分别发布了公开台。观看者当前能发现 A，不能发现 B。观看者从 A 的串流台进入该创作者主页。

**待确认问题**：主页是否只展示当前设备按可见性／邀请规则能访问的台，而不会因为属于同一个创作者，就自动列出 B 上原本不可见的台？

**此前限制方案已被用户否决**：不采用“创作者主页仍只能展示原本可见设备上的台”的限制。

**用户结论**：否。前提是创建者已经以用户身份登录；观看者应当能通过该创作者看到其在 A、B 设备创建的公开台，同时不破坏原先同隧道设备、已关注设备的可见设备发现规则。

**最终原则**：

- 普通设备发现列表继续按“同隧道设备／已关注设备”筛选。
- 创作者主页是另一条公开台发现途径，可展示同一用户在不同设备发布的公开台，不要求观看者先发现或关注每一台创建设备。
- 主页展示公开台，不等于展示该用户各设备上的全部本地配置、草稿或未开放的台。公开信息可供主动发现和进入，不形成账号配置自动同步。
- 观看者浏览或打开这些台，不因此自动加入来源隧道、关注创建设备或把配置导入为自己的台。

### Q13（主线）：对外发布串流台是否必须登录全局用户

**已有边界**：Q12 明确了已登录创建者的主页发现规则；尚未明确未登录设备是否也可以只凭设备身份发布串流台。

**待确认问题**：是否要求串流台对外发布前先登录全局账号？

**此前强制登录方案已被用户否决**：不要求串流台必须绑定账号才能创建和提供观看。

**用户结论**：创建串流台不需要登录；观看者看到部分台只有来源设备、没有创建者用户名是正常情况。创建后登录账号不会自动认领已有的无归属台，用户可以主动将无归属台设为归属于自己。没有归属任何账号的台，创建设备上的任意已登录／未登录操作者均可控制；远端观看者不会因此获得管理权限，见 Q14。

### Q13 后补充确认：归属、登录与退出的边界

- 登录身份、台归属和创建设备是三个不同概念。设备登录某个账号，不自动把已有无归属台挂到该用户名下，也不替换原台归属。
- 对已有无归属台，用户主动认领后才产生该用户归属；已登录后新建的台按 Q27 默认归属当前账号。不能因为用户名相同或当前会话切换而擅自改已有台的归属。
- 归属用户可以在创建设备随时控制自己的台及放弃其归属，不限于创建时才能选择无归属。放弃后按无归属台规则处理，不改变其创建设备。跨设备仍为观看者视角，具体可执行操作按 Q34；Q35 明确放弃归属仅在创建设备执行。
- 放弃归属时，一并撤销原归属用户针对该台授予观看者的特殊操作权限；此操作不取消普通观看许可或订阅记录，见 Q28 及 Q30 的术语更正。
- 无归属台可只展示创建设备信息；有归属台向观看者展示归属用户，支持其主页及后续创作者会员入口。Q12 的用户主页聚合以实际归属为准，不能把设备上所有台都算作当前登录用户的台。
- 用户从设备退出账号时，当前设备中归属于这个用户的台自动下线，并灰显禁止控制，但仍允许删除。不能通过切换到其它账号或退出到未登录状态重新控制这些有归属台。
- 原归属用户再次登录回这个设备后，才恢复对这些台的控制资格；恢复控制资格不自动等于重新上线放送。
- Q45 明确账号在某设备上已退出或登录失效时，必须由用户本人在该设备恢复登录，不能从其它设备远程完成账号上线。账号在该设备有效在线后，归属用户可从其它设备遥控其台上下线；这不等于把该台配置同步到其它设备。
- 退出仅影响当前设备中归属该用户的台，不自动下线其它设备的台，也不改变无归属台的归属。
- Q42 确认本机可以保留多个账号的登录状态。只要 U1、U2 都没有退出，其在本机各自归属的台均可继续运行，不因当前账号切换而下线；退出其中一个账号时，该账号在本机归属的台全部下线。
- 本机管理端可以显示属于其它账号的台，并明确标注账号归属。当前账号为 U1 时，尝试管理 U2 的台应引导切换到 U2；若 U2 已退出则引导登录，不能直接借用其身份管理。此规则不将其它设备的台配置同步到本机。
- 主动退出账号触发下线，与关闭浏览器／设备暂时离线不同。Q43 确认账号登录状态确实到期失效时，也将其本机归属台下线并锁定；重新登录只恢复控制资格，不自动上线。不把暂时网络异常或设备离线误判为登录失效，Q5 的离线续播和 Q11 的服务恢复也不能绕过已确定的下线状态。
- Q47 确认账号本身下线时，同时结束其在本机各台的摄像头／屏幕采集会话，不影响其它仍在线账号或无归属台；Q46 保留采集的规则只适用于账号在线、台单独下线。本人在源设备恢复登录及必要的采集授权后，台仍不自动上线。
- 删除台不等于删除来源文件，继续遵守 Q6 不复制、不冻结、不延长源内容生命周期的规则。

**具体场景**：B 在与 A 同隧道时订阅 A 的公开台。后来 B 离开该隧道，也没有关注 A；A 没有踢出 B，台仍公开且来源仍可读取。

**待确认问题**：B 是否仍能通过“我订阅的”进入观看，不因同隧道／关注关系消失而自动失去已有订阅资格？

**建议答案（已确认，按用户补充更正模型）**：是。设备可见关系限定普通设备发现列表及通过该列表首次进入的范围；变化后不自动撤销已获观看许可，也不限制 Q12／Q23／Q32 确认的其它进入渠道。踢出、公开转仅限邀请及下线仍按既定规则处理。观看资格保留不等于不可读取的来源因此变得可用，也不表示必须先订阅。

**用户结论**：是。另外明确：订阅和是否可观看是两个概念，不需要订阅就可以观看；要订阅，首先要登录用户。

**对旧模型的纠正**：这不是无关支线，而是观看、观看许可及订阅记录的核心区分。保留此前问答作为历史，但其中把观看许可写成“订阅许可”、把接受邀请写成必须订阅的内容，均以本次补充为准；订阅记录不能作为自动放行或拒绝观看的依据。

### Q31（主线）：订阅列表是否跟随用户账号跨设备共用

**已有边界**：Q30 已确定订阅需要登录；本问提出前，尚未决定订阅记录仅保留在当前设备，还是跟随用户账号。此前明确不自动同步的是各设备创建的串流台配置及加入的隧道集合，不能直接代替订阅列表的决定。

**待确认问题**：同一用户在不同设备登录时，是否可以看到同一份“我订阅的”列表，而各设备自己创建的台、加入的隧道及监控布局仍各自独立？

**建议答案（已确认）**：是。订阅记录跟随用户账号，不因此同步台配置或扩大设备的隧道／发现范围；某台能否在当前设备观看，仍独立检查观看许可。

**用户结论**：是。

### Q32（主线）：公开台的直接观看链接是否可独立进入

**已有边界**：普通设备发现列表按同隧道／已关注设备筛选；Q12 的创作者主页和 Q23 的通用邀请是其它进入途径，Q30 又明确观看不需要订阅。本问提出前，公开台直接观看链接的进入条件尚未单独明确。

**具体场景**：B 拿到一个公开台的直接观看链接，但与创建设备不同隧道，也未关注它；该链接不是包含邀请凭据的邀请链接。

**待确认问题**：B 是否也能直接观看，无需先关注、加入同一隧道或另取邀请？

**建议答案（已确认）**：是。公开台的直接链接可作为观看入口，普通设备发现列表的范围不因此扩大；仅邀请台仍需相应观看许可，被踢及下线限制也不因此绕过。

**用户结论**：是。

### Q33（主线）：登录后接受通用邀请的观看许可是否跟随账号

**已有边界**：Q31 只确认订阅列表跟随账号，不等于观看许可自动跟随；Q24 的定向设备邀请明确只允许指定设备接受。本问单独确认通用邀请的授权归属。

**具体场景**：用户在手机上登录并接受某个仅邀请台的通用邀请，之后在电脑上登录同一账号。原邀请可能已经到期，但原先已获许可未被撤销。

**待确认问题**：该用户是否可以在电脑上使用已获观看许可，无需再次索取邀请？

**建议答案（已确认，按 Q39 补充更正）**：是。通用邀请取得的观看资格可跟随账号；先未登录接受、之后再登录，也可通过账号携带订阅及相应观看资格在其它设备进入。通用邀请本身还可以转交给其它设备多次使用，不能把未登录接受理解成只能在首次接受的设备观看。定向设备邀请仍只作用于指定设备，不因同一账号登录其它设备而扩展，也不因此同步台配置或加入来源隧道。

**用户结论**：是。

**邀请与跨设备观看对照（按 Q39 更正）**：

| 邀请类型 | 接受时的身份 | 观看许可归属 |
| --- | --- | --- |
| 通用邀请 | 已登录 | 当前用户账号，可在其它设备登录后使用 |
| 通用邀请 | 未登录 | 可将通用邀请带到其它设备使用；之后登录，也可随账号及订阅入口携带相应观看资格 |
| 定向设备邀请 | 已登录或未登录 | 被指定的接收设备，不随账号扩展 |

### Q34（主线）：归属用户是否可以跨设备进行全局播控

**已有边界**：各设备创建的台配置不自动同步，Q27 允许归属用户控制自己的台；本问提出前，尚未明确从其它设备登录后控制的视角及操作范围。这里区分远程播控与把台配置导入另一设备。

**具体场景**：用户在 A 创建了归属自己的台，台仍在服务，A 未主动退出账号。该用户在 B 登录同一账号并打开这个台。

**待确认问题**：是否允许用户从 B 对自己的这个台执行全局播放／暂停、切换节目及调整进度，而不把 A 的台配置导入 B？

**此前建议由用户进一步限定**：允许部分跨设备控制，但不把归属用户在 B 端的界面变为创建者视图，具体操作采用下述用户结论。

**用户结论**：用户在 B 端不能将自己在 A 创建、归属自己的台视为本机创建的台，只能以观看者视角发现和打开。界面可以标明创建者是自己、来源设备是 A。允许切换节目、调整全局进度、暂停／播放，以及设置下线／公开／仅邀请；不允许修改导入源、删除串流台等重大管理操作。

**视图与操作边界**：

- A 的台不加入 B 的本机创建台集合，不自动同步或导入其配置；B 仍沿用观看者界面。
- B 可展示“创建者为自己”和真实来源设备 A；归属身份开放本问明确的播控及可见性操作，Q36／Q37 另补充邀请及观看设备访问管理，不等于开放完整创建者管理界面。
- Q27 的随时放弃归属仍成立；Q35 进一步明确，该操作只在创建设备 A 执行，B 的观看者视图不提供。

### Q35（主线）：放弃归属是否只在创建设备执行

**已有边界**：Q27 允许归属用户随时放弃归属，Q34 又限定其它设备上的观看者视角不能修改来源、删除台等重大操作。放弃归属的设备范围需要明确。

**待确认问题**：放弃归属是否也作为重大管理操作，只在创建设备 A 执行，B 的观看者视角不提供这一项？

**建议答案（已确认）**：是。归属用户可在 A 随时放弃归属，B 保留 Q34 明确的播控与可见性操作。

**用户结论**：是。放弃归属仅在创建设备 A 执行，B 的观看者视图不提供该操作。

### Q36（主线）：归属用户在其它设备能否管理邀请

**已有边界**：Q34 允许同一归属用户从 B 的观看者视图进行全局播控及可见性设置；Q35 将放弃归属限制在创建设备 A。本问提出前，尚未明确生成、发送和撤销邀请是否可从 B 执行。

**具体场景**：A 暂时离线，但没有主动退出归属账号，串流台仍可提供观看服务；归属用户已在 B 登录同一账号。

**待确认问题**：同一归属用户在 B 的观看者视图中，是否允许生成、发送及撤销该台的邀请？

**建议答案（已确认）**：是。归属用户可以从 B 生成、发送及撤销该台的邀请，不因此获得修改导入源、删除台或放弃归属等仅限创建设备的操作权限。撤销邀请仍按 Q20 处理，不追溯撤销已经取得的观看许可。

**用户结论**：是。

### Q37（主线）：归属用户在其它设备能否管理观看设备的访问

**已有边界**：Q36 允许归属用户从 B 管理邀请，但撤销邀请不等于终止已经取得的观看许可；Q8 将终止某设备访问及阻止立即重入定义为单独的踢出操作。

**待确认问题**：同一归属用户在 B 端的观看者视图中，是否也允许踢出某个观看设备，以及重新允许被踢设备加入？

**建议答案（已确认）**：是。归属用户可以从 B 踢出该台的某个观看设备，以及重新允许被踢设备加入。作用仍限于所选设备及该台，不扩大为来源资源或完整台配置的管理权限，踢出后的限制继续按 Q8 处理。

**用户结论**：是。

### Q38（主线）：公开转仅邀请时是否使此前生成的邀请失效

**已有边界**：公开转仅邀请会使旧接收端退出并撤销旧观看权限，这一点已明确，不重复询问。邀请链接／邀请码与接受后取得的观看许可分别处理；本问提出前，尚未明确这次切换是否也撤销此前生成、仍在有效期内的邀请。

**具体场景**：创建者曾生成一份通用或定向邀请，后来将公开台改为仅邀请。接收者此时才打开切换前生成、尚未到期的邀请。

**待确认问题**：是否让切换前生成的邀请链接／邀请码也一并失效，需要由创建者重新发出邀请？

**建议答案（已确认）**：是。切换前生成的通用及定向邀请一并失效；切换后使用新生成的邀请取得观看许可，避免旧邀请继续作为加入入口。已有订阅记录仍按 Q30 保留，不将撤销观看权限等同于取消订阅。

**用户结论**：是。

### Q39（主线，原建议已否决）：通用邀请不因最初未登录接受而限制跨设备使用

**原提问前提**：此前把未登录时接受通用邀请取得的观看许可限制为仅属于当前设备，再询问之后登录是否仍保持这一限制。该建议混淆了通用邀请与定向设备邀请，已被用户否决，不作为实施规则。

**具体场景**：手机在未登录时接受通用邀请，获得该设备的观看许可；用户随后在手机登录账号，并在电脑登录同一账号。

**待确认问题**：是否仍保留手机原有的设备观看许可，不因后来登录而自动转成可跨设备使用的账号观看许可？

**此前建议（已否决）**：登录不扩大原设备许可，电脑必须另行接受邀请。不能沿用该建议限制通用邀请的跨设备使用。

**用户结论**：否。通用邀请可以供多个设备多次进入，定向邀请仅限固定设备多次进入。手机接受通用邀请时即使未登录，也可将通用邀请拿到其它设备使用；之后登录账号，通过账号携带订阅到电脑，电脑可以进入。若手机收到的是定向邀请，电脑不能凭该邀请进入，不论是否登录账号。

**生效边界**：

- 邀请类型决定是否限定设备，不能把“接受时未登录”当作通用邀请绑定设备的理由。
- 手机先接受通用邀请、后登录，不阻止相应观看资格随账号及订阅入口在电脑使用；不因这次澄清自动同步创建台配置或来源隧道。
- 通用邀请可多设备多次使用，不等于取消既定的到期、撤销、踢出及公开转仅邀请限制；这些规则继续按 Q7／Q8／Q20／Q38 处理。
- 观看仍不要求先订阅，订阅仍需登录；本次没有要求把接受邀请改为自动订阅。

### Q40（主线）：同一 Plus 用户的多设备自由观看进度是否独立

**已有边界**：Plus 资格跟随用户账号，个人自由观看只影响本人，不改变串流台全局节目及进度。本问提出前，尚未明确同一账号同时在两台设备自由观看时，两边是否共用个人播放位置。

**具体场景**：同一 Plus 账号在手机和电脑同时打开一个有权观看的串流台，两边都进入自由观看模式。

**待确认问题**：手机和电脑选择的节目及播放进度是否各自独立，不因一端换节目或拖动进度而改变另一端？

**建议答案（已确认）**：是。Plus 资格按账号共用，个人自由观看状态按当前设备分别保持；一端换节目或拖动进度不改变另一端，各端仍可主动回到全局同步。

**用户结论**：是。

### Q41（主线）：同一来源能否在节目单中多次编排

**已有边界**：Q15 允许为静态节目设置停留时间、为视频和音乐设置起始时刻，Q19 允许手动排列已导入节目。本问提出前，尚未明确同一来源文件能否重复加入，并在不同位置采用不同播放参数。

**具体场景**：创建者希望同一张图片在节目单前后各出现一次，或将同一个视频分别设置不同起始时刻放在两个位置。

**待确认问题**：是否允许同一来源文件多次加入节目单，每次加入分别设置适用的停留时间或播放起始时刻？

**建议答案（已确认）**：是。每次加入作为可单独排序及配置的节目项，移除其中一项不同时移除其它位置，也不删除来源文件；不因此复制媒体内容。

**用户结论**：是。

### Q42（主线）：切换当前账号是否与退出归属账号分别处理

**核对事实**：现有网盘可保留多个账号的登录状态；选择当前账号与退出某个账号是不同操作。Q13 已确认主动退出归属账号会使该设备上归属于它的台下线并锁定。本问提出前，尚未明确仅切换当前账号时的行为。

**具体场景**：同一设备同时保留 U1、U2 两个账号的有效登录。U1 的串流台已经上线，用户将当前账号切换为 U2，没有退出 U1。

**待确认问题**：是否让 U1 的台继续运行，但 U2 不能因此取得其管理权限；切回 U1 后可继续管理？

**建议答案（已确认并扩展）**：是。仅切换当前账号不触发 Q13 的主动退出下线规则，也不改变台归属或转移控制权；明确退出某个账号时，该账号在本机归属的台全部下线。管理端的跨账号台展示及操作引导采用下述用户补充。

**用户结论**：是。只要 U1、U2 未退出，本机归属于这两个账号的台都可继续运行；某账号退出后，其在本机管理的台全部下线。当前账号为 U1 时，管理端仍可看到 U2 的台，并标注属于另一个账号；尝试管理时，引导切换或登录 U2。

**实施边界**：此处的跨账号可见只指本机创建台的管理列表，不扩展为把 U2 在其它设备创建的台自动导入本机。退出、锁定及重新登录后的恢复继续按 Q13 处理，不将重新登录视为自动重新上线。

### Q43（主线）：登录状态到期失效是否与主动退出一样使本机归属台下线

**已有边界**：Q13／Q42 明确主动退出账号会使该账号在本机的台下线并锁定，单纯切换当前账号不会。Q5 还区分了创建设备暂时离线与串流台主动下线。本问提出前，尚未明确账号没有主动退出、但登录状态确实到期失效时的行为。

**待确认问题**：登录状态确实到期、需要重新登录时，是否也使该账号在本机归属的台下线并锁定？

**建议答案（已确认）**：是。登录状态确实到期失效时，该账号在本机归属的台下线并锁定。重新登录后恢复控制资格，但不自动重新上线；不把暂时网络异常或创建设备离线误当作登录状态已经失效。

**用户结论**：是。

### Q44（主线）：实时台的全台暂停是否暂停供流并在恢复后追当前实时

**核对事实**：历史方案对摄像头／屏幕的播放暂停写着“需定义冻结或停发行为”。本问提出前，澄清只确定实时源没有文件式时间轴、采集必须由本机主动授权，以及本机暂停观看不影响其它设备；这些不能直接决定发起端的全台暂停行为。

**待确认问题**：发起端对摄像头／屏幕台执行全台暂停时，是否保留本机采集预览、暂停向所有观看端送流；恢复后直接显示当前实时画面？

**建议答案（已确认）**：是。全台暂停不等于关闭本机采集，界面应明确显示仍在采集但已暂停对外供流；恢复后追当前实时，不录制或补播暂停期间的内容。“停止本机采集”继续作为独立操作，不把它与本机暂停观看混为一谈。

**用户结论**：是。

### Q45（主线，原提问前提已纠正）：账号在线与串流台上下线分别处理

**原提问**：摄像头／屏幕台下线时，是否同时停止采集，重新上线后必须在创建设备主动重新开始？原建议把台下线统一处理成结束采集，并限制为本机恢复，用户指出不能直接用是／否回答，要求先区分账号登录与台上下线。

**原建议（不采用）**：一律结束采集、每次台重新上线都必须到创建设备操作。不能把此建议当作用户已确认的业务限制。

**用户结论**：

- 远端设备上的账号若已下线，必须由用户本人到该设备操作，使账号重新上线，不能远程操控设备替账号完成登录。
- 只要该账号在所属设备在线，就可以从其它设备遥控它在该设备上的串流台上线／下线，仍按既有归属及操作权限判断，不向普通观看者开放管理权。
- 无须按主动退出或登录失效分别设计远程账号上线流程；账号在原设备恢复在线后，其台即可接受有权限的远程上下线控制。
- 远程将摄像头／屏幕台上线时，应自动恢复采集。这是本次明确的产品目标，不等于已经验证所有浏览器状态下都能无条件重新采集。

**技术核对（2026-10-18，与产品决定分开）**：普通网页每次重新调用屏幕采集 `getDisplayMedia()`，都需要源页面上的用户操作及屏幕选择；屏幕共享许可不能持久保存后静默复用。账号在线不替代这项浏览器要求。依据：[W3C Screen Capture](https://www.w3.org/TR/screen-capture/#dom-mediadevices-getdisplaymedia)、[MDN getDisplayMedia 安全要求](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getDisplayMedia#security)。

因此必须区分“恢复仍有效的已授权采集会话”和“会话已结束后重新请求屏幕采集”。前者可作为远程恢复发送的方案；后者不能在普通网页中仅靠远程上线命令静默完成。摄像头按其已有授权及实际可用状态处理，不把两类授权机制混为一谈。本次只核对现有采集代码及公开规范，未实施或实测串流台自动恢复。

### Q46（主线）：是否保留已授权采集会话以支持远程恢复

**待确认问题**：账号仍在线、只是将串流台下线时，是否保留已授权采集会话但停止对外发送，并在本机明确显示该状态，以便远程将台上线时自动恢复发送？

**建议答案（已确认）**：是。账号仍在线、台单独上下线时复用仍有效的采集会话，台下线期间停止对外发送并在本机明确显示状态，不偷偷录制或补播；用户主动停止共享、关闭采集页面或授权失效后，不能将已结束的屏幕采集当作仍可远程恢复，应显示需要在源设备恢复授权。不扩大普通观看者的控制权限；Q47 进一步确认账号本身下线时结束其采集会话。

**用户结论**：是。

### Q47（主线）：账号本身下线时是否结束其采集会话

**已有边界**：Q46 的采集保留规则以账号仍在线为前提；Q13／Q43 已明确账号退出或登录状态确实到期失效时，其本机归属台下线并锁定。本问不再区分这两种账号下线原因，只确认是否同时结束采集。

**待确认问题**：账号本身下线时，是否一并结束它在本机各台的摄像头／屏幕采集会话，而不只是停止对外发送？

**建议答案（已确认）**：是。保留采集以便远程恢复只适用于账号在线、台单独下线的情况。账号下线后结束其采集使用，不影响其它仍在线账号或无归属台的正常运行；用户本人回到源设备登录并恢复必要的采集授权后，才具备后续远程恢复的条件，台仍不自动上线。

**用户结论**：是。

### Q48（主线）：Markdown 节目源的观看许可是否包含其明确引用的隧道资源

**已有边界**：Q1 允许观看者读取该台所选来源，不要求其另有来源网盘／隧道权限；Markdown 消息支线已允许引用隧道 Blob。本问提出前，尚未明确节目单中的 Markdown 文件引用图片等资源时，这些资源是否一并纳入该节目必要的观看范围。

**具体场景**：A 将一个 Markdown 文件作为串流节目源，其中内嵌了 A 有权读取的隧道图片。B 有该台的观看许可，但没有原隧道的访问权限。

**待确认问题**：B 是否可通过该节目的观看许可显示 Markdown 明确引用的隧道图片等资源，无需另行加入原隧道？

**建议答案（已确认）**：是。仅覆盖创建者有权读取、且该 Markdown 明确引用的隧道资源，不开放整个隧道或其它文件，也不把引用资源另行加入节目单。本问针对 Markdown 节目源，不改变邀请通知只承载说明、链接及可选缩略图的规则。

**用户结论**：是。

### Q49（主线，对误导性提问的纠正）：订阅是账号级收藏书签

**原提问的问题**：此前使用“手机取消订阅后，电脑能否继续观看”的场景，将已经明确的账号级订阅重新放进设备维度讨论，制造了不必要的歧义。早期方案中把设备订阅、观看连接及取消订阅捆绑的表述，也不能作为当前实施依据。

**用户结论**：订阅是账号级别的，不存在设备订阅串流台。取消订阅只是像少了一个收藏书签，不代表不能观看；此前将手机与电脑的观看作为待确认影响，提问具有误导性。

**已确认原则**：

- 订阅及取消订阅只修改账号的收藏书签，各设备展示同一账号列表。
- 观看资格、当前观看连接与收藏书签分别处理；取消订阅不撤销观看许可，也不关闭有权进行的观看。
- 不再使用“设备订阅某台”的模型，也不把这项已明确的原则继续拆成跨设备问题。历史问答保留作背景，以上最新规则优先。
