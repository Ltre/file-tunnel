## 一、目标与定位

### 1.1 核心目标

借助未来向 **npm Registry 发布、通过 `npx` 执行** 的机会，提前建立 Drop2Tunnel 的**独立生产构建和发行体系**，而不是把整个 GitHub 源码目录原样发布出去。

将当前“从源码目录直接启动”逐步变为：

```text
GitHub 开发源码
  ├─ server.js / server/ / client/ / pages/
  └─ tools/ / docs/ / tests/ / 开发资料
          │
          ▼
统一生产构建：筛选、合并、压缩、重写资源引用、校验
          │
          ▼
专用发行目录：dist/npm/
  ├─ 直接可运行的服务端及必要资源
  ├─ 压缩和合理分包的前端资源
  ├─ 极简 npx CLI 入口
  └─ 不含用户数据、开发材料、站点专属配置
          │
          ▼
npm publish（将发行目录作为 npm 包发布）
          │
          ▼
npx -y drop2tunnel@latest
          │
          ▼
直接运行独立发行版，用户无需 Git、源码树或本地构建
```

本计划**第一阶段的重点是“可直接通过 npx 执行的精简发行包”**，不是先开发通用安装器、后台自动更新器、进程管理框架或复杂的版本回滚平台。

### 1.2 两种长期并存的产品形态

| 形态 | 用途 | 特点 |
|---|---|---|
| 源码版 | 开发、测试、调试 | 仍可从 GitHub 工作树运行，保留未经压缩的 JS/CSS 和开发工具 |
| 发行版 | 用户自部署 | 仅含经构建筛选后的运行必需文件，无需 `.git`、开发依赖及源码构建步骤 |

源码版与发行版必须基于**同一套业务实现**，避免复制出两份各自演化的前后端代码。

## 二、当前分支现状与可复用基础

### 2.1 已具备的基础

- `tools/deploy/build.mjs` 已实现生产资源处理，包括前端脚本哈希命名、JS/CSS/HTML 的部分压缩、资源路径改写、Service Worker 应用壳清单、后端必要文件复制及 `release.json` / `build-manifest.json` 生成。
- `tools/deploy/verify.mjs` 已能校验构建结果中的关键静态文件、资源引用与部分脚本语法，可扩展用于 npm 发行包验证。
- `server.js` 已支持通过 `TUNNEL_DATA_DIR` 指定数据目录，很多服务端模块也已接收该统一目录。
- 已有生产依赖、Node 版本要求和部署 Profile，可作为通用构建的参考，但不能把某台机器的 Profile 当作全体用户的默认运行配置。

### 2.2 主要不适配点

| 文件/位置 | 当前状态 | 需要调整 |
|---|---|---|
| `package.json` | `name: instant-tunnel`、`version: 1.0.0`、`main: server.js`，没有 `bin` | 规划正式包名、版本、CLI 入口和发行包 `files` 白名单 |
| `server.js` | `PROJECT_CONFIG_PATH` 固定指向 `__dirname/tunnel.config.json` | 支持独立配置目录与清晰的读取优先级 |
| `server.js` | 未设置环境变量时，数据默认写入 `__dirname/.tunnel-data` | npx 运行必须使用包外的稳定数据位置 |
| `server.js` | `manifest.hosts.json` 从程序目录读取 | 不把开发者自己的域名和 PWA 配置硬编码给所有用户 |
| `server.js` | 使用 `express.static(path.join(__dirname))` | 发行版只暴露允许公开的静态资源，禁止访问内部文件 |
| `tools/deploy/build.mjs` | 构建需指定 `txsl`、`txhk`、`alyhk` 等 Profile | 增加通用、与具体服务器无关的 `npm` 构建目标 |
| `tools/deploy/verify.mjs` | 面向已有部署产物 | 增加 npm 文件清单、独立启动和请求级验收 |
| `start.sh`、`start.bat` | 在当前工作目录检查依赖并直接执行 `node server.js` | 保留原启动方式，同时新增 npx CLI；不靠进入源码目录运行 |
| `vclient/index.js` | 默认从当前工作目录读配置及 `.vclient-data` | 若后续把 VClient 一并纳入发行包，应统一路径策略 |
| `tools/deploy/rollback.sh` | 仍是占位脚本 | 作为未来自动更新阶段的工作，不阻塞第一版发行包 |

**说明：** 当前 `TUNNEL_DATA_DIR` 使用相对路径时会依赖进程启动目录；发行版应明确要求归一化为确定的绝对路径，不能根据 npm 缓存目录推断用户数据位置。

## 三、专用 npm 发行目录

### 3.1 建议结构

```text
dist/npm/
├── package.json                 # 面向 npm 用户的发布元数据与生产依赖
├── bin/
│   └── drop2tunnel.cjs          # npx 命令入口（薄封装）
├── runtime/
│   ├── server.js                # 服务端程序入口
│   ├── server/                  # 实际运行所必需的后端模块
│   ├── pages/                   # 构建后的 HTML
│   ├── assets/                  # 合并、压缩、哈希后的前端 JS/CSS
│   ├── client/                  # 仍需固定路径的图标、Worker、库等资源
│   ├── service-worker.js
│   ├── tunnel-icon.svg
│   ├── build-manifest.json
│   ├── release.json
│   └── docs/                    # 服务端运行时确实会读取的帮助文档
├── README.md
└── LICENSE
```

该结构为**拟议产物**，并非当前仓库已经存在。最终可以微调目录深度，但应保持三个原则：

1. **包内程序只读**：可以从任意工作目录启动，不能因为运行就修改 `node_modules` 或 npx 临时缓存中的内容。
2. **必需资源自足**：生产包不依赖 `.git`、源码根目录、构建工具或开发者本机路径。
3. **包外持久数据**：配置、数据库、密钥、缓存、任务恢复数据和日志不属于升级时可替换的发行文件。

### 3.2 应当纳入与排除的内容

**纳入：** 服务端必要模块、前端编译产物、固定路径静态资源、Web Worker、必要 WASM/第三方运行资源、运行时引用的 Markdown 手册、发布清单、CLI、必要的迁移工具和生产依赖声明。

**排除：** 测试用例、开发需求/日志、Git 历史、部署工作树、特定服务器 Profile、开发环境代理配置、原始未压缩且不会被运行时引用的前端副本、用户私有数据、任何 Token/Secret/Cookie。

不要只根据文件扩展名判断是否需要保留。必须以**实际运行时引用及资源清单**决定；例如部分 `.md` 是后台帮助接口实时读取的，不属于可一律删除的文档。

## 四、前后端构建改造

### 4.1 前端：重点优化

| 内容 | 处理方向 | 特别约束 |
|---|---|---|
| JavaScript | 按页面/功能合理合并、压缩与哈希命名，减少重复加载及请求 | 保持脚本执行顺序、全局函数、DOM 事件、动态加载关系 |
| CSS | 按公共样式和页面样式合并、压缩 | 保持样式优先级、响应式布局和按需页面隔离 |
| HTML | 压缩、插入构建后资源引用 | 不改变初始化时序、内联脚本和页面交互语义 |
| Service Worker | 构建时生成对应版本和 `APP_SHELL` | 正确预缓存已发布资源，防止部署后旧资源 404 或页面混用 |
| 图标、图片、字体、WASM、Worker | 按用途保留、可做无损或兼容性验证后的优化 | 不能简单并入 JS；Worker URL、WASM 读取路径要继续可用 |

应避免“为了合并而合并”：**不强制所有前端 JS 变成一个巨大文件**。建议按首页核心、媒体/串流、网盘、后台等业务边界分组；兼顾浏览器缓存、懒加载、首次访问和 PWA 离线体验。

当前首页存在 `defer` 与动态脚本注入加载模式，构建时重排脚本需格外审慎。Socket.IO 事件名、IndexedDB 名称、`localStorage` Key、DOM ID、内联处理器引用和全局方法属于不可随意压缩重命名的兼容边界。

### 4.2 后端：优先裁剪，不追求单文件

- 以运行时依赖为依据，复制真正需要的 `server/` 模块及少量共用的 `client/` 工具。
- 后端可适度压缩或合并，但**不将打成单个 JS 文件作为第一阶段的强制目标**。
- 重点检查 `__dirname` 相对资源读取、动态 `require`、`node:sqlite`、`sql.js` WASM、WebAuthn 浏览器 bundle、Markdown 手册、服务端生成静态资源及外部程序的执行路径。
- 现有 Telegram 网盘、P2P、WebRTC、S3、串流控制台等核心业务行为保持不变；不要借打包全面重构业务模块。

### 4.3 复用现有构建器

在 `tools/deploy/build.mjs` 上新增通用目标，而不是并行维护两套构建逻辑。可考虑未来命令：

```bash
npm run deploy:build -- --target npm
npm run deploy:verify -- --target npm
```

> 以上为拟议 CLI 接口，当前分支尚未实现。

通用 npm 目标不应提前写入开发者特定域名、监听端口、Nginx 路径、FFmpeg 绝对路径或机器名称。构建阶段需要的 `esbuild`、`terser`、`html-minifier-terser` 由**发布构建环境**承担，而不是由终端用户安装后再编译；如果构建工具缺失，不应静默发布降质包，应在正式 npm 发布流程中严格校验。

## 五、运行时的路径与安全边界

### 5.1 三类目录分离

```text
npm/npx 缓存下的 package/          # 可替换：代码、前端静态文件、内置默认模板
用户持久目录 .../drop2tunnel/data/  # 不可随版本替换：数据库、密钥、上传任务、缓存
用户持久目录 .../drop2tunnel/config/# 用户配置：端口、域名、ICE/TURN、FFmpeg 等
```

可选默认位置如 `$HOME/.drop2tunnel/{data,config}`，并提供显式参数或环境变量覆盖。**具体跨平台默认目录还需实施时确定**；不能依赖包安装位置、`process.cwd()` 或当前 npm 缓存目录。

优先复用 `TUNNEL_DATA_DIR`；为配置提供统一的外部路径（例如 `TUNNEL_CONFIG_DIR`），区分内置模板与用户真实配置；若与旧源码部署共存，应制定清晰的旧数据迁移指引，避免同一实例突然读取另一份空库。

特别保护 `.tunnel-data` 中的 `infra.sqlite`、`disk.sqlite`、WAL、各类密钥、Telegram/SNS 相关配置、传输/上传暂存、分片缓存和串流台状态等内容。旧数据库不能在尚未确认迁移路径时被新版本静默覆盖。

### 5.2 静态资源公开白名单

当前 `server.js` 使用 `express.static(path.join(__dirname))`。发行版要限制允许公开的 `pages/`、`assets/`、固定资源和必要应用壳；服务端 JS、`package.json`、私有配置、备份、凭据及内部目录均不应被直接 HTTP 读取。

正式调整时同时检查既有路由、前端资源绝对路径、Service Worker 虚拟资源、独立页面及 Web Workshop Runtime，避免缩小静态目录后无意造成页面 404。

## 六、npm 包、npx 入口与运行方式

### 6.1 第一阶段只需要薄 CLI

未来 `dist/npm/package.json` 包含 npm 所需字段（`name`、`version`、`bin`、`engines`、`files`、`repository`、`license` 和必要生产依赖）；入口 `bin/drop2tunnel.cjs` 定位包内 `runtime/server.js` 并设置稳定的数据/配置路径后启动。

预期用户命令：

```bash
npx -y drop2tunnel@latest
```

> 包名是否可注册、正式 CLI 名称尚未验证；这是目标体验示例。真正发布发生在 **npm Registry**，`npx` 只是执行工具。

使用这个命令，用户不再需要 `git clone`、`git pull`、手动 `npm ci`、自行构建前端及切换到源码目录。npm 负责包及其依赖获取；CLI 负责以正确路径启动服务。

### 6.2 更新能力的准确边界

- 用户下一次运行带 `@latest` 的命令，可以解析并运行相应的 npm 发布版本（需考虑 npm 缓存及注册表刷新）。
- **npx 不会自动替换已经运行中的 Node 进程**，也不会自行完成数据库备份、迁移、回滚或系统服务重启。
- 第一阶段不承诺“执行一条命令即可无停机替换运行中的服务”。用户自行停止旧进程、重新启动最新版本是可接受的最小闭环。
- 将来才扩展 `install`、`upgrade`、`status`、`doctor`、`rollback` 等完整维护命令；这些不是第一阶段的必要入口。

## 七、发布流程及必要校验

建议将发布过程固定为：

```text
源码分支 / 标准版本号
  → 执行测试
  → 通用生产构建到 dist/npm
  → 检查后端依赖、前端资源路径及 Service Worker 清单
  → npm pack --dry-run / npm pack
  → 在没有源码和 Git 的干净环境安装本地 tarball
  → 从任意目录通过 CLI 启动并执行 HTTP / Socket.IO 验收
  → npm publish（人工确认）
```

必要校验包含：

1. **包完整性**：`npm pack --dry-run` 只包含允许文件，且一个文件不少；无敏感数据、开发代理配置或不必要的大文件。
2. **独立启动**：在完全不存在源码树、`.git` 和构建工具的目录中启动成功，并展示版本和监听端口。
3. **读写持久化**：外部数据、密钥、上传任务等均位于包外，停止进程/重新执行 npx 后仍可恢复。
4. **前端可用性**：首次冷加载、静态缓存、刷新、PWA 安装与升级，JS/CSS/Worker/图标/Markdown 等资源均不缺失。
5. **业务回归**：隧道、Socket.IO、P2P/Relay、媒体预览、串流控制台、Telegram 网盘、S3、协同、下载转码及后台页面的关键路径与源码版行为相同。
6. **安全**：公开 URL 无法读到后端源码、Token、密钥、数据库或包内无关文件；用户配置覆盖包内默认设置的策略明确。
7. **跨平台**：至少检查 Node `>=24.15`；Linux 优先，Windows 启动路径及进程信号处理另行验收；`ffmpeg`、`yt-dlp`、`yt-dlp-ejs`、Deno 等外部依赖缺失时应诊断提示，不应误认 npm 安装失败。
8. **版本一致性**：npm 版本、`release.json`、前端构建 ID 与 Service Worker 缓存版本能够追溯到同一个源码提交及发布版本。

## 九、首轮交付与验收标准

### 9.1 首轮交付物

- 一个能够稳定重复生成的 `dist/npm/` 专用发行目录；
- 发行包自己的 `package.json`、薄 CLI、构建清单和版本信息；
- 压缩/合并且可稳定加载的前端资源；
- 可独立运行的精简后端及必要运行手册/静态资源；
- 外部用户数据与配置目录机制；
- 可执行的打包完整性、启动和关键功能验证步骤。

### 9.2 通过判定

> 在一台满足 Node 要求的干净机器上，不克隆 GitHub 仓库、不运行生产构建工具，只从打包好的 npm tarball 安装/调用 CLI，即可启动 Drop2Tunnel；功能行为与源码版一致。运行时写入数据与配置均在发行包以外；卸载或更换 npm 包版本后，原数据不会因程序目录改变而丢失。

第一阶段的成果是**“能通过 npx 获取、直接运行的独立生产发行版”**。它既为将来的通用一键更新打基础，也直接改善代码和资源的部署结构。

## 十、实施约束与待确认项

- 本计划为需求整理和技术方案，**没有修改源码、没有执行 npm 发布、没有在 GitHub 提交变更**。
- `drop2tunnel` npm 包名及版本号需在正式发布前确认。
- 用户级持久目录的最终跨平台位置和多实例命名规则仍需实施时确定。
- 首轮应尽量不改变业务调用协议、数据结构和正常页面交互；任何影响 IndexedDB、Service Worker、前端脚本顺序或后端文件寻址的改动，都需要专门回归。
- 现有 `tools/deploy` 的服务器专用 Profile 和手动部署能力应继续可用，不应因新增 npm 构建目标而回归。
