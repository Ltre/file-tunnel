    ### PWA 缓存这一点，我建议稍微改变你的实现方式

    你提出：

    > 浏览器没开时，想办法离线把缓存直接注入指定 PWA；做不到再暂存在托盘程序存储区。

    我建议直接把后半种方案定成**标准架构**，而不是 fallback。

    也就是：

    ```text
    Tray Cache
         │
         │ PWA 打开以后
         ▼
    Local Bridge
         │
         ▼
    PWA 自己写入自己的缓存
    ```

    **不要让 Tauri/Rust 进程直接修改 Chrome Profile 内部的 Cache Storage、IndexedDB、OPFS 等数据文件。**

    理论上外部程序当然能够找到 Chromium Profile 目录然后研究里面的 LevelDB/SQLite/Blob 数据，但这不是稳定的浏览器接口，还会涉及浏览器版本变化、数据库锁、Service Worker origin 隔离以及事务一致性。一旦直接操作错了，最糟糕的不是“缓存导入失败”，而是目标 Profile 的站点存储损坏。

    因此应该坚持：

    > **只有 PWA 自己拥有向 PWA 缓存正式写入的权限。Tray Agent 只拥有中转缓存。**

    这样也刚好解决“浏览器根本没启动”的情况。

    例如本地可以保存：

    ```text
    %LOCALAPPDATA%\Drop2Tunnel\
        cache\
            objects\
                <sha256>
            index.sqlite
    ```

    索引关系大概是：

    ```text
    CachedObject
      hash
      size
      mime
      localPath

    CacheBinding
      tunnelId
      transferRecordId
      anchorId
      fileId
      hash
      direction        // sent | downloaded
      completedAt
      pwaImported      // false / true
    ```

    所以即使用户三天都没有打开 PWA：

    ```text
    隧道 A
    记录 R521
    文件 F3
        ↓
    Tray Cache 中仍明确知道
        ↓
    这个文件属于
    A / R521 / F3
    ```

    三天后打开 PWA，仍然能精准塞回**原来的传输记录锚点**。

    我建议 Tauri Agent 常驻一个仅监听 loopback 的本地 bridge：

    ```text
    127.0.0.1:<动态或固定端口>
    ```

    ```text
    Drop2Tunnel PWA
         ↓
    检测 localhost Companion
         ↓
    身份握手
         ↓
    GET pending-cache-bindings
         ↓
    发现：
    tunnel=A
    record=R521
    file=F3
    hash=xxxx
         ↓
    从 localhost 流式读取文件
         ↓
    通过 PWA 自己现有的缓存机制保存
         ↓
    关联到 R521/F3
         ↓
    ACK import-complete
         ↓
    Tray Cache 将 pwaImported=true
    ```

    `localhost`/`127.0.0.1` 在浏览器安全模型中属于 potentially trustworthy 的本地来源，因此这种 PWA ↔ 本机 Companion 的 bridge 是合理路线；当然仍然必须做 CORS、配对令牌、Origin 校验和本机身份验证，不能因为监听 localhost 就无条件信任任何网页。[MDN Web Docs](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Secure_Contexts?utm_source=chatgpt.com)

    PWA 当前用什么：

    ```text
    Cache Storage
    IndexedDB
    OPFS
    自定义 chunk cache
    ```

    就继续调用它自己原本的写入逻辑。

    ## “宿主 PWA / 浏览器 Profile”也应该正式成为一个概念

    你的这个想法是合理的，但内部不要把它绑定成：

    ```text
    Google账号 = xxx@gmail.com
    ```

    而应该绑定：

    ```text
    BrowserHost
      browser = Chrome
      browserExe
      profileDirectory
      pwaAppId
      pwaOrigin
    ```

    例如：

    ```text
    Chrome
    C:\Program Files\Google\Chrome\Application\chrome.exe

    Profile:
    Profile 3

    PWA:
    Drop2Tunnel
    appId = xxxxxxxxx
    origin = https://xxx.xxx
    ```

    因为一个 Chrome Profile 可能没登录 Google，也可能登录多个 Google 账号；真正决定 PWA、Service Worker、IndexedDB 和 Cache Storage 隔离空间的是**浏览器 Profile + Origin/PWA**，不是 Google 账号本身。

    而 Windows 上 Chromium 安装的 PWA 本来就带有 Profile 归属。Chromium 的 Windows PWA 集成甚至明确使用类似：

    ```text
    --app-id=<app_id>
    --profile-directory=<profile_dir>
    ```

    来启动对应 Profile 下的 PWA。[Chromium Git Repositories](https://chromium.googlesource.com/experimental/chromium/src/%2B/220833685fab4880ff3ea55bbbebcedb2a0ff233/docs/windows_pwa_integration.md?utm_source=chatgpt.com)

    因此托盘程序完全可以保存：

    ```text
    宿主浏览器：
    Google Chrome

    宿主 Profile：
    Profile 3

    宿主 PWA：
    Drop2Tunnel
    ```

    然后：

    ```text
    [打开 Drop2Tunnel]
    ```

    不是简单执行：

    ```text
    chrome https://...
    ```

    而是打开**那个 Profile 中安装的那个 PWA**。

    用户层面确实不用讲这么复杂，只需要首次设置时告诉他：

    > 请使用你平时使用 Drop2Tunnel 的 Chrome Profile 打开并安装 PWA。

    然后进行一次绑定即可。

    ## 有一个很重要的“缓存归属”细节

    假设用户：

    ```text
    19:00
    托盘下载 A.zip

    19:05
    打开 PWA
    ```

    PWA 必须看到：

    ```text
    原传输记录
    └── A.zip
        └── 已有本地缓存
    ```

    而不是生成：

    ```text
    托盘下载的文件
    ```

    这样一个新的传输记录。

    所以 CacheBinding 必须以**业务身份**为第一关键字，而不是本地路径：

    ```text
    tunnelId
    transferRecordId
    fileId
    ```

    `anchorId` 可以作为 UI 定位信息，但最好不要让 DOM anchor 本身成为数据库主键。

    也就是说：

    ```text
    业务身份
        ↓
    tunnelId + recordId + fileId

    UI anchor
        ↓
    只是由业务身份计算/映射出来
    ```

    否则以后网页 DOM、列表分页、记录锚点格式一改，托盘缓存绑定就会跟着坏。
