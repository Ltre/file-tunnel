# file-tunnel 安全加固开发指南

适用仓库：`Ltre/file-tunnel`（需求讨论基于 `dev/2611-s1`）。本文落实以下 **4 项需求**；开发前应以目标分支的实际代码为准。不得借机重构现有隧道传输架构。

## 一、统一原则

1. **信任模型已确定**：只有管理员亲自指定的可信账号，才能上传风险类型文件、创建／编辑／发送网页 ZIP。普通用户即使已登录，也默认没有这些权限；无须另行讨论可信用户是否可信。
2. **UI 隐藏只是体验约束，服务端鉴权才是强制边界**。任何权限判断不得相信前端传入的账号、设备 ID、创建者 ID 或 `webZip` 标志。
3. **网页 ZIP 内容继续通过原有 Socket.IO／WebRTC P2P 传输**。服务器只接收内容摘要及元数据、负责权限审核和签章；**不上传整个 ZIP 给服务器**。
4. **网页 ZIP 的两套签名机制完全独立**：一套保护可信发布与内容完整性，一套保护创建者和协作者的编辑权限。名称、密钥、用途、API、验证逻辑、注释与文档均不可混用。

## 二、需求 1：后台用户管理与风险文件权限

新增 `/admin` 下的「用户管理」页面：展示用户列表、账号状态及逐用户权限开关，管理员可分别保存／撤销以下 3 项权限：

| 权限 | 允许的操作 |
| --- | --- |
| `disk.s3.manage` | 操作该用户网盘的 S3 开关；不得据此获得其他管理权限 |
| `disk.riskyUpload` | 上传风险类型文件到网盘 |
| `webZip.publishEdit` | 创建、发送、编辑网页 ZIP；编辑他人文件仍需文件级协作授权 |

- 新账号三项权限**默认关闭**；仅管理员能够分配。服务端统一鉴权，覆盖网页、HTTP API、S3 协议上传、覆盖／重命名及其他实际上传入口，不能靠前端禁用按钮。
- 风险类型按**规范化扩展名 + 规范化 MIME + 必要时内容识别**综合判断，不能相信客户端 `Content-Type`；至少审查：`html/htm/xhtml/xht`、`svg/svgz`、`js/mjs`、`xml/xsl/xslt`、`mht/mhtml`，以及可能被主动加载的 `css/wasm`。`pdf`、ZIP／网页归档、服务端脚本（如 PHP/JSP/ASP）、`.htaccess`／`web.config` 按实际预览／执行链路分类；**不要简单禁止所有普通 ZIP**。
- 修复现有 `/s3pub` 等静态响应的 MIME 判断漏洞：正确解析带空白及参数的 MIME（如 `text/html ; charset=utf-8`），统一处理 CSP、`Content-Disposition` 和 `X-Content-Type-Options: nosniff`；无风险文件权限的账号无法借扩展名、MIME 或文件覆盖绕过限制。用户上传目录不得成为服务器可执行代码或配置目录。
- 权限变更立即生效并记录操作者与时间。对需要撤销的静态分享链接，不得依赖 `Cache-Control: public, max-age=31536000` 仍能即时撤销；调整缓存策略或明确清理机制。

## 三、需求 2：网页 ZIP 可信发布、防篡改与协作授权

### 2.1 入口与服务端权限

未登录或无 `webZip.publishEdit` 权限的设备，**不加载**以下 3 个 UI 入口：

1. 隧道传输记录汉堡菜单里的 `编辑此网页`；
2. 控制中心的 `🌐` 磁贴；
3. `连接设备` 区域右上角汉堡菜单里的 `🌐 网页工坊`。

新建、发送、编辑、内容替换、转发／复制、跨隧道同步等**所有相关服务端入口**均须再次检查已登录账号与权限，包括可从 Console 手工构造的 Socket.IO 消息。编辑既有 ZIP 时，还必须同时满足原有**创建者／协作者授权**及隧道授权。普通接收者**可以接收和运行验证通过的网页 ZIP**，但不能据此获得创建、编辑或转发权限。

### 2.2 两套签名——强制独立

| 机制 | 代码文件／类型 | 唯一职责 |
| --- | --- | --- |
| **可信发布与防篡改签名戳** | 新建 `server/web-zip-trust-integrity-stamp.js` / `WebZipTrustIntegrityStamp` | 证明服务器曾向有发布权限的账号签发**指定 ZIP 摘要及相关记录**；用于放行流通与运行 |
| **协作编辑授权凭证** | 将 `server/web-zip-credentials.js` 更名为 `server/web-zip-collaboration-credentials.js` / `WebZipCollaborationCredential` | 仅判断创建者与被授权协作者是否可编辑特定文件；**不是内容完整性签名** |

必须分离**签名密钥、用途标识、签发与验证函数**；原协作凭证密钥及已有权限语义应保持兼容。示例函数分别为 `verifyWebZipTrustIntegrityStamp()`、`verifyWebZipCollaborationCredential()`。**严禁用其中一种凭证替代另一种。**

### 2.3 P2P 签发／验证流程

1. **发送端**：对即将发送的 **ZIP 原始完整字节**计算 SHA-256，仅提交摘要和可信的文件／消息／隧道关联信息，请求服务器签发。
2. **服务器**：从已验证会话取得真实 `accountId`，检查 `webZip.publishEdit`、隧道及文件相关权限；签发 `WebZipTrustIntegrityStamp`，至少绑定 `version`、`sha256`、`fileId`、`messageId`、`sessionId`、`accountId`、`issuedAt`、`expiresAt`、`permissionVersion`，并采用规范、无歧义的字段序列化方式及独立签名密钥。
3. **发送端**：将签名戳附在网页 ZIP **传输记录／元数据**上；获得有效签名后才进入原有隧道链路。**ZIP 数据仍走 Socket.IO／WebRTC，不经过服务器签章上传。**
4. **服务端发布入口**：在转发网页 ZIP 发布／编辑事件前，独立核验签名、关联字段、发布权限及撤销状态；无戳、伪造戳、过期戳、字段错配、重放／跨隧道挪用均拒绝，不能仅依赖前端流程。
5. **接收端**：收齐原始 ZIP 后先重算 SHA-256，带摘要及签名戳请求服务器验证；服务端检查签名、各绑定字段、有效期和权限版本，**验证通过后**才能解压、缓存为可执行网页、预览或运行；失败则明确报错并禁止执行。

补充规则：ZIP 字节发生改变（含协作编辑、内容替换）必须重新计算摘要并签章；复制／转发若改变 `messageId` 或 `sessionId`，必须重新签发且转发者具有发布权限；签章过期或权限撤销后的历史记录按权限版本规则失效，不能靠旧戳绕过。所有预览形式及 Service Worker 虚拟运行路径必须遵守同一校验门槛。

**边界说明**：签章类似可信发布证明，确认「服务器审核了发布账号并签发了该 ZIP 摘要」，**不表示服务器读取、扫描过 ZIP 内容**；不能与文件级协作编辑凭证混为一谈。

## 四、需求 3：「安全中心」管理员会话管理

在 `/admin` 新增「安全中心」，展示当前管理员全部有效／可审计会话：**设备型号（可识别则显示）、操作系统、浏览器、最后活动时间、会话有效期、DBSC 是否成功绑定**；建议同时显示登录／绑定时间、最近成功续期时间及当前设备标识。

- 从当前无状态长效管理员 Cookie 改为**服务端登记的独立 `sessionId`**：保存账号、有效期、吊销状态、DBSC 会话／公钥关联及活动信息；所有管理员页面与 API 都必须核对该状态。
- 提供逐会话「踢掉」操作：立即吊销对应会话，拒绝被复制的旧 Cookie，阻断 DBSC 续期，必要时通知当前在线设备退出；允许踢掉自身会话。
- 型号、IP、User-Agent 等仅作**展示／异常辅助**，不得作为抗伪造认证凭证。

## 五、需求 4：管理员 TOTP 登录后强制 DBSC

1. 访问 `/admin` **及任何管理员 API** 都必须具备有效的**已完成 DBSC 绑定的管理员会话**；浏览器不支持、注册失败或绑定失效时，直接拒绝管理权限，**无普通 Cookie 回退**。
2. 管理员 TOTP 验证通过后，只发放短期、**不能访问管理 API** 的绑定初始化状态；立即触发浏览器原生 DBSC 注册。
3. 服务端验证注册挑战与设备密钥持有证明，建立 DBSC 与 `sessionId` 的对应关系，**确认绑定完成后**才启用真正管理员会话；不能仅靠浏览器版本、前端声明或注册请求已发出判定成功。
4. 管理员 Cookie 采用短有效期，并通过 DBSC 持有证明续期；服务端验证签名、会话有效期和吊销状态。建议 `Secure; HttpOnly; SameSite=Strict`、主机限定（可用 `__Host-` 前缀），全站 HTTPS，并核对反向代理的安全配置。
5. DBSC 续期失败、会话被踢或超时均禁止再访问管理功能，不得回落到原有 30 天 Cookie。**DBSC 主要约束续期，短期 Cookie 在失效前仍可能被重放**，因此有效期必须短；设备信息显示不能代替真实 DBSC 证明。

## 六、开发验收（必须覆盖）

- 未授权／匿名账号：三个网页工坊入口不可见；Console 直调 Socket.IO／HTTP 也不能签发、发送、编辑、替换、转发 ZIP，不能上传风险文件或操作 S3 开关。
- 有权限可信账号：正常 S3 上传和网页 ZIP 发布可用；已有创建者／协作者编辑授权不被破坏。
- 修改 ZIP 任意字节、替换摘要／戳、跨记录／跨隧道复用戳、过期／撤权后重放：**服务端及接收端均拒绝**；未验证数据不能从 Service Worker 或直接访问的运行链接绕过执行校验。
- P2P 大文件传输、转发、协同编辑仍可用，**整个 ZIP 不上传服务器**；编辑后能获得新戳，旧戳不再验证新内容。
- 仅通过 TOTP、复制管理员 Cookie 至新设备、伪造 UA／设备指纹、禁用或不支持 DBSC 均无法进入管理后台；已绑定会话正常续期；踢掉后旧 Cookie 与续期均立即无效。
- 测试 MIME 空白／参数变体、扩展名与 MIME 不符、S3 协议入口绕过、静态分享缓存撤销；对 ZIP 解压设置合理的单文件／总量／处理时间上限，避免解压炸弹。

> 备注：独立 Origin／更严格浏览器沙箱、WebAuthn 敏感操作再认证及 FFmpeg 参数限制均是原安全审查提出的**额外纵深防护**，可另立任务，不与这四项已确认需求及两套签名职责混淆。
