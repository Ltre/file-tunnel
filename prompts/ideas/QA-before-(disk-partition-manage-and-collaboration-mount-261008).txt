    ## 1. 齿轮设置：需求本身没问题，但“分区”目前还不够像真正的实体

    UI 位置很明确。现在头部本来就是：

    `更多 / 已分享等 → 刷新 ↻ → 退出 → 最小化 → 关闭`

    所以齿轮直接放在刷新左边最合理。现有代码其实已经有一个“管理分区 / S3”面板，只是入口在账号区域，能力只有：

    新建分区 + 当前分区 S3 配置。

    真正的问题在服务端。

    目前所谓分区的 `diskSpace` 名称，同时承担了：

    **显示名称 + 数据 namespace / scope key。**

    比如 `"我的资料"` 不只是给用户看的名称，很多数据实际拿它作为作用域：

    `userId + diskSpace + file/path`

    而且协同、Share、Static Resource、Operation、Content reference、S3 等不少记录都直接保存 `diskSpace`。

    因此：

    > **“重命名分区”绝不能直接理解成把当前 `diskSpace` 字符串全局替换。**

    这会变成一次危险的 scope migration。

    我建议趁这次正式把分区实体化：

    ```text
    Partition
        partitionId        永久稳定 ID
        ownerId
        scopeKey           永久稳定的内部 namespace
        displayName        用户可修改
        settings
        createdAt
        updatedAt
    ```

    已有分区可以迁移成：

    ```text
    旧 diskSpace = "影音"

    scopeKey = "影音"       // 兼容旧数据，不动
    displayName = "影音"
    partitionId = 新 UUID
    ```

    以后用户把它改成“媒体库”：

    ```text
    scopeKey 仍然 = "影音"
    displayName = "媒体库"
    ```

    这样协同、Content Object、S3、历史 Operation、Share 等都不需要跟着搬家。

    ### 删除分区也有几个没说清楚的地方

    “删除分区”不能等同于删一行 `spaces`。

    它至少会牵涉：

    - Logical Files / directories；
    - Content Object references；
    - 活动协同；
    - 公共分享；
    - Static Resource links；
    - S3 credential / bucket mapping；
    - 未完成 upload / operation / recovery；
    - Content cleanup debt；
    - 分区自身的设置和使用记录。

    特别是 S6 已经是共享 Content Object 模型，所以删除分区应该是：

    ```text
    删除 Logical namespace
    → release Content references
    → 仍被其它 Logical 引用的 Content 保留
    → 0 引用 Content 才进入原有 physical cleanup
    ```

    不能重新退化成“遍历文件删 Telegram message”。

    我建议默认分区 `''` **不允许删除**。是否允许给它改显示名称，可以允许，但内部 scope 仍为 `''`。

    ### “复刻分区”其实可以做得非常漂亮

    S6 现在已经有 Content Object，复刻完全没必要重新上传 Telegram。

    比较合理的是：

    ```text
    源 Partition
        ↓ 一致性快照
    复制目录结构
        ↓
    创建新的 Logical Files
        ↓
    引用原来的 Content Objects
        ↓
    新 Partition
    ```

    也就是说几万个文件也主要是数据库 Logical reference 操作。

    但这里还要明确：**复刻什么，不复刻什么。**

    我的建议是：

    复制：

    ```text
    目录树
    文件名
    MIME
    Logical metadata
    Content Object reference
    用户自定义文件属性
    ```

    不要默认复制：

    ```text
    公开分享
    协同邀请 / 协同成员
    Static Resource 外链
    S3 credential
    正在运行的任务
    历史 Operation
    审核工作流状态
    ```

    至于后面第二项新增的“协同挂载点”，复刻分区时最好做成一个选项：

    `同时复刻协同挂载点`

    默认关闭。即使开启，也只是复制 mount reference，不复制别人文件。

    # 2. “把别人整个协同编辑页挂载进自己网盘”——我认为很有价值

    而且它比现在单独进入 `/disk-collab/...` 页面有用得多。

    应该新增一层：

    ```text
    Collaboration Mount
    ```

    例如：

    ```text
    我的网盘
    └── 项目
        └── 张三共享工程    ← mount point
              ↓
            collaborationId = C123
              ↓
            owner=张三
            diskSpace=工作
            root=/开发/工程A
    ```

    你的目录里只存一个 **Mount Record**：

    ```text
    mountId
    ownerId                 // 挂载者
    localPartitionId
    localParentPath
    displayName

    collaborationId
    createdAt
    ```

    不要保存一个可以独立信任的：

    ```text
    remoteOwnerId
    remoteDiskSpace
    remotePath
    ```

    作为授权依据。

    这些都必须每次通过：

    ```text
    collaborationId
    → 当前 collaboration record
    → ownerId / diskSpace / root / current member
    ```

    重新解析。

    这样对方把协同根目录重命名/移动后，现在已有的 `relocateDirectory()` 机制更新 collaboration target，挂载仍然有效。

    # 3. 最重要的边界：挂载进去，但不能“合并 namespace”

    比如用户说：

    > 挂载到某个分区。

    我建议语义必须是：

    ```text
    目标分区根目录
    └── 某协同项目
    ```

    而不是：

    ```text
    把协同根目录里面的东西直接平铺进目标分区根目录
    ```

    后一种会立刻产生：

    ```text
    本地 A/
    远程 A/

    本地 a.txt
    远程 a.txt
    ```

    还会出现更危险的问题：

    “删除当前目录”到底删本地的，还是顺便递归删掉别人的？

    所以必须保证：

    > **每个 collaboration mount 都是明确的 namespace boundary。**

    即使挂在分区根，也必须表现为一个独立目录项。

    ---

    # 4. 你担心的“嵌套目录污染”确实是核心风险

    我建议第一版直接规定：

    > **Mount 只能建立在自己的原生目录中，不能建立在另一个 Mount 内部。**

    例如：

    ```text
    我的文件/
        A/
            [协同项目1]   ✅
    ```

    可以。

    但是：

    ```text
    [协同项目1]/
        子目录/
            [协同项目2]   ❌
    ```

    先禁止。

    因为第二种意味着在“别人 namespace 的一个目录”里插一个只属于你自己的虚拟节点。

    此时：

    - 对方看不到；
    - 你看得到；
    - 对方改名；
    - 对方删除父目录；
    - 你移动父目录；
    - 全局搜索；
    - recursive delete；
    - S3 LIST；

    都会开始出现 overlay filesystem 才有的复杂语义。

    收益暂时远小于风险。

    # 5. “删除挂载点”和“删除协同里的目录”必须是两个完全不同的操作

    这是 UI 上必须特别明显的。

    例如：

    ```text
    我的网盘/A/[张三项目]
    ```

    对 `[张三项目]` 本身执行：

    > 移除挂载

    只能删除自己的 Mount Record。

    **绝不能操作张三的数据。**

    但是进入以后：

    ```text
    [张三项目]/src/test
    ```

    删除 `test`：

    这是：

    ```text
    collaboration mutation
    → 张三 owner scope
    ```

    真的会删掉协同内容。

    这两个动作不能都叫“删除”。

    否则迟早出事故。

    ---

    # 6. 父目录递归删除尤其要小心

    例如：

    ```text
    我的目录 A/
        local.txt
        [协同项目]
    ```

    删除 `A` 时应该：

    ```text
    删除 local.txt
    删除 A 本地目录
    解除 [协同项目] 挂载
    ```

    而**绝对不能递归进入 Mount 删除远端内容**。

    所以以后：

    ```text
    getDirectoryTree()
    recursive delete
    directory size
    directory file count
    ```

    都不能再把“视觉上的子项”无脑当成本地目录 descendant。

    Mount 必须是终止递归的边界。

    ---

    # 7. 跨 Mount 边界的 Move，我强烈建议第一版禁止

    例如：

    ```text
    张三协同/a.txt
            ↓ 拖动
    我的网盘/Documents/
    ```

    如果叫 Move，其真正含义就是：

    ```text
    给自己创建一份
    +
    删除张三那份
    ```

    跨 owner、跨 scope，而且两边任何一步失败都会产生很难补偿的状态。

    第一版应该只提供：

    > **复制到我的网盘**

    反方向：

    ```text
    我的网盘/a.txt
    → 张三协同目录
    ```

    也叫：

    > **复制到协同目录**

    而不是 Move。

    S6 的 Content Object 在这里正好可以发挥价值。

    经过明确授权的协同来源已经证明用户拥有读取该文件的权限，所以这种显式：

    ```text
    协同文件 → 我的网盘
    ```

    不需要再让用户下载几百 MB 再上传，也没有必要再走一般“陌生 SHA 命中”的 PoP。

    可以直接：

    ```text
    授权源 Logical File
    → Content Object
    → 创建我的 Logical File reference
    ```

    **0 Telegram 正文流量。**

    同理，把自己的文件复制进可写协同目录，也可以生成 owner scope 下的新 Logical reference。

    ```text
    本地文件 A
    本地文件 B
    协同挂载里的 C
    另一个协同里的 D
    ```

    这时候不能让现有：

    ```text
    批量删除
    批量移动
    ```

    建议 mutation 操作必须先按 namespace 分组：

    ```text
    LOCAL(partition X)

    MOUNT(collaboration A)

    MOUNT(collaboration B)
    ```

    > 一次批量 mutation 的所有项目必须处于同一个 mutation scope。

    混合选择仍然可以：

    ```text
    下载
    复制
    转发到隧道
    ```

    但不能直接“一键移动/删除”。

    # 9. Mount 不应该赋予二次分享权限

    现在一个 collaborator 本来只是：

    ```text
    owner
    → member
    ```

    不能因为他把项目挂到自己的网盘，就突然变成：

    ```text
    owner
    → member
    → member 再分享给第三人
    ```

    因此挂载内容默认应该禁止：

    - 创建普通公共 Share；
    - 创建 Static Resource；
    - 再创建 Collaboration invitation；
    - 通过自己的 S3 credential 对外暴露。

    除非未来明确加入 delegated permission。

    这是一个非常重要的权限边界。

    ---

    # 10. S3 是否看得到 Mount，需要提前决定

    我建议第一版：

    > **S3 / External Disk API 不展示协同 Mount。**

    先只让 Web 网盘 UI 看见。

    原因是传统 S3 client 会认为：

    ```text
    LIST
    COPY
    DELETE
    MOVE
    ```

    全部属于一个普通 bucket namespace。

    如果把协同挂载透明塞进去，像 FolderSync 这样的客户端可能一次 recursive delete 就攻击到别人协同目录。

    以后真想支持，可以做一个显式 option：

    ```text
    Expose collaboration mounts to API
    ```

    并设计只读/可写语义。

    第一版不要透明暴露。

    用户进入 Mount 后：

    `搜索当前目录`

    很好定义，就是 remote collaboration scope 内搜索。

    但是人在自己的分区根目录点：

    `搜索所有文件`

    是否搜进 Mounted collaborations？

    ```text
    scopeKey 永远 ""
    ```

    不要为了“默认分区改名”把 `''` 换掉。

    ---

    ### 分区删除

    删除普通分区应该定义成一个 **Partition lifecycle operation**，而不是 `DELETE spaces row`。

    至少状态建议有：

    ```text
    ACTIVE
    DELETING
    ```

    甚至：

    ```text
    DELETE_FAILED
    ```

    删除开始以后禁止新的：

    ```text
    upload
    mkdir
    copy
    mount
    S3 mutation
    collaboration creation
    ```

    然后清理这个 partition 下自己的 Logical namespace。

    这里要区分：

    ```text
    自己发起的 active collaboration
    ```

    和：

    ```text
    别人 collaboration 的 Mount
    ```

    前者我维持上一答建议：

    > 有自己发起的 active collaboration 时，禁止删除分区，要求先结束 collaboration。

    后者可以直接：

    ```text
    remove mount records
    ```

    因为 Mount 只是自己的指针。

    已有 Share / Static Resource 我建议删除分区时自动撤销，因为 partition 都不存在了，它们已经没有继续存活的合理语义。

    S3 credential 同样应失效。

    Content Object 按 S6 现有 reference 语义释放，不直接删除共享 physical。

    ---

    ## 2. CollaborationMount：它不是目录，而是 Native Namespace 中的一种特殊节点

    这个定义非常关键。

    建议实体：

    ```text
    CollaborationMount {
        mountId

        ownerId             // 谁把它挂进自己的网盘
        partitionId
        parentPath          // 只能是自己的 Native Directory
        displayName

        collaborationId

        createdAt
        updatedAt
    }
    ```

    可以额外记录一些**非授权性缓存**：

    ```text
    lastKnownTitle
    lastSeenAt
    ```

    但不要保存：

    ```text
    remoteOwnerId
    remoteDiskSpace
    remoteRootPath
    role
    ```

    然后长期信任这些字段。

    这些都应该每次通过：

    ```text
    collaborationId
    → current collaboration
    → current grant
    ```

    重新解析。

    ---

    ### Mount 在目录里的表现

    例如：

    ```text
    我的网盘/
    ├── music/
    ├── abc.txt
    └── 项目A
    ```

    其中：

    ```text
    项目A.kind = collaboration_mount
    ```

    它和：

    ```text
    file
    directory
    ```

    是第三种 node。

    也就是说 Native list 最终是：

    ```text
    nodes = directories + files + mounts
    ```

    而不是偷偷把 Mount 塞进：

    ```text
    directories[]
    ```

    这一点非常重要。

    ---

    ### Mount 是“文件式叶节点”

    从 Native Namespace 看：

    ```text
    Mount 没有 native children
    ```

    因此这些 Native 操作：

    ```text
    directory recursive traversal
    directory delete
    directory size
    directory clone
    directory collaboration descendants scan
    S3 LIST
    Static Resource traversal
    Share traversal
    ```

    遇到：

    ```text
    kind=collaboration_mount
    ```

    都必须停止。

    只有用户执行：

    ```text
    open mount
    ```

    才发生一次 namespace switch。

    ---

    ### Mount 的名字

    `displayName` 纯本地。

    例如远端 collaboration 名叫：

    ```text
    《A计划》
    ```

    用户挂进来以后可以命名：

    ```text
    张三项目
    ```

    再改成：

    ```text
    共同开发资料
    ```

    不影响 collaboration owner。

    ---

    ### Mount 的 Move

    只允许：

    ```text
    Native Directory A
    →
    Native Directory B
    ```

    实际上只改：

    ```text
    parentPath
    ```

    但目标 B 必须是 Native Namespace。

    不能：

    ```text
    Mount
    → Foreign Collaboration Namespace
    ```

    ---

    ### 删除 Mount

    逻辑必须叫：

    ```text
    Unmount / 移除挂载
    ```

    执行：

    ```text
    delete CollaborationMount record
    ```

    不执行任何：

    ```text
    remote delete
    collaboration disable
    kick member
    Content reference release
    Telegram cleanup
    ```

    ---

    ### 一个 collaboration 可以挂多次

    我继续建议允许：

    ```text
    /工作/项目A
    /快捷入口/项目A
    ```

    对应：

    ```text
    M1 → C1
    M2 → C1
    ```

    不会产生任何数据复制。

    ---

    ### Mount 本身不产生 Content Object reference

    这条要定死：

    ```text
    Mount C1
    ```

    不是：

    ```text
    把 C1 下所有 foreign Logical File
    逐个复制到我的 namespace
    ```

    所以哪怕对方有十万个文件：

    ```text
    一个 Mount Record
    ```

    就够。

    真正执行：

    ```text
    复制到我的网盘
    ```

    时才：

    ```text
    foreign Logical
    → Content Object
    → new local Logical reference
    ```

    ---

    ## 3. Namespace Resolver：以后任何文件操作先回答“你现在到底在哪个世界里”

    目前网盘大量逻辑隐含假设：

    ```text
    当前 userId
    + diskSpace
    + path
    ```

    就足够定位数据。

    有 Mount 后不够了。

    我建议正式定义一个：

    ```text
    NamespaceContext
    ```

    所有 list/read/mutation 在进入真正 store 前先 resolve。

    至少有两种：

    ```text
    NativeNamespace
    ForeignCollaborationNamespace
    ```

    ---

    ### Native Namespace

    例如：

    ```text
    {
        type: "native",

        viewerId: U1,

        ownerId: U1,

        partitionId: P1,
        scopeKey: "影音",

        path: "A/B"
    }
    ```

    含义：

    > U1 正在操作自己的 P1 分区 `/A/B`。

    这里可以看到：

    ```text
    local files
    local directories
    collaboration mounts
    ```

    ---

    ### Collaboration Namespace

    用户从：

    ```text
    P1:/工作/项目A
    ```

    打开 Mount M1 后，不应该变成：

    ```text
    path = 工作/项目A/src
    ```

    这种伪本地路径。

    应该切换成：

    ```text
    {
        type: "collaboration",

        viewerId: U1,

        mountId: M1,

        collaborationId: C1,

        remoteOwnerId: U2,
        remoteScopeKey: "工作",

        collaborationRoot: "ProjectA",
        relativePath: "src",

        role: "editor",
        grantVersion: 7
    }
    ```

    于是 UI 可以显示：

    ```text
    我的网盘 / 工作 / 项目A / src
    ```

    但后端知道：

    ```text
    前三段是 local navigation context
    最后真正的数据来自 U2 scope
    ```

    这两者不能混为一条真实 path。

    ---

    ### Resolver 的核心职责

    以后任何请求先做：

    ```text
    resolveNamespace(context)
    ```

    回答至少这些问题：

    ```text
    数据真正属于谁？
    哪个 partition/scope？
    路径基准是什么？
    viewer 是谁？
    当前 role 是什么？
    允许什么能力？
    是否位于 Mount 内？
    是否允许跨 boundary？
    ```

    输出可以概念化成：

    ```text
    ResolvedNamespace {
        kind

        viewerId

        dataOwnerId
        scopeKey

        localPartitionId?
        mountId?
        collaborationId?

        rootPath
        relativePath
        effectivePath

        role

        capabilities
    }
    ```

    ---

    ### 最重要：Mount 不是 path translation

    不要做：

    ```text
    /my/A/MountX/foo.txt
          ↓ 字符串替换
    /otherUser/project/foo.txt
    ```

    这种实现。

    应该是：

    ```text
    mountId
    → collaboration authorization
    → remote root
    → relative path
    ```

    每次动态解析。

    否则 collaboration 被：

    ```text
    移动
    重命名
    撤销
    踢人
    改变角色
    ```

    以后，很容易留下陈旧 path 可以越权。

    ---

    ### Mount authorization 每次重新验证

    Mount Record 只证明：

    > 用户以前建立过这个入口。

    它不证明：

    > 用户现在仍有权限。

    所以打开：

    ```text
    M1
    ```

    必须：

    ```text
    collaborations.authorized(C1, viewerId)
    ```

    如果已经被踢：

    ```text
    ResolvedMount {
        status: inaccessible
    }
    ```

    Native UI 仍然显示：

    ```text
    ⚠ 项目A
    协同访问已失效
    ```

    只能：

    ```text
    移除挂载
    ```

    不能继续进入。

    ---

    ### Role 通过 resolver 转成 capability

    不要让每个 route 自己到处写：

    ```text
    if (role === 'editor')
    ```

    建议 resolver 最终给出 capability：

    ```text
    viewer:
        read
        list
        search
        stream
        download

    editor:
        viewer +
        upload
        mkdir
        rename
        moveWithinScope
        replace
        delete
    ```

    双方都没有：

    ```text
    createMount
    createCollaboration
    publicShare
    staticResource
    s3Expose
    partitionAdmin
    ```

    未来即使角色扩展，业务 route 不需要全部重写。

    ---

    ## 4. Mutation Scope Invariant：所有写操作都必须先证明“不会越过 namespace 边界”

    这是四个概念里最关键的一层。

    不要把它理解成：

    ```text
    一个 validateDestinationPath()
    ```

    而应该定义成：

    > 所有会改变 namespace topology 或 Logical ownership 的操作，在执行前都必须计算 Source Scope、Destination Scope 和 mutation type，然后通过统一规则判定。

    建议抽象：

    ```text
    MutationContext {
        actorId

        operation

        sourceNamespace
        sourceNodes

        destinationNamespace?

        topologyImpact
    }
    ```

    服务端统一：

    ```text
    validateMutationScope(ctx)
    ```

    ---

    # 首先定义三类 mutation

    ### A. Intra-Native Mutation

    ```text
    Native → 同一个 Native partition
    ```

    例如：

    ```text
    rename
    move
    mkdir
    delete
    ```

    正常允许，但仍需要做 Mount/Collaboration subtree invariant 检查。

    ---

    ### B. Intra-Collaboration Mutation

    ```text
    Mount C1 内
    →
    仍然是 C1
    ```

    例如：

    ```text
    ProjectA/src/a
    →
    ProjectA/archive/a
    ```

    如果角色是 editor：

    允许。

    这里真正操作的是：

    ```text
    remote owner scope
    ```

    不是 Mount Record。

    ---

    ### C. Cross-Namespace Mutation

    包括：

    ```text
    Native → Collaboration

    Collaboration → Native

    Collaboration A → Collaboration B

    Partition A → Partition B
    ```

    统一原则：

    > **禁止 Move，只允许 Copy。**

    这是最干净的规则。

    ---

    # 5. Copy 与 Move 必须变成两个不同的底层语义

    例如：

    ```text
    Foreign C1/a.mp4
    → Native P1
    ```

    不得内部写成：

    ```text
    move()
    ```

    而应该明确：

    ```text
    copyAcrossNamespace()
    ```

    它：

    ```text
    读取 source authorization
    → resolve source Logical
    → resolve Content Object
    → destination 创建新的 Logical File
    ```

    源 Logical 完全不动。

    ---

    ### Native → Collaboration

    必须：

    ```text
    source read allowed
    destination editor allowed
    ```

    然后：

    ```text
    在 collaboration owner scope
    创建新 Logical reference
    ```

    ---

    ### Collaboration A → Collaboration B

    需要：

    ```text
    A: canRead
    B: canWrite
    ```

    即可：

    ```text
    C1 Logical
    → shared Content Object
    → C2 owner 新 Logical
    ```

    依然没有 Telegram 正文流量。

    ---

    # 6. Topology Invariant：防 Mount / Collaboration 嵌套污染

    这是你刚才补充后最应该正式写成数学不变量的地方。

    定义：

    ```text
    M = 所有 Mount node
    C = 所有 active directory collaboration root
    ```

    要求：

    > 对任意 `m ∈ M` 和 `c ∈ C`，二者在同一个 Native scope 中不能存在 ancestor/descendant 关系。

    也就是永远不能：

    ```text
    CollaborationRoot
    └── ...
        └── Mount
    ```

    也不能：

    ```text
    Directory containing Mount
    ↑
    后来把祖先开启成 CollaborationRoot
    ```

    ---

    ### 创建 Mount 时

    必须验证：

    ```text
    destinationParent
    ```

    不位于任何：

    ```text
    active collaboration root
    ```

    之内。

    因为一旦 parent 在 collaboration subtree：

    ```text
    reject
    ```

    ---

    ### 开启 Collaboration 时

    设目标目录为 A。

    必须验证：

    ```text
    A subtree
    ```

    不存在任何：

    ```text
    CollaborationMount
    ```

    哪怕在十层下面：

    ```text
    A/a/b/c/d/Mount
    ```

    也拒绝。

    ---

    ### Move Mount 时

    目标 parent 必须重新验证：

    ```text
    not inside active collaboration subtree
    ```

    ---

    ### Move Native Directory 时

    这是最容易漏掉的。

    假设：

    ```text
    B/
    └── Mount
    ```

    用户移动：

    ```text
    B
    →
    A/
    ```

    而 A 属于 active collaboration。

    必须拒绝。

    所以移动目录必须计算：

    ```text
    sourceSubtreeHasMount
    destinationInsideCollaboration
    ```

    组合验证。

    ---

    ### Move Collaboration Root / ancestor

    反方向同样危险。

    例如：

    ```text
    CollabRoot/
    ```

    移动到：

    ```text
    X/
    └── Mount
    ```

    也会形成非法相交。

    所以 topology validator 应看**操作完成后的拓扑**，而不是仅检查 source 当前是否合法。

    ---

    # 7. 并发不变量

    这些检查绝不能：

    ```text
    HTTP request:
    check()
    ...
    几百 ms
    ...
    write()
    ```

    完全分离。

    必须和 mutation 写入共享同一个：

    ```text
    atomic/CAS boundary
    ```

    至少要保证：

    ```text
    createMount
    enableCollaboration
    moveMount
    moveDirectory
    ```

    彼此不能同时穿透检查。

    例如两个并发事务：

    ```text
    T1:
    A 没有 Mount
    → 开 Collaboration

    T2:
    A/x 不在 Collaboration
    → 加 Mount
    ```

    不能全部提交成功。

    建议以后 topology 有一个：

    ```text
    namespaceRevision
    ```

    或者利用 S6 现有 repository revision/CAS，让：

    ```text
    validate topology
    +
    mutation
    ```

    在同一个原子 persistence operation 内完成。

    ---

    # 8. Foreign Namespace 应从数据模型层禁止“能力型资源”

    这一条我建议不要只是 route 黑名单。

    可以正式定义：

    ```text
    NamespaceCapabilities
    ```

    Native：

    ```text
    files
    directories
    mount
    collaboration
    share
    staticResource
    s3
    partition
    ```

    Foreign Collaboration：

    ```text
    files
    directories
    ```

    就这两个。

    所以 foreign 中：

    ```text
    Share
    StaticResource
    Collaboration
    Mount
    S3
    Partition
    ```

    不是“没权限执行”，而是：

    > **该 namespace 根本不存在这种资源类型。**

    这样设计更稳。

    ---

    # 9. “特殊文件”最好独立 kind，不要真的伪造成 file

    你说“视为一种特殊文件”这个产品理解是对的。

    但底层不建议真的：

    ```text
    kind = file
    mime = application/x-collaboration
    ```

    否则现有：

    ```text
    download
    contentId
    size
    thumbnail
    replace
    Content Object
    ```

    全部会被误套。

    应该明确：

    ```text
    kind:
        file
        directory
        collaboration_mount
    ```

    UI 上它可以表现得像“特殊文件”。

    底层绝不能认为它是 Logical File。

    ---

    # 10. Native Directory 统计也要定清楚

    例如：

    ```text
    A/
    ├── 1GB 本地文件
    └── Mount
        └── 500GB foreign
    ```

    A 的：

    ```text
    大小
    文件数
    递归 properties
    ```

    我建议只算：

    ```text
    1GB 本地内容
    ```

    不把 Mount 内 500GB 算进去。

    可以另外显示：

    ```text
    1 个协同挂载
    ```

    否则：

    - 分区 quota；
    - 目录统计；
    - 复刻估算；
    - delete impact；

    都会变得含糊。

    ---

    # 11. Partition clone 与 Namespace Resolver 的关系

    复刻：

    ```text
    P1 → P2
    ```

    实际上应该调用：

    ```text
    cloneNativeNamespace(P1)
    ```

    只遍历：

    ```text
    Native Directory
    Native Logical File
    ```

    遇到：

    ```text
    collaboration_mount
    ```

    停止并计入：

    ```text
    skippedMounts
    ```

    这样天然满足你已经确定的：

    > 不复制 Collaboration。

    不用专门再做一套排除 foreign file 的逻辑。

    ---

    # 12. Search 也可以正式基于 Namespace 定义

    你已经确定：

    ```text
    所有文件
    附加已挂载的协同内容
    ```

    可以精确定义成：

    ### 所有文件

    ```text
    search NativeNamespace(currentPartition)
    ```

    只搜：

    ```text
    我的 Logical Files
    ```

    不 traverse Mount。

    ### 附加已挂载的协同内容

    再执行：

    ```text
    for each accessible Mount in current partition:
        search ForeignCollaborationNamespace(mount)
    ```

    最后 merge results。

    结果要保留 origin：

    ```text
    {
        kind: file,
        origin: "native"
    }
    ```

    或者：

    ```text
    {
        kind: file,
        origin: "collaboration",
        mountId: M1,
        collaborationId: C1
    }
    ```

    如果同一个 C1 挂了两次，我建议搜索时**按 collaboration 去重执行查询**，但结果导航可以选择一个 canonical Mount，或者在结果里标记：

    ```text
    通过“工作/项目A”进入
    ```

    避免同一个文件因为两个快捷 Mount 出现两遍。

    ---

    # 13. 四个概念最终关系

    可以压缩成：

    ```text
    Partition Identity
        │
        │ 提供稳定 Native Scope
        ▼
    Native Namespace
        │
        ├── Directory
        ├── Logical File ──→ Content Object
        │
        └── CollaborationMount
                    │
                    │ resolve
                    ▼
            Collaboration Grant
                    │
                    ▼
         Foreign Collaboration Namespace
    ```

    所有操作先走：

    ```text
    Namespace Resolver
    ```

    所有写操作再走：

    ```text
    Mutation Scope Validator
    ```

    也就是：

    ```text
    request
       ↓
    resolve namespace
       ↓
    resolve authorization/capabilities
       ↓
    classify mutation
       ↓
    validate topology + scope invariant
       ↓
    atomic mutation
    ```

    ---

    ## 我认为可以把这四个定义最终浓缩成四句话

    **Partition Identity**

    > 给用户自己的 Native Namespace 一个永久不随名称变化的身份；`displayName` 只是表现，`scopeKey` 是兼容底层数据的稳定作用域。

    **CollaborationMount**

    > 存在于 Native Namespace 的特殊叶节点，只保存进入某个 Collaboration Grant 的入口，不复制 foreign files，也不拥有 Content Object。

    **Namespace Resolver**

    > 将“用户当前看到的路径”解析成真正的数据 owner、scope、collaboration grant、relative path 和 capabilities，禁止通过字符串路径拼接跨作用域。

    **Mutation-Scope Invariant**

    > 任何写操作只能在一个 namespace 内真正 Move；跨 namespace 永远 Copy，并且任何 topology mutation 都必须保证 Collaboration subtree 与 Mount subtree 永不相交。

    有了这四层以后，后面的“齿轮设置、分区改名/复刻/删除、协同挂载、viewer/editor、搜索和跨 scope Copy”都可以建立在同一个一致模型上，而不是各功能分别打补丁。
