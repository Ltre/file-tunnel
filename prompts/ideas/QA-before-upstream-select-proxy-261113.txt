	但这意味着 Cookie 不只是用于身份验证，它还可能直接改变 yt-dlp 的请求路径。

	因此，同一个视频、同一个 IP，有 Cookie 和没 Cookie，也可能产生完全不同的结果。

	### 2. `Video unavailable` 不等于服务器无法连接 YouTube

	你第一段日志已经完成了多个阶段的请求。

	最终错误：

	```
	ERROR: [youtube] O-cgsD4mxG4:
	Video unavailable. This video is not available
	```

	通常说明 yt-dlp 没有从播放器响应中获得可播放的视频。

	可能是播放器返回 `UNPLAYABLE` 等状态，也可能是账号、地区、客户端兼容性等因素导致。

	这与普通网络异常，例如：

	```
	Connection timed out
	Connection refused
	SSL certificate verify failed
	```

	不是同一类故障。

	因此，我暂时不把 DNS 解析失败、TCP 连接被阻断或 FFmpeg 故障列为首要原因。

	另外，你本机已经可以下载目标类型的内容，所以也不应直接认定资源已经在 YouTube 全局下架。

	### 3. 你设置新加坡代理的方式还有一个疑点

	你执行：

	```
	export HTTP_PROXY=http://127.0.0.1:58591
	export HTTPS_PROXY=http://127.0.0.1:58591
	export ALL_PROXY=socks5://127.0.0.1:51837
	```

	这里同时设置了两个不同的代理入口。

	对于 HTTPS 请求，常见代理实现会优先选用 `HTTPS_PROXY`，而不是 `ALL_PROXY`。

	因此 yt-dlp 很可能使用的是：

	```
	HTTP 代理：127.0.0.1:58591
	```

	而不是你设置的 SOCKS5 端口 `51837`。

	即使两个端口都来自同一个代理客户端，也不能保证两者使用相同的出口节点。

	此外：

	```
	Downloading tv samsung player API JSON
	```

	只是请求阶段的提示，不代表请求成功，也没有告诉我们 HTTP 状态码。

	你第二次贴出的日志没有最终结果。因此不能判断是恢复了、卡住了，还是最终仍然返回相同错误。

	## 二、发现的四个关键问题

	### 1. 后台强制指定 Node.js 作为 JS Runtime

	位置：[server.js 第 5543–5551 行](https://github.com/Ltre/file-tunnel/blob/38e3e0f6415f8c9732a4a4b8ea7dfa56d08e6d16/server.js?utm_source=chatgpt.com#L5543-L5551)。

	实际代码：

	```
	const args = [
		'--js-runtimes',
		process.env.SOCIAL_YTDLP_JS_RUNTIME || 'node'
	];
	```

	也就是说，除非你设置了环境变量 `SOCIAL_YTDLP_JS_RUNTIME`，否则后台始终添加：

	```
	--js-runtimes node
	```

	这与你直接执行：

	```
	yt-dlp --cookies yt-cookies.txt -F URL
	```

	不是相同的执行条件。

	你虽然安装了 Deno，但后台默认选择 Node，并不直接使用 Deno。

	这不一定造成 `Video unavailable`，但如果 Node 的版本、PATH、JS Challenge 组件或与 yt-dlp 的兼容性有问题，就可能导致格式解析异常。

	### 2. Premium 和 SNS 使用不同 Cookie

	代码中明确设置：

	```
	const YOUTUBE_PREMIUM_COOKIE_PATH =
		path.join(SERVER_DATA_DIR, 'yt-premium-cookies.txt');

	const SNS_COOKIE_FILES = Object.freeze({
		youtube: 'yt-cookies.txt',
		// ...
	});
	```

	因此，你此前在 `.tunnel-data` 执行的：

	```
	yt-dlp --cookies yt-cookies.txt -F URL
	```

	只对应普通 SNS Cookie，不对应 Premium 页面。

	这两份 Cookie 可能来自不同账号、不同浏览器会话，甚至具有不同的失效时间。

	我认为这是当前应该优先验证的差异之一。

	此外，后台还会把 Cookie 复制到临时文件后再传给 yt-dlp，但没有发现它在这个复制步骤中主动改写 Cookie 内容。

	### 3. `Video unavailable` 不触发项目的播放器客户端回退

	这是明确存在的程序处理缺口。

	源码：[server.js 第 5480–5523 行](https://github.com/Ltre/file-tunnel/blob/38e3e0f6415f8c9732a4a4b8ea7dfa56d08e6d16/server.js?utm_source=chatgpt.com#L5480-L5523)。

	目前程序只在特定失败场景进行回退，例如：

	- `Requested format is not available`
	- `Only images are available`
	- `Sign in to confirm you're not a bot`
	- `Page needs to be reloaded`

	对于 `Page needs to be reloaded`，程序会改用：

	```
	--extractor-args "youtube:player_client=web_embedded,android,tv_embedded"
	```

	但针对你遇到的：

	```
	ERROR: [youtube] O-cgsD4mxG4:
	Video unavailable. This video is not available
	```

	程序没有专门匹配这个错误的客户端回退逻辑。

	所以它会直接返回失败。

	不过，这只能解释为何程序没有进一步尝试恢复，不能解释 YouTube 最初为什么返回 `Video unavailable`。

	### 4. 前端解析请求漏传 `asMusic`

	在 Premium 页面发现一个独立问题。

	源码：[youtube-premium-dl.html 第 2133–2142 行](https://github.com/Ltre/file-tunnel/blob/38e3e0f6415f8c9732a4a4b8ea7dfa56d08e6d16/pages/youtube-premium-dl.html?utm_source=chatgpt.com#L2133-L2142)。

	前端当前发送：

	```

		url,
		refresh: forceRefresh === true
	})
	```

	但是后台读取：

	```
	forceMusic: req.body?.asMusic === true
	```

	前端格式解析请求没有发送 `asMusic`。

	这样即使你勾选“以音乐形式下载”，后台解析阶段仍可能根据元数据自行判断是歌曲还是视频。

	对于 `www.youtube.com/watch?v=...` 形式的 YouTube Music 曲目尤其值得注意。

	这个问题会影响媒体类型识别和格式选择，但本身不应造成 YouTube API 返回 `Video unavailable`。

	## 三、我还发现代理环境存在一个容易忽略的问题

	后台 `buildYtDlpEnv()` 使用的是：

	```
	const env = { ...process.env };
	```

	也就是说，它读取的是正在运行的 Node 服务进程的环境变量。

	如果你先启动了 Node 服务，之后才在 Git Bash 终端执行：

	```
	export HTTPS_PROXY=http://127.0.0.1:58591
	```

	这个操作不会自动改变已经启动的 Node 服务的环境变量。

	所以你在终端代理测试得到的结果，不能直接代表 Node 后台也通过同一个代理出口访问 YouTube。

	而且代码设置代理时采用 `||=`，如果 `HTTPS_PROXY` 已经存在，即便配置了 `DR2T_PROXY`，也不会覆盖已有值。存在代理优先级与实际行为不完全一致的问题。

	源码：[server.js 第 5357–5373 行](https://github.com/Ltre/file-tunnel/blob/38e3e0f6415f8c9732a4a4b8ea7dfa56d08e6d16/server.js?utm_source=chatgpt.com#L5357-L5373)。

	## 三、HAProxy 跳板与 TLS 验证

	你描述的网络结构应该是：

	file-tunnel / sing-box 客户端

	发起 Trojan + TLS 连接

	TLS 加密数据

	HAProxy 中转服务器

	TCP 透传，不终止 TLS，不解密内容

	原样转发加密数据

	最终 Trojan-GFW 服务器

	完成 TLS 握手、认证并处理流量

	对于这个场景，sing-box 可以这样配置：

	```

	{
	  "type": "trojan",
	  "tag": "jp-relay-01",
	  "server": "relay.example.com",
	  "server_port": 443,
	  "password": "YOUR_TROJAN_PASSWORD",
	  "tls": {
		"enabled": true,
		"server_name": "origin.example.com",
		"insecure": true
	  }
	}

	```

	字段含义：

	| 参数                   | 作用                  |
	| -------------------- | ------------------- |
	| `server`             | 实际连接的 HAProxy 中转服务器 |
	| `server_port`        | 中转服务器监听端口           |
	| `password`           | 最终 Trojan 节点的认证密码   |
	| `tls.enabled: true`  | 保持 TLS 加密           |
	| `tls.server_name`    | 最终 TLS 服务端使用的域名/SNI |
	| `tls.insecure: true` | 不验证服务端证书可信性         |

	sing-box 官方将 `insecure` 定义为允许接受任意服务器证书，而不是禁用 TLS。

	sing-box+1



	### 这里有一个重要的安全区别

	实际上，HAProxy 只做 TCP 透传，并不要求 `insecure: true`。

	如果最终 Trojan 服务器的证书有效，并且 `server_name` 填写正确，即使经过 HAProxy 中转，也可以保持：

	```
	{
	  "enabled": true,
	  "server_name": "origin.example.com",
	  "insecure": false
	}
	```

	这是更安全的方式。

	只有最终节点使用了自签名证书、证书域名不匹配等情况，才可能需要跳过验证。也可以考虑配置可信 CA 或证书公钥指纹，避免完全放弃身份验证。
