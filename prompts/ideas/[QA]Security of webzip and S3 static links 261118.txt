### **1. 高危：文件 MIME 类型可能绕过 CSP 防护**

- [server/s3/routes.js · 第 210 行](https://github.com/Ltre/file-tunnel/blob/dev/2611-s1/server/s3/routes.js?utm_source=chatgpt.com#L204-L212)

S3 上传接口允许请求提供 `Content-Type`，保存后会成为文件的 MIME 类型。

公开文件访问接口试图对 HTML、SVG、XHTML 添加 `Content-Security-Policy: sandbox`，阻止上传的文件在网站同源环境中执行脚本。

但判断条件存在缺口。

本地静态复核结果（没有访问目标系统）

| 文件 MIME 类型                      | 是否触发 sandbox |
| ------------------------------- | ------------ |
| `text/html`                     | &#x20;是      |
| `text/html; charset=utf-8`      | &#x20;是      |
| `text/html ; charset=utf-8`     | &#x20;否      |
| `image/svg+xml ; charset=utf-8` | &#x20;否      |

原因是正则表达式要求 MIME 类型后面立即跟分号或字符串结束，但标准 MIME 解析允许忽略相关空白。

[image](https://www.google.com/s2/favicons?domain=https://mimesniff.spec.whatwg.org\&sz=32)

mimesniff.spec.whatwg.org



**潜在后果：** 如果攻击者能通过合法账户上传可控 MIME 类型的文件，并生成公开静态链接，受害者访问该链接时，浏览器可能将内容作为同源 HTML 或 SVG 执行，而服务端没有附加原本预期的 sandbox 防护。

这可能进一步影响同域登录会话。

**建议修复：** 对 MIME 类型先进行规范化；对 HTML、SVG、XHTML 等主动内容，优先强制下载，避免直接在业务主域内联展示。更稳妥的是将用户上传内容放在独立的无登录 Cookie 域名下。

这使 ZIP 内的 HTML 具有 `d2tunnel.com` 的 Origin，而非独立的不可信 Origin。

更严重的是预览页面的 iframe 配置：

```
<iframe
  id="viewer"
  sandbox="allow-same-origin allow-scripts allow-forms allow-modals allow-downloads allow-popups">
</iframe>
```

这里同时出现了两个危险权限：

- `allow-scripts`：允许网页 ZIP 内的 JavaScript 执行。
- `allow-same-origin`：保留真实 Origin，不强制隔离为不透明 Origin。

MDN 和 HTML 标准均明确指出：对于同源 iframe，同时允许这两个权限，嵌入页面可以移除 sandbox 属性并重新加载，破坏预期隔离。

[image](https://www.google.com/s2/favicons?domain=https://developer.mozilla.org\&sz=32)

MDN+1



更重要的是，**即使不移除 sandbox，恶意 JavaScript 也可能利用同源身份调用主站接口。**

### **2. 可能造成什么后果？**

如果普通用户能够把网页 ZIP 分享给其他人预览，并且受害者在同一浏览器中登录了主站账号，就有以下风险：

| 潜在影响                  | 风险判断     |
| --------------------- | -------- |
| 读取当前 Origin 下可访问的存储数据 | 高        |
| 以受害者身份调用同源接口          | 高        |
| 访问未充分隔离的主站页面数据        | 高        |
| 管理员预览时滥用管理员接口         | 严重       |
| 直接得到服务器 Shell         | 尚未发现直接证据 |

网页 ZIP 的设计本身允许用户运行 HTML 和 JavaScript，这是功能需求，不是漏洞。

**真正的漏洞是：你允许不可信用户编写的 JavaScript，以主站可信网页的身份运行。**

由于预览 URL 与主站同源，风险不只限于 ZIP 预览界面，也会影响通过独立窗口打开的网页 ZIP。

### **3. 修复方向**

最重要的措施是**为网页 ZIP 分配独立 Origin**，而不只是修改 iframe 属性。

例如：

| 用途             | 域名                        |
| -------------- | ------------------------- |
| 主站、登录、网盘、管理员后台 | `d2tunnel.com`            |
| 网页 ZIP 运行环境    | `zip-sandbox.example.net` |

第二个域名应当采用独立的可注册域，不共享主站 Cookie、认证状态、localStorage 或 IndexedDB。

同时，应将 ZIP 预览接口限制为最小权限，跨域通信采用经过来源验证的 `postMessage`，不要直接授予 ZIP 网页主站 API 的访问能力。

仅删除 `allow-same-origin` 可以减少 iframe 内的风险，但不能单独解决用户直接打开同源 ZIP 页面的问题。

### **4. 还发现 ZIP 解压资源限制不足**

[client/folder-archive.js：ZIP 解压实现](https://github.com/Ltre/file-tunnel/blob/dev/2611-s1/client/folder-archive.js?utm_source=chatgpt.com#L101-L140)

`extractZip()` 使用 `DecompressionStream` 解压文件，并将解压结果完整读入内存。

当前没有看到明确的以下限制：

- 单个文件的解压后大小上限；
- 整个 ZIP 的解压后总大小上限；
- 压缩比限制；
- 累计处理时间和内存预算。

恶意构造的高压缩比 ZIP 可能导致浏览器占用大量内存、卡死或崩溃。

这是**客户端拒绝服务风险**，不是已证实的服务端 RCE。因为当前这条 ZIP 解压路径主要运行在浏览器中。

## **二、管理员 Cookie 绑定设备指纹，能不能防止盗用？**

**可以提高盗用难度，但单靠设备指纹，无法可靠防止攻击者复制 Cookie 后在另一台设备冒用身份。**

需要区分三类防护：

| 方案                            | 防止 Cookie 异机复用 | 抵抗设备信息伪造       |
| ----------------------------- | -------------- | -------------- |
| Cookie 绑定 User-Agent、IP       | 有一定检测能力        | 弱              |
| Cookie 绑定 Canvas、WebGL 等浏览器指纹 | 有一定检测能力        | 弱至中等           |
| Cookie 绑定不可导出私钥，并验证加密签名       | 强得多            | 强，取决于密钥保护方式    |
| 浏览器原生 DBSC 硬件绑定               | 强              | 强，但受浏览器和平台支持限制 |

### **为什么普通设备指纹靠不住？**

例如，服务端保存登录时的浏览器信息：

```
{
  "browser": "Chrome",
  "os": "Windows",
  "resolution": "1920x1080",
  "timezone": "Asia/Singapore"
}
```

之后每次请求都检查这些信息是否一致。

问题是，这些属性并非设备独有的秘密。有些能直接通过 HTTP 客户端伪造，有些可以通过浏览器自动化模仿。

甚至可以发生以下情况：

1. 攻击者通过恶意 JavaScript 读取受害者的部分设备指纹。
2. 将获取的指纹数据发送到攻击者设备。
3. 攻击者同时复制 Cookie 和相关指纹，构造看似相同的请求。

所以，**设备指纹更适合做异常检测，不适合作为不可伪造的第二身份凭证**。OWASP 也把 IP、User-Agent 等属性绑定定位为会话风险检测和辅助保护机制。

[image](https://www.google.com/s2/favicons?domain=https://cheatsheetseries.owasp.org\&sz=32)

OWASP Cheat Sheet Series+1



要达到你说的「即使 Cookie 被窃取，也无法在另一台设备冒用」，需要引入真正的**密码学持有证明（Proof of Possession）**，而不是比较浏览器特征。

## **三、推荐方案：设备密钥绑定 + WebAuthn + 服务端会话管理**

对 `d2tunnel.com` 这样的 Node.js 应用，我建议采用三层保护。

### **第一层：设备绑定会话，阻止 Cookie 异机重放**

优先研究 **Device Bound Session Credentials（DBSC）**。

它正是为解决你描述的问题而设计的：浏览器生成设备绑定密钥，服务端通过密码学证明确认会话仍由原设备持有，避免单凭被盗 Cookie 就能长期冒用身份。

### **第二层：敏感操作必须重新验证 WebAuthn**

这层解决另一个问题：攻击者即使不能把 Cookie 偷走，也可能通过 XSS 在受害者当前浏览器中调用管理员 API。

因此，建议对以下操作要求 WebAuthn 二次验证：

- 查看、导出 SNS Cookie 或其他凭证；
- 修改 Telegram Bot、S3 密钥与代理出口配置；
- 创建或运行自定义 FFmpeg 模板；
- 修改管理员认证及安全配置；
- 执行高风险的数据删除或备份恢复操作。

验证时，服务端生成一次性挑战，绑定操作类型和关键参数，校验 WebAuthn 的签名、Origin、RP ID 和用户验证结果。

这并非绝对防 XSS：同源恶意代码仍可能诱导用户批准认证请求。但配合严格的 Origin 隔离、具体操作确认和短时授权，可以显著降低静默滥用风险。

## **一、第 2 条有五个需要修正的问题**

### **1. 有权限的用户仍然可以发布恶意网页 ZIP**

最严重的问题

假设攻击者已经获得网页 ZIP 发送权限：

1. 创建包含恶意 JavaScript 的网页 ZIP。
2. 服务器确认攻击者已登录，而且具有发送权限。
3. 服务器为这个 ZIP 签发合法签名。
4. 受害者收到 ZIP，浏览器计算 SHA-256。
5. 服务端确认签名和摘要匹配。
6. 浏览器放行，恶意 JavaScript 正常执行。

整个验证流程都通过了，但 XSS 仍然存在。

这是因为：

**签名验证只能证明文件经过授权发布、内容没有被篡改，不能证明文件不存在恶意代码。**

例如，你给可信用户颁发网页 ZIP 权限后：

- 用户账号可能被盗；
- 用户可能误上传包含恶意依赖的网页；
- 授权用户本身可能恶意操作；
- ZIP 中的外部 JavaScript 也可能在发布后发生变化。

任何一种情况都会让「合法签名的 ZIP」成为攻击载体。

因此，需要将两项安全措施分开：

| 安全机制              | 解决的问题                 |
| ----------------- | --------------------- |
| 账号权限 + 签名戳        | 谁有资格发布、文件是否被篡改        |
| 独立 Origin + 浏览器沙箱 | 即使网页包含恶意 JS，也不能取得主站权限 |

后一项才是解决网页 ZIP XSS 的关键。

你目前的预览页面同时设置了 `allow-same-origin` 和 `allow-scripts`。对于与主站同源的内容，MDN 明确警告这种组合不能提供可靠隔离。

[image](https://www.google.com/s2/favicons?domain=https://developer.mozilla.org\&sz=32)

MDN



### **2. 你忽略了 file-tunnel 的 P2P 文件传输架构**

这是实施层面很容易踩的坑。

你的项目支持 Socket.IO、WebRTC P2P 等传输方式。

第 2 条写道：

> 发送的网页ZIP要先经过服务器标记签名戳，然后下发到客户端。

这里存在两种完全不同的实现。

**方案 A：整个 ZIP 上传服务器签名**

服务器能够直接计算文件摘要，证明它实际见到的字节内容。

但是：

- 可能增加服务器带宽消耗；
- 改变现有 P2P 传输流程；
- 大 ZIP 会增加服务器处理负担。

**方案 B：发送端计算摘要，由服务器签发**

流程是：

**发送端计算 ZIP 的 SHA-256**

提交文件摘要和发布元数据

**服务器认证并授权签名**

核实账号、网页 ZIP 权限、隧道权限和文件记录

**ZIP 经原有通道传输**

签名戳随文件记录下发，实际文件可继续走 WebRTC P2P

**接收端完成校验后运行**

对完整文件重新计算摘要，服务端验证签名及授权状态

建议选择方案 B

它更符合你之前强调的原则：尽量不改变现有文件传输架构。

不过要明确，方案 B 的服务器只证明自己授权过这个摘要，并没有亲自检查 ZIP 内容。不能把它当成服务端文件安全扫描。

### **3. 签名戳不能只签署 SHA-256**

如果服务器只对文件摘要签名：

```
{
  "sha256": "文件摘要",
  "signature": "服务器签名"
}
```

可能出现签名被复制到其他文件记录、其他隧道，或者旧签名被重复使用的问题。

建议签名内容至少包括：

| 字段                  | 作用           |
| ------------------- | ------------ |
| `version`           | 签名协议版本       |
| `sha256`            | ZIP 原始字节的摘要  |
| `fileId`            | 文件唯一标识       |
| `messageId`         | 对应的传输记录      |
| `sessionId`         | 所属隧道         |
| `accountId`         | 获得发布授权的账号    |
| `issuedAt`          | 签发时间         |
| `expiresAt`         | 签名有效期        |
| `permissionVersion` | 权限版本，用于撤销旧授权 |

特别注意两点：

- 摘要应针对**收到的 ZIP 原始字节**计算，并在解压和执行前验证。
- 网页 ZIP 更新、转发、复制时，要明确签名继承与重新签发规则，否则会破坏现有的转发同步功能。

你现有的 `server/web-zip-credentials.js` 已有 HMAC 授权凭证，但它绑定的是编辑权限及相关记录字段，**没有绑定 ZIP 内容摘要**。不能直接把它当成新增的内容签名。

### **4. 服务端权限检查必须覆盖所有发送入口**

你已经意识到「隐藏按钮不等于禁止调用」，这个判断是正确的。

不过仍需补充：

不能只检查 `web-zip-publish` 事件。

还要覆盖：

- 新建并发送网页 ZIP；
- 编辑已有网页 ZIP；
- 替换文件内容；
- 转发、复制和跨隧道同步；
- 普通文件上传接口通过修改扩展名或文件元数据冒充网页 ZIP；
- Socket.IO 自行构造消息、重放旧签名。

每一次相关操作都应由服务器根据**已经验证的账号身份**判断权限，而不是相信客户端上传的 `deviceId`、`creatorDeviceId`、`webZip` 等字段。

另外，账号的「发送/编辑网页 ZIP」权限，不等于能够编辑其他人的 ZIP。已有的文件所有权、协作者授权、隧道权限仍须同时满足。

### **5. 浏览器验证成功，不代表网页运行环境安全**

即使签名机制完全正确，只要网页 ZIP 最终继续以主站 Origin 运行，它仍可能访问主站同源 API。

而且，浏览器本地验证只是正常产品流程的入口控制。不能把「前端验证返回 true」作为不可绕过的安全边界。

必须确保：

- 未验证的 ZIP 不会进入任何可执行的预览路径；
- iframe、独立窗口、全屏预览等入口使用一致的隔离策略；
- Service Worker 不会绕过安全检查，直接把未授权内容作为可执行 HTML 返回；
- 直接访问网页 ZIP 运行 URL 也不能获得主站 Origin 权限。

最稳妥的方案仍然是独立 Origin。短期内若不能迁移，至少要同步修改 iframe 沙箱，并为网页 ZIP 的 HTML 响应强制设置不包含 `allow-same-origin` 的 CSP `sandbox` 策略，覆盖直接打开的情况。这属于临时缓解措施，仍需验证是否影响现有网页功能。

### **1. 为什么推荐&#x20;**`trust-integrity-stamp`**？**

你提出的 `tamper-proof` 很直观，但从密码学术语来看：

- **Tamper-proof**：防止篡改，容易让人理解成内容无法被修改。
- **Tamper-evident**：篡改可检测。内容即使被修改，也无法通过原签名验证。
- **Integrity**：完整性验证。属于密码学中更常见、简洁的术语。

你的机制实际上是：

> SHA-256 内容摘要 + 服务器签名，确保网页 ZIP 的可信发布来源及内容完整性。

所以 `trust-integrity-stamp` 同时体现了两个关键属性：

- `trust`：由服务器确认发布者具有可信发布权限。
- `integrity`：验证内容完整性，识别未经授权的篡改。

如果特别希望文件名直接包含“篡改”字眼，也可以使用：

`server/web-zip-trust-tamper-evident-stamp.js`
