	二、另一种技术：Related Origin Requests（ROR）
	这才是你可能更感兴趣的部分。

	传统 WebAuthn 受到 RP ID 限制：
	当前网页	Passkey RP ID	默认是否允许
	accounts.google.com	google.com	允许
	mail.google.com	google.com	允许
	youtube.com	google.com	不允许
	example.net	example.com	不允许

	但是 Chrome 从 128 版本开始引入的 ROR 能力，可以允许经过授权的其他主域名使用同一个 RP ID。

	developer.chrome.com

	ROR 如何工作？
	假设你运营两个网站：
	- https://d2tunnel.com
	- https://tun.miku.us
	希望用户只需注册一次 Passkey，就能直接在两个域名的登录页面使用。

	可以将主 RP ID 固定为：
	d2tunnel.com

	然后在主域名提供：

	https://d2tunnel.com/.well-known/webauthn

	内容：
	{
	  "origins": [
		"https://d2tunnel.com",
		"https://tun.miku.us"
	  ]
	}

	之后，在两个域名的 WebAuthn 请求中统一指定：
	const credential = await navigator.credentials.get({
	  publicKey: {
		challenge,
		rpId: "d2tunnel.com",
		userVerification: "required"
	  }
	});

	当支持 ROR 的浏览器发现 tun.miku.us 试图使用 d2tunnel.com 的 Passkey 时，会检查主 RP ID 域名发布的授权关系。

	检查通过后，允许该网页调用同一 RP ID 下的凭据。

	Google 官方开发文档提供了这种跨主域复用 Passkey 的具体方案。

	web.developers.google.cn+1

	但有三个重要限制
	1. 这只解决 Passkey 跨域调用问题，不负责跨域登录状态共享。 两个网站仍需要处理各自的 Session。
	2. 不是所有浏览器、版本都具备相同的 ROR 支持。 不支持时需要准备其他登录路径。
	3. 服务端必须验证 WebAuthn 响应中的 origin、RP ID 绑定、挑战值及签名。 不能因为两个域名都是自己的，就放宽验证。
	还有一个容易误解的地方：

	ROR 不意味着浏览器把私钥从 d2tunnel.com 复制到 tun.miku.us。私钥仍由 Passkey 提供程序管理，两个网站只是被授权使用同一个 RP ID 进行认证。

	三、还有第三种方案：跨域 iframe
	WebAuthn 还支持在符合安全策略的情况下，从跨域 iframe 内调用认证接口。

	例如：
	- 页面位于 youtube.com。
	- 页面嵌入一个来自 accounts.google.com 的认证 iframe。
	- 认证操作在 iframe 自己的来源上下文中进行。
	这需要正确配置 Permissions-Policy、iframe 的 allow 权限，以及 CSP 等安全策略。

	但这不等于父页面可以任意读取 iframe 中的数据，也不等于任何第三方页面都可以冒用该 Passkey。

	web.dev

	四、三种方案怎么选？
	对比	统一认证中心 SSO	ROR	跨域 iframe
	不同主域使用同一 Passkey	✅	✅	✅
	Passkey 验证发生在哪里	统一认证域名	各个获授权的域名	iframe 所属认证域名
	是否需要跳转认证中心	通常需要，也可采用弹窗等方式	不需要	不一定
	是否自动实现跨域登录状态共享	需通过 SSO 流程建立会话	❌	❌
	浏览器兼容性	较容易提供兼容方案	受 ROR 支持情况影响	受 iframe 和权限策略限制
	更适合的场景	多产品统一账号体系	多域名直接调用同一 Passkey	需要嵌入式认证体验

	对你的 Drop2Tunnel，我更推荐哪种？
	如果你准备让：
	- d2tunnel.com
	- tun.miku.us
	- 未来其他独立域名
	共用一套管理员或普通用户的 Passkey，我优先推荐统一身份认证中心，并视需要增加 ROR。

	例如：
	- 使用 auth.d2tunnel.com 作为唯一 Passkey 注册与管理入口。
	- 用户登录其他产品时，统一交给这个认证中心。
	- 各产品通过短期、一次性的认证结果建立各自的 Session。
	- 以后如需在各产品页面直接弹出 Passkey，再考虑 ROR。
	这样既能统一管理用户 Passkey 的新增、撤销与认证策略，也方便在后续增加新的产品域名。

	最后强调一点：Google 统一账号使用同一个 Passkey 是有官方依据的；ROR 也是 Google 官方支持的跨域方案。但不能据此断言 Google 自己的 YouTube、Gmail 等产品一定使用了 ROR。 从公开资料可以确认统一认证体系的存在，不能确认其所有内部认证实现细节。

	**统一 RP ID + Related Origin Requests（ROR）+ 跨域兼容登录。**

	## **一、先说你目前两个错误的原因**

	你描述的情况是：

	1. 用户在 `a.com` 注册账号 `aaa`，并创建 Passkey。
	2. 到 `b.com` 输入 `aaa` 登录，报 `PASSKEY_ACCOUNT_NOT_FOUND`。
	3. 再尝试注册 `aaa`，报 `USERNAME_EXISTS`。

	这两个错误放在一起，很有代表性：

	| 错误                          | 暴露的问题                  |
	| --------------------------- | ---------------------- |
	| `PASSKEY_ACCOUNT_NOT_FOUND` | 登录流程未找到当前域名可用的 Passkey |
	| `USERNAME_EXISTS`           | 注册流程发现用户名 `aaa` 已经存在   |

	**我怀疑目前的实现是：用户账号在全站共享，但 Passkey 查询按域名进行了隔离。**

	例如数据库可能存在类似逻辑：

	```
	用户表
	  aaa  → userId: 123

	Passkey 表
	  userId: 123
	  rpId: a.com
	  credentialId: xxx
	```

	当用户从 `b.com` 登录时，程序可能执行：

	```
	SELECT *
	FROM passkeys
	WHERE user_id = 123
	  AND rp_id = 'b.com';
	```

	自然查不到。

	但注册时：

	```
	SELECT *
	FROM users
	WHERE username = 'aaa';
	```

	又确实存在。

	这能解释你遇到的两个报错，但**还需要检查实际报错对应的代码，才能确认是不是这个原因**。

	即便把数据库查询放宽，也还不够，因为浏览器层面还有 WebAuthn 的 RP ID 限制。

	## **二、推荐方案：所有域名统一使用&#x20;**`a.com`**&#x20;作为 RP ID**

	**统一 Passkey 身份**

	推荐方案

	Passkey · RP ID = a.com

	一份用户身份记录、一组 Passkey 凭据

	a.com

	b.com

	c.com

	所有域名使用同一个 RP ID；每个域名仍建立自己的登录会话。

	### **1. 固定 RP ID**

	不要再根据当前网页域名动态生成 RP ID。

	例如，原本可能是：

	```
	const rpId = window.location.hostname;
	```

	需要改成由服务端统一提供：

	```
	const rpId = "a.com";
	```

	无论用户通过：

	- `https://a.com`
	- `https://b.com`
	- `https://c.com`

	访问系统，创建和验证 Passkey 时，都使用：

	```
	RP ID = a.com
	```

	**这样三个域名使用的是同一组 Passkey，而不是三个不同的 Passkey。**

	### **2. 配置跨域授权**

	在以下地址提供 JSON：

	`https://a.com/.well-known/webauthn`

	内容：

	```
	{
	  "origins": [
		"https://a.com",
		"https://b.com",
		"https://c.com"
	  ]
	}
	```

	即使 `c.com` 尚未绑定，也可以在正式启用时再加入。

	这相当于由 `a.com` 声明：

	> 我允许这些经过确认的域名，使用属于 `a.com` 的 Passkey 进行认证。

	当用户在 `b.com` 调用 WebAuthn，并指定 `rpId: "a.com"` 时，支持 ROR 的浏览器会检查上述文件，确认 `b.com` 已获得授权。

	[image](https://www.google.com/s2/favicons?domain=https://web.dev\&sz=32)

	web.dev

	### **3. 统一服务端 Passkey 数据**

	你的系统既然只有一套服务器和数据库，就没有必要为每个域名保存一套独立 Passkey。

	建议采用以下关系：

	| 字段              | 示例              | 作用                |
	| --------------- | --------------- | ----------------- |
	| `userId`        | `123`           | 用户唯一身份            |
	| `username`      | `aaa`           | 全站统一用户名           |
	| `credentialId`  | `xxx`           | Passkey 凭据标识      |
	| `publicKey`     | 公钥数据            | 验证签名              |
	| `rpId`          | `a.com`         | Passkey 绑定的 RP ID |
	| `createdOrigin` | `https://a.com` | 注册来源，仅用于审计等用途     |

	这里最重要的是：

	**不要用当前访问域名&#x20;**`b.com`**&#x20;去过滤掉属于统一 RP ID&#x20;**`a.com`**&#x20;的凭据。**

	服务端应先根据用户名 `aaa` 找到同一个用户，再获取该用户绑定到统一 RP ID 的 Passkey。

	不过，`rpId` 和 `origin` 不能混为一谈。

	在 `b.com` 登录时：

	```
	rpId   = a.com
	origin = https://b.com
	```

	服务端验证时必须确认：

	- RP ID 与凭据绑定的 RP ID 相符。
	- `origin` 属于明确授权的域名。
	- Challenge 正确、未过期、未被重复使用。
	- 凭据 ID 对应合法用户。
	- Passkey 签名验证成功。

	绝不能为了实现跨域登录，直接关闭 `origin` 校验。

	## **三、现有的&#x20;**`aaa`**&#x20;Passkey 能不能直接用？**

	**很可能可以，关键取决于它创建时使用的原始 RP ID。**

	假设：

	```
	用户名：aaa
	注册域名：https://a.com
	实际 RP ID：a.com
	```

	那么：

	| 场景                   | 预期结果                |
	| -------------------- | ------------------- |
	| `a.com` 登录 `aaa`     | 使用原有 Passkey        |
	| `b.com` 登录 `aaa`     | 通过 ROR 使用原有 Passkey |
	| 将来 `c.com` 登录 `aaa`  | 授权后使用同一 Passkey     |
	| 在 `b.com` 再次注册 `aaa` | 不需要，应提示账号已存在并引导登录   |

	这不需要把 Passkey 私钥复制到其他域名，也不需要让用户重新注册。

	但如果原来的 Passkey 实际绑定的是：

	```
	www.a.com
	```

	而不是：

	```
	a.com
	```

	就要保留正确的原始 RP ID，不能直接把数据库字段改成 `a.com`。

	因为 Passkey 的 RP ID 是创建时就已经确定的密码学绑定，不能仅靠修改数据库把它转换成另一个 RP ID。

	[image](https://www.google.com/s2/favicons?domain=https://web.dev\&sz=32)

	web.dev

	### **如果已经有人在&#x20;**`b.com`**&#x20;创建了 Passkey 呢？**

	这就复杂一些。

	例如：

	- 用户 A 的 Passkey 绑定 `a.com`。
	- 用户 B 的 Passkey 绑定 `b.com`。

	这两把凭据虽然可以属于同一套用户系统，但它们的 RP ID 不同。

	**不能直接把&#x20;**`b.com`**&#x20;的旧 Passkey 改造成&#x20;**`a.com`**&#x20;的凭据。**

	迁移时建议：

	1. 保留旧凭据，避免现有用户无法登录。
	2. 新创建的 Passkey 统一使用 `a.com`。
	3. 旧凭据按其原 RP ID 继续兼容。
	4. 用户成功登录后，可以引导其创建统一 RP ID 的新凭据。
	5. 确认新凭据可用后，再允许用户删除旧凭据。

	## **四、还要处理浏览器兼容问题**

	ROR 并非所有浏览器都具备一致的支持。

	Google 的开发文档目前明确列出了 Chrome、Safari 的相关支持情况，而 Firefox 等环境不能默认具有相同能力。

	[image](https://www.google.com/s2/favicons?domain=https://web.dev\&sz=32)

	web.dev

	所以，我不建议只做 ROR。

	建议同时做一个兼容方案：

	### **不支持 ROR 时，自动通过&#x20;**`a.com`**&#x20;完成认证**

	例如用户在 `b.com` 登录：

	1. 用户输入 `aaa` 并点击 Passkey 登录。
	2. 系统检测到当前环境无法完成 ROR。
	3. 浏览器跳转至 `https://a.com` 的统一认证页面。
	4. 在 `a.com` 使用原有 Passkey 完成认证。
	5. 服务端签发短期、一次性的跨域登录凭证。
	6. 浏览器返回 `b.com`。
	7. `b.com` 验证一次性凭证，建立自己的登录 Session。

	整个过程仍然使用用户最初创建的那把 Passkey。

	**用户不需要在&#x20;**`b.com`**&#x20;注册第二把 Passkey。**

	而且不要求 `a.com` 和 `b.com` 共享 Cookie。

	要注意，这里的跨域登录凭证需要严格限制有效期、目标域名和使用次数，不能直接把用户的长期 Session Token 放进 URL。

	## **一、先说最关键的结论：不能自动复制，但可以快速创建第二把**

	Passkey 的私钥由系统或密码管理器保护。

	网站只能调用 WebAuthn：

	- `navigator.credentials.create()`：创建新 Passkey。
	- `navigator.credentials.get()`：使用已有 Passkey 验证身份。

	| `b.com` 的 Passkey 在 `a.com` 完成身份认证         | 可以，通过 ROR 或跳转认证    |

	| 静默复制 `b.com` 的私钥到 `a.com`                  | 不可以                |

	## **四、如何安全实现跨域身份验证？**

	这是本次真正需要新增的核心能力。

	因为 `a.com` 和 `b.com` 是不同主域名，不能简单依靠共享 Cookie。

	当前 `server/disk-account-sessions.js` 使用的是不带跨主域共享属性的登录 Cookie。

	所以：

	**在&#x20;**`b.com`**&#x20;登录成功，不代表&#x20;**`a.com`**&#x20;自动取得了同样的登录证明。**

	我建议增加一个短期的“跨域身份验证与 Passkey 绑定授权”流程。

	### **流程设计**

	**第一阶段：在&#x20;**`a.com`**&#x20;发起绑定请求**

	服务器创建临时授权记录：

	```
	{
	  "flowId": "random-id",
	  "userId": "user-123",
	  "username": "aaa",
	  "sourceRpId": "b.com",
	  "targetRpId": "a.com",
	  "targetOrigin": "https://a.com",
	  "purpose": "bind-passkey",
	  "expiresAt": 1234567890,
	  "used": false
	}
	```

	其中 `userId` 必须由服务器根据账号查询确定，不能相信前端提交的身份。

	**第二阶段：到&#x20;**`b.com`**&#x20;验证**

	用户通过 `b.com` 的原有 Passkey 完成 WebAuthn 认证。

	服务端确认：

	- 使用的是 `aaa` 账号已经登记的凭据。
	- RP ID 确实为 `b.com`。
	- 签名、Challenge、Origin、用户验证均正确。

	验证成功后，给原先的绑定请求授予短期授权。

	**第三阶段：回到&#x20;**`a.com`

	通过一次性凭证恢复绑定流程。

	验证通过后，服务器才允许：

	```
	userId = user-123
	rpId   = a.com
	```

	创建新的 Passkey。

	随后追加到原用户记录。

	### **安全要求**

	这个跨域授权必须满足：

	- 有效期短，例如 2～5 分钟。
	- 只能使用一次。
	- 绑定发起请求的浏览器会话。
	- 绑定明确的 `userId` 与目标域名。
	- 不能被拿去绑定其他账号。
	- 不能通过修改 URL 中的用户名改变绑定对象。
	- 认证失败、过期或取消，不得产生新的 Passkey 关联。
	- 不允许仅凭用户名存在，就直接跳过旧凭据验证。

	尤其不能为了完成这件事，直接让前端传入 `existingUserId`，然后相信它。

	当前 `existingUserId` 是服务端从已登录身份取得的，这个安全边界必须保留。

	## **五、进一步改进：允许 ROR 作为辅助，不作为基础依赖**

	虽然你不希望所有 Passkey 固定到 `a.com`，但 **ROR 仍然可以成为辅助能力**。

	例如用户有：

	```
	b.com Passkey
	```

	但还没有：

	```
	a.com Passkey
	```

	如果浏览器支持 ROR，可以让 `a.com` 使用 `b.com` 的 Passkey 进行认证。

	这就不一定需要真正跳转到 `b.com`。

	只要 `b.com` 发布：

	`https://b.com/.well-known/webauthn`

	```
	{
	  "origins": [
		"https://a.com",
		"https://c.com"
	  ]
	}
	```

	就可以授权其他域名请求使用 `b.com` RP ID 下的凭据。

	FIDO 社区的 passkeys.dev 文档甚至专门讨论了这种**已经存在多个不同 RP ID 的系统如何兼容**，包括按用户名查找原始 RP ID、重定向验证，以及为不同 RP ID 配置双向 ROR。

	[image](https://www.google.com/s2/favicons?domain=https://passkeys.dev\&sz=32)

	passkeys.dev

	但注意：

	**ROR 让&#x20;**`b.com`**&#x20;Passkey 在&#x20;**`a.com`**&#x20;可用，不等于产生了第二把独立的 Passkey。**

	如果将来 `b.com` 下线，ROR 对它的依赖可能失效。

	因此，我建议：

	| 机制             | 用途                  |
	| -------------- | ------------------- |
	| 每个域名独立 Passkey | **长期核心方案，提供域名退役冗余** |
	| 跨域验证与新增绑定      | 用户首次访问新域名时建立独立凭据    |
	| ROR            | 在支持的浏览器上减少跳转、简化验证   |
	| 跨域跳转验证         | 不支持 ROR 时的兼容路径      |

	还有个限制：ROR 授权来源数量存在浏览器实现限制，不能假定未来绑定几十个完全不同的域名都毫无限制。当前开发资料建议按最多约五组不同的可注册域名标签规划。

	## **八、最终推荐方案**

	我建议把最终需求定为以下六条：

	1\. **全站用户身份唯一。** 不同域名共用相同的用户 ID、用户名及账号数据。

	2\. **Passkey 按域名独立绑定。** 每个域名使用自身 RP ID，不设置不可替代的主认证域名；同一用户允许拥有不同 RP ID 的多把 Passkey。

	3\. **已有账号跨域验证。** 用户首次在新域名使用已有用户名时，可以通过已绑定的其他域名 Passkey 证明账号所有权，验证成功后直接登录，不创建新用户。

	4\. **新域名快速绑定。** 在账号所有权得到验证后，允许用户通过一次系统 Passkey 创建确认，将新域名的凭据追加到原账号；不要求重新填写注册资料。

	5\. **ROR 优化与兼容。** 浏览器支持时，可以通过 ROR 直接使用其他域名的既有 Passkey；不支持时回退到安全的跨域验证跳转。

	6\. **域名退役保护。** 删除或停用某个系统域名之前，系统应识别仍只持有该域名 Passkey 的用户，并提供提前绑定其他域名的路径，避免域名下线后无法登录。

	## **一、正确的登录查找机制**

	你的业务流程可以保持不变，但底层应这样实现：

	1. 用户在前台输入用户名 `aaa`。
	2. 服务端根据 `username = "aaa"` 查找用户记录，取得用户 ID。
	3. 查询该用户关联的 Passkey。
	4. 根据 RP ID 选择当前域名可用的凭据，包括通过 ROR 获得授权的其他域名凭据。
	5. 服务端向浏览器提供对应的 Credential ID 列表。
	6. 浏览器根据 **RP ID + Credential ID**，从可用的密码管理器或认证设备中寻找凭据。
	7. 用户完成身份验证后，服务端验证签名，确定其身份。

	这里不能把第 6 步写成“按照备注名 `aaa` 查找”。

	WebAuthn 标准明确区分了用户显示名称与身份标识：`name`、`displayName` 主要用于用户界面，不能作为身份认证的判断依据。
