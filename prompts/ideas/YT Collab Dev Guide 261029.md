# YT Collab 多宫格 YouTube 观看与队列协作——开发指南

> 项目：Drop2Tunnel · YT Collab  
> 文档性质：需求整理、架构约束、交互规范与验收指导  
> 依据：2026-10-29 整理的两轮问答；**以用户第二轮补充为最终要求**。  
> **本指南不指定需要修改的源代码文件，也不预设现有代码的具体实现。开发前应先检查当前分支可复用的身份、实时通信、存储和界面能力。**

## 1. 产品定位与开发边界

### 1.1 产品目标

YT Collab（俗称“监控大爷模式”）用于集中管理、分配和观看每天在 YouTube 发现的一批感兴趣的视频。核心问题不是“怎样下载 YouTube”，而是“如何在有限时间内，更快筛选、观看、暂停、继续、转移和整理大量待看视频”。

- 在一个观看窗口中同时管理多个独立的 YouTube 播放格子。
- 每格具有自己的观看上下文和队列，不使用、也不依赖 YouTube 自带播放队列、稍后观看、播放列表。
- 用户可将视频在不同格子的队列间单个或批量复制、移动。
- 用户可单独或批量调整格子的静音状态和音量。
- 队列与窗口配置可以保存、恢复、备份，并从另一台设备编辑和遥控。
- 观看公开且允许嵌入的视频**不要求登录 YouTube**；YT Collab 也应允许不登录本站账号的临时使用。本站账号只作为可选的跨设备身份关联方式。

### 1.2 需要实现的功能范围

**必备：** 六种布局、独立格子与队列、最近视频及进度恢复、视频基本资料、单项/批量队列复制移动、单格/批量静音与音量、队列配置文件、窗口配置文件、跨设备遥控（二维码/短码及可选账号关联）、数据持久化和异常处理、入口与新页面。

**建议增强（可排在核心功能之后）：** 重点格子/临时放大、音频独占与偏好恢复、已看/跳过标记、批量 URL 粘贴、时间戳标记、播放速度、观看进度排序、操作撤销。

**本次不做：** yt-dlp 媒体解析、视频下载/转码/缓存二进制、调用私人 YouTube Premium Cookie、自动抓取 YouTube 个人首页推荐流、AI 字幕摘要、浏览器扩展、独立桌面应用。以上均不能变成核心功能的前置条件。

### 1.3 与 Drop2Tunnel 的关系

YT Collab 是 Drop2Tunnel 内的一项**独立应用功能**，而不是普通隧道的一个记录、文件资源或协同编辑对象。优先复用现有 Web 服务、实时通信、持久化、用户/设备身份和国际化/界面基础设施，但不要把“每个宫格”实现成一条普通 Drop2Tunnel 隧道。

入口精确要求：**“连接设备”区域 Header → 汉堡菜单 → `YT Collab` → 打开新的独立页面**。被控端/遥控端都应能直接进入各自适合的视图。

## 2. 播放器技术边界与基本策略

### 2.1 不解析流，直接用 YouTube 播放器

网页版应采用官方 YouTube 嵌入播放器及 IFrame Player API，播放资源始终由 YouTube 提供；Drop2Tunnel 只处理队列、元数据、偏好、观看状态和遥控指令，不代理视频流。

**注意“直接打开 YouTube 页面”与“显示完整 watch 网页”的区别：** 普通跨站 iframe 不能直接把完整 `youtube.com/watch` 页面嵌入并任意移动其内部 DOM。标准网页版应使用 `youtube.com/embed/{videoId}` 类的官方播放器，**不要尝试以 iframe 裁剪偏移来显示 watch 网页的局部**。如果将来确需显示完整 watch 页面且操作内部布局，应另行评估受授权的浏览器扩展或专用桌面容器，而不属于本次实施范围。

### 2.2 显示与操作规则

- 每格应呈现**完整播放器区域**：不裁切视频画面，不遮挡 YouTube 控件、品牌标识及链接。
- 保持视频原比例，常见情况是 16:9；在格子可用空间内做等比最大化、居中和留空处理。必要时容器留边，但不强制拉伸视频。
- 自有工具条（队列、音量、复制、放大、格子名称等）置于播放器**之外**，不得覆盖播放器表面。
- 窗口大小变化、全屏切换、侧栏展开、布局切换后，重新计算玩家视口尺寸；不因尺寸变化而丢失当前视频或观看进度。
- 每格有稳定的 `cellId`；在可行时保留播放器实例，只改变格子排布和显示状态，避免重复重建 iframe 导致卡顿、重复初始化或重播。
- 单个视频加载失败，不得拖垮其他格子或整个窗口。保留原 URL 与队列项并提供“在 YouTube 打开”。

### 2.3 自动播放的限制

官方最低功能要求：嵌入播放器视口至少 **200×200 CSS px**，16:9 推荐 **480×270 CSS px**；一个页面或屏幕不能让超过一个嵌入播放器**同时自动播放**。程序化播放也被归入自动播放规则。

因此：

- 初次打开窗口默认**不启动九格自动播放**。
- 自动恢复时以“加载视频/预览及进度”优先，不自动让所有格子有声播放。
- 各格可以独立由用户主动操作播放器；对多路播放是否可同时使用，必须按照当时的 YouTube 政策与浏览器实际行为验证，不承诺“批量开始播放所有格子”。
- 自动播放下一条如需支持，同一时刻只允许符合政策的一路自动播放，其他格保持待播放/预览状态。
- 浏览器阻止脚本播放时，反馈“需要在被控设备上激活播放”，不得静默循环调用播放接口。

## 3. 六种布局与设备准入条件

六种布局是**固定规格，不要求每种都适配每一种屏幕**：

| 名称 | 排布（行×列） | 格子数量 | 播放区域推荐总尺寸（不含操作 UI、间距） |
|---|---:|---:|---:|
| 九宫格 | 3×3 | 9 | 1440×810 CSS px |
| 田字格 | 2×2 | 4 | 960×540 CSS px |
| 横屏双列 | 1×2 | 2 | 960×270 CSS px |
| 横屏三列 | 1×3 | 3 | 1440×270 CSS px |
| 竖屏两行 | 2×1 | 2 | 480×540 CSS px |
| 竖屏三行 | 3×1 | 3 | 480×810 CSS px |

上述数字是基于**单播放器推荐 480×270**推得的参考值，绝非整页最低分辨率，不能直接用显示器物理像素判断。实际需要额外计入顶栏、边框、间距、队列抽屉、安全区等。

### 3.1 适配检测

对布局候选项实时计算：

- **几何硬条件：** 实际播放器视口不得小于官方 200×200 CSS px；若按 16:9 完整展示视频，应检验相应的等比可用空间，不能只看总屏幕宽度。
- **推荐条件：** 每格能达到 480×270 或产品规定的更高舒适尺寸；充分留出外部操作工具条空间。
- **环境条件：** 浏览器支持 IFrame Player API 所需能力，网络可访问 YouTube，未被安全策略禁止嵌入。
- **性能条件：** 设备可承受目标数量的播放器实例、视频解码、内存与网络流量；实际性能需通过测试或运行时检测判断，不能从 DPI、UA 或屏幕尺寸单独推断。

布局状态推荐：`推荐`、`可以尝试（可能性能不足）`、`不可用（尺寸或环境不满足）`。

### 3.2 操作与边界

- 不满足几何/技术硬条件的布局禁止选择，显示**具体不满足的条件**。
- 推荐尺寸不足、硬条件满足时允许尝试，同时显示性能/观看体验提示。
- 窗口缩小使当前布局不再满足硬条件时，提供切换建议；不允许继续把 iframe 压到官方下限以下。
- 容量从 9 格切到 4/3/2 格时，**隐藏格子的绑定关系和队列不得删除**；保留配置并按策略暂停/卸载隐藏播放器，切回时恢复。
- 当前播放格子遇到布局变更，尽量维持播放；若必须重建播放器，先保存视频 ID、时间点和播放状态，再安全恢复（不强制自动播放）。
- 仅根据实际容器 CSS 尺寸确定排布；系统 DPI、浏览器缩放和 DPR 会改变实际情况，但不可将 DPR 直接当 CSS 宽度。

## 4. 核心领域模型与配置文件体系

坚持用户指定的**两类配置文件**，第三类“视频资料/观看记录”是内部数据管理实体，不应取代这两类对外概念。

### 4.1 QueueProfile（队列配置文件）

逻辑上每条队列独立保存，有自己的 ID、名称、排序、成员项和版本。一个格子默认绑定一条队列；队列与格子不应永久耦合，以便窗口配置切换时重复引用或重新绑定。

建议概念字段：

```json
{
  "id": "queue-A",
  "name": "科技资讯",
  "revision": 12,
  "entries": [
    { "entryId": "entry-001", "videoId": "VIDEO_ID", "order": 0, "status": "watching" }
  ],
  "updatedAt": "2026-10-29T07:00:00Z"
}
```

`entryId` 与 `videoId` 必须区分：前者是某个队列内的条目身份；后者标识 YouTube 视频。同一视频能被复制到多个队列。条目的排序、待看/在看/完成/跳过等队列特定属性应保存在此层。

### 4.2 WindowProfile（窗口配置文件）

一个 WindowProfile 定义窗口布局、固定格子身份、位置→队列引用、各格最后打开的队列项/视频、音量偏好与静音偏好，以及窗口使用偏好。

```json
{
  "id": "window-001",
  "name": "晚间巡查",
  "layout": "2x2",
  "revision": 6,
  "cells": [
    { "cellId": "A", "queueId": "queue-A", "activeEntryId": "entry-001", "muted": false, "volume": 80 },
    { "cellId": "B", "queueId": "queue-B", "activeEntryId": null, "muted": true, "volume": 25 }
  ]
}
```

- **位置**与**身份**分开：`cellId` 稳定；布局改变的是显示映射，不是把队列数据移动到另一个 ID 下。
- 保存多份窗口配置；每份可以引用不同组合的队列。
- 切换 WindowProfile 时先保存旧窗口当前状态，恢复新窗口最后视频和时间点；如果新窗口布局不适用，应提示调整，而非清空配置。
- 音量范围建议统一 0～100；静音状态与数值音量**分别保存**，静音/取消静音不应将原音量覆盖成 0。

### 4.3 VideoCatalog（内部共享视频资料）

以规范化 `videoId` 为索引保存与 YouTube 视频本身相关的数据：

- 原始 URL、规范化 URL、视频 ID；
- 标题、作者/频道名称、频道 ID（如可取得）、合作作者列表（可为空）；
- 封面、视频发布时间/可获得的上传时间、时长、是否允许嵌入；
- 元数据来源、成功抓取时间、刷新状态与错误原因。

YouTube 标准数据不保证提供完整结构化合作作者；可提供 `collaborators[]` 和用户手工补充，**不得编造合作作者**。官方 API 提供的 `publishedAt` 一般应显示为“发布时间”；不要假称它必然是原始上传时间。

### 4.4 WatchHistory（用户自己的观看记录）

按 `viewerProfileId + videoId` 保存统一观看统计：

```json
{
  "videoId": "VIDEO_ID",
  "lastPositionSec": 518.3,
  "lastPlayedAt": "2026-10-29T07:00:00Z",
  "playCount": 3,
  "totalWatchedSec": 1437
}
```

- **默认跨队列共享同一视频的观看位置和次数**；队列各自保持排序、状态和最后选择的条目。
- “本人播放次数”是 YT Collab 自己的有效观看次数，必须标明不是 YouTube 官方播放量。推荐同一有效观看会话达到连续或累计 10 秒后计数一次，暂停、缓冲、Seek 不重复计数。
- 每 5～10 秒定期写入有效观看位置，暂停、切换视频、切换配置、隐藏格子时额外保存；异常退出后允许少量时间误差。
- 避免多设备同时播放同一视频时互相覆盖进度：记录更新时戳与版本，采用明确的“最近有效播放状态”策略，冲突可提示。
- 匿名使用时需要稳定的本地 `viewerProfileId`；登录本站账号后可选择关联/迁移，不能静默把不同人的记录合并。

### 4.5 实际文件、数据库和备份的关系

用户所说的“队列配置文件”“窗口配置文件”须在**逻辑数据模型与导入导出层真实成立**：每队列独立标识、可单独导入/导出，每窗口独立标识、仅保存队列引用而不复制整份队列。

运行时可以利用现有服务端持久化体系管理结构化状态，并提供独立 JSON 配置导出/导入；不应为满足“文件”二字强制采用不安全或难以并发更新的逐文件写盘方式。无论具体存储介质如何，必须支持备份、恢复、版本兼容和关联队列缺失时的明确提示。

## 5. 页面及交互设计

### 5.1 观看端

顶部：当前窗口配置名称、布局切换、窗口配置选择/保存、遥控连接入口、全局宫格选择操作。

每格自有区域包括：

1. 格子序号/名称、队列名称；
2. 完整 YouTube 播放器；
3. 当前视频标题、当前/总时长、队列位置；
4. 上一条/下一条、打开原始 YouTube 链接、队列入口；
5. 静音状态、音量值/滑杆和格子选择框；
6. 加载、错误、受限、遥控连接状态。

控制区域应为紧凑式，优先保证播放器完整显示。较小窗体时将队列管理和非核心操作放到侧栏/抽屉，队列管理 UI 不能遮挡播放器本体。

### 5.2 队列管理

- 支持粘贴单个视频 URL；建议同时支持一行一个的批量 URL 导入。
- URL 需规范化，可识别常见 watch、youtu.be、Shorts、Live 链接中的视频 ID；保留用户原 URL 供查看。
- 无法识别的 URL 显示行级错误，不影响批量导入其他有效项。
- 可查看队列、排序、定位当前视频、删除、批量选择、全选/反选、搜索（建议）、复制/移动至其他队列。
- 重复添加同一视频时显示提示；是否允许重复入队由清晰策略决定，不能默默破坏既有条目。
- 队列删除、移除条目与“删除共享视频资料/观看历史”要严格区分。

### 5.3 批量复制 / 移动

完整流程：选择源格子及队列 → 勾选一个或多个视频 → 选择目标格子/队列 → 选择复制或移动 → 预览数量/重复项 → 执行并反馈结果。

- **复制：** 源条目保留，目标新增独立 `entryId`，共享 `videoId` 及观看历史。
- **移动：** 源移除、目标新增应视为一次原子业务操作；失败不能出现源已删但目标未新增。
- 正在播放的源视频被移动时，不应强行切断正在播放的媒体；随后按更新后的队列状态处理上一条/下一条。
- 同一源队列和目标队列不应执行无意义移动；可改为队列内排序。
- 多设备并发编辑以服务端修订号协调，反馈冲突和重试结果，不允许静默丢失其中一方修改。

### 5.4 批量格子音频控制

- 格子支持独立静音/取消静音、调整 0～100 音量。
- 多选选择目标格子，提供**全选、反选、取消选择**；选中后执行**批量静音、批量取消静音、设置统一音量**。
- 批量取消静音恢复各格自身的数值音量，而不是给所有格统一一个预设值（除非用户刚进行了“统一音量”操作）。
- 一次批量控制应给出每格成功/失败反馈，不能因为一格播放器未就绪而使其他格操作失败。
- 可选“音频独占”：临时只保留一个选中格子的声音；退出后恢复全部格子之前保存的静音和音量偏好。

## 6. 视频元数据获取策略

**必须与视频播放脱钩：** 输入有效视频 URL 即可加入队列，不允许因“标题/封面暂不可用”而禁止入队。

推荐多级路径：

1. 先从 URL 提取、校验并保存 video ID；
2. 使用官方 IFrame API 在播放时获得其允许提供的基础资料/播放状态；
3. 如果站点管理员配置了合法的 YouTube Data API 凭据，可使用 `videos.list` 补齐标题、频道、缩略图、发布时间、时长及可嵌入状态；
4. 元数据缺项保留 `null/unknown`，允许用户手动补充；未来可重试刷新。

不要求用户登录 YouTube；使用公共 Data API 如需密钥，应将其放在服务端并限制调用配额。不得以 yt-dlp、网页抓取或非公开接口作为必须依赖的元数据后备。获取的官方 API 数据需要按 YouTube 的存储/刷新政策处理，通常不应长期缓存超过 30 天而不刷新或删除；要记录 `metadataUpdatedAt`。

## 7. 观看端与遥控端的实时协作

### 7.1 两种独立角色

- **Player（被控端）：** 真正装载 YouTube 播放器、执行播放命令、反馈播放状态。可以是 PC、平板或其他兼容浏览器。
- **Controller（控制端）：** 显示远程窗口与队列的可操作镜像，编辑配置、发指令、看执行反馈。手机控制端**不应复制加载所有视频 iframe**，以节省资源。

每个在线被控窗口拥有独立 `playerSessionId`；会话与 `windowProfileId` 不同：同一配置可以先后在不同设备打开，但每一个在线页面都有自己的实时会话。

### 7.2 两条遥控授权路径，均为需求范围

**A. 无账号临时遥控：** 被控端显示二维码或遥控短码 → 控制端加入请求 → 被控端确认 → 建立限定权限的临时授权 → 开始操作。短码须有失效时间、尝试次数限制、一次性或短期令牌；被控端可以随时撤销。不能把普通隧道的公开加入短码当成长期遥控令牌。

**B. 相同本站身份：** 如果已有可信的 Drop2Tunnel 账号/身份体系，另一台登录同一身份的设备可发现自己授权的在线 YT Collab 会话并选择控制。**不要因为缺少此身份能力而阻塞无账号临时遥控**；需要识别现有账号体系实际能力后接入。

注意：不上 YouTube 账号不等于允许匿名陌生人控制私人队列。所有遥控写操作都要服务端授权校验。

### 7.3 同步与执行流程

分离两类消息：

**实时播放器指令：** 如 `PLAY`、`PAUSE`、`SEEK`、`SET_VOLUME`、`MUTE`、`UNMUTE`、`LOAD_VIDEO`、`SELECT_CELL`。控制端发请求，服务端验证后仅转发给目标 `playerSessionId`；被控端执行并回传成功、失败或需用户手势的状态。**不可把“已发送”当成“已执行”。**

**持久配置变更：** 如 `QUEUE_ADD`、`QUEUE_REMOVE`、`QUEUE_COPY`、`QUEUE_MOVE`、`QUEUE_REORDER`、`WINDOW_LAYOUT_CHANGE`、`WINDOW_CELL_BIND`。服务端先检查版本和权限并持久化，再把最终版本广播给所有控制端与被控端。

播放器进度以节流方式上报；不得每一帧向服务端广播。建议让实时状态、长期配置、操作请求分别具有独立标识和版本号，支持重连后的快照校准。

### 7.4 故障与并发处理

- 控制端断开：被控端继续使用，队列与播放不受影响。
- 被控端断开：控制端仍可管理持久队列；播放/暂停/跳转等实时指令明确失败或不可用，不应在重连后无条件延迟执行。
- 被控端重连：以服务端的配置版本拉取最新队列及布局；实时播放位置按既定规则恢复。
- 多控制端同时改同一队列：用 revision/事务防止覆盖；冲突时返回最新版本及冲突对象。
- 遥控被拒绝、失效、撤销：立即取消写权限并通知控制端。
- 收到非法 `cellId`、过期 `playerSessionId`、不存在的队列 ID：明确拒绝且不得改动其他数据。

## 8. 播放器状态机与恢复

每个播放器至少区分：`未初始化`、`加载中`、`就绪/已提示`、`播放中`、`已暂停`、`已结束`、`错误`、`受限/不可嵌入`、`因布局隐藏而停用`。

- 页面刷新恢复到原窗口配置、原布局、每格所绑队列与最后视频；位置尽量恢复到最近持久化的 `lastPositionSec`。
- 不因页面刷新执行多路自动播放。
- 格子切换视频前先保存原视频进度；下一条/上一条应只影响该格子所属队列。
- 暂停、Seek、结束、视频不可嵌入等状态需要及时同步到控制端。
- 错误时允许继续选下一条、改为预览或在 YouTube 打开；队列成员不应自动消失。
- 考虑自动进度恢复的竞争条件：在视频准备好、可 Seek 后执行恢复，防止时间点被初始化事件覆盖为 0。

## 9. 资源预算和性能策略

**不要把创建九个 iframe 等同于九路同时播放。**多路资源消耗包括脚本、内存、GPU 解码、网络缓冲、UI 渲染及浏览器进程。

可支持以下策略，但不得违反 YouTube 的自动播放限制：

- `节能`：只有当前需要观看的格子保留活动播放器，其他格子显示视频信息/封面；
- `标准`：加载多个播放器，限制非重点格子的活动；
- `高性能实验`：尽量保留更多实例，让用户主动逐格操作，清楚提示设备耗用和政策边界。

具体是否默认开放高性能档取决于真实设备测试，不可凭静态分辨率作保证。应观察：首次加载时间、每格操作延迟、CPU/内存/GPU 使用率（可用时）、掉帧、音画同步、拖动布局卡顿、网络总量、隐藏标签页行为、手机温度/耗电与 Safari/Firefox 差异。

优化重点：避免无效销毁 iframe、减少 DOM 批量重绘、队列管理虚拟化/分页、减少状态广播频率、隐藏格子的按需卸载、媒体元数据请求去重、合理的断线重连退避。

## 10. 安全、合规与异常情况

- 使用官方播放器，保留 YouTube 原生控件、标识和链接，不覆盖、不隐藏广告，不通过裁剪规避限制；不抓取或存储视频二进制。
- 站点对外须遵守 YouTube API 服务相关条款；如果使用官方 Data API，按要求处理凭据、隐私告知、API 数据缓存及删除。个人观看次数和进度属于 YT Collab 本地业务统计，须与 YouTube 官方数据区分。
- 不从现有私人 Premium 下载功能读取 Cookie，登录 YouTube 不作为前置条件。
- 浏览器嵌入请求应正确标识来源；不要因过严的 Referrer Policy 导致播放器报错。官方播放器 API 建议正确提供 `origin` 等参数。
- 视频私有、地区限制、已删除、作者禁用嵌入、年龄限制、网络异常等，要能独立显示错误与“前往 YouTube”操作。
- 后台对窗口/队列资料访问控制不能以隐藏 URL 或短码本身替代授权；短码需时效、限速、授权确认与撤销。
- 禁止任意 URL 变成服务器端抓取目标；只识别规范化的 YouTube 视频链接与合法 Video ID，防止开放代理/SSRF。
- 对含脚本/HTML 的标题和用户自定义队列名称按纯文本安全呈现，防止 XSS。
- 匿名资料需明确存储范围与恢复策略；浏览器清理站点数据后不能承诺一定找回，建议支持手工导出与重新导入。

## 11. 推荐实施阶段

### 阶段 1：本机完整播放工作台

建立独立入口和页面、六种布局及硬条件检测、播放器实例/状态管理、每格独立队列、单格/批量静音与音量、最后视频和进度恢复、独立 QueueProfile/WindowProfile 持久化。先验证 2/3/4/9 格在目标浏览器上的行为。

**验收：** 能用不同布局观看公开 YouTube 视频；不合适布局有明确禁用原因；关闭重开保留每格视频、队列、进度及音频偏好；无九路自动播放；任何时候都完整显示播放器。

### 阶段 2：完整队列与视频资料管理

完成 URL 规范化、独立视频目录、必要元数据、合作作者的空值/手工补充、单/批量队列复制移动、排序、去重提示、个人观看次数、配置导入导出、并发修订/异常恢复。

**验收：** A→B 复制和移动正确，多个队列引用同一视频但进度不乱；批量操作失败无半完成；元数据不可得时仍能入队；配置可独立备份并恢复关联关系。

### 阶段 3：完整跨设备协作

实现 Player/Controller 会话、二维码/遥控短码、临时授权及撤销、独立控制端 UI、实时播放命令回执、实时与持久状态同步、账号身份关联（具备条件时）、断线重连和多端冲突处理。

**验收：** 电脑显示宫格、手机不加载视频也能远程管理队列/音量/布局；手机断开不影响电脑播放；电脑离线时实时命令不会假装成功；多人同时操作不会丢配置。

### 阶段 4：使用效率与性能完善（建议增强）

按真实使用反馈加入重点格子、独占音频、待看/完成/跳过、批量粘贴、时间戳标记、进度筛选、性能档位和设备兼容矩阵。此阶段不应反过来阻塞前三阶段的原始必备需求。

## 12. 关键测试场景与最终验收清单

### 12.1 布局/播放器

- [ ] 六种布局均可选择，格数与排布正确；不适用的布局能识别并解释原因。
- [ ] 浏览器缩放、系统 DPI、窗口缩放、横竖屏变化下，播放器完整可见、无控件遮挡及非法缩小。
- [ ] 从九宫格切换田字格再切回，隐藏格绑定、队列及视频状态不丢失。
- [ ] 一个格子加载失败，其余格子正常操作；错误视频可跳到下一条。
- [ ] 打开/恢复窗口不触发九路自动播放；受限浏览器脚本播放有清楚反馈。

### 12.2 队列/存储

- [ ] 每格有独立队列；同一视频可存在不同队列，条目身份独立。
- [ ] 复制不删源、移动不保留源、重复处理有提示；批量操作原子化。
- [ ] 每队列、每窗口能独立保存/导出/导入，引用缺失时有明确错误。
- [ ] 最后 URL、标题、作者（含合作作者结构）、封面、时间、进度、最后播放时间、个人播放次数按可得性保存。
- [ ] 关闭/重开恢复状态；异常退出、并发操作、网络断线不会把配置写坏。
- [ ] 静音/取消静音保留原音量；全选、多选、反选、批量调音均正常。

### 12.3 遥控/安全

- [ ] 二维码/短码绑定、确认、过期、撤销、错误次数限制均有效。
- [ ] 控制端无须打开九个视频 iframe，可操作目标格子/队列/窗口。
- [ ] 远程播放/暂停/Seek/音量/静音有目标会话与执行结果反馈。
- [ ] 同一用户（如本站身份能力可用）可发现自己的在线被控窗口。
- [ ] 控制端断线、被控端断线、重连、多端并发更新均无越权或数据串写。
- [ ] 不登录 YouTube 可以使用公开且允许嵌入的视频；无需 Premium Cookie 或 yt-dlp。

## 13. 实施原则与对开发 Agent 的要求

1. **先审计现有能力，再选择复用方案。** 不要假定用户身份、设备配对、SQLite、队列 UI 的当前实现与历史评估完全一致。
2. **不改产品定位。** YT Collab 是独立队列 + 多格观看 + 跨设备控制，不是 YouTube 原生播放列表的皮肤，也不是下载器。
3. **优先维护清晰边界。** 窗口配置、队列配置、共享视频资料、观看记录、在线播放器会话分别建模；临时播放命令和需要持久化的操作分开。
4. **不要以“技术上可以尝试”冒充“已验收”。** YouTube 播放政策、浏览器自动播放限制、无法嵌入的视频、硬件性能均需按实际运行验证。
5. **优先保证数据可恢复与可迁移。** 操作要原子化、有修订号；备份应包含队列、窗口、视频引用与个人观看记录的合理关联。
6. **阶段性交付可用功能。** 每阶段输出已实现事项、尚未实现事项、真实测试结果、兼容性与已知限制；不要将方案建议误列为用户明确的必备需求。
7. **不在开发指南中指定修改哪些源代码文件。** 具体改动范围由开发 Agent 根据当前分支结构审计决定。
