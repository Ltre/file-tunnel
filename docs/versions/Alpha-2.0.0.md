# Alpha-2.0.0：Telegram 网盘与缓存节点、SNS 下载中心、远程协作及网页工坊

## Telegram 网盘与持久存储体系

新增完整的 Telegram 网盘体系，将 Telegram 文件存储进一步抽象为可长期管理的文件空间：

* 支持目录、上传、移动、重命名、删除、搜索、多选、拖放、公开分享及跨隧道发送，并提供独立的浏览器文件缓存。
* 建立浏览器分片上传 → 服务端队列 → Telegram 的并行流水线，以及按需 Range 读取和服务端临时分片缓存，大文件可直接用于音视频预览与续播。
* 支持 Telegram OIDC、Passkey、多用户及 `disk_space` 分区，并开放独立网盘 API 供其它系统接入。
* 新增网盘后台管理、空间占用统计、审核、分片缓存清理及数据使用页面。
* 大量修复移动端触控、目录拖放、预览历史、图片缩放、媒体播放器、大文件限流、失败恢复及任务后台继续等问题。

## 隧道审计与 VClient 缓存节点

进一步补齐服务端长期运行和离线恢复能力：

* 持久记录隧道成员、传输记录、文件元数据及直接资产事件，后台可查看创建时间、活跃/历史设备、文件数量、占用空间等审计指标。
* 新增独立运行的 **VClient 缓存节点**，可长期驻留一个或多个隧道，为没有普通设备在线时继续提供文件副本。
* Admin 支持按隧道启用、停止和查看缓存节点，并新增 `/vclient` 管理视图。
* 增加缓存 SHA-256 校验、异常断线收敛、节点接管及 Shell → VClient 文件推送能力。

## SNS 下载与媒体处理

新增独立 `/sns-dl` 下载中心，与 YouTube Premium 的私人任务体系相互隔离：

* 支持 TikTok、Facebook、Instagram、Threads、Twitter/X、LINE，后续补充 Bilibili。
* 提供格式选择、指定片段、任务队列、持久缓存、预览、备注标签、失败重试及发送到隧道。
* 新增 `/video-transcode`，通过可复用方案驱动 FFmpeg 转码任务。
* 增加音视频轨道错位修正版下载，并将耗时 FFmpeg 处理改为后台队列，提供实时进度和结果缓存。

YouTube Premium 本轮继续完善歌曲内嵌封面、Album artist、Track/Disc 专辑核验和 Telegram 封面复用，但不改变 1.9.x 已建立的 Premium 基础任务体系。

## 设备远程协作与控制中心

设备交互从单次文件传输进一步扩展：

* 增加不依赖当前隧道会话的设备语音呼叫，提供拨号、来电、接听/拒绝、通话状态和铃声配置。
* 支持远程打开另一设备上的图片、视频或音乐，并持续执行上一项/下一项、播放暂停、退出全屏等控制。
* 支持剪贴板图片变化检测和快捷发送。
* 移动端“隧道”面板升级为控制中心，集中提供切换隧道、主题、设置、扫码、光媒、资源管理器和 Telegram 网盘等入口。
* 新增设备通知中心，为跨设备请求和提醒提供统一承载位置。

## 网页 ZIP 与网页工坊

新增 `.html.zip` 类型和完整的网页工坊：

* 可以创建、导入、编辑、预览和发布由 HTML/CSS/JS/资源组成的网页 ZIP。
* 使用 Service Worker 虚拟目录运行包内网站，支持相对路径、子目录、脚本、样式及其它资源，不需要先解压到公开静态目录。
* 支持草稿、目录树、文件编辑、编辑授权、更新已有传输记录以及跨设备取得新版内容。
* 针对首次运行、旧缓存、外链 JavaScript、MIME、发布竞态及更新后仍显示旧版本等问题进行了多轮修复。

## Telegram 与运行稳定性

* 新增指定 Telegram 目标转发，可保存最近目标、备注并发送原文件或视频预览。
* 新增 Telegram Bot 内容管理页，对频道、群组和私聊进行消息归档、查看和发送；聊天正文归档到 Telegram 网盘，本地仅保存索引指针。
* 聊天记录增加三天缓存、锚点双向分页和 DOM 数量控制，改善长聊天加载性能。
* 修复 Service Worker 曾导致应用外壳大量强制并发回源的问题，显著减少 PWA 首页加载时的源站压力。
* 持续扩充 Telegram 网盘、VClient、SNS、远程控制、网页 ZIP、转码及历史恢复等回归测试。

这版我建议 title 就保持这个，不再往标题里塞“视频转码 / Telegram Chat / Passkey”等次一级功能，否则 2.0.0 标题会过长。




问：



    如何评价这次1.9.5->2.0.0的升级
    
    
    
    
答：




我会把这次 `1.9.5 → 2.0.0` 评价为：**不是普通的大版本更新，而是一次“产品边界扩张 + 基础设施升级”同时发生的跃迁，2.0.0 这个版本号是合理的。**

最明显的变化，是 Drop2Tunnel 已经不再只是“隧道内做文件传输、协同和媒体处理”的工具了。1.9.5 之前，系统核心仍然围绕 **隧道 + 浏览器设备 + P2P/Relay + Telegram/SNS 辅助来源**；到了 2.0.0，已经开始出现几个相对独立、能够长期存在的子系统：Telegram 网盘、VClient 常驻缓存节点、独立 SNS 下载中心、视频转码、Telegram 内容管理、网页 ZIP/网页工坊，以及更完整的设备远程控制。

这意味着架构性质发生了变化。

### 我认为这次升级最有价值的地方

**第一，Telegram 网盘是最大的结构性变化。**

以前 Telegram 更多是：

> Bot 接入、文件备用来源、媒体发布渠道。

2.0.0 以后，它开始成为真正的**持久存储后端**。

而且不是简单“把文件发到频道”：

* 有虚拟目录；
* 有文件索引；
* 有分片；
* 有 Range；
* 有任务状态；
* 有缓存；
* 有公开分享；
* 有多用户和 disk space；
* 有开放 API；
* 有后台管理。

这一步实际上给后面很多功能提供了一个统一底座。

例如以后你做：

* MusicoletWeb 文件存储；
* S3 Compatible；
* 视频长期缓存；
* SNS 素材库；
* 数据库备份；
* 服务器之间的数据迁移；

都不需要重新发明一套存储。

所以单从架构意义上说，**Telegram Drive 是 2.0.0 最重要的变化。**

---

**第二，VClient 把“在线浏览器设备”扩展成了“常驻基础设施节点”。**

这个意义也很大。

以前：

> 浏览器打开 → 设备在线 → 可以成为 Provider。

现在：

> 可以有一个独立进程长期驻留，专门承担文件缓存和供源。

这等于把系统从：

> 浏览器应用

逐渐推进成：

> 浏览器客户端 + 常驻节点 + 服务端协调

这种拓扑。

而且你没有直接把 VClient 粗暴做成服务器内部的缓存逻辑，而是仍然把它当作一种特殊客户端，这个设计是比较正确的。

它保留了现有文件资产协议的统一性。

以后即便出现：

* Linux CLI Client；
* NAS Client；
* Android 后台节点；
* 中继节点；

都可以继续沿着这个抽象发展。

---

**第三，2.0.0 开始出现真正的“应用平台”倾向。**

网页 ZIP / 网页工坊是这一点最明显的信号。

`.html.zip` 已经不只是“上传一个 ZIP”：

> 编辑 → 草稿 → 文件树 → 资源引用 → 权限 → 发布 → Service Worker 虚拟目录执行 → 更新原记录。

这实际上已经是一个小型的：

> Web App Package Runtime

甚至可以理解成 Drop2Tunnel 内部的“小程序雏形”。

和 Telegram 网盘放在一起看，就更明显：

> 网盘负责资产
> 网页工坊负责内容生产
> 隧道负责分发
> 浏览器负责运行

这个组合已经远远超过文件传输器。

---

### 设备能力也明显跨了一层

1.9.5 有摄像头共享，但 2.0.0 里设备间能力开始形成一套控制体系：

* 全局语音呼叫；
* 远程媒体预览；
* 上一项/下一项；
* 播放/暂停；
* 退出全屏；
* 音乐播放器接管；
* 剪贴板图片快捷发送；
* 设备通知中心；
* 移动端控制中心。

也就是说，“设备”从：

> 文件来源 / 接收者

开始变成：

> 一个可以被发现、通信、控制、调用能力的端点。

这是另一个很关键的产品方向变化。

---

### SNS / YouTube 这一块，则是从“功能”变成“工作流”

1.9.5 其实已经有比较完整的 YouTube Premium 能力。

所以 2.0.0 真正值得说的不是“又增强了 yt-dlp”。

而是媒体链已经越来越完整：

> URL
> ↓
> 解析
> ↓
> 下载
> ↓
> 指定片段
> ↓
> 元数据处理
> ↓
> 音轨修复
> ↓
> 视频转码
> ↓
> 浏览器缓存 / Telegram 网盘
> ↓
> 发到隧道 / Telegram

尤其 `/sns-dl` 被独立出来以后，YouTube Premium 和通用 SNS 终于在业务层真正分离，这比继续往一个页面里塞 extractor 要健康得多。

---

## 但这次升级最大的隐患也非常明显

就是：

**功能增长速度已经明显快于架构收敛速度。**

91 个 commit、约 140 个文件变化，而且跨度覆盖：

* 文件协议；
* Telegram；
* 用户系统；
* 网盘；
* IndexedDB；
* Service Worker；
* FFmpeg；
* yt-dlp；
* WebRTC；
* WebAuthn；
* OIDC；
* 网页运行时；
* 后台任务；
* 虚拟客户端。

这已经不是“小项目加功能”的复杂度了。

从开发日志里其实已经能明显看到这种压力：

> 【有BUG】
> 【有严重BUG】
> 先固定代码
> 修复上一轮
> 再修复修复后的竞态

这并不是说质量差，而是说明**系统已经进入复杂系统阶段**。

以前一个功能出错，可能只是一个 modal 或一次 transfer。

现在一个改动可能影响：

> Service Worker → 页面加载 → Runtime → IndexedDB → Telegram → 后台任务。

例如网页 ZIP 和 Service Worker 那一串问题就是典型案例。

---

## 目前最应该警惕的三个技术债

第一是 **Telegram 网盘的数据层**。

你自己后来也已经意识到了：

```text
telegram-drive-index.json
telegram-drive-directories.json
disk-shares.json
disk-operations.json
disk-auth.json
...
```

继续用多份 JSON 支撑：

* 多用户；
* 并发操作；
* 分享；
* 上传事务；
* 目录操作；

规模再上去风险一定会越来越高。

所以你后来规划的：

> SQLite + WAL + transaction

我认为不是优化，而是**迟早必须做的结构性重构**。

---

第二是 **app.js 已经太重**。

这次 diff 里 `app.js` 又增加两千多行，而同时已经出现：

* `disk-ui.js`
* `telegram-content.js`
* `web-workshop.js`
* `audio-track-repair.js`

说明实际上你已经在往模块化迁移。

下一阶段最好继续把：

* 隧道控制中心；
* 远程设备控制；
* preview；
* clipboard；
* history actions；

逐渐从 `app.js` 拆出去。

否则以后一个功能修改导致首页初始化回归的概率会越来越高。

---

第三是 **Service Worker 已经成为关键基础设施，而不是普通 PWA 附属代码。**

现在它承担：

* PWA 缓存；
* 页面启动；
* 网页 ZIP Runtime；
* 虚拟资源；
* MIME；
* Range；
* 版本更新。

所以以后 SW 修改最好视为和 `server.js` 同级的重要组件。

2.0.0 期间已经出现过：

> 为了容错预缓存，结果把整套 APP_SHELL 强制并发回源。

这种问题非常典型：局部修改合理，但全局行为发生巨大变化。

---

## 从版本命名来看

如果只是：

* Telegram 网盘；
* 或 VClient；
* 或网页 ZIP；

单独任何一个，我都未必认为必须升 2.0。

但是这次是这些东西**同时出现**。

所以从产品演化来说：

> **1.x = 以 Tunnel 为中心的跨设备传输工具**
> **2.x = 以 Tunnel 为核心、向存储 / 媒体 / 设备协作 / Web Runtime 扩展的平台**

这个分界是成立的。

甚至我认为你这次的 `2.0.0` 比前面的 `1.8 → 1.9` 更有“大版本”的理由。

### 综合评价

如果简单打一个工程意义上的评价：

**功能价值：很高。**
出现了 Telegram 网盘、VClient、网页 ZIP 这几个可以长期支撑后续发展的基础模块。

**产品跃迁：明显。**
已经开始从“文件传输工具”变成“跨设备个人基础设施”。

**架构压力：也很高。**
模块数量和状态机数量已经跨过一个临界点，后面不能继续只靠功能迭代，需要专门投入版本做数据层、模块边界和运行时治理。

所以我会把 Alpha-2.0.0 定性为：

> **Drop2Tunnel 第一次真正的平台化版本。**
>
> 1.x 主要解决“东西怎么在设备之间流动”；
> 2.0 开始解决“东西存在哪里、谁长期保存、如何加工、怎样运行、设备之间还能做什么”。

这才是这次升级最值得强调的地方。
