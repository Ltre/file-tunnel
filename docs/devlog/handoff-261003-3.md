## 已落地的核心实现

### SQLite / 三层生命周期

- 新增 `server/disk-content-repository.js`，`disk.sqlite` schema v2；Logical File、共享 Content、物理 revision / Telegram Anchor 分离。
- Key：`sha256:v1:<size>:<完整 SHA-256>`，不包含名称、目录、MIME、用户或 Bot；没有 content block。
- 新表：`disk_contents`、`disk_content_keys`、`disk_content_revisions`、`disk_content_anchors`、`disk_content_parts`、`disk_content_refs`、`disk_content_leases`、`disk_content_cleanup`、`disk_content_pop_challenges`、`disk_content_batches`、`disk_content_claims`、`disk_content_caption_jobs`、`disk_content_legacy_history`。
- 最新未验证补丁另增 `disk_content_revoked_sessions`，见下文。
- `disk-content-repository.js` 的 `syncFile()` 与 Logical 写入同一短 SQL 事务，维护 refs、版本、CAS、claim/lease/grant；异步网络或 hashing 不进入写事务。
- `disk-repository.js` v1→v2 前先 `VACUUM INTO` 一致性备份，再同事务包装旧记录；超过支持 schema 拒绝启动。
- 旧记录只按完全相同的物理集合保守归并；部分 Anchor 重叠设为 `anchor_conflict`，旧 history 隔离，不猜完整 SHA 或历史后端。
- 删除最后一个引用进入 DELETE_PENDING，60 秒宽限；读/证明/复用 lease 保护消息。GC 原子 claim DELETING、移除 canonical key、token fencing、退避重试，保留 47 小时 57 分钟占位替换。
- 当前 revision、隔离异常、旧 revision reader 都受保护。退休清理只标记实际清理的 Anchor，不能把仍被当前 revision 使用的封面误记为 CLEANED。

### 上传、持有证明、整批提交

- 新增 `client/disk-content-hash-worker.js`，1 MiB slice 增量 SHA；随机字节与 Node SHA 对照测试已通过。
- 新增 `server/disk-content-proof.js`；普通、第三方、协同 API 增加 `/content/preflight`、`/content/proof`、`/content/release`。
- 同实际用户持有可直接取 reuse ticket；跨用户必须 PoP，32 Byte nonce、最多 8 个分散 64 KiB 样本，客户端仅提交摘要，不返回服务端 expected digest 或其它用户来源。
- proof/claim 绑定 viewer、登录指纹、owner、scope、应用、协同授权代次、目标 name/path/MIME、size/hash；15 分钟有效期、一次性消费、有配额和限流。
- 命中后不发正文，不重新 sendDocument/sendMediaGroup，不再上传封面；批内重复内容共用首个构建。
- MISS 保留渐进 staging、独立 reader/writer、现有 Telegram 调度及 Album finalization。Node 实际完整 SHA 验证后才持久化可信结果；声明不符不能提交或误恢复为成功。
- v3 manifest 持久化候选、完整 SHA、claim、reuse lease、批内复用、空文件和授权上下文；整批全部就绪后才提交所有 Logical/ref/batch marker。
- 命中 lease/claim 定时续租；重启检查 SQL batch marker，已提交不重建引用。过期 lease 仅在内容仍可用且摘要匹配时重建；UNKNOWN 仍不盲重发。
- Worker 或 WebCrypto 不可用退回普通正文上传；取消仍作为取消。没有破坏旧客户端上传协议。

### Repair / S3 / 协同 / 缓存

- 同二进制 repair 切 Content physical revision，全部引用受益；协同 replacement 只切该 Logical 绑定并递增 logicalContentVersion，含同长度和 0 Byte 替换。
- 协同按真实 viewer 验证 PoP；`disk-collaboration.js` 维护成员授权代次，踢出再加入不能使用旧 proof/在途上传。
- `syncFile()` 直接查询当前 SQLite collaboration payload，避免另一连接撤销成员后仍由旧内存快照提交；还检查根范围和文件 ID。
- S3 同用户、同 Bot Copy 直接建引用；完整 SHA 声明 PUT 仍接收并验证全部正文/MD5，命中零新 Telegram 消息；UNSIGNED/未知 hash 流保留早推，EOF 后 canonicalize，可能有 loser 消息补偿。
- 不提供跨账号 S3 Copy；不同 Bot 不裸复用 file_id。相同 Bot 但不同 backend UUID 的并发 canonical 处理仍保守，不假定跨后端都可共享。
- Range / Share / thumbnail / S3 GET 固定 revision lease；上游等待后重新核对 Share/协同授权。
- 浏览器正文、thumbnail、播放进度按 Logical ID + logicalContentVersion；同内容 repair 保留，异内容 replacement 失效。
- 分片缓存保持 2 天；按用户/分区清理前重建全部共享片 owner。分享缓存 7 天、P2P/provider/Chat 字典原链路保留。
- 当前没有可信容器 parser：mediaIndex 明确 unavailable，不信客户端 ranges/offsets。未增加 HLS。

### Caption / 工具 / 部署

- 共享 caption 只含 Content/revision/physical part/消息定位及可选首次排障名；Logical rename/move/review/share/collab 不编辑共享 caption。
- 最终 caption 由 typed outbox 补注，不在 SQL 提交前重写；响应丢失后的 not-modified 幂等完成，不重传正文。
- 关键 ID 不整体截断；过长关键字段报告 BLOCKED。清理和 caption jobs 有独立 token/lease/retry。
- 新工具 `tools/migrate-tgdisk-content-objects.cjs` 和 `.md`：默认只读预检，apply 要 `--service-stopped`，先内置备份、再结构包装，校验 integrity/FK/引用一致性，无 Telegram 或自动全库 hashing。
- `change-tgdisk-channel-id.cjs` 更新 typed revision/Anchor/caption/outbox，查消息身份冲突；`hasChannel()` 包含其它 scope、在途上传、退休 revision 和清理债务。
- JSON→SQLite 原工具保留幂等性；诊断工具只输出 Content 聚合计数，不输出 PoP/secret/正文。
- 后台 `/api/telegram/disk-admin/content-objects`、`/:id` 返回汇总/详情；`/:id/verify` 返回 202 operation，显式全文件 SHA 验证，`merge:true` 才合并历史对象。
- build 纳入 Worker 指纹重写、新文档及迁移工具；SW 缓存为 `instant-tunnel-v78-content-v1`。
- 新说明 `docs/telegram-drive-content-objects.md`；传统 API 和 S3 两文档分别更新，未混淆两套协议。
