### 第 1 项：已展开的 Markdown 进入对话框仍长时间等待

**复现及根因：**

- 使用真实捆绑的 Marked、DOMPurify 和 `client/tunnel-markdown.js`，构造包含 X 原帖链接及四张隧道引用图片的记录。在行内四张图片全部显示后，阻塞后续资源读取，再打开真正的 Markdown 预览对话框。
- 修改前，对话框正文保持隐藏，卡在“正在加载 Markdown…”。不先展开、直接阻塞首次媒体读取时，也无法看到正文。两项浏览器断言均失败。
- 行内 `mount()` 已经持有图片 Blob URL；`previewRecord()` 却另行执行 `resolve()`，逐个重新读取所有引用，并在 `content.hidden = true` 的状态下等待全部资源及图片加载。单张图片的加载等待上限为 15 秒，读取引用本身还可能等待网络。
- 复现后分别核对重复读取、整页显示条件、图片加载等待三条路径。未发现点击预览再次启动 SNS 帖子转换；打开时仍会进行本地 Markdown 解析，但已保存正文被资源读取及图片等待挡住，才是本次可以复现的等待原因。

**实际修改：**

- 对话框先显示经过原有解析、净化处理的正文；首次引用尚在读取时保留非阻塞的加载提示，并用待加载状态区分，不将其提前标为未获准或已失效。后续失败仍显示正文、具体错误和重试入口。
- 用 WeakMap 关联同一个消息对象、相同正文、仍连接在页面中的行内预览。对话框复用其已读取结果，或等待其已经开始的同一次读取，不重复下载四张已显示的图片。
- 常见的已展开记录只解析一次对话框内容；首次读取尚未完成时先显示正文，再更新引用内容。修改后的正文或不同消息对象不借用旧映射，重新按原读取接口解析。
- 引用结果采用独立、幂等的使用计数：行内预览、一个或多个对话框可共享同一组 URL；全部视图释放后才撤销 URL。关闭过程中迟到的读取结果会释放，移除行内记录不会提前破坏仍打开的对话框。
- 复用范围限于本页当前记录已取得的资源；没有新增全局字节缓存、持久化缓存或来源授权，也没有修改隧道传输、网盘 API、账号或 SNS 转换流程。原引用数量和总字节限制保持不变。
