## 2. 先看结论：最终版本究竟与旧版差在哪里

1. **原生 WebRTC 建链区域相同，但整个链路不相同。** 两端相应区域规范化后均为 15085 个字符，SHA-256 均为 `6244a29a1d945a17401713fd339651a2fd133bdf1d62097dbd28c11e4575edd3`。隧道准入、来源授权、历史事件、恢复入口、缓存写入、发送进度、接收隔离和服务端信令处理不在这个“相同”的结论范围内。
2. **文件调度、分块、背压和主要失败分支，已经在 4102438 撤回到旧版做法。** 33 个常量相同；九个关键方法除明确保留的 UI／诊断调用外，AST 控制流相同。11 月中旬曾加入的 `abandonedAttemptId` 和 `file-asset-progress` 协议，最终 HEAD 都已撤回，不能再当作现有实现描述。
3. **仍保留了后来的传输类差异。** 包括来源身份／凭据及锚点、发现元数据合并、实际范围开始才显示进度、发送范围汇总、异步完成与迟到尝试隔离、负完成回执、Relay 实例隔离和实际连接采样。
4. **外围流程的变化比两个传输文件更广。** 准入和授权失败、历史没有触发补源、缓存状态判断、服务端媒体恢复、目标副本证明等，都可能在正文开始前结束流程；只把两个文件换回，不能等同于恢复整个隧道传输。
5. **当前显示仍有与实际线路不一致的旧有口径。** 多源接收统一报告 `receiving-multi-source`，UI 将其解释为 P2P，即便某个实际范围走了 Relay；旧基线也这样。当前发送端的新汇总则是供源端本机口径，不是接收端已持久保存的比例。因此，“接收显示 P2P、某供源显示 Relay”本身不能证明两端描述的是同一个范围或同一条线路。
6. **其它业务不能随链路一起回退。** 串流台、媒体库、网盘分区／协同／多账号／Content／S3、Markdown 帖子、网页回源、后台出口管理等均有新增或实质扩展；它们与隧道授权、缓存、历史和资源生命周期有具体连接点，第 9 节逐项列出。
7. **失败状态没有被历史通过记录覆盖。** HEAD 已明确保存为“不传输”的失败产物，用户本轮继续要求恢复。此前隔离 Chrome／Node 测试通过，只能说明对应条件下通过；本轮没有证据确认真实现场停传、SNS 低速、代理影响和进度异常已经解决，也没有凭这次静态对比确定唯一根因。

## 6. 改过哪些 BUG，哪些仍不能算验收通过

### 6.1 传输和缓存

- **缓存正文被还原元数据覆盖：** 最终写入保护在同一 IndexedDB 写事务内读取当前记录，合并时保留已完整正文／缓存引用及相应完整状态；内存回退也不拿过期快照覆盖后来完成的正文。显式清缓存通过单独选项保留原语义。证据 E02:1001。
- **不同来源身份串用：** 跨隧道请求从只传来源 ID，升级为来源隧道对应的设备身份和授权对象；解析失败不借用另一身份的旧凭据。证据 E04:301、E23。
- **来源锚点／队列元数据丢失：** discovery 和 available 合并已有请求信息，保留 `recordMessageId`、跨隧道来源和目标副本所需字段。证据 E04 的 `sourceAuthorization / requestProviderDiscovery / handleAvailable`。
- **无实际范围仍显示空进度：** 清单到达不立即建立 0% 多源行；范围开始才显示；全等待／失联清理空闲显示、保留任务。证据 E04 多源方法。
- **迟到分块／完成污染新尝试：** 核对 provider、attempt、活动 range；等待异步块／writer／store 后再核对同一实例。被拒绝的 P2P／Relay 完成不再回成功 ACK。证据 E04:961、2003、2339。
- **Relay 旧启动清掉新实例：** 清理前校验对象仍是当前 relay；生命周期拒绝仍失败回 ACK，但不全部当通用服务异常。证据 E05:664。
- **内网 IP 探针解析错位：** 修正 ICE candidate 提取表达式，跳过 priority 字段再读地址；这不是创建新的 LAN 传输协议。证据 E02:1519。
- **进度多次归零／过早满值：** 做过范围汇总、最多 99%、完成确认及 UI 清理修改；但这不是整个现场问题已解决的证据，当前比例仍有第 8 节所述限制。

### 6.2 转发、网页与 Markdown

- 增加目标隧道副本证明、持久历史查询及目标锚点，处理目标成员没有来源隧道 grant 时的合法副本读取。
- 保护转发的固定来源／目标身份、权限及重复请求：超时结果不明确时沿用同一记录并查询确认，不立即再造一份记录。
- 粘贴图片新增已消费签名及去重，处理重复发送；网页工坊补充移动触摸拖放、路径引用和发布状态。输入区增加自适应高度与对应键盘处理。
- 增加网页编辑来源凭据、源锚点／root、版本核验、撤权和回源队列；最新处理同源多副本连续编辑。
- X 帖子四图、视频清单、作者、Markdown 刷新引用、附件删除／复活及转发组做过对应修正。
- Bilibili HTTP 567 后一次 Range 兜底已经在最终源码；当前阶段真实外网媒体测试记录仍有 DNS 失败，不能写成当前真实下载全部通过。

这些代码属于必须评估保留的功能／修正，但用户仍反馈过来源隧道授权错误，且最新 HEAD 是失败版本。不能用“存在副本判定函数”取代合法目标副本真的能读、能同步的验证。

### 6.3 网盘、账号和后台

- 修正分区、挂载、账号、路径、导入及操作来源的作用域；补充上传重名、取消、任务恢复和目标定位。
- 处理批量上传时目录响应、HTTP 连接占用、远端确认进度和失败分类，避免把服务端失败一概写成用户取消。
- 加入浏览器缓存身份／内容版本检查，避免逻辑文件更新后误复用旧正文或缩略图。
- 处理账号切换／登录回调的旧请求交叉和弹窗交接；Telegram App 灰度表现不能仅凭桌面回调通过下结论。
- 最后层定位并修正统一出口包装把 Telegram 同步 `parts()`／`setAnchorGuard()` 变成 Promise，导致后台读取路由把 Promise 当分片数组的问题；现在只包实际远程方法，保留同步接口。默认 `disk_space=` 合法，不是该故障的直接根因。证据 E25:220 附近。
- 已锁定格式票据交给新下载任务时，主动保存继承的出口记录，覆盖“直连成功但详情暂无记录”。没有把直连排除在正常记录之外。证据 E25:237。
- 手写格式、歌曲证据、音乐文件名、FFmpeg 进度及翻译／主题对比度做过局部修正，保留各自原业务边界。

### 6.4 基础设施与安全

- 基础审计数据库从 sql.js 内存导出改为 `node:sqlite` 原生连接和 WAL，避免运行中导出导致句柄关闭／全量快照问题。
- 数据层增加事务、版本／删除状态和查询索引，审核／共享引用／清理走相应逻辑文件边界。
- 新增密钥文件初始化工具及并发创建保护、回调安全字段、上游目标地址／重定向保护和敏感日志过滤。
- 锁文件中 Engine.IO 为 6.6.11，并提供对应安全修复工具；新增依赖和 Node 下限见第 7 节。

本节没有把这些问题都归因于最后一次提交：它们分布在 9 月到 11 月，多次提交带有“有 BUG”“未完成”说明，现场验收可能推翻阶段结论。

### 7.2 当前仍生效的策略变化

- **授权：** 知道隧道 ID 不等于有访问权；来源请求使用对应身份／grant。目标合法转发副本另按目标所属关系和服务端证明读取，而不是要求所有目标成员都加入源隧道。
- **转发：** 固定发起时上下文，确认目标记录持久保存；重试不重复生成身份。目标副本、Markdown 附件和网页可编辑来源分别处理，不能把三者的权限混为一个开关。
- **缓存：** 元数据写入保护完整正文；用户明确清理保留独立入口；旧 OPFS 可读兼容保留，但不启用新的 OPFS 接收写入。
- **多源显示：** 清单和等待不代表已经传字节；实际范围开始才显示，空闲 UI 可以清掉而任务保留。
- **发送显示：** 本机汇总改为“文件＋接收设备”，范围 ACK 不代表整文件完成；最多 99% 到最终确认。该口径仍不是接收端实时已存字节。
- **上游出口：** 首次取得所需有效内容／格式前允许候选轮询；成功后锁定；并发任务隔离；写请求不因统一适配而任意重放；新任务不继承其它任务碰巧成功的节点。
- **轮询等待：** 最终候选循环没有固定 30～60 秒间隔，也没有统一“每 10 秒切换”的定时器；通常等待上一请求失败／超时后才继续。请求超时和候选间隔不能混写，不能为了“10 秒”切换已经成功锁定的出口。
- **格式缓存：** YouTube／SNS 持久解析缓存仍在，命中缓存不是本次网络尝试成功；格式票据、出口记录与媒体字节缓存是不同对象。
- **表单云保存：** 由用户显式选择；编号冲突先到先得，按本地与服务端已占号分配空位；取消云保存保留本地内容。
- **任务生命周期：** 关闭面板不取消后台工作；切换账号、目标或页面不把已发起任务改绑到新上下文。
- **文案／语言：** 下载菜单简化为“下载”、串流术语改“收藏”；初始中英与延后下载其它语言包；中文参考信息保留 `zh` 兜底而非禁止该代码。
- **运行环境：** package 声明 Node `>=22.16.0`，新增固定 `undici 7.30.2`、`ws 8.21.0`；不能把“Node 22”当作任意 22.x 均满足声明。sing-box 组件与上述 JavaScript 依赖分开管理。

## 8. 传输链路：经历过什么、最终剩什么

### 8.1 先把“链路”分成可理解的层

```text
加入隧道／取得身份和权限
    → 历史／实时记录到达
    → 识别文件及本机是否缺完整缓存
    → 普通资产补源，或服务端媒体恢复队列
    → 来源与目标副本授权、发现在线供源／清单
    → 整文件或多源范围调度
    → WebRTC 信令、PeerConnection、文件 DataChannel
    → P2P 发块；按原有条件失败处理／Socket.IO Relay
    → 接收范围／正文、校验、写缓存、完成 ACK、广播可供源
    → 各业务记录刷新、下载／预览、进度绘制及隐藏
```

恢复其中一个框不等于恢复全部。授权或记录事件没有进入调度，可能既无进度也无正文；显示错误则可能正文继续走、UI 不准确。这是需要区分的故障类别，**不是本轮已确定当前停传发生在哪一框**。

### 8.5 当前发送／接收进度的精确含义和限制

**整文件发送：** 循环提交数据块时，以本机已提交字节减当前 DataChannel 缓冲量报告，最多 99%；等待排空和接收完成 ACK 后才报 100%。这不等于每次绘制都读到了接收端落盘字节。

**范围发送：** 以文件＋接收设备汇总，范围键为起止位置，同一范围只保留最大累计值；分母是整份文件大小。某个供源只发送一部分范围时，它的比例并非“本供源任务完成百分比”，也非其它供源合计后的接收比例。范围 ACK 不直接把整份文件置为 100%。

**汇总完成：** 收到接收端完整缓存 available 时结束对应汇总；如果供源没有收到该通知，本机行可能留到空闲清理。当前最多 64 个汇总组，90 秒无更新会清理未完成显示。该限制只清理 UI 状态，不证明文件丢失。

**刷新节奏限制：** 背压／排空等待内部已恢复旧版，不会因为等待而周期性刷新发送比例；因此一段等待期间发送 UI 可能停住，而接收端仍推进。当前以范围最大值累计也不会在重试时把旧估计倒扣。本轮没有以这些静态事实直接认定用户所有“0%、99%、消失再出现”的现场都已解释完。

**多源接收：** 按已完成范围＋活动范围已收字节统计，最多 99%，全部写入完成再显示完成。`reportMultiSourceProgress` 固定报告 `receiving-multi-source`，显示函数固定解释为 `multi-source P2P`；不读取各范围真实 `transport` 来构成线路标签。这一处理与旧基线相同。

因此，当前版本不能保证“进度条写 P2P，所以整份文件所有范围都走局域网直连”；也不能从某供源显示 P2P 推断另一供源没有 Relay。中途出现过的复合线路／远端进度方案与当前源码要分开，不能从历史现场直接断言当前仍使用那个协议。

### 8.6 服务端 Relay 的最终净变化

- 启动阶段保留本次 relay 对象，接收端拒绝后只清理仍匹配的那个实例。
- 将未请求、旧请求、已有 P2P／整文件／多源／传输等生命周期拒绝分类记日志并失败 ACK；不假报传输成功。
- “接收端已有完整缓存”原来就是幂等成功，不是这次首次加入。
- 完成阶段增加 phase、耗时和关键 ID 的错误诊断；原来的接收端完成 ACK 和 90 秒等待保留。
- 最终未加入 `file-asset-progress` 服务端中继，也未保留放弃尝试字段。

### 8.8 SNS／服务端媒体的恢复链路：旧逻辑和新接入信息

静态 AST 核实，以下五个辅助函数在两个端点相同：`hasCompleteFileCache`、`shouldAutoRequestFileAssetCache`、`requestServerAssetWithPeerPreference`、`scheduleServerAssetRecovery`、`drainServerAssetRecoveries`。

其中恢复流程原本就包含：检查完整缓存／主动清理状态；队列并发最多 2；先请求在线设备；在下载队列时等待出队；默认等 3500ms 再检查；已有整文件／多源／供源传输活动时保留；没有活动则取消该补源工作并进入 HTTP／Telegram 回源。YouTube Premium 的现成副本有专门直接回源分支，手动入口还可给更长 peerWait。

**差异在调用方和保存／授权外围：** 自动／实时／预览／资源恢复等入口补上目标记录锚点，收到正文后保留 `isServerAsset`／URL 等业务信息，来源授权变成对象，服务端增加合法副本判定和持久引用兼容。

所以，不能把 SNS 的特殊恢复队列全部归为近期造成的策略退化；同样，也不能因队列函数相同就排除入口、权限、回源、缓存或数据来源变化。当前没有足够现场证据把“SNS 媒体慢”统一归因到其中一项。
