| 方案 | 优点 | 成本与局限 |

### 第 7 项：多域名 Passkey 调查与处理建议（仅分析）

1. 当前缺口可以从源码确认：disk-auth.passkeyOptions 按账号名找到同一用户后，要求凭据 rpID 精确等于服务端识别的 Origin.hostname，生成的 RP ID 也取该 hostname；不匹配就在 options 阶段返回 PASSKEY_ACCOUNT_NOT_FOUND，尚未调起客户端验证。verify 同时验证注册时保存的 RP ID、挑战及 Origin。本轮没有修改这些代码或真实凭据。
2. WebAuthn 的 Origin 与 RP ID 是不同概念。Origin 含协议、主机及端口，客户端签名数据携带实际调用来源，服务端应按受信来源核验；RP ID 是域名范围，不含协议/端口。凭据绑定 RP ID，不靠账号名就能搬到另一个 RP ID。浏览器在调起认证器之前会校验调用域名能否使用指定 RP ID，并非服务端单方面允许就够。[W3C WebAuthn Level 3](https://www.w3.org/TR/webauthn-3/)
3. 例如 a.example.com 与 b.example.com 可以使用共同的 example.com RP ID，但已经绑定 a.example.com 的旧凭据不能只修改数据库字段就变成 example.com 凭据。不同可注册域名更不能直接互换；系统使用多个域名与凭据安全作用域是两件事。
4. Related Origin Requests（ROR）允许受控的不同来源使用同一个 RP ID：原 RP 域名通过 HTTPS 的 `/.well-known/webauthn` 列明允许来源，B 的请求仍用 A 的 RP ID，服务端仍核验实际 B Origin，而非伪装为 A。浏览器/提供方需要实际支持；仅增加 CORS、改密码管理器显示分组或让服务端按同账号返回所有 key，均不能绕过客户端的作用域校验。[Google/Chrome 说明](https://developer.chrome.com/blog/passkeys-updates-chrome-129)、[ROR 配置及浏览器支持说明](https://web.dev/articles/webauthn-related-origin-requests)
5. Google 密码管理器保存/同步凭据并不意味着同名账号的密钥可跨任意网站选取。应区分密码自动填充的关联规则、界面分组、Passkey 的 RP ID、浏览器 ROR，以及原生应用的 Digital Asset Links。Google 官方提供跨网站/Android 应用关联配置示例，但不能据此宣称用户的具体国产浏览器已支持。[Google 凭据共享实验](https://codelabs.developers.google.com/seamless-credential-sharing)
6. 业界调查：Google 已公开提供 ROR 能力、配置示例及密码管理器配合示例；这证明存在标准化复用方式，不足以确认 Google 账号所有生产域名都直接采用该方案。GitHub 官方资料确认域名绑定、同步和跨设备认证；本次没有查到足以证实 github.com 与另一不相关域名共享同一 Passkey 的官方说明。对 github.com/.well-known/webauthn 的单次公开读取返回 404，对 Google 对应地址的工具读取不可用；这些结果不能推出它们所有域名都不使用 ROR。[GitHub 官方资料](https://docs.github.com/en/authentication/authenticating-with-a-passkey/about-passkeys)
7. 建议方向：先固定可持续拥有的 RP ID，保留已有凭据的原 RP ID；为明确受信的新域名评估 ROR，并验证目标浏览器/密码管理器。若客户端不支持，可评估统一认证域名的独立登录窗口及一次性回执，让业务页留在原地；它依然使用原 RP 下的同一凭据，但涉及跨域回执和各域会话签发，不能复用同源 Cookie 假装完成。旧域名失去控制或无法提供所需认证/声明时，不能承诺旧凭据无条件迁移。禁止为了兼容而移除 Origin/RP ID 检查，或信任任意请求主机作为跨域授权。
8. 结论：产品不必限制为单一业务域名，但“添加任意新域名即自动复用旧凭据”不是当前代码或标准的无条件能力。本条仅记录分析建议，不添加配置、ROR 端点、认证窗口或修改凭据绑定。

### 第 1 项：废除中间宽度纵向堆叠布局

- 原默认样式在 1200 CSS px 以下改单列，767 CSS px 以下才启用移动选项卡；中间区间因此出现 C 型。布局没有硬件分辨率/DPI 联合门槛，主题另有列宽覆盖。两个 2560×1600 平板在不同浏览器中仍可能具有不同 CSS 视口；没有取得原设备视口、缩放和实际样式数据，不能把具体设备差异唯一归因于某一系统设置。
- 改为 A/D/B：**≥1100 CSS px** 三栏，1100～1200 使用紧凑列宽；**768～1099 CSS px** 两栏；**≤767 CSS px** 沿用底部选项卡。桌面固定工作区及面板内部滚动扩展到两栏范围，避免重新出现整页纵向堆叠。
- D 型在传输记录标题栏右侧提供 `📝协同编辑`，展开原有编辑器到顶栏以下区域，保留内容、同步及发送入口。关闭按钮、边缘遮罩与编辑区域内 Escape 支持收起；跨断点时清除展开状态。没有克隆或重建编辑器，顶栏仍可见、可操作。新按钮复用已有 `协同编辑`、`关闭` 翻译项。
- 浏览器验证覆盖 1440、1201、1200、1100、1099、1024、800、768、767、390 CSS px 与默认/graphite/atelier 三种主题，核对列数、面板对齐、正文宽度、水平溢出和工作区底部。1024×800 核对遮罩上边缘不越过顶栏、编辑内容经关闭/重开和改变宽度保留。

### 第 2 项：小窗精简与整窗拖动
