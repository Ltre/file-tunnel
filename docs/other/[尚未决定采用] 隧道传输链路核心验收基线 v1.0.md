# **Drop2Tunnel 隧道传输链路核心验收基线 v1.0**



&#x20;只读分析

基于 `dev/2611-s1`

未修改代码或仓库文件



这份基线的目的很明确：**以后无论修什么 Bug、增加什么功能，都不能把已经正常工作的隧道传输能力改坏。**

我检查了 `dev/2611-s1` 分支中的客户端传输逻辑、服务端文件资产调度、WebRTC 连接管理、缓存恢复逻辑和相关回归测试。

建议把验收要求分成两级：

- **P0：硬性指标。** 任意一项不通过，就不能认为新版本的传输核心合格。
- **P1：性能与体验指标。** 需要记录基线数据，防止功能虽然还能用，但速度、成功率、稳定性明显倒退。

下面的内容区分了**分支现有能力**和**建议固定的验收要求**。尤其是速度阈值，不能在没有实测的情况下凭空写一个数字。

## **一、P0：传输核心不可退化指标**

### **A. 传输路径与自动降级**

| 编号        | 核心指标          | 必须满足的验收条件                                                          |
| --------- | ------------- | ------------------------------------------------------------------ |
| **P0-01** | WebRTC P2P 优先 | 两端已建立可用的 WebRTC 文件数据通道，且处于正常选择窗口内时，文件数据应优先通过 P2P 传输。不能无故全部改走服务器中继。 |
| **P0-02** | P2P 失败自动降级    | WebRTC 建立失败、文件通道超时或实际发送失败时，应自动尝试 Socket.IO Relay。用户不需要重新发送文件。      |
| **P0-03** | 降级不得重复传输      | P2P 已成功完成的文件，不得因为迟到的超时、失败事件，再启动一轮 Relay 传输。                        |
| **P0-04** | 单文件路径唯一有效     | 同一文件可以经历不同传输尝试，但同一时刻不能出现两个相互竞争的有效尝试，导致重复写入、进度混乱或结果覆盖。              |
| **P0-05** | P2P 背压处理      | DataChannel 缓冲区暂时拥塞时，应等待可继续发送，不能直接误判为失败并启动重复 Relay。                |
| **P0-06** | 连接复用          | 同一对设备并发请求多个文件时，应尽量复用已有 PeerConnection，不能为每个文件无意义地重复协商、重复创建连接。      |

**这里需要固定一条原则：**

> P2P 优先是传输策略要求，但不代表所有网络环境都必须成功建立 P2P。验收应检查实际传输路径，而不是仅凭局域网、VPN 状态或前端提示推断。

例如，两端网络条件允许 P2P，但最终却全部使用 Relay，这属于需要调查的退化；如果实际 ICE 无法连通，自动走 Relay 则是正常行为。

### **B. 文件完整性与完成状态**

| 编号        | 核心指标       | 必须满足的验收条件                                                        |
| --------- | ---------- | ---------------------------------------------------------------- |
| **P0-07** | 文件内容完整     | 接收文件与原文件必须逐字节一致。测试验收采用 SHA-256 对比，包括文件大小、内容及最终哈希。                |
| **P0-08** | 100% 的定义准确 | 只有接收方已接收全部字节，且缓存写入、提交完成后，才能认定接收成功。不得把“发送完毕”或“网络接收完毕”直接当作最终完成。    |
| **P0-09** | 发送与接收状态分离  | 发送端发完数据、接收端确认完成，是两个不同事件。不能因为发送端进度达到 100%，就假定对方已得到完整文件。           |
| **P0-10** | 大文件稳定传输    | 文件大小超过单次消息承载能力时，必须通过分块、流式等现有传输链路完成，不得整体塞进单次 Socket.IO 消息造成卡死或超限。 |
| **P0-11** | 文件属性正确     | 文件名、扩展名、类型、文件大小及所属记录关系，在传输后必须保持正确。不同文件不得发生内容串用。                  |

需要特别说明：**SHA-256 是我建议固定的验收方法，不等于目前普通浏览器传输链路已经内置了完整的端到端 SHA-256 校验。** 当前代码主要使用接收字节数、预期大小和缓存提交状态判断完成；VClient 的持久化缓存另有哈希校验逻辑。

验收时使用外部哈希工具对比，可以先不改变传输协议。

### **C. 多文件、多来源与调度**

| 编号        | 核心指标      | 必须满足的验收条件                                                 |
| --------- | --------- | --------------------------------------------------------- |
| **P0-12** | 多文件独立性    | 同时发送多个文件，一个文件失败、超时或取消，不得导致其他正常文件永久卡住。                     |
| **P0-13** | 文件集合完整    | 一次发送文件集合后，接收端应得到正确的集合记录、文件数量、文件名、总大小及各文件资产的对应关系。          |
| **P0-14** | 多来源并行下载正确 | 同一文件由多个在线设备提供时，允许按范围并行获取；所有分片必须正确合并，不得缺片、重复拼接、错位或相互覆盖。    |
| **P0-15** | 来源失效后恢复   | 某个提供设备离线或传输失败时，应按现有机制使用其他有效来源重试；不能因为一个来源失效就使整个任务永久失去恢复能力。 |
| **P0-16** | 任务调度不堵塞   | 大文件、慢来源、失败重试、不可用缓存等情况，不能无期限占住队列，阻塞其他本来可以完成的文件。            |

这里尤其要防止以前出现过的那类问题：**多个来源看起来都在参与传输，但实际进度停滞，或者某个旧来源的失败事件把当前正常任务覆盖了。**

### **D. 缓存、恢复与资源可用性**

| 编号        | 核心指标       | 必须满足的验收条件                                                   |
| --------- | ---------- | ----------------------------------------------------------- |
| **P0-17** | 本地完整缓存直接使用 | 当前设备已有完整且有效的文件缓存时，下载、预览等操作应直接使用本地数据，不得无意义地重新向其他设备请求。        |
| **P0-18** | 接收后成为可用来源  | 设备成功接收并保存完整文件后，在具备对应权限且在线的情况下，应能按现有机制向其他设备提供该文件。            |
| **P0-19** | 记录与实体分离    | 历史记录存在，不代表文件实体仍存在。不能把只有元数据、没有有效文件内容的资源显示为“本地已缓存”或“可直接下载”。   |
| **P0-20** | 手动恢复可靠     | 用户触发缓存恢复后，应能重新寻找有效来源。重复点击不能制造相互冲突的任务，也不能因为某次旧请求失败而覆盖后续成功结果。 |
| **P0-21** | 正在传输的任务受保护 | 手动恢复、来源刷新、页面状态更新等操作，不得无故中断一个仍在正常取得数据的任务。                    |
| **P0-22** | 缓存清理不误删    | 清理游离资源、删除集合文件或释放缓存时，不得误删其他记录仍在引用的有效文件，也不能误删唯一可用的安全副本。       |

`dev/2611-s1` 已包含对正在进行的恢复任务的保护判断。例如，部分恢复操作会检查近期是否仍有进度，避免直接推翻有效任务。这类保护不能在后续重构中丢失。

### **E. 断线、重连与异步竞争**

| 编号        | 核心指标        | 必须满足的验收条件                                                 |
| --------- | ----------- | --------------------------------------------------------- |
| **P0-23** | 网络波动可恢复     | 短暂断线、Socket.IO 重连、P2P 通道异常后，系统不能进入永久无法传输的状态；已有恢复机制必须正常工作。 |
| **P0-24** | 旧事件不能污染新任务  | 旧请求的 ACK、失败、超时、分片或完成事件迟到时，不得取消、覆盖或破坏更新的传输尝试。              |
| **P0-25** | 重复事件幂等      | 重复收到开始、完成、资源公告等事件时，不得生成重复有效任务、重复写入或重复清理。                  |
| **P0-26** | 取消后不再复活     | 用户取消传输后，迟到的 Relay Start、分片或其他旧事件不能重新启动该任务。                |
| **P0-27** | 重连不无故破坏 P2P | Socket.IO 信令连接短暂重连时，如果已有 WebRTC 数据连接仍然有效，不应无条件销毁它并重新建链。   |

这组指标必须重点验收。很多“明明修好了一个 Bug，又莫名其妙坏掉”的问题，实际就是**异步旧事件与新状态之间的竞争**。

### **F. 隧道隔离、权限与历史记录**

| 编号        | 核心指标     | 必须满足的验收条件                                               |
| --------- | -------- | ------------------------------------------------------- |
| **P0-28** | 隧道间严格隔离  | 隧道 A 的文件、缓存、历史消息、来源信息、异步回调，不得错误进入隧道 B。即使设备 ID 相同也不能串数据。 |
| **P0-29** | 权限约束有效   | 文件请求、来源公告、跨隧道转发和资源访问，必须遵守当前隧道的授权关系，不能通过直接构造请求绕过。        |
| **P0-30** | 跨隧道转发正确  | 转发文件或文件集合时，目标隧道中的文件标识、资源关系必须正确，不能造成与原隧道文件 ID 冲突或错误引用。   |
| **P0-31** | 历史记录不丢不乱 | 页面刷新、断线重连、历史恢复后，已有记录不能无故丢失、重复、错序或跨隧道出现。                 |
| **P0-32** | 删除状态一致   | 已删除的记录、集合项及其对应引用不能因为旧历史响应、迟到事件而重新出现。                    |

## **二、传输状态必须统一定义**

这是后续最容易被改乱的地方之一。

**前端状态必须反映真实传输事实，不能为了让 UI 看起来有进度而制造假状态。**

| 状态    | 必须代表的实际含义              | 不允许发生的情况       |
| ----- | ---------------------- | -------------- |
| 仅有记录  | 有文件元数据，但尚未确认有效数据来源     | 直接显示为已缓存       |
| 等待来源  | 暂时没有有效来源，或正在寻找来源       | 虚构一个正在传输的任务    |
| 排队中   | 已存在待执行请求，但尚未实际开始数据传输   | 当作已经收到文件数据     |
| 正在传输  | 存在有效传输尝试，且已经进入实际数据传输阶段 | 仅收到来源清单就显示正在传输 |
| 传输中断  | 当前尝试因异常停止，可能仍允许重试      | 直接丢失可恢复任务信息    |
| 接收完成  | 所有字节已接收，缓存提交成功         | 数据尚未落盘就显示完成    |
| 本地已缓存 | 本机确有完整、可读取的文件数据        | 只有文件记录或不完整缓存   |
| 无法获取  | 当前确实没有可用来源或恢复途径        | 仍有可用来源却直接宣告失败  |

需要固定三个细节：

1. **进度不得虚报 100%。** 数据写入、缓存提交仍未完成，就不能显示接收完成。
2. **重试进度不得混用。** 新一轮实际重传需要准确反映新尝试的进度，不能沿用旧失败尝试的百分比制造假象。
3. **不得出现幽灵任务。** 没有真正开始传输，却在传输抽屉中持续显示“正在传输”。

## **三、P1：性能与稳定性指标**

这些指标建议保留，但**具体阈值先通过&#x20;**`dev/2611-s1`**&#x20;的实际运行数据确定**。

| 编号    | 指标         | 建议固定的验收方式                                      |
| ----- | ---------- | ---------------------------------------------- |
| P1-01 | P2P 建链耗时   | 固定设备和网络条件，统计成功建立文件 DataChannel 的 P50、P95 耗时。   |
| P1-02 | 首字节延迟      | 从发起文件请求，到接收端实际得到第一段数据，统计 P50、P95。              |
| P1-03 | 传输吞吐量      | 分别测量 P2P、Socket.IO Relay 的实际 MiB/s，不能混在一起算。    |
| P1-04 | 传输成功率      | 在固定环境下，统计最终成功取得完整文件的任务比例。                      |
| P1-05 | Relay 降级比例 | 在相同测试环境中，统计 P2P 成功、Relay 降级、最终失败的占比。           |
| P1-06 | 大文件资源消耗    | 测试大文件传输时浏览器内存、CPU 及服务端内存变化，特别检查是否随已传输字节持续无限增长。 |
| P1-07 | 并发吞吐量      | 同时传输 1、3、5 个文件，检查总吞吐量及是否发生明显队列饥饿。              |
| P1-08 | 失败恢复耗时     | 记录来源离线、通道关闭、Socket.IO 重连到重新开始有效传输的耗时。          |

建议采用两层标准：

- **基础合格线：** 必须满足全部 P0 指标。
- **性能防退化线：** 同设备、同网络、同文件样本下，与留存的稳定基线比较。例如可先将吞吐量明显下降超过 20%、P95 延迟明显上升超过 20% 设为人工复核触发条件。

这里的 20% 是**建议的候选阈值**，不是从仓库测出来的数值，也不是当前版本已经达成的承诺。性能基线应该实测一次后固定。

## **四、必须覆盖的回归测试矩阵**

不能再只测“两个浏览器传一个文件成功”就认为传输核心没问题。

以下测试应该成为每次修改核心传输逻辑后的固定验收项。

| 场景               | 测试内容                             | 重点观察                    |
| ---------------- | -------------------------------- | ----------------------- |
| **T01：基础 P2P**   | 两台设备网络互通，发送小文件、中等文件、大文件          | 实际使用 P2P；内容一致；进度正确      |
| **T02：P2P 不可用**  | 人为制造无法建立文件 DataChannel 的条件       | 自动走 Relay；无需手动重发；最终完整   |
| **T03：P2P 中途失败** | 传输过程中关闭或破坏 P2P 数据通道              | 正常处理失败及降级；无重复完成或永久卡死    |
| **T04：并发传输**     | 同时传输多个文件，混合大小文件                  | 不相互阻塞；不发生重复协商风暴         |
| **T05：多来源**      | 同一文件有两个以上在线来源                    | 按范围获取时不缺片、不重叠写入；完整合并    |
| **T06：来源中途离线**   | 传输中断开其中一个提供设备                    | 其他来源可继续承担恢复；旧失败事件不覆盖新任务 |
| **T07：断线与重连**    | 关闭网络数秒后恢复，或重连 Socket.IO          | 任务不永久卡死；已有有效 P2P 不无故销毁  |
| **T08：连续重试**     | 文件失败、重新请求、再次失败、再成功               | 仅最终有效尝试决定任务状态           |
| **T09：重复操作**     | 快速多次点击下载、恢复、取消                   | 不产生竞争性任务、不重复写入          |
| **T10：本地缓存**     | 下载完成后再次下载或预览                     | 使用本地完整缓存，不重复消耗网络        |
| **T11：刷新与恢复**    | 文件收到后刷新页面、重新进入隧道                 | 历史记录正确，缓存可用性判断正确        |
| **T12：隧道切换**     | 在 A 隧道发起异步请求后立即进入 B 隧道           | A 的迟到消息、缓存、任务状态不污染 B    |
| **T13：集合传输**     | 一次发送多个文件，随后删除、转发部分文件             | 集合关系、文件 ID、缓存引用保持正确     |
| **T14：缓存清理**     | 存在多个引用、外部文件句柄或唯一安全副本             | 不误删仍需使用的文件数据            |
| **T15：超时竞争**     | 接收完成后故意让旧 ACK、超时或 Relay Start 迟到 | 不重新传输，不把成功改成失败          |

### **建议固定的文件样本**

每次测试统一使用同一批文件：

- `0 B`：空文件边界。
- `1 KB`：极小文件。
- `512 KB` 附近：当前客户端小文件阈值边界。
- `1 MB`、`10 MB`：普通文件。
- `15 MB` 附近：服务端大文件并发调度边界。
- `40 MB`：针对你之前遇到过的卡死问题。
- `100 MB`：长时间传输与缓存提交。
- `500 MB` 或更大：大文件、内存和长时间稳定性。
- 文件名包含中文、日文、空格及特殊字符的样本。

对每份非空样本保留原始 SHA-256。

**所有测试成功后，必须比对实际接收文件的 SHA-256。** 仅仅能下载、能打开、能播放，都不能单独证明传输完整。

## **五、**`dev/2611-s1`**&#x20;中值得保留的实现边界**

以下是代码中现有的部分参数和机制。它们可以作为**兼容性与边界测试依据**，但不应未经讨论就全部变成永久不可调整的产品需求。

| 项目            | 当前实现情况                     |
| ------------- | -------------------------- |
| 客户端小文件阈值      | `512 KiB`                  |
| 部分传输分块大小      | `64 KiB`                   |
| 服务端单个文件资产上限   | `1 GiB`                    |
| 每会话文件资产数量上限   | `500`                      |
| Relay 单分块大小上限 | `256 KiB`                  |
| 多来源分片范围上限     | `4 MiB`                    |
| 接收端同时活跃文件资产上限 | `5`                        |
| 较大文件的并发控制     | `15 MiB` 起适用额外限制，活跃数上限 `3` |

重点是：**这些参数可以经过验证后优化，但优化参数时不得破坏上述 P0 结果。**

比如把分块从 64 KiB 改为其他值，并不天然属于需求违背；但改完导致大文件卡死、多来源错位、Relay 失败，就属于 P0 回归。

还有一项值得单独固定：当前代码对某些 OPFS 接收写入路径采取了限制。以后不能因为想“优化存储性能”，未经全套缓存恢复与完整性验收，就直接重新开启相关路径。

## **六、已有自动化回归测试必须保留**

这个分支不是完全没有自动化测试。实际上已有多组测试覆盖了重要的传输故障。

## **七、以后修改隧道核心代码的强制验收规则**

我建议把以下规定直接作为项目开发约束：

## **核心传输链路变更红线**

适用于发送、接收、WebRTC、Socket.IO Relay、来源调度、缓存、恢复、文件集合及跨隧道转发相关修改。

1. **P0 指标全部必须保持成立。** 不能以“修复了本次问题”为理由，容忍原有传输功能退化。
2. **修复前必须描述故障条件。** 说明在什么网络、文件大小、设备数量、传输阶段发生问题。
3. **修复时不得无故改变其他传输路径。** 例如修 Relay 问题，不能顺手改变正常 P2P 的优先策略。
4. **所有涉及异步任务状态的修改，都必须覆盖旧事件迟到、重复事件、取消、重试和重连。**
5. **原有自动化测试不能随意删除或放宽断言来制造通过结果。** 行为确实需要变更时，必须先明确新需求。
6. **新增故障必须新增对应回归用例。** 避免下次再次发生同类问题。
7. **必须验证真实数据完整性。** 不能只凭前端提示“传输成功”或进度 100% 验收。
8. **没有运行的测试必须标记为未验证。** 不能将代码审查、模拟测试或单机测试冒充跨设备实测。
9. **P1 性能明显退化必须说明原因。** 若没有明确收益和用户批准，不应接受明显降低传输效率的修改。
10. **核心链路改动未通过验收，不得宣布完成。**

### **我认为最需要锁死的五条底线**

如果以后给 AI 开发工具的提示词不想写太长，至少必须保留这五条：

① 可 P2P 时优先 P2P，失败自动 Relay；不得重复传输。

② 文件内容必须完整一致；接收方缓存提交成功才算完成。

③ 多文件、多来源、断线重连、失败重试不得相互干扰或永久卡死。

④ 历史记录、文件实体、缓存状态必须准确区分；不同隧道绝不能串数据。

⑤ 修复任何传输 Bug，必须通过相关自动化回归和真实跨设备测试，证明没有破坏上述能力。
