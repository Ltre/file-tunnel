## 1. 项目创建与第一个可运行版本

仓库第一个 Commit `192ecb...` 只有最小 README 和 .gitignore，产品定位只有一句：

当时的核心形态已经很清晰：

- QR 进入相同 Session；

## 2. 6 月 21-22：会话历史和协同编辑开始变复杂

最初很快遇到两个核心问题：

1. 新设备加入后历史并不天然一致；
2. 富文本图片如果直接用 `data:image` 同步，会造成巨大 payload 和刷新后重复传输。

因此 6 月 21-22 演进出：

- session-history；
- history diagnostics；
- 老设备/新设备同步；
- editor asset ID；
- 本地 Blob 渲染；
- P2P editor asset；
- P2P 失败时 Socket.IO relay；
- editor asset 本地缓存。

这奠定了后续“消息 metadata 与文件/资源 byte 分离”的架构。

## 6. 6 月 26-29：P2P / Relay 进入状态机阶段

这一时期大量修复说明“P2P 成功/失败”不能只靠一个 Boolean。

逐步加入：

- backpressure；
- 大文件请求队列；
- multi-source；
- 每次请求 `requestId`；
- 每次传输 `attemptId`；
- range attempt isolation；
- stale transfer rejection；
- receiver-already-cached；
- provider missing / rediscovery；
- watchdog；
- Relay start/chunk/complete ACK；
- P2P complete ACK。

最重要的语义收敛：

> “发送完成”必须是接收端已经完成组装、校验和本地落库，而不是供源端把最后一个 chunk 塞进网络 buffer。

## 7. 6 月 29：历史对账与缓存保护

为避免：

- 老快照覆盖新状态；
- 同 fileId 重复记录；
- 服务端有限快照误删浏览器长期历史；
- 供源端完整缓存被 metadata-only write 覆盖；

系统加入：

- canonical snapshot；
- message/file 幂等；
- 显式删除；
- 本地完整缓存保护；
- history reconcile。

这些兼容逻辑后来又发展为 tombstone、startup reconcile 和 audit isolation。

## 13. 本阶段留下的长期设计原则

1. 记录 metadata 与文件 byte 分离；
2. 浏览器缓存是资产来源，不只是 UI cache；
3. P2P 必须有 Relay fallback；
4. transfer attempt 必须有身份，迟到事件不能污染新任务；
5. 接收端确认才算完成；
6. session history 必须对账，不只靠实时广播；
7. device identity 可以跨 tunnel；
8. UI history/back 与文件/播放器状态是实际业务状态；
9. 大量兼容分支来自真实失败版本，不能只因为代码“看起来重复”就删除。

后续修改 P2P、历史、富文本、播放器、设备直连、磁链或外部句柄时，应先读这一阶段 Devlog 和 Git Log。
