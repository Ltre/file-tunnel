# 2026-06 至 2026-07：核心隧道、传输、协同与播放器演进

## 2. 文件传输从简单消息走向资产层

早期 file message 更接近“消息携带文件”。

随着大文件、刷新恢复、多设备出现，逐步拆成：

- message metadata；
- file asset；
- provider；
- cache；
- transfer attempt。

这使后来可以：

- 多个记录引用同一个文件资产；
- 当前缓存设备成为供源；
- server asset / Telegram 成为 fallback；
- 清记录不一定立刻删 byte。

## 3. 2606 多设备同步

2026-06 后期的重要里程碑是：

- 多设备缓存传输；
- P2P/relay retry isolation；
- message fallback；
- 强拉恢复；
- progress state。

Git 历史同时保留了 WRONGCODE 回退点，说明多源传输很容易因为 attempt lifecycle 不完整而出现：

- 重复发送；
- 进度回退；
- 完成后继续 relay。

## 6. 音乐播放器的反复修复

2026-07-02 ~ 07-04 的 Git Log 有大量播放器提交。

重要教训：

- queue state 不能只存在 DOM；
- current index 不是稳定 identity；
- background preload 不能改变 active track；
- queue drawer 的 back/minimize/close 是三种动作；
- history 层级要和播放器层级一致；
- poster metadata 是异步的，不能因为暂时缺失就覆盖缓存。

## 9. Rich Text Versioning

从协同编辑器发送出的富文本后来支持：

- 再次编辑；
- version history；
- diff；
- optimistic baseVersion；
- conflict；
- pending offline edit。

因此旧“协同编辑区”和“已发送富文本记录”是两种状态：前者是 live draft，后者是 versioned history record。

## 10. 2607B P2P 深水区

7 月底到 8 月初围绕：

- LAN-only experiment；
- rollback；
- standard P2P concurrent negotiation；
- mDNS host candidate；
- public domain preconnect；
- multi-device progress；
- multi-source chunk。

一个重要历史结论：

> “只允许 LAN candidate”一类理论上更安全/简单的实验，实际破坏了公网域名下的 P2P，最终回退。

所以不要仅凭网络理论重新加死 candidate 过滤。
